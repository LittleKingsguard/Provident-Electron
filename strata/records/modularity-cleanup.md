## 3. Anomalies standing (the sweep's worklist)

- **`AN-1` — UPSTREAM: the store does not carry a synchronous main half's return.** `direct.register(h, () => ({direct:true}))` then a write answers `returnedValues: {}`; `async () => ({direct:true})` answers `{[h]: {direct:true}}`. So the channel's `return` arm is **async-only** and its entry is otherwise indistinguishable from an undefined returner. Upstream-owned (`D-5`): fix shape is the store's — stand the synchronous return on `returnedValues` as `C-2` reads it. `CH-1`/`CH-2` use a thenable, as `M-11` does. **Sweep:** re-measure at the next pin; if upstream lands it, the channel's `return` arm may accept the sync form and the row's thenable becomes one arm of two.
- **`AN-2` — UPSTREAM-FACING, HOST-OWNED: `serializeNode` emits no `handlers`.** `src/shared/demo-envelope.ts` authors **30** `handlers:` entries; the engine's serializer emits none (`H-2`/`OWED-14`). This is why the serializer round-trip is refused for composition (`D-317`) and why `contribute` merges the AUTHORED document instead. **Sweep:** if reverse emission ever carries handlers, `D-317`'s refusal is re-weighable — but the authored-document route stays the cheaper one and no change is owed.
- **`AN-3` — `module.update`'s new `client` source is never evaluated.** The executor sends a registration frame on install **and** update; `CapabilityRouter.registerModule`'s one-frame guard drops the second. Recorded as `D-318`; `M-2b`'s third arm waits on `S-23`/`U6`'s inverse. **Sweep:** with `U6`, add the replace-on-update path (withdraw listeners/actions/contributions, evaluate the new source, remove the old contributed subtree from the authored document) and file `M-2b`.
- **`AN-7` — `installModuleActions` re-applies every earlier module's closures on each new module.** One `state-slice` per matching node per call: idempotent in effect, N−1 redundant writes in cost, and each re-dirties the node. **Sweep:** install only the new module's actions, or skip nodes whose handler already carries a function body.
- **`AN-10` — the re-drive depends on a boot read having landed.** `reDriveModuleShapePaints` drives from `tabsClientReading`/`getViewClient().reading()`; a module installed before either read drives nothing, and its paints land when the boot read does. Correct, and worth a sentence in the page rather than a change.
- **`AN-11` — two claimed battery paths do not exist.** `strata/modules.json` claims `tests/e2e/module-channel/` (module-channel) and `tests/e2e/module-parity/` (module-system); neither directory exists. A `paths` entry is a CLAIM, and nothing distinguishes "built" from "planned" without a `stat`. **Sweep:** either create the batteries or mark the claims (`planned`) — a map whose paths are half aspirational measures nothing.
- **`AN-13` — §6's "Proven by" column now mixes vocabularies.** `renderer-wiring`'s cell lists `RW-M1…RW-M4` (integration ids) beside `M-n` rows. **Sweep:** either the column states "rows that prove it, any battery" or the integration ids move to the module's own page.
- **`AN-21` — a module's listeners have NO TYPED manifest member.** `src/main/modules/admission.ts`'s `declaredListeners` reads `capabilities.listeners` **through a cast** (`ModuleCapabilities & { listeners?: readonly ListenerDeclaration[] }`), because `src/shared/types.ts`'s `ModuleCapabilities` declares only `tools`, `hooks` and `transforms`. So the one member a module MUST fill to be bound is unspellable in the contract the manifest is written against, and the executor's cast is the only place it is written down. **Sweep:** add `listeners?: readonly { address; main?; client? }[]` to `ModuleCapabilities` (or re-home `ListenerDeclaration` where `types.ts` can name it without a cycle) and drop the cast — `ipc-contract` owns that file, so it is a cross-seat edit.
- **`AN-22` — the `M-11`/`M-13` witness's surface recipe, measured while scoping the battery.** A module records what its client half was handed with **`ctx.store.write(<address>, 'temp'|'mem', <value>)`** (the client store is async and the channel settles it) and the row reads it back with **`provident.data.read`**, whose payload member is **`path`** (`provident.data.write` likewise; the address is a dense array of string keys and indices) and whose answer wraps the node with `_tier`/`value`. That is one boot, one install, one `provident.data.write` at the declared address, and no graph contribution, no `provident.dispatch` and no `get_node_state` — the design's node-and-action route is `M-2b`'s and stays there. **Sweep:** write `M-11`/`M-13` on this recipe; the addresses stay a scratch pair under one root unless the view crossing's own `['panes']` pair is proven safe to write.
- **`AN-24` — A WRITE AT A ROOT'S REACH IS NOT STABLE, SO `M-13`'s SECOND WRITE IS RETIRED.** Measured twice on the same row: after a leaf write (root + leaf), a write at the ROOT with a CHANGED root literal and an IDENTICAL leaf literal produced **both** entries in one run (the leaf told — the store's touched arm, `D-66`/`Q-6`) and **the root's alone** in the next (the leaf's literal unchanged — `D-193`'s value condition). ## 4. Process rules this unit learned (keep them; they are cheaper than rediscovering them)

- **`PR-1` — a declaration dies at its commit.** A path declared in pass *N* and committed must be **dropped** from the page's block when the page is edited in pass *N+1*, or `P-5` reds it as a clean path. This bit three times in one session (`strata/modules.json`, `D-316`'s block, `D-317`'s block).
- **`PR-2` — one live block per page.** `strata/decisions.md` accumulates a block per decision row; when the page is next in flight every block is read, and two blocks naming the same path red `B-1` as a duplicate. The page keeps **one** block — the newest row's — and landed ones are removed when the page next moves.
- **`PR-3` — a multi-pass unit re-declares the same `src/**` paths each pass.** Correct under `D-146`, and it produces churn (a block reduced to itself, then re-extended). Nothing to fix; expect it.
- **`PR-4` — the four legs are fully green only on a CLEAN tree.** `F-9(b)` and the boundary rows measure the tree, so the order is: typecheck / typecheck:tests / build and a filtered suite on the dirty tree → commit → `npm test` on the clean tree → report.
- **`PR-5` — filing order is not enforced.** `M-30` was written a pass before it was filed (`L1` §6's reserved set ended at `M-29`, `RG-…`/`CH-10`). A row and its filing should move together.
- **`PR-6` — measure a row's stimulus path before authoring its harness.** Doing so saved a battery that would have redded on a design-ladder dependency, not a defect (`D-318`, `AN-3`). A gating row that cannot green is evidence of nothing (`D-30`, `D-40`); finding that out *before* writing 650 lines is the cheap direction.
- **`PR-7` — a page that invents a member is a page that did not read the tree.** `RG-5`'s `paneNodeIds` was written from the cell's prose and did not exist. Read the site before writing a stub; a stub is a claim about the tree, not about the design.
