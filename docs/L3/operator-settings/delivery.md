## 1. The crossing, the four addresses, and the one registration that moves

| | |

- **WHAT THE CREATION FIRES IS THE ADOPTED SET ∩ THE ADDRESSES THAT RESOLVE**, not the set a repair wrote: `index.d.ts`'s `StoreConfig.listeners` states it (*"after the constraints pass and after the save, the adopted listeners WHOSE WATCHED ADDRESS RESOLVES are fired — once per distinct handle, with that address as their one argument"*), `index.mjs`'s `registerHolds` counts every answer but `AddressNotFound` as present, and `deliverAtTheCreation` walks the adopted list **once per address, in CREATION ORDER**, deduped by address. **So this batch fires FOUR on a cold profile and FOUR on a warm one** — the two `file` addresses resolve from the file and the two `mem` ones are re-minted (`CD-3`, `CD-10`) — and `D-220`'s **four fires out of five entries** at the profile store is this same rule read the other way: `drag` is silent because its address does not resolve, a family no invariant holds (D-145). **Fewer than four is the pathological arm**: an address that fails to resolve is SILENT — no invocation, no code, no log row and no throw, the construction returning its instance — and a refused construction adopts nothing and fires nothing (`:1176`).
- **THE DRAIN'S ORDER, AND WHY A ROW MUST NOT ASSUME ANOTHER**: the creation's `deliver` calls run **in the entry list's order**, not in repair order, so the held set is `[RECORD, EXCLUSION, APP_STATE, PANE]` when all four resolve, and no address can fire twice inside the one creation instant (`index.mjs`'s per-address dedupe).

## 2. The four entries, one per ADDRESS and never per root

- **FOUR ENTRIES, ONE PER ADDRESS, AT THE SAME FOUR ADDRESSES THE SUBSCRIPTION BINDS TODAY** (D-104's finding: *"the third handle is registered exactly as the other two are; what differs is the ROUTING"*). The list `subscribe` spells at `:1323` — `[RECORD, EXCLUSION, APP_STATE, PANE]` — becomes the construction's ONE list, from which the four entries are built, so **the four addresses keep a single spelling in this one file** (the one-file spelling `D-104` pinned to `ISO-7`'s census).
- **ONE ENTRY AT THE STORE ROOT `[]` IS REFUSED, AND THE ADDRESS IS THE REASON**: an entry's `address` carries **exactly one** address (`guide §6`) and no act of this instance writes `[]` — the invariant's two seats stand at the two halves' own addresses and `CD-16` measures that no `[]` stands in the batch — so a root entry would be a registration that can never fire: **the row-that-cannot-fail class, in address form**, refused on `D-220`'s reasoning exactly as `listener: () => {}` is refused below.
- **THE TWO-BODY SPLIT IS NOT DUPLICATED IN THE REGISTRATION**: all four entries carry the SAME `listener`, `deliver`, and each subscriber's `body` — transcribed from `:1324`–`:1339` — is applied INSIDE the fan-out. So the split of `D-104` stays a ROUTING fact (which of a subscriber's two bodies hears an address) and never becomes a registration fact.
- **THE ROUTING DOES NOT MOVE**: the app-state arm stays `typeof appStateListener === 'function' && address[0] === APP_STATE_ADDRESS[0]` → second body and `return`; everything else → `listener(detach(address))`. **So an `APP_STATE_ADDRESS` delivery with NO second listener supplied falls through to the FIRST body**, and the one-argument subscription's **total reading is unchanged** — it hears all four addresses through its one body, today and after, and the drain goes through that same routing.
- **TWO OWN MEMBERS ARE NOT ENOUGH AND A THIRD THAT DOES NOTHING IS REFUSED**: `listener` is required at `1.11.0`; the package's own migration route (`listener: () => {}`) satisfies the refusal and **changes nothing** — refused here verbatim on `D-219`'s and `D-220`'s ground, and `OG-2` keeps it refused at L4.

```ts
// PRIVATE, declared beside `handleFor` — no export, no `OperatorSettings` member and no `N` figure moves (§6 `OD-1`)
interface OperatorDeliveryEntry { readonly address: OperatorSettingsAddress; readonly handle: string
  readonly listener: (address: OperatorSettingsAddress) => void }     // the ONE argument is the watched address
interface OperatorDelivery { readonly entries: readonly OperatorDeliveryEntry[]
  stand(body: (address: OperatorSettingsAddress) => void): () => void }        // the withdrawal is local (D-70)
function createOperatorDelivery(): OperatorDelivery      // minted BEFORE `storeCreate`; holds addresses, never values
```

## 3. The queue: where it lives, what arms it, and what a withdrawal does to it

- **WHERE IT LIVES**: in the delivery object's own closure — **minted before `storeCreate`, because `cfg.listeners` is read inside the call that creates the store** (`:1175`), and held by that construction for the instance's life. It holds **ADDRESSES, never values**: the delivery is a signal and every consumer answers it with a re-read (D-92; `D-106`'s *"one delivery, one signal, no payload"*). **Refused: holding the value a repair wrote** — a held value is a second authority over the store (`D-129`'s class) and, at the creation instant, the read-side copy `D-85` deleted. **No queue for this crossing stands anywhere else** — not in `settings-surface`, not in `src/main/main.ts`: the two queues that file builds are the tab record's and the view record's (`:195`–`:196`), and they carry neither of this crossing's two pushes.
- **WHAT ARMS IT — AND THIS IS THE DIFFERENCE IN KIND FROM `D-220`'s QUEUE**: the profile store's consumers are **windows in another process**, so that queue arms on the `IPC_READY` handshake after `markReady()` (measured: `attachWindow` runs **before** `loadFile` and cannot flush). **This crossing's consumers are IN-PROCESS: there is no window, no readiness handshake and nothing to arm against. What replaces it is the consumer's own arrival — the FIRST `subscribe` — and the drain runs INSIDE that call, before it returns.** That is `D-218`'s *"re-delivery at attach"* fulfilled where the attach **is** the subscription: no channel, no `ipcMain` site and no bridge member is added (D-18, D-104, D-106). **Refused with it**: a queue owned by `main.ts`, or a minted `ready` signal for a crossing that has none.
- **THE DRAIN IS ONCE, IN CREATION ORDER**: the held addresses are replayed in the order they fired (§1), each handed to the routing and **removed from the held set as it is handed over**.
- **THE SECOND SUBSCRIBER DOES NOT RECEIVE IT, WITH ONE EXCEPTION STATED IN THE SAME BREATH.** The held set is the CREATION's event and is handed to the consumer that stood first; a later subscriber's answer to *what stands* is the total `read()`/`readAppState()`, not a replay — **except the remainder an interrupted drain leaves held** (see the third arm below). **Refused: replay-to-every-subscriber**, which paints a stale event as if it were a change (the class `D-216` names), under `D-90`'s one-consumer rule where the app has one subscriber and a second-subscriber replay would be a shape with no route.
- **A WITHDRAWAL AND A HELD SET, THE THREE ARMS**: (i) **after the drain** the held set is empty and the withdrawal is local — the fan-out entry leaves and no `unlisten` is owed, because the entries are the instance's for its life (D-70); (ii) **before the drain** cannot arise from outside, the drain running inside the `subscribe` call before it returns; (iii) **during the drain** — whose only producer is the body's own containment (`:1338`), `ASM-L2-6`'s withdrawn-throwing subscriber, now a LOCAL drop of that subscriber instead of a `unlisten` — the **undelivered remainder STAYS HELD**, so no address of the creation's event is silently dropped and the next subscriber to stand drains the rest. **Refused**: dropping the remainder with the withdrawn subscriber, which is the loss this pass exists to remove.
- **TOTALITY IS LOAD-BEARING AT THIS CONSTRUCTION, AND THE FAILURE IT BUYS IS SILENT.** `deliver` writes nothing (a listener's write opens a commit of its own inside the one that fired it, `guide §6.5` item 1) and **contains its own throw and every subscriber's** (`ASM-L2-6`): an uncontained creation-fired body refuses the act at rank `21` `ListenerBodyThrew` (`index.d.ts`; `index.mjs`'s `listenerBodyRefused`). **At this construction that throw is caught — the `try` at `:1168` and the `catch` at `:1176` — and answered as a value**, `refusalOf` carrying the caught `status` verbatim: every later write answers `ListenerBodyThrew` and every read serves `FIRST_RUN`, with nothing logged — **a silent outage where the profile store would have taken `D-80`'s fatal arm.** That is why `OG-3` is a guardrail and not a style note.

## 4. What the first delivery would carry, who consumes it, and what it cannot reach

- **IT CARRIES THE ADDRESS AND NOTHING ELSE** — one call per held address, §2's routing applied, `detach(address)` the one argument. No value, no member name, no receipt.
- **IN-PROCESS, THE CONSUMERS ARE REAL AND THEY STAND**: `settings-surface`'s `onDelivery` (the gate re-patch, `onSecurityChanged`, the exclusion's `onExclusionChanged`) and its `onAppStateDelivery` (`onAppStateChanged` → `main`'s `IPC_MODULE_CHANGED`) — `src/main/settings-surface/index.ts:137`, `:168`, `:186`; `src/main/main.ts:235`–`:246` (D-104, D-106, D-123). **The tier-4 holder write is NOT among them: it went with its holder at `D-117`.**
- **THE MEASURED ORDER AT `attach`, AND IT INVERTS THE OBVIOUS ARGUMENT**: `attach` **subscribes FIRST** — its own sentence is *"no change can fall between the acts"* (`settings-surface/index.ts:286`–`:290`) — and only then reads the record and patches (`:291`, `:297`–`:299`). **So the drain runs BEFORE the boot patch**, and the gate is patched by a DELIVERY and then re-patched from the read with the same value.
- **THE MCP SURFACE: THE END STATE IS UNMOVED AND THE ROUTE MOVES.** The gate ends the instant holding the record's values either way, and the tools read the gate and never the store; what changes is that **a delivery is now the first hand to touch it**, which is `D-82` clause 2's shape held at the creation instant. **And the read at `:291` is thereby the SECOND answer of one value**: deleting it is `settings-surface`'s ruling and not this page's, and this pass makes that ruling smaller rather than taking it (§8 carries the item as that owner's).
- **THE ISOLATED PANE GRAPH: NOTHING AT ALL AT THAT INSTANT.** `PANE_ADDRESS`'s held delivery reaches the surface's record body (the pane is not the app-state address) and the realm's render follows the realm's own delivery (D-127); **a creation instant has no realm**.
- **THE CROSS-PROCESS HALF IS NOT CLOSED HERE, AND THIS PASS CANNOT CLOSE IT.** This crossing's two pushes are bare broadcasts over `BrowserWindow.getAllWindows()` (`src/main/main.ts:235`–`:246`) and the tree's only two `createDeliveryQueue` instances are the tab record's and the view record's, armed at `IPC_READY` (`:195`–`:196`, `:756`+). **No queue stands for `IPC_SECURITY_CHANGED` or `IPC_MODULE_CHANGED`**, so a creation-instant push reaches no window and is dropped. **The renderer's boot fills therefore remain the realm's only channel** — `startSecurityShape` and `startAppStateShape` (D-106, D-104) and `main()`'s `bridge.security.get()` tier-4 snapshot (D-106 class (i)) — the read-not-listen pattern `D-218` named, open on that side. Closing it needs a queue for those two pushes **in `app-shell`**, armed at the app's arrival signal: `D-220` gap (ii)'s analogue at the second crossing, named and routed, never designed or built here.
