## 3. The composition: the rule, the order, and the port's absence

```ts
allowedToolNames(): string[] =
  composePublishedSet(
    registeredToolNames(this._gate, ProvidentMcpServer.ALL_TOOLS),    // the STATIC half: group-filtered, ALL_TOOLS' own order
    this._modulePort === null ? [] : this._modulePort.activations(),  // the DOOR's half: ActivationLike[], activation order
    (name) => this._gate.toolAllowed(name),                           // the GROUP predicate: exact row first, then `module:` → `module`
  )

composePublishedSet(staticNames, activations, admits):
  out = [];  seen = {}
  for name of staticNames:              if (name ∉ seen) push, mark   // the foundation's seats are the caller's own, unmoved
  for activation of activations: for tool of activation.tools:
      if (!admits(tool)) continue                                    // a name its group does not admit is ABSENT, never present-and-refusing
      if (tool ∉ MODULE_NAMESPACE) continue                           // the dynamic half IS the executor's `module:<n>.<t>` namespace
      if (tool ∈ seen) continue                                      // first occurrence wins: no name is re-seated, no name stands twice
      push, mark
  return out
```

- **The order is two blocks and no sort**: the static half in `ALL_TOOLS`' order, the dynamic half after it in the registry's activation order, first occurrence winning. Sorting would re-seat a foundation name whenever a module activated (L2 §10; D-41).
- **The group rule is `security.ts`'s own and is asked ONCE**: `groupForTool` answers `module` for `module:<n>.<t>` and `null` for a bare `module:` (malformed, denied), so `admits` is the ONE reading of the GROUP rule (`security.ts`'s `groupForTool`; L2 §10). **The namespace test beside it is not a second spelling of that rule, and saying why is what keeps it honest**: `admits` answers a group for ANY name it is given, so a static name arriving in an activation would be published by the group test alone; `MODULE_NAMESPACE` asks the other question — *is this a composed name at all* — and its `module:` literal is the executor's namespace (`docs/L2/module-system/interface.md` §1), not a copy of the group's two literals in `security.ts`, which are that file's and stay untouched (D-16's second-copy hazard named, not propagated).
- **The port has NO default that reads anything else** (§10 `ASM-1`): with no port injected the dynamic half is EMPTY — exactly the set a server publishes today with no router — so no second source stands behind the composition, and the ONE object that answers the names is the ONE object that answers the call. **The price is L2's and is stated**: the controls that build a server with a realm router and no name source (`tests/integration/mcp-surface/registration.test.ts`'s `I-5`/`I-6`) publish no dynamic name, and that file's re-grain is L2 §7/§13's declared debt and not this page's write (D-26).
- **The port is handed in, and neither its object nor its line is this seat's**: `createModuleExecutor` is `module-system`'s code and `main.ts`'s one option pass is app-shell's file, so this surface CONSUMES a port and constructs none (D-3, D-5; L2 §13). **And that literal is a COUPLED SITE, named so no reader meets it as a surprise**: `main.ts`'s `ProvidentMcpServer` construction passes `router` and calls `syncModuleRouter` twice, so the option member, that function and those three lines retire in ONE act — app-shell's — and until then `router?` stands declared and `syncModuleRouter` exported, read by nothing in this module's composition, which is why this pass reds no other module's typecheck (§2's two RETIRE rows).

## 4. The `module` group, the two-gate's three instants, and the predicate's SCOPE

- **A composed name needs no `TOOL_GROUPS` row**: an exact row wins first, then any `module:<n>.<t>` resolves to `module` by prefix, and a `module:` with an empty rest is malformed and denied — so `ALL_TOOLS` grows no row and the group table grows none (`security.ts`'s `groupForTool`; L2 §10; L1 §1).
- **`registrationAllowed(name, enabled)` is the landed rule FACTORED and never re-decided**: `module.install`/`module.update` register only while `module` AND `code` both stand; every other name — `module.list` and a dynamic `module:<n>.<t>` included — registers by its GROUP alone. `registeredToolNames` delegates to it, so no row that pins today's construction moves (L2 §10's construction clause).
- **ITS SCOPE IS THE REGISTRATION SITES ONLY, AND THIS BULLET EXISTS BECAUSE THE OTHER TWO MECHANISMS MUST NOT BE ROUTED THROUGH IT**: the RE-GATE's toggle keeps the landed PAIR predicate over every `module.`- and `module:`-prefixed handle (which is why a `code` withdrawal closes the census door, `M-5`'s grain and L2's `I-5`), and the INVOCATION keeps `moduleToolAllowed(name, enabled, { executable: true })` — checked at this side BEFORE the door (§7). One function returning one answer for `module.list` cannot say "group alone" at construction and "the pair" at the re-gate, so the asymmetry is the contract's and not a simplification to make (L2 §10; §9 `G-8`).
- **TOTALITY OVER A MALFORMED `enabled` IS THIS PAGE'S OWN RULE AND NOT THE LANDED ONE** (§10 `ASM-4`): the predicate answers `false` for `null`, `undefined` and a non-iterable, and never throws — the posture `moduleToolAllowed` already carries in the same file (its `F3` note), which the landed `toolAllowed` does NOT. `null`/`undefined` come free (an empty set); the non-iterable arm is the new rule, and the alternative is recorded (§10).

## 5. Re-registration on activation, the door's arms, the delivery, and the declaration the call rides

- **A delta, and `added` is what the MAP GAINED**: `syncPublishedTools()` answers `{ added, withdrawn }`, where `added` is read off the capture map before and after the registration pass — never off the candidate list. The distinction is load-bearing: a name the gate admits but NO REGISTRATION ARM can answer is not an `added` name. The worked case is `ALL_TOOLS`' `provident.data.*` names, which register only when a `dataSurface` was supplied (`mcp-server.ts`'s data arm and its own `D-11` note; L2 §10).
- **`withdrawn` reads the port's set UNFILTERED by group** (§10 `ASM-5`): every captured `module:`-prefixed name `activations()` no longer holds is withdrawn, and a name whose GROUP is off is not — it stays captured and toggled, which is the landed mechanism (L2 §10, §12; `G-4`).
- **The CONSTRUCTION captures too, and that is what makes the first `added` empty**: `createServer` registers `allowedToolNames()` through the one call `registerTools`, so the map is populated by construction and `syncPublishedTools()` moves a set that already stands rather than opening it (§2's `registerTools` row; L2 §12).
- **Two SDK calls carry the whole move, and no third is invented** (the installed SDK; offsets are a date, the members are the claim — D-46): `McpServer.registerTool(name, …)` answers the `RegisteredTool` and THROWS on a name already registered, which is why the capture map is the guard; `RegisteredTool.remove()` (`update({name: null})`) withdraws a name outright, while `update({ enabled })` only hides it from `tools/list` and leaves a call answering the protocol's `-32602 … disabled`. Both registration and every update fire the tool-list-changed notification, which is how a connected client learns the set moved with no reconnect.
- **Withdraw is `remove()` and never `update({enabled:false})`, and the ground is the axis**: a disabled handle is indistinguishable from a group-off one, so the group axis could never restore it, and a later re-activation of the same name would meet the SDK's already-registered throw. The group axis keeps the LANDED mechanism — a handle stays resolvable and is toggled, never deregistered (`mcp-server.ts`'s `regateLiveServer` note; L2 §10).
- **The call reads the DOOR AT THE TURN, and this side's judgement precedes it — the READER IS DECLARED, in ONE spelling**: the private field is `_modulePort`, the reader is `liveDoor: () => ModulePort | null` — the shape the landed `liveGate: () => SecurityGate` establishes — and `invokeModuleTool(door, gate, toolName, args)` answers this side's arms first and then the door's: a name that is not `module:`-prefixed THROWS, a `moduleToolAllowed(…, { executable: true })` refusal THROWS the error naming the pair (the SDK's tool-error arm, §7), a null door THROWS the null arm's own words **RE-GRAINED to name the EXECUTOR rather than the router the route retires** (`signatures.md` §5), and otherwise the door's answer — a handler's value OR the door's own refusal VALUE — is returned VERBATIM with no wrapper beside it (§7; §9 `G-6`). **AND THE CLASS'S OWN `invokeTool` ACCESSOR MOVES IN THE SAME CELL, which is what makes `router?` read by nothing here**: its null-door arm and its `this.router.invokeTool(…)` delegate become the same two arms over `_modulePort`, one shape with the free function and no second spelling — the fourth of the head's seven errors, and the member `G-6`'s one-door rule binds (§9 `G-6`; `signatures.md` §5).
- **THE DELIVERY IS TWO FACTS ON TWO STORES, AND THE ARM WRITES BOTH WHERE A PORT STANDS** (L2 §10's delivery clause; `docs/L2/module-system/interface.md` §11): the `module.install`/`module.update` arm FIRST makes the landed `handleModuleTool(moduleStore, name, args)` call — the PERSISTED registry row, `file.modules.*` through the settings surface (`mcp-server.ts`'s `ModuleStore`) and the one `module.list` and `status().loaded` read — and a `rejected` or `no-op` answer ENDS THE ARM, because nothing moved and there is nothing to activate; where the row stands, the same `source` goes to the port's `install({kind:'source', source})`, which IS the activation, and the verdicts it returns are this arm's answer, with `rePublish()` following in the same act. **The two stores answer two questions and are NOT one registry, said plainly because the opposite is a claim a reader can check**: the `ModuleStore` is the census of INSTALLED rows, while the executor's registry is its own activation table reached only through `activations()`/`invoke`, and `ModuleHost.store` is the profile store, not this census (`src/shared/module-contract.ts`) — so a delivery is written once to each, and no sentence here renames one the other (L2 §10; D-43).
- **THE RETIRED LINE AT THAT SITE WAS `syncModuleRouter(router, moduleStore)`, AND WHAT REPLACES IT IS NOT A CALL**: its target is the router's tool table, a half that declares no tool table and whose ctx carries no `tool` (L2 §10), so the tool chain it closed is what §5's composition and door replace, and the function itself retires whole in app-shell's pass (§2's RETIRE row). **Nothing in this module calls it after the landing.**
- **THE ARM'S DECLARED SCHEMA IS WHAT DECIDES WHETHER AN ARGUMENT CAN REACH THE DOOR AT ALL, AND IT IS THE ONE CELL THIS REV ADDS TO THE ROUTE, ON THE L2 PAGE'S OWN SENTENCE THAT IT MUST MOVE "IN THE SAME ACT"** (L2 §10's finding): the arm declares `inputSchema: {}`, an empty raw shape the SDK normalises into a memberless object schema, and `McpServer.validateToolInput` parses every call against the registered declaration and hands the handler `parseResult.data` — so that shape has TWO symptoms, and both are the point: a call carrying members is answered `parseResult.data === {}`, every member STRIPPED, and a call that omits `arguments` altogether is refused by the parse itself and never reaches the handler.
