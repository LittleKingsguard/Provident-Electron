## 3. The composition: the rule and the order

```ts
allowedToolNames(): string[] =
  composePublishedSet(
    registeredToolNames(this._gate, ProvidentMcpServer.ALL_TOOLS), // the STATIC half: group-filtered, ALL_TOOLS' own order
    this._activations().map((a) => a.tools),                       // the REGISTRY's half: the activation order, full names
    (name) => this._gate.toolAllowed(name),                         // the GROUP predicate: an exact TOOL_GROUPS row first, then `module:` → `module`
  )

composePublishedSet(staticNames, activations, admits):
  out = [];  seen = {}
  for name of staticNames:            if (name ∉ seen) push, mark   // the foundation's seats are the caller's own, unmoved
  for tools of activations: for tool of tools:
      if (!admits(tool)) continue                                  // a name its group does not admit is ABSENT, never present-and-refusing
      if (tool ∉ namespacePrefix) continue                         // the dynamic half IS the `module:` namespace
      if (tool ∈ seen) continue                                    // first occurrence wins: no name is re-seated, no name stands twice
      push, mark
  return out
```

- **The order is two blocks and no sort**: the static half in `ALL_TOOLS`' order, the dynamic half after it in the registry's activation order, first occurrence winning. Sorting would re-seat a foundation name whenever a module activated (L2 §10; D-41).
- **The prefix guard is `security.ts`'s own, not a second spelling**: `groupForTool` already answers `module` for `module:<n>.<t>` and `null` for a bare `module:` (malformed, denied), so `admits` is the ONE reading of that rule (security.ts's `groupForTool`; L2 §10).
- **The port's default, stated as a decision with its price** (§10 `ASM-1`): when no source is injected, the `activations` option's default reads `() => [{ tools: this.router?.listTools() ?? [] }]` — the SAME registry, through the router this surface already invokes, so the published and the invocable sets cannot disagree at any instant. When the composition passes module-system's `activations()`, the default retires in one option pass at `main.ts` (app-shell's file, not this seat's).

## 4. The `module` group, the two-gate's three instants, and the predicate's SCOPE

- **A composed name needs no `TOOL_GROUPS` row**: an exact row wins first, then any `module:<n>.<t>` resolves to `module` by prefix, and a `module:` with an empty rest is malformed and denied — so `ALL_TOOLS` grows no row and the group table grows none (security.ts's `groupForTool`; L2 §10; L1 §1).
- **`registrationAllowed(name, enabled)` is the landed rule FACTORED and never re-decided**: `module.install`/`module.update` register only while `module` AND `code` both stand; every other name — `module.list` and a dynamic `module:<n>.<t>` included — registers by its GROUP alone. `registeredToolNames` delegates to it, so no row that pins today's construction moves (L2 §10's construction clause).
- **ITS SCOPE IS THE REGISTRATION SITES ONLY, AND THIS BULLET EXISTS BECAUSE THE OTHER TWO MECHANISMS MUST NOT BE ROUTED THROUGH IT** (`F-5`): the RE-GATE's toggle keeps the landed PAIR predicate over every `module.`- and `module:`-prefixed handle (which is why a `code` withdrawal closes the census door, `M-5`'s grain and L2's `I-5`), and the INVOCATION keeps `moduleToolAllowed(name, enabled, { executable: true })`. One function returning one answer for `module.list` cannot say "group alone" at construction and "the pair" at the re-gate, so the asymmetry is the contract's and not a simplification to make (L2 §10; §9 `G-8`).
- **TOTALITY OVER A MALFORMED `enabled` IS THIS PAGE'S OWN RULE AND NOT THE LANDED ONE** (§10 `ASM-4`, `F-3`): the predicate answers `false` for `null`, `undefined` and a non-iterable, and never throws — the posture `moduleToolAllowed` already carries in the same file (its `F3` note), which the landed `toolAllowed` does NOT. `null`/`undefined` come free (an empty set); the non-iterable arm is the new rule, and the alternative is recorded (§10).
- **`S-8` is a later sub-unit and its shape is not on the L2 page**: `ToolGroup` becoming the registered set moves the group DOMAIN, and this predicate reads the gate's enabled SET, so the domain may move under it without moving it (L1 §3 `S-8`; L2 §10's group-domain clause hands that step to `S-8`, and D-16's second `VALID_GROUPS` copy is `operator-settings`' path, untouched).

## 5. Re-registration on activation, and the exact SDK surface it rides

- **A delta, and `added` is what the MAP GAINED** (`F-1`): `syncPublishedTools()` answers `{ added, withdrawn }`, where `added` is read off the capture map before and after the registration pass — never off the candidate list. The distinction is load-bearing: a name the gate admits but NO REGISTRATION ARM can answer is not an `added` name. The worked case is `ALL_TOOLS`' five `provident.data.*` names, which register only when a `dataSurface` was supplied, so a server built without one publishes five names it captures nothing for (mcp-server.ts's data arm and its own `D-11` note; L2 §10).
- **`withdrawn` reads the registry's set UNFILTERED by group** (§10 `ASM-5`): every captured `module:`-prefixed name the registry no longer holds is withdrawn, and a name whose GROUP is off is not — it stays captured and toggled, which is the landed mechanism and the reading `F-1` did not touch (L2 §10, §12; `G-4`).
- **The CONSTRUCTION captures too, and that is what makes the first `added` empty**: `createServer` registers `allowedToolNames()` through the one call `registerTools`, so the map is populated by construction and `syncPublishedTools()` moves a set that already stands rather than opening it (§2's `registerTools` row; L2 §12).
- **Two SDK calls carry the whole move, and no third is invented** (the installed SDK; offsets are a date, the members are the claim — D-46): `McpServer.registerTool(name, …)` answers the `RegisteredTool` and THROWS on a name already registered, which is why the capture map is the guard; `RegisteredTool.remove()` (`update({name: null})`) withdraws a name outright, while `update({ enabled })` only hides it from `tools/list` and leaves a call answering the protocol's `-32602 … disabled`. Both registration and every update fire the tool-list-changed notification, which is how a connected client learns the set moved with no reconnect.
- **Withdraw is `remove()` and never `update({enabled:false})`, and the ground is the axis**: a disabled handle is indistinguishable from a group-off one, so the group axis could never restore it, and a later re-activation of the same name would meet the SDK's already-registered throw. The group axis keeps the LANDED mechanism — a handle stays resolvable and is toggled, never deregistered (mcp-server.ts's `regateLiveServer` note; L2 §10).
- **A composed name is public whether or not a router stands, and a call is then refused by NAME — the READER IS DECLARED** (`F-2`): the dynamic arm reaches the router through `liveRouter: () => CapabilityRouter | null`, the same shape the landed `liveGate: () => SecurityGate` uses, and `invokeModuleTool` gains the null arm that answers the instance method's landed words, `invokeTool: no module router configured`. So the listing never depends on the router and the call never depends on a second spelling (§9 `G-6`).
- **Three callers and no fourth** (L2 §12; L1 §3 `S-5`; D-123): (i) the `module.install`/`module.update` handler, right after the registry re-sync that already runs there; (ii) the re-gate's widen arm, which today re-registers newly-allowed names by hand and now calls this one member; (iii) the composition's activation delivery where the registry moves outside a tool call, which is module-system's and calls this member and nothing else.
- **`http` needs no re-registration and gets none**: that transport builds a fresh server per POST from the current gate, so it reads the composition at construction by construction (L2 §12; mcp-server.ts's two transport sites). No row of the battery drives `http`.
