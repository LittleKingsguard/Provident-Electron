## 1. The subject, and the four things it moves

- **`ToolGroup` STOPS BEING A CLOSED UNION AND BECOMES THE REGISTERED SET** (`S-8`): the six ids survive as the **foundation's contribution** — one ordered literal, read by the registry and by this file, never re-spelled (`C-4`, `ASM-DR-2`). The API's type is a string id; which ids exist is the registry's answer, and no compile-time net stands in for it.
- **THE GATE'S OWN VALIDATOR IS THE LOAD-BEARING SITE, AND THAT IS MEASURED RATHER THAN ASSERTED**: `src/main/security.ts`'s `VALID_GROUPS` (the file's own copy of the six ids, beside `operator-settings`' — `S-9`'s) is what `isToolGroup` checks every `apply({groups})` and `apply({disable})` against. **A module-declared group that the validator does not admit can never be ENABLED**, so "defaults OFF" would be unimplementable — the patch would be rejected whole and the group would be off for ever (`applyPatch`'s F4 arm, unchanged in posture).
- **`groupForTool` STAYS THE FOUNDATION'S RULE AND THE COMPOSED MEMBERSHIP WRAPS IT**: the exact rows, then the `module:` prefix, then `null`, unmoved; `composedGroupRule` answers a declared membership FIRST and falls through to it, which is safe because a declared name is a `module:<n>.<t>` tool that no exact row carries (§3).
- **THE INVOCATION PAIR IS RE-GRAINED FROM `module` TO THE TOOL'S OWN GROUP**: today `moduleToolAllowed` requires `module` AND, for an executable tool, `code` — a requirement that a tool declared into another group could never satisfy, because `module` is no longer its group. The `code` half stands unchanged: an executable module tool is still trusted-equivalent to `code` (`design.md` §4, `G-8`).
- **`defaultSecurityConfig()` IS UNMOVED — `['read','dispatch']`** (`S-8`, brief §2): a module-declared group is absent from it, and **that absence IS what "defaults OFF" means**; no second default, no per-module grant and no "enabled unless disabled" arm exists.

## 2. Structure — one injected rule, one declaration, one shared literal

| Name | Site | Kind | What it is |
|---|---|---|---|
| `ToolGroup` | `security.ts` | MOVE · the union retires, the NAME stays | `string` — an id in the registered set. **The name survives because `S-8` names it and a rename would move four files' imports to spell nothing different**; the union's six members are `TOOL_GROUP_IDS` and no type closes over them (`ASM-GD-1`) |
| `GroupRule` | `security.ts` | NEW · exported interface | the TWO questions the gate asks of a group domain and no third: `groupOf(name): ToolGroup \| null` and `groups(): readonly ToolGroup[]` |
| `foundationGroupRule` | `security.ts` | NEW · exported value | the DEFAULT rule: `TOOL_GROUPS`' exact rows, the `module:` prefix, and `TOOL_GROUP_IDS` as its set — this file's own foundation contribution, and the only default any function here takes (`ASM-GD-1`) |
| `composedGroupRule` | `security.ts` | NEW · exported function | `(foundation, groups, carriers) → {rule, refused}`: `groupOf` is the declared membership first and the foundation's rule second, `groups()` is the SET IT IS HANDED — the registry's `declaredGroups()` — so the set has ONE authority and this function never derives it (`D-129`). `carriers` is the registry's own `DeclarationCarrier[]` (`docs/L3/declaration-registry/signatures.md` §2), so membership and ids are read from ONE input in ONE shape |
| `GroupRefusal` | `security.ts` | NEW · exported interface | `{status:'refused', reason:'declaration-duplicate' \| 'declaration-overstated', subject}` — a VALUE, never a throw (`D-105`); structurally a `DeclarationRefusal` wherever the reason is the duplicate, so the boot names both lists as one |
| `SecurityGate`'s `groups?` | `security.ts` | NEW · constructor option | the composed rule, injected at the boot's ONE construction site; absent, the gate holds `foundationGroupRule` |
| `SecurityGate.groupRule` | `security.ts` | NEW · getter | the rule the gate holds, so the two FREE predicates the server calls (`registrationAllowed`, `moduleToolAllowed`) are handed the gate's own rule instead of defaulting to the foundation's |
| `isToolGroup` | `security.ts` | MOVE · private, reads the rule | validates a patch's ids against `rule.groups()`; the SIX-id literal beside it retires (`S-9` retires the second copy in `operator-settings`) |
| `FOUNDATION_GROUPS`, `TOOL_GROUP_IDS` | `src/shared/types.ts` | NEW · **cross-seat**, `ipc-contract`'s | the six ids **with their labels** in roster order — the foundation's contribution, in the ONE shared file both realms read (`ASM-GD-2`); **`S-10` re-grains the literal to the pairs** because the renderer's roster needs the labels and may not spell the ids again, so `TOOL_GROUP_IDS` is the pairs' projection (`docs/L3/secure-panels/roster-and-placeholders.md` §3) |
| `ModuleGroupDeclaration`, `capabilities.groups?` | `src/shared/types.ts` | NEW · **cross-seat**, `ipc-contract`'s | `{id, label, tools?}` — the declaration a module makes (§3, `ASM-GD-3`) |

- **ONE OBJECT, NOT TWO CALLBACKS**: a rule that answered the membership but not the set (or the reverse) would let `apply` admit a group no tool resolves to, or refuse one a tool already answers — the drift `D-129` refuses, in the one place it would be silent.
- **THE RULE IS CARRIED BY EVERY RE-CONSTRUCTION THE GATE MAKES OF ITSELF, AND THAT IS THE TRAP THIS PAGE EXISTS TO CLOSE**: `SecurityGate.apply` and `withExclusion` both answer `new SecurityGate(...)` — `T-3`/`T-4`'s no-op arm included — so a gate that held the composed rule in a field but re-constructed without it would lose every module group at the first patch or exclusion transition, and the no-op arm is the one nobody watches because it reads like a return. The rule rides the same object as `token`/`enabled` through both sites, and `apply` hands it to `applyPatch` as well.
- **THE SET IS THE REGISTRY'S AND THE MEMBERSHIP IS THE DECLARATIONS', AND NEITHER IS DERIVED TWICE**: `composedGroupRule` is handed `declaredGroups()` and answers it unchanged, so the group SET has one authority (`docs/L2/declaration-registry/interface.md` §4) while the membership — which the registry's entries cannot carry, an entry being per-id (`C-9`) — is projected here from the same `capabilities.groups` the registry composed its ids from. **Two facts, one input; folding membership into an entry would make `groupEntries()` answer a map and break `C-9`.** The set is already foundation ∪ module — the registry composes both — so this function performs no union of its own.
- **THE DEFAULT READS THIS FILE'S OWN LITERAL AND NOTHING ELSE** (`ASM-1`'s posture at this axis): `foundationGroupRule` composes `TOOL_GROUPS` and `TOOL_GROUP_IDS`, both this file's and the foundation's, so a bare gate measures the foundation's six and no module group. **A test that constructs a gate without the composed rule is therefore measuring the foundation, and that is stated rather than discovered.**
- **`TOOL_GROUPS`' ROWS DO NOT MOVE**: every exact row keeps its group, `ALL_TOOLS` grows none and the `module:` prefix still covers the dynamic half (`design.md` §4; `L2` §10). What moves is the TYPE of a row's value and the SET the validator admits.

## 3. The composition — the foundation's rows, the declaration, the namespace default

- **THE ORDER IS FOUR ARMS AND NO SORT**: (i) an exact `TOOL_GROUPS` row; (ii) a declaring module's group whose `tools` carries the name; (iii) `module` for a `module:<n>.<t>` name with a non-empty rest; (iv) `null` for everything else, a bare `module:` included (`security.ts`'s landed F4 arm, unmoved). **ARMS (i) AND (ii) CANNOT COLLIDE** — a declared membership names a `module:<n>.<t>` tool, which no exact foundation row carries — so their order is immaterial and `composedGroupRule` asks the membership first because it is the narrower list; a reader must not take the order for a precedence rule.
- **A MODULE MAY NOT DECLARE A FOUNDATION ID**: a `groups[].id` equal to one of `TOOL_GROUP_IDS` is `{status:'refused', reason:'declaration-duplicate', subject: id}` at the registry's composition — never a merge, never a shadow (`ASM-DR-3`; `C-4`'s *"no module may declare a foundation id"*).
- **ONE NAME, ONE GROUP**: a tool named in two modules' `tools` lists, or twice in one, is `{status:'refused', reason:'declaration-duplicate', subject: <the tool>}` — **and it is `composedGroupRule`'s refusal rather than the registry's**, because the registry composes IDS and this is the first place the membership exists; a last-wins membership would let a second module move a tool out of the group its author declared. The boot names it beside the registry's refusals, in one list.
- **MEMBERSHIP RIDES THE GROUP ENTRY AND IS CHECKED AGAINST THE REGISTRATION** (`ASM-GD-3`): a `tools[]` element the same manifest's `capabilities.tools` does not carry is an OVERSTATEMENT, refused by name (`declaration-overstated`) **where the two lists are first in one hand — `composedGroupRule` — and not by a second arm in admission**, whose `declaration-overstated` compares a declaration against the ENTRY's registered set (`src/main/modules/admission.ts`), a different pair; `C-12`'s rule is asked once and no second list is minted beside it.
- **THE LABEL IS THE DECLARATION'S AND THE ROSTER'S, NEVER THE ENTRY'S** (`C-9`): `capabilities.groups[].label` is read by the renderer's roster (`S-10`), and the registry's `DeclarationEntry` still carries `{id, source, origin}` and no label (`docs/L2/declaration-registry/interface.md` §2).
- **A TOOL WITH NO DECLARED GROUP STAYS IN `module`** (`ASM-GD-4`): every module landed before this step keeps today's answer with no manifest edit, and the namespace default is the rule's third arm rather than a per-module grant.

## 4. The three instants, unmoved — and why the re-grain does not unify them

- **REGISTRATION: THE GROUP ALONE** (`design.md` §4's `registrationAllowed`, unchanged): a name registers iff its group is enabled; `module.install`/`module.update` keep their `module`+`code` pair because they are FOUNDATION names whose group is still `module`.
- **INVOCATION: THE TOOL'S OWN GROUP, PLUS `code` WHEN EXECUTABLE** (§1's fourth move): `moduleToolAllowed` still refuses a non-`module:` name, still defaults `executable` to TRUE (fail-closed), and still answers a VALUE-free `false` that this side turns into the SDK's error arm before entry (`design.md` §7; `D-105`).
- **THE RE-GATE: THE LANDED PAIR OVER `module.`/`module:` HANDLES** — untouched, because that predicate's breadth is the EXCLUSION axis's toggle and not this domain's membership (`design.md` §4, `G-8`; `MS-4`). **`G-8`'s rule survives this rev exactly as it survived `S-5`**: one function returning one answer for one name cannot say "group alone" at construction and "the pair" at the re-gate, so the asymmetry is the contract's.

## 5. What this page does not own

- **The registry's entry, composition rule and queries** are `docs/L2/declaration-registry/interface.md`'s (`S-6`), and the group domain's `declaredGroups()`/`groupEntries()` pair is that page's cell; this page states what the GATE asks of it and nothing of its shape.
- **The second `VALID_GROUPS` copy** is `S-9`'s (`operator-settings`), and **the label table's compile-time net** is `S-10`'s (`secure-panels`); this page names both and writes neither.
- **`ALL_TOOLS` is unmoved**: it stays the foundation half of the published set (`design.md` §1), and no group move adds, removes or re-orders a name in it.
- **`signatures.md` §1's `ToolGroup` STUB IS `S-5`'S, AND `SD-1` PINS THE PAIR** (`tests/unit/mcp-surface/signatures.test.ts`): that page must transcribe `design.md`'s CURRENT rev, so it may not be re-stamped ahead of a design that has not moved — and `S-8`'s design is THIS page, not `design.md`'s. **When `S-8` lands, the union stub and this page's `string` are one fact declared twice and the landing act must retire the stub (or re-point it here) in the same edit**, because a signature page still declaring a type the tree no longer has is exactly the drift `SD-1` exists to catch.
- **No MCP tool, resource, transport or bridge member is added** (`D-18`); the rule is in-process data read at the gate's construction.

## 6. The battery — `M-8`, and the arms its witness can take

- **`M-8` IS RESERVED AND FILED WITH `S-8`** in `tests/e2e/modularity/`, and it is RED until this design lands (`L1` §6; `D-40`). Its witness is ONE boot over a SEEDED profile, because a seeded `enabled` list is the only grant a spawning battery can supply (`D-85`; `L1` §6 (vi)).
- **THREE ARMS, AND THE THIRD IS THE ONE THAT MAKES THE DOMAIN MOVE REAL**: (i) seeded WITHOUT the declared group — the module's tool is ABSENT from `tools/list`, which is "defaults OFF" as a reading and not a promise; (ii) seeded WITH it — the name is published and its invocation passes the pair; (iii) seeded WITH the declared group and WITHOUT `module` — **the tool still publishes and still invokes**, because its group is its own, while every undeclared module tool in the same boot is absent. An arm that disabled `module` and expected the declared tool gone would pass on a rule that never moved.
- **THE VALIDATOR'S ARMS ARE THE UNIT BATTERY'S, NOT `M-8`'S**: `apply({groups:[<declared>]})` is accepted and `apply({groups:['no-such-group']})` is rejected WHOLE, in `tests/security-gate.test.ts` — a path this module's map row already claims. An e2e row cannot reach `apply`, so `M-8` does not claim it.
- **THE REFUSALS ARE READ BY NAME, NOT BY COUNT**: a module claiming `read` and a tool named in two groups each answer `declaration-duplicate` with their subject, and the boot names what it refused (`ASM-DR-3`, `D-105`).
- **WHAT NO ROW HERE CAN SEE**: a rendered roster (`S-10`'s, and the pane graph is not this module's), the operator's click, and any module's own body — a green here is the gate's and the published set's, never the app's (brief §6, `D-27`).

## 7. Assumptions, each with the alternative it rejected

- **`ASM-GD-1` — one injected `GroupRule` answering both the membership and the set, defaulting to this file's foundation rule.** Rejected: two callbacks (they can disagree, and `apply` would admit a group no tool resolves to), and importing the registry into `security.ts` (a boot-order cycle — the registry is constructed before the gate, and a module-level import would make the gate's own default read a composition it is not handed).
- **`ASM-GD-2` — the six ids live in `src/shared/types.ts`, `ipc-contract`'s file, which both realms already read.** Rejected: a new `src/shared/*.ts` file (a new map path and a new claim for one literal), and a literal inside `src/shared/registry/` (it would make the registry author its own input, which `ASM-DR-2` refuses).
- **`ASM-GD-3` — membership rides the group entry (`tools?`), checked against `capabilities.tools`.** Rejected: a separate `capabilities.toolGroups` map (two lists for one fact, and the drift `C-12` exists to catch would be structural rather than checkable).
- **`ASM-GD-4` — a module tool with no declared group stays in `module`.** Rejected: requiring every module to declare a group, which would break every landed module's manifest and move a member `OWED-6` is already retiring.

## 8. Debts this page does not discharge

- **`src/shared/types.ts` IS `ipc-contract`'s** (`OWED-6`'s precedent): `FOUNDATION_GROUPS`/`TOOL_GROUP_IDS` and `capabilities.groups` are edits in that module's file, declared here and carried there — and `OWED-9`'s *"`types.ts`'s one edit is `OWED-6`'s retirement"* is a COUNT this rev falsifies, re-grained where that row is written and not here. **`TOOL_GROUP_IDS` LANDS WITH THE REGISTRY AND NOT WITH `S-8`**: `FoundationDeclarations.group` (`docs/L3/declaration-registry/signatures.md` §2) cannot be handed by either realm without it, and the registry is the plan's step 1 — so `S-8` is the step that makes the GATE read it, not the step that mints it. **AND `S-10` OWNS THE PAIRS' SHAPE**: `FOUNDATION_GROUPS` is that step's (`docs/L3/secure-panels/roster-and-placeholders.md` §3), because the labels are the roster's need and `TOOL_GROUP_IDS` remains this page's member at its projection.
- **`main.ts`'s ONE CONSTRUCTION SITE BUILDS THE COMPOSED RULE, AND `mcp-server.ts`'s TWO FREE PREDICATES ARE HANDED IT** — `const {rule, refused} = composedGroupRule(foundationGroupRule, registry.declaredGroups(), carriers); new SecurityGate({…, groups: rule})`, and the server's `registrationAllowed(name, enabled)` / `moduleToolAllowed(name, enabled, opts)` call sites pass `gate.groupRule` — **two files and two seats**: `main.ts` is `app-shell`'s and `mcp-server.ts` is this module's, in the same act as the boot census's registry construction (`D-316`'s order: registry first, gate second, because the rule reads the registry's set). A call site left on the default would refuse a declared group at registration while the gate admitted it — the split the page's `groupRule` getter exists to prevent.
- **`operator-settings`' copy is `S-9`'s and `secure-panels`' roster is `S-10`'s**; this page is the shape both read, and neither is written here.
- **`M-8`'s witness is not filed by this rev**: a reserved row is filed with the step whose landing makes it green (`L1` §6; `D-40`).
