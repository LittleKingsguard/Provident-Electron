## 1. The gesture, and the three shapes it could have been

- **THE HANDLE OWNS THE DRAG, SO RELOCATION CANNOT BE THE SAME GESTURE WITHOUT BECOMING TWO GESTURES** (`D-178`'s rule: a gesture's felt behaviour is unverifiable here, **so the DESIGN must make it unambiguous rather than discoverable by trial**): one box that sometimes resizes and sometimes relocates is a person's guess about a record write, and no row of the four legs can see which meaning a hand intended.
- **AND A DROP-ONTO-A-ZONE IS NOT EXPRESSIBLE WITH THE MACHINERY THAT EXISTS — MEASURED, NOT PREFERRED**: the affordance's session is local to its element, because **no pointer capture is installed** (`demo-envelope.ts`'s own handle comment: *"this composition installs NO pointer capture, so the session's tracking listeners are LOCAL to the element"*, and design.md §3's `R`-order says the same) — so **a drag that leaves the strip's box loses its reading**, and a pointer over another zone is a pointer the gesture cannot see. A modifier on the same drag is worse: it is invisible in the markup, has no data form (`D-177`: an element is provident data or it does not exist), and is exactly the "discoverable by trial" the corpus refuses.
- **SO IT IS A SECOND AFFORDANCE, AND ITS VERB IS A PICK RATHER THAN A DRAG.** The pane carries **one MOVE grip** (`cursor: 'grab'`, an authored glyph, `props.tabindex: '0'`) and **four DROP nodes, one per declared zone**, authored as the grip's CHILDREN and revealed while the grip holds focus — **the menus' own mechanism, exactly** (`demo-envelope.ts:866`–`:875`: `props.tabindex: '0'`, a `:focus-within` rule in the page sheet, *"NO STATE, NO TOGGLE AND NO NEW RECORD"*), so **no arming state exists anywhere**: not in a record, not in a closure, not in a `props` write.
- **WHAT TELLS A PERSON THE TWO GESTURES APART IS FOUR THINGS AT ONCE, AND NONE OF THEM IS A FEELING**: the **verb** (the strip is dragged continuously and moves one figure; the grip is pressed and then a destination is chosen, so the second click is the act); the **box** (a `14px` strip on the edge the adjustable axis moves, against a `14×14` grip at the pane's flow origin carrying a glyph); the **cursor** (`row-resize`/`col-resize` against `grab`); and the **ids** (a strip's own id against the grip's and its drops'). A press on a drop can never be a resize and a press on a strip can never be a move.

## 2. The drop target: the GRAPH names it, and no hit-test is taken

- **THE QUESTION "WHICH ZONE?" IS ANSWERED BY THE NODE THAT WAS PRESSED, AND NEVER BY ARITHMETIC ON BOXES**: each drop authors **`props.pane`** (the record id its act addresses) and **`props.zone`** (the declared zone id it relocates to), and the turn reads both **off the node** through the file's own `authoredPropOf` — **the `props.role` idiom the menus items already use** (`D-177`, `D-235`), so the act's two operands are authored data with a node id in the address book.
- **NO HIT-TESTING IS NEEDED, AND THE ALTERNATIVE IS UNMEASURABLE RATHER THAN MERELY UNVERIFIED**: the only box idiom in this corpus is `getBoundingClientRect`, and **it THROWS in the layout-less DOM shim** — `element.getBoundingClientRect is not a function`, which the shim-realm rows of `tests/ui-leg-contract.test.ts` assert as the shim's own signature — **so a drop resolved from a pointer's position would be unmeasurable in every module row of this unit** and would need an Electron leg for its every reading (`D-27`: a node green is envelope-green; `D-178`: an unverifiable list already carries the edges). **A design that cannot be measured where its rows live is not a design this corpus takes.**
- **IF A FREE POINTER DRAG IS EVER WANTED, THE SEAM IS NAMED AND NOT TAKEN**: `src/shared/relocate.ts` declares `candidatesFor?` and has **no `src/` importer** (`D-111`; `D-168` deleted the only implementation). That seam is where a candidate set would come from — the four zone nodes resolved by `runtime.elementForNodeId` (the graph read, never a selector) and boxed by `getBoundingClientRect` — and it would need pointer capture on the session first. **Refused here on the two grounds above, and named so a later pass inherits the question rather than rediscovering it.**

## 3. The turn — `startPaneMove(runtime)`, one live body per drop, ONE write per act

```
startPaneMove(runtime):                                        // boot, once, beside the affordance's attach and the menus'
M1  for each of the EIGHT declared drop ids:                   // the census IS the address book (`D-235`), and the ids are literals on both sides (§7)
M2    pane = authoredPropOf(runtime, dropId, 'pane')           // the RECORD id the drop addresses — read OFF THE NODE
M3    zone = authoredPropOf(runtime, dropId, 'zone')           // the DECLARED zone id — same read, same relation, no table of its own
M4    install the LIVE body under the drop's own authored handler pair, as ONE `state-slice` (`D-239`'s path)   // so `provident.dispatch` at the drop runs the act
M5    attach ONE `click` listener for the human cause, calling that same body                  // one act, TWO causes (`D-239`, `AL-3`'s instrument)

the body:                                                     // every arm answers a value and NOTHING throws (`D-127`)
X1  standing = the shape's pane record for `pane`; absent → report and RETURN   // no record, no act: nothing is invented
X2  value = { ...standing's `id`/`width`/`height`, `zone`: zone }               // BOTH FIGURES VERBATIM (§4) and NO `bounds` (§4)
X3  void dataRoute('write', { path: ['panes', pane], tier: 'file', value })     // ONE write, the family's own address, the realm's existing route
    .then(answer → refused: `console.error` (reason + message) ; unread: `console.warn` ; committed: SILENCE)   // `D-117`'s register
X4  the RECORD's own push repaints: no paint call stands here, no re-read, no poll (`D-82` clause 4)
```

- **WHY THE WHOLE RECORD AND NOT A ROUTE OF ITS OWN** (`D-191`, `D-189`, `view-shape.ts:187`): **no route of the view-record module writes a `zone`** — `commitPane(id, { width?, height?, bounds? })` carries three members and none of them is the placement, and it *refuses* a member the pane's `zone` does not make adjustable (*"a `width` handed to a sidebar pane is a fault, not an update"*). A relocation changes the member SELECTION itself, so it is not an update to either member: it is the record. **The act writes ONE record at the family's own address through the realm's `data.write` passthrough — the same verb `focusActRoute` uses for one tab row** (design.md §3, `D-156`/`D-157`), which is why this costs **no route, no channel, no bridge member and no new MCP tool** (`D-18`, `D-112`, `D-123`).
- **ONE WRITE AND NOT A PAIR**: `zone` and the `bounds` removal would be two leaves, and two leaves are two attempts, two commits and two deliveries for one act (the failure `D-142`'s settled `(b)` measured for the tab record, one family over) — so the value is the whole record and the address is the pane's own.
- **THE CENSUS IS BY ID AND NOT BY A CLASS OR A WALK** (`D-235`: *"the census is the address book"*): eight ids, eight `props` pairs, and **a drop whose `pane` or `zone` the record does not declare is refused by the STORE rather than dropped by the reader** — an undeclared zone id is `undeclared-zone`/`paneNodeAdmits`' second seat (`AL-8` measures the refusal), and an undeclared pane id is `undeclared-pane`. The turn therefore invents no judgement of its own.

## 4. What the record's members become on arrival — the charter's sentence, honoured by NOT writing a figure

- **NO FIGURE IS INVENTED ON ARRIVAL, AND THAT IS THE WHOLE POINT OF THE SPLIT** (`D-189`, `D-191`, `D-192`): **both members are STORED for every pane, always** — the creation repair writes both (`viewPanesPlaceholder`), `paneOf` admits no half geometry (*"no finite non-negative width or height"* is `panes-must-stand`'s refusal), and a member delete or a whole write missing one is refused. **So a pane arrives in its new zone already carrying the figure that zone makes adjustable**, and the answer to *"the new zone's extent, the old zone's other member, or a declared default"* is **none of the three: it is the figure the pane already stores for that axis.**
- **AND THE MEMBER IT NO LONGER ADJUSTS BECOMES MEMORY, NOT A CASUALTY** (`D-189`'s own sentence: the unpainted member *"is the memory that stops a zone change reusing one value"*): a `pane-menus` dragged out of `top` at `width: 100` into `left` keeps `100` in `width` and paints its stored `height`; dragged back, the `width` it had is exactly what it resumes — **which is the charter's sentence discharged by the record's shape rather than by an arrival rule.**
- **THE ONE MEMBER THAT DOES NOT TRAVEL IS `bounds`, AND ITS REMOVAL IS THE DESIGN'S DECISION**: `bounds` is the DRAG's pixel clamp and **it belongs to the axis it was measured on** (`D-243`'s distinction: *"the fill is a layout relation the cascade resolves; bounds are the drag's pixel clamp"*), while **a zone-resident pane's clamp is the LAYOUT's and its `bounds` is ABSENT AND LAWFUL** (`D-186`, `D-192`, and `readPaneBounds`' `undefined` arm now answers the measured pair — `D-238`). Carrying `pane-a`'s stage pair `{0, 200}` into a `top` zone would let a stale pixel ceiling govern a width never measured for it: **`D-129`'s second-authority fault in its quietest form.** So the arrival states no `bounds`, and a pane that returns to the stage answers the measured pair through the read's own absent arm — **no repair invents a pair, and `D-186`'s *"no repair reads `['zones']`"* is untouched.**
- **A DROP ON THE ZONE THE PANE ALREADY STANDS IN IS A WRITE OF THE RECORD THAT STANDS**: idempotent, answered `committed`, no guard added — a "nothing to do" arm would be a judgement about the record's current value, and `D-129` refuses a local copy of it. The eight drops are eight addresses, not four destinations and a check.

## 5. And the fill relation FOLLOWS THE ZONE — automatically, because `D-243` reads the record's zone every delivery

- **THE PAINT MOVES NO BYTE, AND THE REASON IS A DECLARATION THAT ALREADY READS ITS SUBJECT** (`D-243`): `paneFillAxisOf(record['zone'])` (`:2054`) answers the fill axis and the scroll axis from `LAYOUT_ZONE_AXES` **on every delivery**, `paneAxisMembers(record['zone'])` (`:2104`) selects the member the paint may write, and `nodeIdForPane` (`:2090`) maps the pane to its authored node without consulting the zone at all. **So the next delivery after the write paints the NEW zone's triple — fill on the axis the new zone fixes, the record's figure on the axis it makes adjustable, the scroll on the axis it adjusts — because the only input is `record['zone']`.**
- **IT IS MEASURED, NOT MERELY ARGUED**: `AL-10`'s fourth arm already **writes `['panes','pane-menus','zone']` at its own leaf** and asserts the three parts flip (`:2843`–`:2903`, `D-243`'s re-grain, including its false arm and the restore). **This page's act writes the same member through a different door**, so the paint's behaviour is the one a gating row already reads.
- **WHAT BREAKS IF IT IS NOT AUTOMATIC — STATED, BECAUSE IT IS THE FAILURE THIS SECTION EXISTS TO EXCLUDE**: if the fill were composed once (baked into authored `css`, or remembered at the first paint), a relocated pane would keep the OLD zone's fill axis while its figure landed on the axis that fill occupies — **one axis with two figures, `D-129`'s defect exactly**, and the pane would present its content on the wrong axis while every markup row stayed green. **The two authored fills (`menusPaneStyle`'s `height: 100%`, its `overflow-x`) are therefore DEAD data after the first paint and must not be read as the live answer** (`D-234`'s measured collision, restated by `D-243`).
- **`PM-1`'s MAP TOTALITY IS UNMOVED, AND THAT IS THE POINT OF ASKING**: `PANE_NODE_IDS` maps a PANE ID to a NODE ID and names no zone, so **a relocation changes no entry and the map's totality over `DECLARED_PANE_IDS` is untouched** (`design-pane-node-map.md` §2, §7). The same is true of `reportMeasuredFigures`' subject key, which is the record's pane id. **What would move either is a third declared pane, and nothing here declares one.**

## 6. The declared limit: the RECORD relocates, the RENDER does not — and it is `D-182`'s, not this page's

- **A PANE'S NODE IS AUTHORED INSIDE ONE ZONE AND NOTHING MOVES IT**: `#pane-menus` is a child of the `top` zone node (`demo-envelope.ts:841`) and `#gutter-pane` of the gutter card inside the stage (`:1094`); **post-bootstrap placement routing does not work** — a mint dirties only its target, the container is never recompiled, and path-compiling double-emits — **recorded upstream-owned at `D-182` (`D-5`, `D-52`) and deliberately relied on by nothing** (L1 §1: *"the `zone` member is DECLARATIVE ... every pane and row is authored where it belongs"*, `C-8`: *"no step reads it to place anything"*).
- **SO THE ACT'S MEASURABLE HALF IS REAL AND ITS UNMEASURED HALF IS NAMED**: after the write, the pane's FILL, ADJUSTABLE AXIS, PAINTED FIGURE and SCROLL all follow the new zone (§5, `AL-10`-measurable), while **the REGION it renders inside stays the authored tree's** — a pane relocated to `left` becomes a vertical pane drawn where it was authored, until one of two lawful shapes lands: **(a)** the upstream routing defect closes and a placement op can re-parent an authored node, or **(b)** an authored re-parent through the envelope's own mint/placement route is designed — **neither of which is this page's to invent** (`D-5`, `D-3`).
- **AND THE ROW THAT WILL MEASURE IT WHEN IT CLOSES IS NAMED NOW** (§8's `PR-2`): the same write, followed by a read of which ZONE node the pane's element stands under. Until then **the design says the pane changes its axes and not its address, and a reader must not conclude that the gesture is broken** — the `D-236` habit: a limitation stated at the place a person meets it.

## 7. The nodes, and the census

- **TWO GRIPS AND EIGHT DROPS, AUTHORED — SEE `app-envelope` rev 7 §10** for the fields, the `css` and each node's one-line reader (`D-177`). What THIS page states about them: **the grip is the pane's FIRST child and stands at the pane's flow origin** (`14×14`, `cursor: 'grab'`, an authored glyph, `props.tabindex: '0'`, `props.id`), which is the one placement channel a painted parent leaves — **no `position` on a pane, because the paint replaces its `css.style` whole** (`D-234`, `D-243`) — while **the grip's OWN style is never painted**, so it carries `position: 'relative'` and its four drops carry `position: 'absolute'` offsets. **The four strips of `design-zone-handles.md` and these two grips are the same class of node and the same reason: an affordance's placement must stand on a node the paint does not write.**
- **THE IDS ARE LITERALS ON BOTH SIDES** (`D-188` debt 2, `D-41`): the envelope authors them at the site and this page's turn spells them in its census list, **the zone ids'/`PANE_NODE_IDS`' precedent, with the equality a ROW and never a derivation**; **no export joins the published surface**, which is why `app-envelope`'s `endpoints` figure does not move (and is already stale at `19` for a surface of `21`, `D-239`).
- **`props.zone` IS THE DECLARED ZONE ID AND `C-9`'s ABSENCE RULE IS NOT REACHED**: the four destinations are zones (`DECLARED_ZONE_IDS`), so **no drop sends a pane to the stage** — a fifth destination would need a marker for `zone`'s absence, and the charter's own sentence moves a pane *"from a sidebar to a top/bottom zone"*. **The stage is therefore not a destination and a pane moved into a zone cannot be moved back by a hand**: the record still permits it (absence IS the stage, `C-9`), an agent's `data.write` reaches it, and **a stage drop is OWED to L1/L2 as a design question rather than invented here.**

## 9. Guardrail notes — what L4 must NOT do

- **Do not put the relocation on the resize handle or on a modifier** (`D-178`, §1): one box, one meaning; a gesture whose felt difference is a key press is the one thing this corpus cannot verify.
- **Do not resolve a drop from a pointer's position, and do not call `getBoundingClientRect`** (§2): it throws in the shim realm, so such a row could only stand in an Electron leg — and the corpus's one seam for candidates (`src/shared/relocate.ts`) still has no `src/` importer (`D-111`).
- **Do not write a `width`, a `height` or a `bounds` on arrival** (§4): both figures travel VERBATIM from the standing record and `bounds` is dropped; an arrival default would be right once and false after (`D-174`), and a carried `bounds` would clamp a new axis with a stale ceiling (`D-129`).
- **Do not add a route, a channel, a bridge member or a `zone` arm to `commitPane`** (`D-18`, `D-112`, `D-123`, `view-shape.ts:187`): the write is `data.write` at the family's own address, and `C-8`'s *"no route of this module writes a `zone`"* is a statement about the PANE route and not a licence to add one.
- **Do not compose, guess or remember the pane's current zone** (`D-129`): the store judges the value; the turn writes what the drop names and what the record holds, and reports the answer in `D-117`'s register.
- **Do not paint, place or re-parent a node from this act** (§6): the region is the authored tree's, the paint's inputs are the record's, and a second author of either is `D-182`'s defect dressed as a fix.
- **Do not add a state, a toggle or a record to reveal the drops** (§1): the reveal is `props.tabindex` + one `:focus-within` rule, the menus' mechanism, *"NO STATE, NO TOGGLE AND NO NEW RECORD"*.

## 10. What this rev does not claim

- **The region does not move** (§6) — the one sentence a reader must carry away rather than discover.
