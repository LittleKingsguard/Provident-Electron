## 2. The map's home — the WIRING, and why that is not a second store spelling

**Chosen: `src/renderer/renderer.ts`, a private declaration beside `LAYOUT_ZONE_AXES` (`:1587`). Four grounds, each a measurement or a citation rather than a taste:**

- **(a) THE POSITION ASSIGNS IT TO THE RENDERING, AND THE RENDERING IS THE RENDERER** (`view-shape.ts:137-138`). The envelope is provident **data** the rendering consumes: it authors nodes and names nothing about the record (`D-177`'s reader rule, `D-41`).
- **(b) THE MAP'S KEY IS A RECORD ID, AND THE ENVELOPE HAS NO BUSINESS NAMING ONE.** A map beside the envelope would make `demo-envelope.ts` **import `DEFAULT_PANE_ID`/`MENUS_PANE_ID` from `view-shape.ts`** — the data asserting what the store calls a pane. **That is the second store spelling this page exists to avoid**: not a second `['panes']` value, but a second declaration *of the record's id space*, standing in the module forbidden to hold one.
- **(c) THE ENVELOPE PUBLISHES NO CONSTANT FOR EITHER PANE NODE, MEASURED.** `gutter-pane` and `pane-menus` are **raw literals** (`:960-961`/`:723-724`); the published surface its map row counts (`endpoints` `19` in `strata/modules.json`, `20` at rev 6 — a CARRIED figure, `D-26`/`D-43`) contains neither, and **`:699-703` states why the zone ids stayed literals too**. So the envelope-side option buys nothing and costs a census.
- **(d) AND A THIRD HOME IS REFUSED TOO**: a new `src/shared/` module holding both vocabularies would be a **new file** — the `srcTypeScriptFiles` census and a map row, claimed at the map and never ahead of it (`D-10`, brief §2) — for two literals and a `find`; while `view-shape.ts`'s own home is refused on its charter, **the shape and NOT a store** (`D-78` ruling 3): an authored-node spelling inside the record's shared shape is the *mirror* of the error this page avoids, not its cure.

**THE COUNTER-ARGUMENT, ANSWERED RATHER THAN DISMISSED**: *the envelope is where a node's id is spelled*, and it is — **the envelope keeps that spelling** (its literal stands, unmoved). What it does not carry is **the mapping**, because a mapping is a claim about **two** vocabularies and only the rendering holds both. **AND THE ENVELOPE-WINS ARGUMENT LOSES ON ITS OWN TERMS ANYWAY**: a `GUTTER_PANE_ID` export would state **one side** (`nodeId`) and never the pair, so **the map would still have to exist** — the export would move only *who spells the node id*.

**SO THE NODE SIDE IS A LITERAL HERE, ON A PRECEDENT THAT ALREADY STANDS IN THIS FILE**: `:1582-1586` spells the four zone ids *"because the envelope spells them"*, publishes no constant, and hands the equality to `AL-10` **as a measurement, never a derivation** (`D-188` debt 2). **The pane map does the same on its node side and imports the record's key from `view-shape.ts` on the other** — one spelling each side, the correspondence declared once, here.

## 3. The stub L4 receives, the one fallback it must not have, and WHICH NODE

```
// BESIDE `LAYOUT_ZONE_AXES` — the SAME shape, so the file has ONE idiom for "the ids this turn addresses":
const PANE_NODE_IDS: readonly { readonly paneId: string; readonly nodeId: string }[] = [

  { paneId: MENUS_PANE_ID,  nodeId: 'pane-menus' },     // measured EQUAL today and DECLARED regardless — an equality nothing derives (§6)

function nodeIdForPane(paneId: string): string | null    // PRIVATE, TOTAL over any string
P1  find the entry whose `paneId` is the argument — `paneGeometryIn`'s own `find` (`view-shape.ts:264`)
P2  answer its `nodeId`, or `null` where this map declares none — and NEVER the pane id itself
```

- **`null` AND NOT THE IDENTITY, AND THAT IS `D-174`'S STANDARD APPLIED TO A LOOKUP**: an identity fallback is *right once and wrong after* — it makes `pane-menus` work **by coincidence**, and it hands **every** undeclared pane id a live route to any element that merely shares its name, which is the confusion `view-shape.ts:137-138` refuses. **A declared absence cannot be wrong**; a fallback that happens to answer correctly today can.
- **A DECLARED LIST AND NOT A `Record<string, string>`**: `tsconfig.json` carries `strict` but **NOT `noUncheckedIndexedAccess`**, so an index signature would type the lookup `string` and **lie at runtime** about a missing key; a `find` over a declared list is total, and `LAYOUT_ZONE_AXES`/`paneGeometryIn` are the two shapes already used.
- **`'gutter-pane'` AND NOT `'gutter-card'`, WHICH IS THE ONE THING HERE THAT IS A READING AND NOT A PREFERENCE.** `D-214` and `D-224` both say the stage pane's box is *"`gutter-card`"* — the **ancestor `section`** (`demo-envelope.ts:953-955`) that holds the `h2`, the pane and the read-out. **The record's subject is the PANE, not the card**: `#gutter-pane` is the node that carries `props.resizable: 'true'` and the authored `paneStyle` (`:959-961`), `docs/L2/app-envelope/interface.md`'s *"No type is exported…"* bullet names `#gutter-pane` as **the pane whose record is `pane-a`**, and `tests/pane-drag-compliance.test.ts:2591`/`:2625` seeds and drives **`'gutter-pane'`** as that family's element. A height written on the card would drag the heading and the read-out's layout into the record's figure — the wrong node, and one no row would call wrong.

- **WHAT A MISSING ENTRY WRITES**: **nothing to the DOM** — there is no element, and inventing an id for `paintStyle` is the invention `D-129` refuses — **and `pane-x.<member>=absent` IN THE CARRIER**, at the record's own key. **The absence is a DECLARED READING and never a silent skip** (`D-127`'s arm one level down): an omitted subject and a stated `absent` **are different text**, and only the second is a reading. **`absent` KEEPS ITS ONE MEANING** — *no authored element answered for this subject* — and **no fifth word is minted** for "the rendering does not display it" (`D-174` deletes exactly that); the *reason* is this page's to state: **a pane the carrier reports `absent` is either a pane this rendering does not display or a node that would not resolve, and for the carrier's only reader those are one fact — the figure is not there.**
- **THE CARRIER'S KEY RULE, STATED ONCE, BECAUSE IT IS THE ONLY THING THIS PASS CHANGES ABOUT THE INSTRUMENT'S TEXT**: **the `id` the carrier prints is the PAINT'S SUBJECT KEY.** It **coincides** with the node id for the zones and the rows, whose record ids *are* node ids there, and it **is the record's pane id** for the pane family. **WHY THE RECORD'S ID AND NOT THE NODE'S**: (i) the only reader compares the carrier **against the record** (`AL-12`), so the key must live in the record's key space or the row must carry the rendering's map; (ii) **a pane the map does not declare HAS NO NODE ID TO PRINT** — a node-keyed carrier could only skip it silently or synthesize a name, so the record key is what makes a declared absence expressible at all; (iii) it keeps every subject a row already names (`pane-menus.width=…`, `top.height=…`) spelled as it is, so the rows move on VALUES and PROSE and never on addressing.
- **AND THE ONE LIMIT THAT SURVIVES, MEASURED RATHER THAN HOPED** (`D-224`'s limit `(ii)`, and it is sharper than a fill coincidence): **the carrier cannot catch a wrong map entry that names another EXISTING node**, because the write and the report consult the **same** `nodeIdForPane` — the paint would write the record's figure onto the wrong element and the report would read that figure back. **So the carrier proves APPLICATION and never WHICH NODE**, and *which node* is the MARKUP's to measure (`AL-10`'s `style` attribute on `#gutter-pane`, §7). Two instruments, two claims, neither pretending to be the other (`D-224`: *the row reads the carrier; the TURN reads the computed style*).
