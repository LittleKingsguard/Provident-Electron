## 1. The structure — three files, one owner each

The module is main-side and has no renderer code (D-63's client role; §6). Three files, and each exists because a different thing could go wrong:

| File | Holds | Why it is separate |
|---|---|---|
| `src/main/tabs-record/index.ts` | the record over the APP'S ONE STORE: **three** address constants, **six** batched declarations and **four** routes — and no instance and no file of its own (D-64, D-65) | every write is one whole record at `['tabs']`, so the surface holds no store verb and `main.ts` holds no file path |
| `src/main/tabs-surface/index.ts` | the surface: the one reference to the record, the one subscription (`attach`/`detach`), the shape arm and the refusal mapping (L2 §2, L2 §3) | the record is constructed once at boot, and this module is the only one that holds it (the `settings-surface` arrangement, `docs/L1/security-store-storeroom.md` §4) |
| `src/shared/tabs-channels.ts` | the **four** channel constants, single-sourced | a channel name spelled in two files is a rename that half-lands (`store-channels.ts`'s precedent) |

**One construction site, and it is the surface's** — `createTabsSurface`: no tabs file constructs an instance and none spells a `provident-*.json` name (measured 2026-11-02: `grep -rn "provident-.*\.json" src/main/tabs-record/ src/main/tabs-surface/ src/shared/tabs-channels.ts` is empty) — because the instance is the boot's and this module is handed a store that already stands (§2, D-65).

## 2. The instance, the three addresses, and the leaf shape

The instance is `provident-storeroom`'s and it is the APP'S CENTRAL ONE (D-64): the boot constructs it with one file path and the batched `cfg.constraints` (§4), and the package owns that file's byte image, its journal, its rollback and its durability (`guide §9`). This module constructs nothing and opens no file; it chooses **three** address constants and **six** declarations and nothing else (D-65).

- **`TABS_RECORD_ADDRESS` is `['tabs']`**, the record root: the `order` seat plus **one flat leaf per tab, named by the tab id** — the landing ENTRY among them, so `['tabs','landing']` is its leaf and no second seat is stored (D-76).
- **`TABS_ORDER_ADDRESS` is `['tabs','order']` and it is the ONE SINGLETON SEAT**: the ordered place of every tab id and the sequence every judgement is seated from. **`TABS_LANDING_ADDRESS` is `['tabs', TABS_LANDING_ID]`** — the landing entry's own leaf, where the witness is derived and never stored. An entry id spelling the seat is unrepresentable and is refused `seat-name` before any store act, at both routes that take an id (L2 §3, D-76).
- **A TAB'S LEAF IS ONE FLAT ROW**: `id`, `target` (the data object it contains), `active`, and optionally `label`, `error` and `lastActiveAt`, each guarded by its own pair (§4; `src/shared/types.ts`'s `TabsRecordRow`).
- **THE ACTIVE ID IS DERIVED, NOT STORED** (D-76, D-140): `landingOf` answers the landing entry's row where that row reads active, else `order`'s first row reading active, else `null`, which `read()` spells `''`. A writer therefore hands the family `order` and one member per tab and **no witness member at all** (site `landingOf`, and `read`'s `seats`).
- **THE RECORD IS ONE ROOT AT ONE TIER**: `TABS_RECORD_TIER` is spelled once and published only through `tabsDeclaredRoots`, which answers `['tabs']`/`file` and nothing else — which is what admits a `file`-tier write there and refuses any other (D-101, D-142).
- **A construction that cannot stand is not this module's arm**: no route answers `FilePathUnreachable` (measured 2026-11-02: `grep -rn 'FilePathUnreachable' src/main/tabs-record/ src/main/tabs-surface/` is empty) — the boot hands it a store that already stands, and the existence pair has already created the root (D-65, D-69).

## 3. The four routes, and the one that is absent

**`window.provident.tabs` CARRIES FOUR ROUTES AND NO FIFTH** — `read()`, `commit(row)`, `remove(id)` and `onChanged(handler)` (L2 §2; site `src/main/preload.ts`'s `tabs` member) — and the surface module behind them holds `read`/`commit`/`remove` beside its ONE subscription (`attach`/`detach`), while the record's own interface spells the fourth route `subscribe` (`TabsRecord`, whose one subscription `createTabsSurface` installs). **`read()` is TOTAL** — `{status:'committed', order, landing, rows}` — so the refusal type it is declared against is never minted at the record (L2 §2).

**`remove` is a caller's act, and it rewrites the whole record without the tab**: the member leaves, its seat leaves, and no successor is chosen there, because the referent discipline is the repair's one home (§7). One verb is absent and named so no reader looks for it: **there is no `journal`** (the record's history is the package's, and a second reader of it would be a second opinion about the past).

## 4. The constraint — the engine's gate, and the engine's repair

**The gate and the repair are both the engine's.** This module writes six bodies and registers them at construction through `cfg.constraints`, whose element carries the pair **and** the function and is armed before any filesystem act (`guide §7.2` route one). The engine invokes a body and reads its answer: **`true` is the only pass value** and an object carrying a `message` is a **rejection** (`guide §7.2`, `§7.5`). The body **reads the record** to count actives, which `guide §7.6` makes the caller's work — *"if your constraint cares about the state at any other location, it reads that location"*.

**A REPAIR NAMES THE COMMIT IT WAS HANDED AND RETURNS THE OP ITS WRITE LANDED.** The engine invokes `repair(repairContext)` **inside the attempt's own commit** (`../Provident-Storeroom/docs/specs/storeroom-constraints/contract.md` §(viii); that repo's `D-45`, `D-46` item 2). Passing that context at `write`'s **fourth position** makes the repair's write **join** the open attempt; without it the same write is refused `KC-7` — *"a constraint attempt is already open at `tabs`; it is disposed of by its own K-3 and by no other act"* (D-67, D-73). A `void` return "produced no op" and failed `KC-4` at `1.7.0`, which is filed upstream as `ST-F2`; the installed release credits a repair by the legs its own write wrote, and this module takes none of that licence, so **a repair answers ONE OF TWO DECLARED ARMS** — `{ok: true, op}`, carrying the op its write landed, through the one constructor `repairAnswer`; or `{ok: false, message}`, where it reached no write route, was handed no commit, or held no record to correct — and `TabsRepairAnswer` makes `void`, `undefined` and a bare `{ok: true}` compile errors (D-72; `writeWholeRecord`'s and `repairOrderSeat`'s failed arms).

**ONE HOME FOR "WHAT IS A CORRECTED RECORD".** A repair correcting only its own field hands the re-run a record that still violates the others, and each repair then nests another until the restart budget (`RESTART_LIMIT` 3) is spent — so all six compose through `healedFamily`, which fills all three field defaults, drops a seat the record cannot justify, names a repeated seat once, leaves exactly one row active, and never lets an empty sequence survive: the landing ENTRY takes that seat (site `healedFamily`; D-83). **The survivor's precedence is §7's**, derived from the same body.

**THE TWO CREATION-INSTANT PAIRS ARE UNWRAPPED, AND THE ARITY DIFFERS BY INSTANT.** `tabs-must-stand` and `order-names-its-tabs` are not wrapped by `body`, because the boot binds no handle until `storeCreate` answers and a wrapped body abstains at the one instant it must act. A registration-instant repair's record carries a `write` member and **three positions and no fourth** — a fourth there is a `TypeError` before any store act — while a landing-instant record is the six-member one whose commit MUST be named at the fourth; the branch is the record's own `write` member, never the instant's name (D-69, D-73, D-83; `writeWholeRecord`). **AND `order-names-its-tabs` STANDS AT `['tabs']` AND NOT AT THE SEAT'S OWN ADDRESS, WHICH IS A MEASUREMENT**: a pair at `['tabs','order']` is handed the SEAT at a registration instant, so its repair could write an `order` and never the rows that order names — and `{order: ['landing']}` over a record holding no `landing` row is the state the pair exists to refuse (D-83).

**ONE WHOLE VALUE AT `['tabs']` MINTS THE ROOT, THE SEAT AND EVERY MEMBER IN ONE CALL**: a nested write does not create its parent — measured, `write(['tabs', id])` on a fresh store answers `AddressNotFound` with an EMPTY `log`, so no constraint is ever asked (`guide §2`'s fifth rule, quoted at `composeRecord`; §8) — **AND THE MEASUREMENT IS TRUE WHILE THE INFERENCE IS NOT THE COMPOSER'S REASON: the parent is ENFORCED and trusted present, and §10 corrects the reason in `D-135`'s register**. **So a fresh record carries the landing tab before any act** — and the root cannot be deleted out from under the app: measured 2026-11-01, a `delete(['tabs'])` is answered as the store's own success while the existence pair's repair re-creates the record inside the same commit (D-69).

**SIX DECLARATIONS RIDE THE BATCH, NOT ONE, AND THE REASON IS THE SENTENCE A CALLER GETS**: a violation is a fact about ONE field, so a body that tested all of them could not say WHICH one was repaired — and `guide §7.2` rejects a repeated `id` in one supplied list, so the six are named apart (D-65, D-83).

| id | Holds when | Repair |
|---|---|---|
| `tabs-must-stand` | the address `['tabs']` holds a record at all | **creates** it: the landing entry, seated and active |
| `order-names-its-tabs` | the `order` seat is a non-empty sequence naming the record's OWN tabs, each **once** | **writes the corrected order** inside the one legal record (D-83) |
| `exactly-one-active` — `TABS_CONSTRAINT_ID` | at least one member survives **and** exactly one entry reads active | **§7's normalisation** |
| `tab-has-title` | the tab's `label` is a non-empty string | writes `'untitled'` |
| `tab-has-content` | the tab's `target` is a non-empty string | points it at the authored landing page — `'tabs-landing-page'`, a CONTENT target and not an id (D-76) |
| `tab-has-lastActiveAt` | the tab carries an activation stamp | stamps it with **now**, as an ISO string so the byte image stays JSON-plain |

**A REPAIRED ACT ANSWERS `committed` WITH `repaired: true`, AND THE MEMBER IS DERIVED, NEVER PREDICTED** (D-70, L2 §3): the write's own record carries no member for a repair inside its own commit (`guide §6.4`), so the act compares the record it INTENDED with the record that STANDS — canonically, member order and absence normalised, or a clean act would report a false difference — omitting the member on a clean act and never answering `false` (sites `standsAsIntended`, `canonicalRecord`).

## 5. The listener — an address, never a payload

**`onChanged` takes ONE subscription and delivers exactly ONE notification per committed change of the record** — a `commit`, a `remove`, a whole-record write through `data.write`, and a repair's own write inside that same commit, which JOINs it rather than opening a second one (D-67, D-142). The delivery names the **triggered address** and never the value (`guide §6.4`), so a client re-reads; **a write a pair REFUSES delivers NOTHING**, because the pairs are asked, the pass throws, and the delivery window never opens (D-71).

**THE LISTENER STANDS AT `['tabs']` ITSELF, BESIDE ALL SIX PAIRS** (D-71): the one cross-kind restriction is the HANDLE — a listener whose handle equals a pair's `id` is refused `AddressMalformed` — and this module's handles are `tabs-record:<n>@tabs`, MINTED per subscription so a second subscriber cannot starve the first (site `handleFor`). The installation is two acts (`listen` reserves, `register` fills), the body WRITES NOTHING — a listener's write opens its own commit — and it CONTAINS the caller's throw, which would otherwise cross into the write that fired it (`guide §6.2`, `§6.5`). **The withdrawal is its own answer and is idempotent** — one `unlisten` per handle, a lawful no-op over a handle already withdrawn — and a listener that outlives its window is a leak no client can see (`guide §6.2`; `attach`/`detach`).

## 6. What the record still refuses to be

- **No MCP surface.** No tool, resource or `RpcMethod` member names the instance or its file; the crossing is the bridge's, and an agent's own door to this record is `provident.data.*` (D-101).
- **No renderer import, and the renderer reaches the record by TWO doors and holds no third.** `src/renderer/**` never imports these files: the client's `read()` and its `onChanged` delivery are the first door, and one whole-record write, composed from its own reading and handed to `data.write` at `file`, is the second (§8). **The clause that it reached the record "through `window.provident.tabs` and nothing else" is what `D-142` supersedes**, and neither the tabs surface nor this module gains a route or a composer for it (D-142, D-136).
- **No second record.** One construction site and no file of this module's own (§1, §2): a client holds no rows, no `order` and no landing seat of its own — no mirror, no cache, no renderer-side copy of the family (D-62, D-142).
- **No second authority over the invariant.** No client registers a pair at `['tabs']` and none re-implements the normalisation: a caller that cleared the older flag, or refused its own two-active composition, would be the authority the repair exists to be (§7, D-65, D-129).
- **`order` is never a client's invention.** The member written is the one the reading carried, so the composition is a copy of a record READ and never a sequence made up (D-140, D-142).

## 7. The normalisation — what a write seating two active rows becomes

**A WRITE THAT SEATS TWO ACTIVE ROWS IS NORMALISED DOWN TO ONE INSIDE ITS OWN COMMIT** (D-142, D-140): `exactly-one-active` rejects the record and `healRecord` writes the corrected one, joined to the attempt, so the re-run reads one legal record and the caller's write stands. **THE CALLER NEVER CLEARS THE OLDER FLAG** — doing so would make the caller the authority the repair exists to be (D-142, D-129).

**AND THE SURVIVOR'S PRECEDENCE IS THE CODE'S, AT `healedFamily`, MEASURED AND NOT RESTATED FROM THE RENDERER'S ALGORITHM**: **(i)** the **written referent**, where it survives in the seat; **(ii)** else the **removed entry's pre-position**, folded onto the survivors; **(iii)** else the seat's own order — `order`'s **first row reading active** where several stand, and `order`'s **first row** where none does. The rest are deactivated **in the same object**, so the re-run reads one corrected record and not an intermediate state (site `healedFamily`; D-142, D-140, D-76).

**THE PRE SIDE IS THIS MODULE'S OWN OBSERVATION, AND THE RULING MAKES IT OLDER THAN IT USED TO BE.** The engine hands a body the landing op and its value and never the machinery's pre-write capture, so the referents are derived against the last record this module saw — refreshed by every `read` and every `commit`, and NOT by a whole-record write through `data.write`, which reaches the store through neither (§8). The window is one delivery long: the record's own push fires on every committed change and a client re-reads after each, which is what closes it (D-136's stated cost, D-137, L2 §2).

**A repaired act is `committed`, never `refused`** — the repair is the engine working, and a refusal would leave the older row standing (D-103, D-105).

## 8. The write paths, after the ruling

| Path | Who composes | Who judges | What passes through unchanged |
|---|---|---|---|
| `tabs.commit(row)` and `tabs.remove(id)` — this module's own verbs, reached through `window.provident.tabs`'s four routes (L2 §2) | **this module**: `composeRecord` writes the `order` seat and one member per seated id, and `remove` composes the same family without the tab (§3) | the six declarations at `['tabs']` (§4) | the caller's row, admitted field by field and written as admitted: no member is invented and no successor is chosen (§4, D-140) |
| the renderer's **whole-record write** — `window.provident.data.write({path:['tabs'], tier:'file', value})` → `ipcMain.handle(IPC_DATA_WRITE)` → `createDataSurface().write` → the store's write verb (sites: `src/main/main.ts`'s handler, `src/main/data/surface.ts`'s `write`) | **the renderer**, from its own committed `tabs.read()` reading: `order` plus one member per tab, and nothing invented — D-136's seat, which is where formatting belongs | **`exactly-one-active`, at `['tabs']`, the address the invariant is registered at**: the write is JUDGED and its repair run, never refused by this surface (§4, §7, D-142) | the value, **byte for byte**: the handler forwards to the store's write verb and transforms nothing (D-136, D-142) |

**"TRANSPARENT" MEANS NO TRANSFORMATION, NOT NO REFUSAL** (D-142). `data.write` still answers `malformed-arguments`, `declared-tier`, `parent-absent` and the store's own refusals, because those are the STORE'S judgement passing THROUGH rather than this surface's decision (sites `src/main/data/args.ts`, `src/main/data/mapper.ts`, `src/main/data/surface.ts`); `['tabs']` being a declared root at `file` is what admits the legal tier and refuses every other (§2, D-101, D-142). **AND THE JUDGEMENT COMES BACK AS THE STORE'S OWN ANSWER**: a repaired write answers `repaired: true` beside the commit's materialized `log`, derived from a `repair-run` entry's PRESENCE and never from an empty list, so a caller reads the pass rather than inferring it (D-103).

**GUARDRAIL FOR WHOEVER LANDS THE RENDERER'S SIDE — THE COMPOSITION IS THE RENDERER'S, AND IT IS BOOKED.** It is the one whole-record composition `strata/pending.md` row `2` books as `composeRecord`, under which D-142 books the renderer's as well (D-139, D-142) — **and this module's half of that entry is JUDGED AND KEPT at §10, which replaces the reason this paragraph used to inherit**. **THIS DOCUMENT LICENSES NO SECOND COMPOSER INSIDE THE RECORD**: no write route is added to `tabs`, no composer is exported for a caller's value, and no caller's repair is licensed here — `commit` and `remove` compose the record they write because a membership change is a SEAT and a MEMBER in one act, in an order that differs by act (§10, D-136). **AND A WHOLE VALUE AT THE ROOT REPLACES WHAT THE STORE HOLDS**: a caller that hands a record it did not read erases every row it did not carry, which is why the composition is a copy of a record READ and never a sequence the caller made up (§6, D-140).

## 10. `composeRecord`, `writeJoined`, `TabsCommitCarrier` — judged: all three KEPT

**THE JUDGEMENT ROW `2` WITHHELD IS TAKEN HERE, AND IT IS A RETENTION WITH THREE SEPARATE REASONS.** `composeRecord` is ONE FUNCTION WITH TWO CLASSES OF CALL SITE — the acts' whole-record writer and the repairs' family writer — and only the first was ever in question; `writeJoined` and `TabsCommitCarrier` are not composers and are settled by another argument below. **No hunk is owed to L4 and no battery row is re-grained.**

**FIRST THE REASON THE CODE STATES IS CORRECTED, BECAUSE THE JUDGEMENT RESTS ON THE RIGHT ONE.** §4's measurement stands — `write(['tabs', id])` on a FRESH store answers `AddressNotFound` with an empty `log` — and the inference drawn from it is superseded: `tabs-must-stand` demands the root and its repair mints it at construction (D-69), and `viewOf`'s own fallback READS `['tabs', id]` per id, so the parent is ENFORCED, TRUSTED PRESENT and a per-tab leaf is an address that resolves (D-135's rule, at this family). **So `D-139`'s precondition is MET here and the composer is still lawful**, which is the whole finding.

**THE RECORD IS A MAP AND A SEAT, AND THAT IS WHAT `D-138`'s TEST NEVER ASKS.** `order` is one member beside one member per tab, and `order-names-its-tabs` demands the seat name members the record HOLDS and never that every member be NAMED (site `orderNamesItsTabs`: the loop runs over `seat` alone). A membership change is TWO members in one act, ordered differently by each act:

- **CREATION — row, then seat — is legal at every intermediate state and is UNDER-JUDGED.** The seat arm passes over a member it does not name, and until the seat write that row is INVISIBLE: `viewFrom` builds `entries` from `order` alone, so neither `exactly-one-active` nor the three field pairs (`entriesOf`) can see it. When the seat lands two rows read active, the pair refuses, the written referent is the NEW id (a first active key) and `healRecord` keeps it — so the act is right FOR THE REPAIR'S REASON and answers `repaired: true` on every clean creation. And a repair landing between the two writes files `composeRecord(order, rows)`, a record WITHOUT the unseated row: **the caller's creation is erased, and the seat write then wears the refusal a seat naming no member earns.**
- **REMOVAL CANNOT RUN THAT WAY, AND ITS REPAIR SAYS WHY.** A member removed under a seat that still names it is exactly `order-names-its-tabs`'s sentence, and the body answering it is `repairOrderSeat` — hints `NO_HINTS` — which resolves the successor by §7's arm (iii), the seat's own order, where the removal's discipline is arm (ii), the removed entry's pre-position, carried only by `exactly-one-active`'s hints. So removal writes the SEAT first and the member second: **THE OPPOSITE ORDER FROM CREATION.**

**THE ASYMMETRY IS REAL, AND IT IS THE COMPOSER'S REASON.** One write makes the order-dependence of the act irrelevant; a split moves it INTO the act, which must then know which sequence its own intent needs. What a split costs: one commit becomes TWO, with a delivery apiece (§5's one-per-committed-change becomes two per act) and a journal entry apiece; a transient member no client, no pair and no comparison can see; and `standsAsIntended`'s `repaired` becomes a measurement of a repair the split caused on purpose rather than one the engine chose (D-70).

**AND THE DECISIVE GROUND: A SPLIT WOULD NOT DELETE THE COMPOSER.** Three of its five call sites are REPAIRS — `mintRecord`, `healRecord`, `repairOrderSeat` — and D-83 measured that a repair must write the rows it names and never a seat alone (a pair at `['tabs','order']` can write an order it cannot fill). A split would move two call sites and leave `composeRecord` standing for the repairs, the class `D-139` itself files as MUST-STAY BECAUSE A DERIVATION. **One name, two call-site classes, two answers: `D-139` tested the NAME.**

**`writeJoined` AND `TabsCommitCarrier` ARE SEPARABLE, AND SEPARATING THEM SETTLES THEM.** The carrier is `write`'s FOURTH position, available on ANY write at ANY address, so a leaf write names its commit exactly as a root write does; `writeJoined` composes nothing — its one statement is the store's own `write` — it is the REQUIRED ARITY that makes a carrierless repair write a compile error, and its reason is the ENGINE's: an unnamed repair write opens a second attempt and is refused `KC-7` or credited against the wrong op (D-73). Kept, and kept INDEPENDENTLY of the composer — a split would need it MORE, the repairs being the writes that must join.

**WHAT `D-139` GOT WRONG, STATED ONCE SO ITS TEST IS NOT READ AS THE FAILURE.** The test was RIGHT about `composeZones` and `composePanes` and its PRECONDITION was wrong twice, both having been removed by CLOSING their id domains rather than by leaving them open (D-152, D-154). Here the precondition is MET and the test still does not decide, because it asks *can a leaf write destroy a sibling?* and never *is the act expressible as a leaf write at all?* A pane's and a zone's act changed ONE member; this act changes the MEMBERSHIP, and its two members must be written in an order the act chooses. **So `D-138`'s test is NECESSARY AND NOT SUFFICIENT, it must be applied to the ACT and not to the function name, and a composer whose call sites fall into two classes is judged twice.** Closing a tab-id domain is no substitute either: ids are MINTED AT RUNTIME (`newTab: true`, `mintTabId`), so a closed set would delete the feature.

**AND THE OTHER SITE UNDER ROW `2` IS NOT THIS MODULE'S.** `src/renderer/renderer.ts`'s `composeRecord` is the RENDERER's, born of D-142's ruling that the writing realm composes the value it hands to `data.write` at a declared root; it is outside this document's scope (D-3) and no route here changes for it (§8's guardrail).
