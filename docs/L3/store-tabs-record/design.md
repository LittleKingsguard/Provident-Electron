## 1. The structure — three files, one owner each

The module is main-side and has no renderer code (D-63's client role; §6). Three files, and each exists because a different thing could go wrong:

| File | Holds | Why it is separate |
|---|---|---|
| `src/main/tabs-record/index.ts` | the record over the APP'S ONE STORE: **three** address constants, **six** batched declarations and **four** routes — and no instance and no file of its own (D-64, D-65) | **neither act composes a WRITE at this head**: `remove` is ONE TARGETED `delete`, `commit` ONE leaf row write, and the three repairs alone write a WHOLE RECORD (§3) — so the surface holds no store verb and `main.ts` holds no file path |
| `src/main/tabs-surface/index.ts` | the surface: the one reference to the record, the one subscription (`attach`/`detach`), the shape arm and the refusal mapping (L2 §2, L2 §3) | the record is constructed once at boot, and this module is the only one that holds it (the `settings-surface` arrangement, `docs/L1/security-store-storeroom.md` §4) |
| `src/shared/tabs-channels.ts` | the **four** channel constants, single-sourced | a channel name spelled in two files is a rename that half-lands (`store-channels.ts`'s precedent; §1, D-63) |

**One construction site, and it is the surface's** — `createTabsSurface`: no tabs file constructs an instance and none spells a `provident-*.json` name (measured 2026-11-02: `grep -rn "provident-.*\.json" src/main/tabs-record/ src/main/tabs-surface/ src/shared/tabs-channels.ts` is empty) — because the instance is the boot's and this module is handed a store that already stands (§2, D-65).

## 2. The instance, the three addresses, and the leaf shape

The instance is `provident-storeroom`'s and it is the APP'S CENTRAL ONE (D-64): the boot constructs it with one file path and the batched `cfg.constraints` (§4), and the package owns that file's byte image, its journal, its rollback and its durability (`guide §9`). This module constructs nothing and opens no file; it chooses **three** address constants and **six** declarations and nothing else (D-65).

- **`TABS_RECORD_ADDRESS` is `['tabs']`**, the record root: the `order` seat plus **one flat leaf per tab, named by the tab id** — the landing ENTRY among them, so `['tabs','landing']` is its leaf and no second seat is stored (D-76).
- **`TABS_ORDER_ADDRESS` is `['tabs','order']` and it is the ONE SINGLETON SEAT**: the ordered place of every tab id and the sequence every judgement is seated from. **`TABS_LANDING_ADDRESS` is `['tabs', TABS_LANDING_ID]`** — the landing entry's own leaf, where the witness is derived and never stored. An entry id spelling the seat is unrepresentable and is refused `seat-name` before any store act, at both routes that take an id (L2 §3, D-76).
- **A TAB'S LEAF IS ONE FLAT ROW**: `id`, `target` (the data object it contains), `active`, and optionally `label`, `error` and `lastActiveAt`, each guarded by its own pair (§4; `src/shared/types.ts`'s `TabsRecordRow`).
- **THE ACTIVE ID IS DERIVED, NOT STORED** (D-76, D-140): `landingOf` answers the landing entry's row where that row reads active, else `order`'s first row reading active, else `null`, which `read()` spells `''`. A writer therefore hands the family `order` and one member per tab and **no witness member at all** (site `landingOf`, and `read`'s `seats`).
- **THE RECORD IS ONE ROOT AT ONE TIER**: `TABS_RECORD_TIER` is spelled once and published only through `tabsDeclaredRoots`, which answers `['tabs']`/`file` and nothing else — which is what admits a `file`-tier write there and refuses any other (D-101, D-142).
- **A construction that cannot stand is not this module's arm**: no route answers `FilePathUnreachable` (measured 2026-11-02: `grep -rn 'FilePathUnreachable' src/main/tabs-record/ src/main/tabs-surface/` is empty) — the boot hands it a store that already stands, and the existence pair has already created the root (D-65, D-69).

## 3. The four routes, the one that is absent, and the TWO acts that compose nothing

**`window.provident.tabs` CARRIES FOUR ROUTES AND NO FIFTH** — `read()`, `commit(row)`, `remove(id)` and `onChanged(handler)` (L2 §2; site `src/main/preload.ts`'s `tabs` member) — and the surface module behind them holds `read`/`commit`/`remove` beside its ONE subscription (`attach`/`detach`), while the record's own interface spells the fourth route `subscribe` (`TabsRecord`, whose one subscription `createTabsSurface` installs). **`read()` is TOTAL** — `{status:'committed', order, landing, rows}` — so the refusal type it is declared against is never minted at the record (L2 §2).

**`commit` IS THE MIRROR OF THAT AND IT WRITES ONE ROW** (rev 15, the user's instruction *"Creating a new tab should be doable as a write, with the repair appending it to the order"*): the same two arms before any store verb, then the PRE reading — taken once and used TWICE, as the comparator's expectation and as `lastView` — then **one `write(['tabs', row.id], TABS_RECORD_TIER, row)` at the TAB'S OWN LEAF**, the caller's admitted row and no composed record at all, then the seat repair APPENDS that id inside the same commit (§4), then `lastView` again on both arms, then the answer from `standsAsIntended` against the creation expectation (§8). **THE APPEND IS THE REPAIR'S AND THE ACT NAMES ONLY THE SEAT ITS CREATION MEANT**: it predicts no position, chooses no successor and composes no sequence, and the `order.includes(row.id)` guard it used to compute `[...order, row.id]` goes with the composition (§12, `D-140`'s one authority). **A LEAF WRITE IS LAWFUL HERE BECAUSE THE PARENT IS ENFORCED AND TRUSTED PRESENT** — `tabs-must-stand` mints `['tabs']` at the instance's construction and §4's nested-write measurement is what a FRESH address answers — so no composed value is needed to mint the branch tree, and the store's own `AddressNotFound` at the address rung is §3's store arm.

**`remove` IS ONE TARGETED OPERATION ON THE ROW, AND IT COMPOSES NOTHING** (rev 14): the shape arm and the `namesASeat` arm stand unchanged, an ALREADY-ABSENT arm answers `committed` over an id the `order` seat does not name and reaches no store verb (site `remove` — under the closed bijection the seat IS the membership index, §4, and the store's own "a delete that removes nothing" answers the same, `guide §5.3`), then **`delete(['tabs', id], TABS_RECORD_TIER)`**, then the repairs settle the record inside that commit, then the answer. **THE ACT OWES NO SUCCESSOR AND NO ORDER**: which survivor reads active is `exactly-one-active`'s (§7) and what the seat holds is `order-names-its-tabs`'s (§4), so the act composes no sequence at all — it deletes a row and lets the two owners converge. **`lastView` IS REFRESHED TWICE**: from the reading the act already takes, before the delete, so the PRE side is the record the delete lands against; and from the store after the attempt on BOTH arms, so the next evaluation's PRE side is the record that stands (`guide §5.4`: a refused attempt restores its own state). The delete's receipt is NOT read — its null `op` is the store's statement about versions, and reading it would be a second membership test. One verb is absent and named so no reader looks for it: **there is no `journal`**.

## 4. The constraint — the engine's gate, the engine's repair, and who owns which fault

**The gate and the repair are both the engine's.** This module writes six bodies and registers them at construction through `cfg.constraints`, whose element carries the pair **and** the function and is armed before any filesystem act (`guide §7.2` route one). The engine invokes a body and reads its answer: **`true` is the only pass value** and an object carrying a `message` is a **rejection** (`guide §7.2`, `§7.5`). The body **reads the record** rather than trusting the act's value, which `guide §7.6` makes the caller's work — *"if your constraint cares about the state at any other location, it reads that location"*.

**A REPAIR NAMES THE COMMIT IT WAS HANDED AND RETURNS THE OP ITS WRITE LANDED.** The engine invokes `repair(repairContext)` **inside the attempt's own commit** (`../Provident-Storeroom/docs/specs/storeroom-constraints/contract.md` §(viii)). Passing that context at `write`'s **fourth position** makes the repair's write **join** the open attempt; without it the same write is refused `KC-7` — *"a constraint attempt is already open at `tabs`; it is disposed of by its own K-3 and by no other act"* (D-67, D-73). A `void` return "produced no op" and failed `KC-4` at `1.7.0`, filed upstream as `ST-F2`; the installed release credits a repair by the legs its own write wrote and this module takes none of that licence, so **a repair answers ONE OF TWO DECLARED ARMS** — `{ok: true, op}` via the one constructor `repairAnswer`, or `{ok: false, message}` — and `TabsRepairAnswer` makes `void`, `undefined` and a bare `{ok: true}` compile errors (D-72).

**THE TWO CREATION-INSTANT PAIRS ARE UNWRAPPED, AND THEIR ADDRESS IS A MEASUREMENT.** `tabs-must-stand` and `order-names-its-tabs` are not wrapped by `body`, because the boot binds no handle until `storeCreate` answers and a wrapped body abstains at the one instant it must act; a registration-instant repair's record carries a `write` member and **three positions and no fourth**, while a landing-instant one is the six-member record whose commit MUST be named at the fourth — the branch is the record's own `write` member, never the instant's name (D-69, D-73, D-83; `writeWholeRecord`). And **the seat pair stands at `['tabs']` and not at the seat's own address**: a pair at `['tabs','order']` is handed the SEAT at a registration instant, so its repair could write an `order` and never the rows that order names (D-83).

**ONE WHOLE VALUE AT `['tabs']` MINTS THE ROOT, THE SEAT AND EVERY MEMBER IN ONE CALL**, and a nested write does not create its parent — measured, `write(['tabs', id])` on a FRESH store answers `AddressNotFound` with an EMPTY `log`; **the parent is ENFORCED and trusted present here** (D-135's rule, quoted at `composeRecord`; §10). So a fresh record carries the landing tab before any act, and the root cannot be deleted out from under the app: measured 2026-11-01, a `delete(['tabs'])` is answered as the store's own success while the existence pair's repair re-creates the record inside the same commit (D-69). **AND AT THIS HEAD THE RULE'S SUBJECT IS THE CONSTRUCTION AND THE REPAIRS, NOT THE ACTS**: neither `commit` nor `remove` writes a whole value (§3), so neither mints a branch tree — which is why the leaf write is lawful and why a vanished root would reach a caller as the store's own `AddressNotFound` rather than as a silent re-mint.

**SIX DECLARATIONS RIDE THE BATCH, NOT ONE, AND THE REASON IS THE SENTENCE A CALLER GETS**: a violation is a fact about ONE field, so a body that tested all of them could not say WHICH one was repaired — and `guide §7.2` rejects a repeated `id` in one supplied list, so the six are named apart (D-65, D-83).

| id | Holds when | Repair |
|---|---|---|
| `tabs-must-stand` | the address `['tabs']` holds a record at all — **judged at the record's own node** (§4's node rule) | **creates** it: the landing entry, seated and active |
| `order-names-its-tabs` | the `order` seat is a non-empty sequence holding **exactly** the record's own tabs, each **once** | **recomputes the seat from the ROWS**, preserving every `active` flag (D-83, §7) |
| `exactly-one-active` — `TABS_CONSTRAINT_ID` | at least one member survives **and** exactly one entry reads active | **§7's normalisation** — the ONE repair that chooses a survivor |
| `tab-has-title` | the tab's `label` is a non-empty string | writes `'untitled'` (D-65) |
| `tab-has-content` | the tab's `target` is a non-empty string | points it at the authored landing page — `'tabs-landing-page'`, a CONTENT target and not an id (D-76) |
| `tab-has-lastActiveAt` | the tab carries an activation stamp | stamps it with **now**, as an ISO string so the byte image stays JSON-plain (D-65) |

**THE ARM IS A BIJECTION NOW, AND ITS ONE NEW CLAUSE IS THE DIRECTION NO BODY EVER TESTED** (site `orderNamesItsTabs`; the loop runs over `seat` alone, so the pair tests `order ⊆ rows` and never `order ⊇ rows` — and a row outside the seat is invisible to every pair and every view, because `viewFrom` builds `entries` from `order`). The five clauses stand — the seat is absent or not an array, is empty, carries a non-string or empty member, repeats an id, or names an id the record holds no ROW under — **and it refuses one more: an own key of the record that is not `order` and that the seat does not name**, whatever it holds. Together they are `order ≡ rows`: every named id holds a plain row and every key besides the seat is named, so a dangling id, an unseated row and a stray key (a legacy `landing` string, a scalar) are ONE fault with one repair. **BOTH DIRECTIONS ARE OPEN AT THIS HEAD AND BOTH ASK THE PAIR** (measured on the `1.10.0`: `delete(['tabs','tab-1'])` leaves `order` naming a row that is gone; `write(['tabs','tab-9'], row)` leaves a row the order does not name — each asks the pair, at the act's own address, and repairs neither). **AND THE REPAIR SEATS AS WELL AS DROPS, WHICH IS A HUNK OF ITS OWN**: the view every other pair uses is seat-seated, so the seat repair parses the record by its OWN KEYS — the seat's ids that hold a plain row, in seat order and once each, then every other own key holding a plain row in the record's own key order — and hands that widened view to `healedFamily`; a repair that kept the seat's parse would DROP a row a caller had just written and answer `committed` over a tab that vanished. **THE SENTENCE IS RE-GRAINED, NOT ADDED**: `ORDER_SEAT_MESSAGE` becomes *"the tab record's `'order'` seat carries no sequence of exactly its own tabs, once each"*. **NO SEVENTH PAIR, AND THE CONTRACT CHANGE IS STATED RATHER THAN DENIED**: no id, `reason` token, address, tier or route moves and the batch's six-id census stands — **but the condition an existing pair tests WIDENS, a record that passes at this head refuses at the next, and that widening IS a contract change, which L2 §4 states as one**. A second id would split ONE fault into two sentences for one state and, on the write direction, fire a second whole-record repair in the same attempt (D-65, D-83).

**BOTH BODIES JUDGE THE RECORD AT THE NODE THE WRITE IS AT — D-135's rule, and the discriminator is the CONTEXT'S ADDRESS** (measured: a pair at `['tabs']` is asked for an act at `['tabs', …]` and is handed THE ACT'S `address`, `tier` and `value` — absence for a delete, the leaf's own value for a leaf write; `guide §7.6` with D-56/D-66's membership clause). So the body judges `context.value` when the act's address IS the record root — a registration ask and a root write both — and reads the RAW RECORD at `['tabs']` through the handle when the address is deeper; **the discriminator is the address and NOT "a handle stands", because a caller's own context is what a hand-driven row (`central-data`'s `VA-14`) hands the declaration, and answering it from the store would ignore the value it was given**. `repairOrderSeat` follows the same line — the store's record at a landing instant, the handed record at a registration one — **and the empty-view floor it carries today survives AT THE REGISTRATION INSTANT ONLY**: there is no handle there, and a file whose record is `{order:'x'}` or holds rows and no seat has no other route back to the floor, so deleting that fallback at both instants would make the repair answer the failed arm and `storeCreate` REFUSE the app's unconditional construction (measured: a registration repair answering the failed arm throws and constructs nothing). **`tabsMustStand` gains the same scoping, and it is the REMOVAL that needs it**: a descendant delete hands it `undefined`, so its present arm refuses and its repair MINTS the landing floor over a record holding other tabs — measured under the six pairs, `delete(['tabs','tab-1'])` erased the sibling row and re-stamped the floor — so absence must be refused at the ROOT only.

**TWO REPAIRS, TWO OWNERS, AND THE ASK ORDER IS WHAT MAKES THE SEQUENCE DETERMINISTIC.** `repairOrderSeat` owns the SEAT and never the activeness; `healRecord` owns ACTIVENESS. Both compose through `healedFamily`, which gains a **SCOPE** — `'seat'` or `'family'` — and the difference is exactly one branch: a `'seat'` heal resolves membership, seats what the record holds and drops what it cannot, fills the three field defaults and **preserves every `active` flag as it stands** (minting the landing floor where no row survives, which is the one row it CREATES and no row it chooses); a `'family'` heal does all of that AND applies §7's successor precedence from the hints. **THE PASS ASKS ONE REFUSAL AT A TIME AND RE-RUNS FROM THE TOP** (measured: a delete whose two faults both stand is asked seat, seat, active — three asks, TWO of the three restarts — and delivers ONE notification), and the batch's own order is part of the contract (`tabsConstraintDeclarations`: existence, seat, active-count, then the three field pairs), so on a delete of the active tab the seat repair lands FIRST and the activeness pair is asked on the record it left — which is the arm (ii) invocation the removal needs. **THE CONVERGENCE IS A FIXPOINT, NOT A RACE**: both scopes compute the SAME `order` and the SAME `rows` from the same record and differ only in whether the active arm runs, so `family` ABSORBS `seat` — `seat(family(x)) = family(x)`, and `family(seat(x)) = family(x)` because `seat` never touches `lastView`, the one store of the pre-delete order that supplies arm (ii) (H6 refreshes it before the delete), and because the two are handed DIFFERENT hints whose difference cannot matter, `NO_HINTS` naming no removal at all — so the record the removal leaves is one record and not whichever repair wrote last, **and the only residual is WHICH repair's clock fills a blank `lastActiveAt`, an ISO "now" that no pair, view or battery distinguishes**. **THE FAILURE MODE OF THE ALTERNATIVE, WHICH IS THIS TREE'S**: keep the seat repair's full heal and its `NO_HINTS` successor is §7's arm (iii), the seat's own first survivor — and because that write leaves exactly one active the re-run PASSES, so `exactly-one-active` is never asked at all. **A removal of the active tab would then silently re-seat the seat's first row instead of the removed entry's pre-position**, the discipline the removal needs, and the battery's own row (remove the active tab, expect the pre-position survivor) would red. One owner of activeness is what keeps arm (ii) reachable.

**WHERE A NEW TAB LANDS IN THE ORDER IS THE PARSE'S ANSWER, AND THE ACT'S OLD APPEND AGREES WITH IT FOR EVERY CREATION THE ACT CAN MAKE — AND ONLY THERE.** The parse's tail is `Object.keys` over the record with the seat's key skipped (§4's own-key parse, `seatViewFrom`), so a single stray row lands at the END of the seat, which is exactly the `[...order, row.id]` the composed act used to spell — and ONE stray is all the act can ever make, because it writes one leaf of a record the bijection left legal, and the row it wrote is the only key the seat lacks. **THE TWO DIVERGE ONLY WHERE MORE THAN ONE UNSEATED ROW STANDS AT ONCE** (a whole-record write composing several, or a file that arrived illegal), and there the tail's order is the STORE'S KEY-ORDERED IMAGE and never the caller's: the store rebuilds a value from its own image with its members key-ordered — measured, the profile's root keys read `['panes','tabs','theme']` (`tests/integration/central-data/profile-file.test.ts`'s boot row: *"the store's image is key-ordered, so the reading is stable"*) and a literal `{value, removal}` reads back `{removal, value}` (D-97) — while JS own-key enumeration puts an array-index-like id FIRST whatever the image says (`archive/gate-corpus-2026-10-29/specs/census.md` §2.4 `C-A`'s qualification, measured at `tests/census.test.ts`'s shape (3)), so a tab id spelled `'7'` is not enumerated like `'tab-7'`. **A READER MAY THEREFORE RELY ON THE SEAT'S OWN SEQUENCE AND ON NOTHING ELSE**: an id the seat already holds keeps its ranking through every round trip (an ARRAY preserves order where a member's position does not), one creation appends last, and a multi-stray seat is the store's order — which the comparator REPORTS (`repaired: true`, §8) instead of the act pretending to have chosen it. **So the act's semantics do not change for creation; the position stops being the act's to promise at all, and a caller that needs a rank reads the `order` it is answered.**

**A REPAIRED ACT ANSWERS `committed` WITH `repaired: true`, AND THE MEMBER IS DERIVED, NEVER PREDICTED** (D-70, L2 §3): the write's own record carries no member for a repair inside its own commit (`guide §6.4`), so the act compares the record it MEANT with the record that STANDS — canonically, member order and absence normalised, or a clean act would report a false difference — omitting the member on a clean act and never answering `false` (sites `standsAsIntended`, `canonicalRecord`). **AND THE MEANT RECORD IS EACH ACT'S OWN EXPECTATION — THE REMOVAL'S DELETE-ONLY, THE CREATION'S ADDITIVE**: `remove` means the pre reading's `order` and rows MINUS the id, activeness untouched (§8); `commit` means that same reading PLUS the caller's admitted row PLUS the seat naming it — `composeRecord` over `pre.order` with `row.id` appended where the seat did not already name it — so the creation names the seat its act MEANT and predicts no position and no successor (§8). **BOTH SIDES ARE ONE COMPOSER AND ONE COMPARATOR** (§10): `composeRecord` supplies the value on each side, `canonicalRecord` projects it onto §2's six members, and a member outside that projection is not a difference either act reports.

## 5. The listener — an address, never a payload

**`onChanged` takes ONE subscription and delivers exactly ONE notification per committed change of the record** — a `commit`, a `remove`, a whole-record write through `data.write`, and a repair's own write inside that same commit, which JOINs it rather than opening a second one (D-67, D-142). **AND A CREATION IS STILL ONE DELIVERY**: `commit`'s leaf write at `['tabs', row.id]` is heard because the listener's address is a PREFIX of it, and the seat repair's whole-record write inside that commit is the same commit (`guide §6.3` item 2, the site's own PREFIX clause). The delivery names the **triggered address** and never the value (`guide §6.4`), so a client re-reads; **a write a pair REFUSES delivers NOTHING**, because the pairs are asked, the pass throws, and the delivery window never opens (D-71).

**THE LISTENER STANDS AT `['tabs']` ITSELF, BESIDE ALL SIX PAIRS** (D-71): the one cross-kind restriction is the HANDLE — a listener whose handle equals a pair's `id` is refused `AddressMalformed` — and this module's handles are `tabs-record:<n>@tabs`, MINTED per subscription so a second subscriber cannot starve the first (site `handleFor`). The installation is two acts (`listen` reserves, `register` fills), the body WRITES NOTHING — a listener's write opens its own commit — and it CONTAINS the caller's throw, which would otherwise cross into the write that fired it (`guide §6.2`, `§6.5`). **The withdrawal is its own answer and is idempotent** — one `unlisten` per handle, a lawful no-op over a handle already withdrawn — and a listener that outlives its window is a leak no client can see (`guide §6.2`; `attach`/`detach`).

## 6. What the record still refuses to be

- **No MCP surface.** No tool, resource or `RpcMethod` member names the instance or its file; the crossing is the bridge's, and an agent's own door to this record is `provident.data.*` (D-101).
- **No renderer import, and the renderer reaches the record by TWO doors and holds no third.** `src/renderer/**` never imports these files: the client's `read()` and its `onChanged` delivery are the first door, and one whole-record write, composed from its own reading and handed to `data.write` at `file`, is the second (§8). **The clause that it reached the record "through `window.provident.tabs` and nothing else" is what `D-142` supersedes**, and neither the tabs surface nor this module gains a route or a composer for it (D-142, D-136).
- **No second record.** One construction site and no file of this module's own (§1, §2): a client holds no rows, no `order` and no landing seat of its own — no mirror, no cache, no renderer-side copy of the family (D-62, D-142).
- **No second authority over the invariant.** No client registers a pair at `['tabs']` and none re-implements the normalisation: a caller that cleared the older flag, or refused its own two-active composition, would be the authority the repair exists to be (§7, D-65, D-129).
- **`order` is never a client's invention.** The member written is the one the reading carried, so the composition is a copy of a record READ and never a sequence made up (D-140, D-142).

## 7. The normalisation — `exactly-one-active`'s, and the one repair that chooses a survivor

**A WRITE THAT SEATS TWO ACTIVE ROWS IS NORMALISED DOWN TO ONE INSIDE ITS OWN COMMIT** (D-142, D-140): `exactly-one-active` rejects the record and `healRecord` writes the corrected one, joined to the attempt, so the re-run reads one legal record and the caller's write stands. **THE CALLER NEVER CLEARS THE OLDER FLAG** — doing so would make the caller the authority the repair exists to be (D-142, D-129).

**AND THE SURVIVOR'S PRECEDENCE IS THE CODE'S, AT `healedFamily`, MEASURED AND NOT RESTATED FROM THE RENDERER'S ALGORITHM**: **(i)** the **written referent**, where it survives in the seat; **(ii)** else the **removed entry's pre-position**, folded onto the survivors; **(iii)** else the seat's own order — `order`'s **first row reading active** where several stand, and `order`'s **first row** where none does. The rest are deactivated **in the same object**, so the re-run reads one corrected record and not an intermediate state (site `healedFamily`; D-142, D-140, D-76). **THIS IS NOW THE ONLY PLACE A SURVIVOR IS CHOSEN** (rev 14): the membership repair passes `'seat'` and preserves the flags verbatim, so a delete of the active tab reaches arm (ii) once — through `healRecord`'s hints — and never twice through two bodies that disagree (§4).
