## 1. The goal, in the operator's own terms (D-35)

An operator opens the app, finds the Security Settings pane, and sees **one toggle per gate group — six of them**, the sixth being `data`; they can **grant and revoke `data`** from that pane exactly as they grant `graph`, `code` or `module` today (the pane's `GROUPS` roster and `paneEnvelope()`'s per-group toggle rows, both in `src/renderer/secure-panels.ts`; D-35). The grant reaches the running app: the five `provident.data.*` tools enter and leave `tools/list` as the toggle moves (`src/main/security.ts:38-42`; D-11). It survives a restart, because **the operator-settings instance owns the grant** and the pane is a view and a setter over it — never an authority (D-17, D-19, D-22).

Two sentences carry the document. The **defect**, in the state this design was declared against, is a data set of five names against a gate that validates six (the pane's `GROUPS` roster, then a hand-written literal; `src/main/security.ts:3,159`). The **repair** is a sixth entry in that data set, on the graph path that already exists: `paneEnvelope()` builds one toggle per `GROUPS` entry and `syncConfig()` refreshes every `toggle:<group>` node from the carrier's `enabled` list (`src/renderer/secure-panels.ts`'s `paneEnvelope()` toggle rows and its `syncConfig` `toggle:` arm). No hand-written DOM is created, and no new structural pattern is introduced (D-35; `brief.md` §2 UI authority).
