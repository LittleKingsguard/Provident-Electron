## 4. The object's contract at the I/O boundary, and the ARM THAT REDS

**IN**: one spec per family — a required TAG member (`tag: 'paired' | 'unpaired'`, the discarding literal naming the arm), `address`, `tier` typed at this module's own tier union (`:273`: THREE distinct words built from four constants — `file`, `mem`, `temp` — so a fourth word reds; a test cannot name that alias, and writes `ViewDeclaredRoot['tier']`), and on the PAIRED arm only, `id` and the constraint BODY FACTORY `(getStore) => body`. **AND THE EXPORTED NAMES THE UNIT'S ROWS MUST IMPORT ARE NAMED HERE, because no layer below may invent them and a row that reds on an import measures nothing**: the union `ViewFamilySpec` with its two arms `ViewPairedFamily` / `ViewUnpairedFamily`, the factory `viewFamily(spec)`, the module-scope tuple `VIEW_FAMILIES`, and the returned object `ViewFamily` — six names, two of them the union's arms, all NEW symbols on an additive export, so none of §6's or §9's costs moves (`D-292` iv, `D-43`).
**OUT**: one object per family with two halves — `root`, a VALUE, and `declaration(getStore)`, a PROJECTION answering a `ViewConstraintDeclaration` or `null`. **THE ASYMMETRY IS THE ORDER AND NOT A TASTE**: `viewDeclaredRoots()` takes no argument and the delivery is built before the store is bound (`D-219` holder order), while a body reads nothing at the registration instant (`D-124` iii) — so the half that needs a store is handed one, and the half that does not is not. Rev 1's OUT half caught a `constraint` the object had no getter to produce; that is corrected here, not patched later.

- **THE MECHANISM IS A DISCRIMINATED UNION ON AN EXPLICIT TAG, AND THE UNPAIRED ARM DECLARES ITS TWO PAIRED MEMBERS AS OPTIONAL `never`** — `readonly id?: never`, `readonly body?: never`, where the `?` is LOAD-BEARING rather than stylistic: a REQUIRED `never` member could not be satisfied by the lawful unpaired spec at all, so the optionality is what lets the arm exist, and it is also what the `undefined` escape below rides on. Two halves closing two DIFFERENT holes, each named with the literal that reds. **(i) THE TAG CLOSES THE OMISSION**: a paired literal that dropped its body is missing a member its own tagged arm requires and is not the other arm — the other arm's tag is a different literal, so no member set of the union admits it. **(ii) THE `never` CLOSES THE CARRIAGE**: an unpaired spec carrying an `id` or a body is refused by the MEMBER'S TYPE, not by a literal's freshness, so a spec hoisted to a `const` and spread reds exactly as a fresh one — the arm excess-property checking can never reach. **Its ONE ESCAPE IS AN EXPLICIT `undefined`** (`id: undefined` compiles while `exactOptionalPropertyTypes` is off, `tsconfig.tests.json:42-50`), which is named here rather than hidden and which no projection can act on: `undefined` is the one value the arm's `null` discipline already separates from a declaration. **Both halves are EPC-INDEPENDENT**, which is the property rev 1's guarantee lacked: its literal `{address, tier, id}` was assignable to the unpaired arm and compiled CLEAN because excess-property checking reads the union's WHOLE member set (`:444-445`) — the very sentence rev 1 quoted to explain the `never` at `:449`, applied to a union it had left without one (`D-72`, `D-292`).
- **THE FIVE LITERALS THIS SHAPE REFUSES AND THE TWO IT ADMITS, NAMED SO A READER CAN CHECK EACH AND SO THE ROW CANNOT DROP ONE**: REFUSED — the blocker's (paired tag, `address`, `tier`, `id`, NO body) on the paired arm's missing body; a paired literal missing its `id` the same way; an unpaired literal carrying an `id`, and one carrying a body, each on `never` from a DECLARED-TYPE fixture so the red can only be the member's type; and a spec at a fourth tier word on the tier member. ADMITTED — a lawful PAIRED spec and a lawful UNPAIRED one (a root with no pair), which are the control that the union is not merely always-red. **AND ONE ARM MUST COMPILE INSTEAD OF FAILING, because it is what distinguishes this form from the `never`-only one rejected below**: a tag-narrowed read of `spec.id` into a `string` (§5 `FH-3` (f)).
- **REJECTED, EACH WITH ITS COST**: `never` WITHOUT A TAG — closes the omission, but leaves the unpaired arm an UNSTATED one (`{address, tier}`), the indistinguishability `ASM-FH-2` forbids, and leaves `id` at `string | undefined` in both arms, so every projection narrows with a runtime `'id' in spec` where a tag narrows by type; A TAG WITH OPTIONAL PAIRED MEMBERS — the tag then classifies nothing, and a paired-tagged spec with no body compiles, which is the blocker wearing a tag; rev 1's UNTAGGED `Paired | Base` — refuted by measurement, above (`D-292`, `ASM-FH-2`).
- **THE UNPAIRED ARM'S `declaration` IS `null`, NEVER `undefined` AND NEVER `{}`**: `null` is a value a projection must TEST, while an absent or empty arm is one `.filter` from being dropped silently — the omission `ASM-FH-2` forbids, and `FH-3` (b) states the `null` rather than letting a filter imply it (`D-292`, `D-145`).
