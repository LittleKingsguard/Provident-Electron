## 1. What this unit is, and what it does not touch

- **THE SKELETON REGISTERS NAMES AND EXECUTES NOTHING, AND THAT IS THE UNIT'S WHOLE SUBJECT** (D-305, `modularity-research.md` A1–A3, A5): `syncModuleRouter` hands each declared capability an echoing handler and states in its own words that `entry` is never evaluated (`src/main/mcp-server.ts`); the only `CapabilityRouter` is constructed in `src/main/main.ts`'s `main()` (and re-synced there); four of seven `ModuleCtx` members are stubs or unwired (`src/renderer/extensions.ts`'s `ModuleCtx`); no module can register a listener at all, because each crossing's delivery adopts ONE registration act at construction — the tab record one entry, the view record one per declared address (`src/main/tabs-record/index.ts`'s `createTabsDelivery`, `src/main/view-record/index.ts`'s `createViewDelivery`); `ModuleDependency.versionRange` is *"declared, no resolver this pass"* and an absent dep is a no-op (`src/shared/types.ts`'s `ModuleManifest` block); the application version is a hard-coded `'0.1.0'` literal beside `createServer` (`src/main/mcp-server.ts`). So "systematize the skeleton" is **build the executor and the crossing the skeleton was shaped for** (D-305).
- **FOUR DOMAINS ARE CLOSED LITERALS WITH GATING ROWS, AND A FIFTH IS AUTHORED BY THIS DESIGN** — a module-declared id is a foundation edit until a registry exists (D-305 (i), findings 1): pane ids `DECLARED_PANE_IDS` and zone ids `DECLARED_ZONE_IDS` (`src/shared/view-shape.ts`), tool groups `ToolGroup` and its valid set (`src/main/security.ts`'s `TOOL_GROUPS`/`VALID_GROUPS`) with ONE live copy of the valid set beside the union in `src/main/operator-settings/index.ts` — whose pane label table is a `Record<ToolGroup, string>` since `E-1` and cannot drift — and tool names `ALL_TOOLS` (`src/main/mcp-server.ts`). **The figures are `brief.md` §2's rows and are not restated here** (D-26, D-43). §4 `C-4` is the one foundation change `D-306` (a) authorizes for those four; **the fifth — the secure overlay's placeholder ids — is ruling (b)'s, and it has no closed literal at this head** (`src/renderer/secure-panels.ts` authors `props.id` strings and no set pins one), so `S-10` AUTHORS it rather than widening it (findings 2, 5).
- **NO PRE-BUILD GRAPH HOOK EXISTS** (findings 10, A9): the bootstrap compile is one-shot and `render()` is private (`src/renderer/runtime.ts`'s bootstrap and `render`); the only module render surface is a post-compile string transform, the `D-231` forbidden class; post-bootstrap placement routing does not work (`D-182`) while relocation does (`D-252`). §3 `S-14`/`S-15` put the ordered modification point where a compile can still see it — before `translateLegacy`, not after it (§4 `C-6`).
- **WHAT THE AUTHORITY GIVES A TWO-HALF LISTENER, AND WHAT IT WITHHOLDS, MEASURED AT THE PACKAGE'S OWN BYTES** (`D-307`): a firing is **one invocation per DISTINCT HANDLE**, handed **one address** — *"the triggering ADDRESS … no other argument is declared and no return value is read"* (`src/entry/delivery.mjs:98-104,154-166,206`) — and a body **cannot tell which binding matched** — *"and that is declared"* (`:137-141`, `AB-3`); **the DELIVERED set is `record.pending` and not `triggered`** and it rides the kernel's `CommitRecord`, so no `write`, `delete`, registration or reversal answer hands the *delivered* set over (`index.d.ts:616-620,705,844-847,962-994`; `index.mjs:743-751`) — note `write` and `delete` DO answer a `triggered` set, and it is not that set; **a fired body's throw is neither caught nor reported by the delivery loop** — *"§2.7 item 4 leaves it NOT caught, not retried and not reported"* (`src/entry/kernel-attempt.mjs:437-441`; `delivery.mjs:206`), so it crosses out of an unrelated writer's call and at a registration *"pre-empts that answer and crosses as rank 21 `ListenerBodyThrew`"* (`index.d.ts:1264-1270`); and an adopted `cfg.listeners` element carries **one address** (`index.d.ts:295-297`) though `listen(handle, addresses)` takes a plural set that it **set-assigns** (`:1194-1198,1213`). **THE CONSEQUENCE IS A GRAIN AND NOT A HANDOFF**: identity must come from the **handle** — one handle per listener DECLARATION, the practice `view-record`'s `createViewDelivery` already keeps, minting one per declared address — so the invocation IS the attribution; **and one address per declaration is a CHOSEN narrowing of a plural verb**, its cost stated at `C-3`. Identities still mint inverses — `listen`, `unlisten`, `removeListener`, `addConstraint` → identity, `removeConstraint` (`index.d.ts:1213,1228,1273,1327,1329`) — so Cordis's runtime-held inverse has a home (§5).
- **What it does NOT touch** (D-306): the secure pane's isolated graph, its `window.provident.*` handlers and its isolation contract — a module's additions land inside the overlay's placeholders and re-define nothing (`C-8`); `provident-ssr` and `provident-storeroom` (D-5), each gap a handoff request (§5); a standing `D-n`; the accepted conversion — the menus pane's and the demo contents' conversion is `U7`, the LAST sub-unit, and its own unit closes it. The four legs and the boundary instrument stay the floor (brief §6, `D-301`, `D-302`).
- **ONE CONTRACT SERVES TWO BUILDS** (D-304 (i), research B2, B3): a module declares two halves and never touches IPC, `window`, `window.provident.*` or `ipcRenderer`; the foundation's passthrough is the only way out, so the same module runs in the Electron build (two realms, main owns the store — D-63) and in the eventual browser/Node host (one realm, the store in the realm — the pending `provident-storeroom` WASM build is assumed by no step, `D-298`). **`D-307` DOES NOT LOOSEN THIS**: a listener's main half runs wherever the store is and its client half wherever the realm is, which is the SAME contract under one realm and under two.

## 4. The constraints this design fixes

- **`C-1` — the passthrough is the only way out, and admission is where that is enforced.** A module's code names no `ipcRenderer`, no `webContents`, no `window`, no `window.provident.*` and no IPC channel; the foundation's ctx is its whole outside (D-304 (i), research B1). **The rule is prompt-level for a HOSTILE module** — modules are trusted-equivalent to `code` and the ctx is *"an ERGONOMICS layer, NOT a security boundary"* (`src/renderer/extensions.ts`'s header; findings 19) — **so the gate the design can build is the one at the door it owns: `S-3`'s install-time refusal, by name**, and nothing here claims isolation it cannot build (D-44). **A route that exists and is forbidden is still forbidden**: `ProvidentBridge`'s `data` member carries five store routes and the renderer reaches them as `window.provident.data.*` (`src/main/preload.ts`), so a module's realm half has a store route in reach and may not name it — the named action is its route, not the bridge.
- **`C-2` — one message per write turn per realm, AND IT CARRIES PER-LISTENER DATA — WHICH IS `D-92` READ AT ITS OWN BOUNDARY AND NOT A REPEAL OF IT** (`D-307`): *"all listeners fired by a storeroom write should be sent in one block in the channel, not piecemeal"* (D-304 (ii)). The foundation's sink flushes ONE message at the turn's end — `{turn, entries}` — where **every entry is `{turn, module, listener, outcome, data?, refusal?}` and the shape is TOTAL over FIVE arms**: `return` with `data` the main half's answer; `empty` with `data` ABSENT, for a DECLARED main half that returned nothing (`D-307`'s *"if any"*); `passthrough` with `data` the address the store handed the binding, for a listener declaring NO main half (`D-307`); `refused` with `data` ABSENT and `refusal: 'not-transport-safe'` — a function, a symbol, a host object, a cycle, a `Promise`; and **`threw` with `data` ABSENT and `refusal: 'main-half-threw'`, the arm the binding exists for**: the store catches nothing (`src/entry/kernel-attempt.mjs:437-441`), so a contained throw is the only form in which a module fault can reach its own client half without crossing out of an unrelated writer's call (D-105). **`module` IS A MEMBER BECAUSE A BATCH MAY CARRY SEVERAL MODULES' LISTENERS** (§3 `S-13`): a listener name is the module's own and is not unique across the app. **`turn` COUNTS COMMITS AND IS THE FOUNDATION'S**, not a journal ordinal: it is the flush unit — one store act including its repairs — which no store member answers to a caller who is not the writer, and the store's own `JournalOp.seq` numbers ops, not that unit (D-129's second-authority class is why the distinction is stated). **THE `D-92` DISTINCTION, STATED SO IT CANNOT BE GLOSSED**: the crossings' own push carries an ADDRESS and never a value, a reading or a record — `main()`'s `createDeliveryQueue` and its arity-0 `push()` are UNMOVED (`src/main/main.ts`; `D-92`, findings 14) — **while a module listener's `data` is the LISTENER'S OWN RETURN, produced by that listener's main half for the firing and never a reading of the store; `D-92` governs the app's paint and does not govern this entry** (`D-307`). **THE TURN IS THE FOUNDATION'S TO MARK**, because the store's surface declares no per-turn notification (its fifteen members, `index.d.ts:1032-1417`) and a main half's own write opens its own commit at the surface (`delivery.mjs:193-206`), so the marking NESTS and the inner turn flushes before the outer (§2 `central-data`). **NO ARM IS UNATTRIBUTED, AND TWO ARMS CANNOT ARISE FROM A MODULE**: `C-3`'s grain removes the unattributed shape, and a module's registration post-dates the construction, so a creation- or boot-fired delivery has no module listener to fire and owes the held queue nothing (`src/main/main.ts`'s `DeliveryQueue`, cited above only for the crossing's arity).
- **`C-3` — ONE HANDLE PER LISTENER DECLARATION IS THE GRAIN OF THE BINDING AND THE INVERSE; BOTH LISTENER PATHS OBEY THE SAME TWO-HALF RULE — THE MAIN HALF AT THE FIRING, THE CLIENT HALF AT DELIVERY** (`D-307`; re-grained from rev 1 by §1's measurement). **THE HANDLE IS THE FOUNDATION'S TO MINT** and its rule is a namespace, not a name: `module:<module>:<listener>`, stable for the declaration's life, re-minted after an `unlisten` (`index.d.ts:1219-1227` says a re-`listen` at the withdrawn address answers a DIFFERENT handle), and **disjoint from every constrained pair's `id`, which the package refuses to share with a listener's handle in both directions** (`:1295-1317`, `D-98`) — so `register`'s replacement rule (`:1194-1198,1325`, and *"register REPLACES, never fans out"*) can never silently overwrite another listener's body, and `C-12`'s two-directional check is made against that namespace. **At an address the module declares for ITSELF** the foundation calls `listen(handle, [address])`: `listen` takes a plural set that it SET-ASSIGNS (`:1194-1198,1213`), and one address per declaration is **this design's CHOSEN narrowing** — the adopted `cfg.listeners` element's own shape corroborating it (`:295-297`) — **whose cost is stated rather than hidden: a module that wants one conceptual listener at two addresses declares two, and gets two entries.** The store then fires **once per distinct handle** with one address (`delivery.mjs:154-166,206`), so **the invocation IS the attribution: the binding contains the main half's throw, runs THAT listener's main half with the address as its argument, and keeps the return — no fired set is ever needed**, which is what the measurement forbids relying on anyway (§1). **At an address a CROSSING already serves** a module's listener is a **SUBSCRIBER** on that crossing's delivery — a subscriber at the crossing's own address (`['tabs']`, a view root) or at a leaf UNDER it, both lawful, because the fan-out is made **ADDRESS-KEYED**: each subscriber carries the ONE address it declared and is notified only where the store's own scope relation says that address stands at or above the delivered one (`isAddressPrefix`, `src/entry/kernel-foundations.mjs:629-647` — the relation the crossing's own delivery already obeys), so *"notified"* means *"fired"* with no guess and no second authority. **THE SUBSCRIBER PATH'S TWO HALVES, AND ITS CARRIER IS THE BINDING ITSELF**: `createTabsDelivery`'s and `createViewDelivery`'s `handlers`/`notify` are widened at `notify`'s own call so the subscriber is handed the **delivered address** and its answer is TAKEN — **additive, because NOBODY SUBSCRIBES IN THE APP AT THIS HEAD** (`main()` supplies only the sinking queue, and `createViewDelivery` says so itself) — and the subscriber the design intends IS the channel's binding, so the answer is composed where the batch already is: **the crossing's sink stays arity-1 and address-only and is NEVER the carrier** (`src/main/main.ts`, `D-92`), the fan-out being a second outlet `D-92` does not govern. **AND A MODULE SUBSCRIBES BEFORE IT REGISTERS**, the order `main()` itself keeps when it builds both deliveries and both queues before the store, so no turn's entry is composed before the realm half that fires it exists.
- **`C-4` — the one-time foundation change is five registries, and the widening's price is paid in the same edit as the widening** (`D-306` (a), findings 1, 2, 16; **the fifth domain is ruling (b)'s and is AUTHORED, not widened** — §1, `S-10`): pane ids, zone ids, tool groups, tool names and the secure overlay's placeholder ids become data; the four closed literals survive ONLY as the foundation's own set, so the rows that pin them (`AL-8`) are re-grained to say *foundation*, never loosened to a lower bound (D-152's lesson); and every census the widening moves is re-read, not left behind (D-146). **No module may declare a foundation id**: the registry refuses a `source: 'module'` entry naming one. **And where a widening retires a COMPILE-TIME net — `E-1`'s `Record<ToolGroup, string>` — the step that retires it ships the runtime row that replaces it** (`S-10`).
- **`C-5` — one author per address.** The six tab declarations own `['tabs']`, the view record's three own the panes, zones and theme roots, and one construction adopts both (`src/main/main.ts`'s one `createProfileStore` call, `D-65`, `D-129`). **A module's own listener or constraint stands at an address it declares and NOBODY ELSE DOES** — a template key it mints in its own namespace, a module pane's leaf under a pane id the registry admitted — and **a declaration that would OWN another author's address, a foundation root or a leaf under one, is refused by name at admission** (findings 18; `S-3`). **A SUBSCRIBER IS NOT AN OWNER, AND THAT IS THE WHOLE DIFFERENCE**: at a crossing's own address, or at a leaf under it, a module's listener adds **no registration and no inverse** and is lawful as a subscription (§4 `C-3`) — which is why the crossing path is a subscription where the module path is an ownership, and why the crossing's `notify` is the one place a leaf listener's firing is decided.
- **`C-6` — the ordered graph point is ENVELOPE COMPOSITION, before `translateLegacy`.** A module contributes graph DATA — nodes whose parents it names by id — and never a post-compile string transform (the `D-231` class) and never hand-written DOM (brief §2, `docs/guides/forking.md` §3.2); the order is the resolver's activation order, so the foundation's nodes exist before any module's addition (D-304's ordering must-have, `S-15`). A throwing contribution is contained and NAMED (D-124, D-105).
- **`C-7` — the post-bootstrap phase is `applyCommand`, is unordered, and claims no placement routing** (D-182, `D-252`). Anything a module needs ORDERED must be in the composition; anything it needs after a boot is a normal command and the design says so rather than implying a lifecycle point that does not exist (findings 4, 10).
- **`C-8` — secure additions are the OVERLAY'S PLACEHOLDERS and nothing else** (`D-306` (b), `D-113`): a module fills placeholder ids authored inside the isolated graph's envelope — **adopted at that graph's OWN composition point, a second point of the same kind as `C-6`'s and never the app runtime's** (`S-21`); the graph, its `window.provident.*` handler bodies and its isolation contract stay foundation-owned, and a module adds NO crossing there. A module's content in that graph is operator-only by construction — which is the point (findings 5).
- **`C-9` — the pane predicate, and it is FIVE NOUNS**: *(declared record id, node id, head, body, geometry source)*, the body being a graph subtree the module mints (findings 15). Nothing about items, roles or menus is a member: the eighteen items are `menus-module`'s CONTENT and must never become the pane API's shape — the over-fit firewall is the substitute predicate plus this sentence (canonical D-23).
- **`C-10` — UI authority holds over modules, and it is `S-2b`'s mechanism** (brief §2, `AGENTS.md`): every module element is graph data driven through the producing graph; **a module's renderer code is reached by a NAMED ACTION registered in the foundation's own table and resolved by the foundation at dispatch** — never by a handler body carrying the module's logic and never by a fragment transform — so `dispatch`, `get_rendered_html` and `get_markdown` see everything a module draws (findings 11, B5). **`D-307` DOES NOT MOVE THIS RULE, AND THAT IS SAID BECAUSE IT COULD LOOK OTHERWISE**: a listener's two halves change WHAT the channel carries and WHEN each half runs, never how a module's element is driven — a client half that draws does so through `C-10`'s named action and through nothing of its own, **which is also how its own observations become readable** (§6, `C-1`'s ban being why). **Where the engine admits no such name, the indirection is the foundation's and the first-class form is `H-2`**.
- **`C-11` — one application-version authority.** One accessor publishes the number the build carries; the resolver judges `requires.app` against it and the MCP transport reports the same number. The `'0.1.0'` literal beside `createServer` (`src/main/mcp-server.ts`) is the SECOND spelling and retires into that accessor (findings 12, A5); a module's `requires.app` that the authority cannot satisfy is refused by name, never silently activated.
- **`C-12` — a module's declaration is checked against its registration.** What a manifest declares and what its entry registers at activation must be the same set, in both directions: an overstated declaration is refused by name at install (`S-3`) and an undeclared registration is refused by name at activation. **A LISTENER DECLARATION IS A DECLARATION LIKE ANY OTHER AND ITS TWO HALVES ARE BOTH CHECKED** (`D-307`): a declared `main` half that registers nothing, and a registered listener the manifest never declared, are each refused by name — and a declaration with **no** main half is not an overstatement but the passthrough arm, a lawful shape and not an absence. A declaration agreeing with itself is not evidence (D-43's rule applied to a manifest).
- **`C-13` — cross-compatibility is a property of the CONTRACT, not of a host.** No Electron type, no IPC name and no `window` member appears in the module contract; the store's verbs a module is handed are the `data`-shaped five (`D-112`) reached through the foundation's one adapter, so the same module runs where the store is main-owned (today) and where it stands in the realm (the browser plan, `D-298`/`D-299`); **the two-half listener is the same contract under one realm and under two** (`D-307`); **the WASM build is assumed by no step and no row** (D-304 (iii)).
- **`C-14` — the floor does not move.** The four legs and the boundary instrument stay the floor (brief §6, `D-301`, `D-302`); every row this unit files under `tests/e2e/` is UNMARKED and gates, and none of them is a row the machinery itself judges (D-40, D-116).

## 5. The Cordis mapping, and the three handoff requests — TWO TO FILE, ONE MEASURED AWAY

- **THE PREDICATE IS THE RULE AND THE NAME IS AN OPTION** (canonical D-23, research C4, findings 20): no `cordis` package exists in this tree's dependency graph (C3), so what this unit builds is the FOUR PROPERTIES, not a dependency. Each is foundation-side or a handoff, and §3 names which step carries each.
- **`C4` (i) DECLARED COEFFECTS, RE-RESOLVED ON PROVISION/UNPROVISION — FOUNDATION-SIDE** (`S-22`): a module declares the modules, addresses, pane ids, groups and placeholders it consumes; the resolver holds the classification and re-computes each module's activation when a provision moves. It needs nothing the store does not already answer.
- **`C4` (ii) A RUNTIME-HELD INVERSE PER EFFECT — FOUNDATION-SIDE, AND THE AUTHORITY ALREADY MINTS THEM** (`S-23`): `listen` answers the handle the store watches under and `unlisten` withdraws it; `addConstraint` answers an identity and `removeConstraint(pair)` deletes it (`index.d.ts:1213,1228,1273,1329`). At `C-3`'s grain one listener is one handle, so its inverse is `unlisten`/`removeListener` and no set-assignment re-`listen` is ever owed — **a listener's two halves being ONE registration with ONE inverse** (`D-307`). **The one effect with no inverse is a COMPILED NODE** — that is `H-1`.
- **`C4` (iii) ACTIVATE/DEACTIVATE DRIVEN BY THE CLASSIFICATION — FOUNDATION-SIDE** (`S-24`), because the classification is `S-22`'s and the inverses are `S-23`'s; the sibling checkout's five-gap retrofit is priced on the graph side (`../Preempt-Providence/docs/specs/cordis-composability-scope.md:32-98`), and this unit narrows its exposure by not claiming a graph inverse it cannot hold.
- **`C4` (iv) COMPONENT-SCOPED REPLACEMENT — FOUNDATION-SIDE FOR THE COMPOSITION AND A HANDOFF FOR THE COMPILED GRAPH** (`S-25`): re-running composition for one module is lawful before a compile; replacing a compiled subtree is not (D-182), so it is `H-1`. **`H-2` IS NOT A SECOND ACCOUNT OF `S-2b`**: `S-2b` delivers the client half and holds the named-action table, and `H-2` is the gap that leaves that table reachable only through a foundation indirection instead of a first-class name in the graph (§4 `C-10`).
- **`H-1` → `provident-ssr`.** **Symptom:** after the first compile a container never re-emits its markup when a child is added, so a module cannot be activated or replaced without a fresh boot; path-compiling double-emits and a first post-bootstrap mint drops an authored bootstrap consumer. **Reproduction:** construct one `Runtime` over an envelope, `bootstrap()`, add a child to an existing authored container, re-render — the container's markup is unchanged (the class this repo recorded as `D-182`, and measured again for the move half at `D-252`). **Suspected root cause:** `render()` bootstraps once and thereafter merges per-node `prevStates`; there is no public invalidation entry keyed by node and no ancestor walk, so an added node's parent is never dirtied. **Proposed fix shape:** a public recompile/invalidate entry keyed by node id that dirties the ancestor chain to the root (or an insert/replace op whose recompile does), plus a stated sentence of what a post-bootstrap structural change re-emits. Upstream-owned, never patched here (D-5, D-52).
- **`H-2` → `provident-ssr`.** **Symptom:** behaviour on a graph node can only be a function-STRING body evaluated at translate, so a module's renderer code must be re-materialised as source text in the graph, which `C-10` forbids and which puts a module's logic where `dispatch` and a fragment read can see it as data. **Reproduction:** author a node whose `handlers[].body` is a function value — the graph admits no closure and dispatch evaluates `body` only (`src/shared/demo-envelope.ts`'s handler contract; findings 11). **Suspected root cause:** the handler contract is `{name, event, body: string}` and the dispatch path has no resolver indirection, so a host-owned function has no representation in graph data. **Proposed fix shape:** admit a `handlers[].ref` whose value is a KEY the HOST resolves at dispatch through a resolver the host supplies — exactly as it already supplies adapter and transform hooks — with an unresolved key contained per handler. Upstream-owned (D-5, D-52).
- **`H-3` → `provident-storeroom`: MEASURED, AND **NOT REQUIRED** — stated with all four of `D-5`'s fields because `D-307` expected it, and withdrawn because the measurement is what `D-307`'s *"probably"* leaves to it.** **Symptom:** the *delivered* set of a turn never reaches the caller — it is `record.pending`, carrying a repair's fired listeners while `triggered` *"IS UNMOVED"* (`index.d.ts:969-993`; `index.mjs:743-751`; `delivery.mjs:948-988`), and it rides the kernel's `CommitRecord`, which no `write`/`delete`/registration/reversal answer hands over (`index.d.ts:616-620,705,844-847,962-994`); the invocation carries one address and *"no other argument is declared and no return value is read"* (`delivery.mjs:98-104`); and a body *"cannot tell which binding matched"* (`:137-141`, `AB-3`). **Reproduction:** bind ONE handle at two of a module's addresses and take a delivery a repair fires inside a write — the caller's `WriteRecord.triggered` does not contain the fired handle, `CommitRecord.pending` is not handed over, `RollbackRecord` carries no fired set, and the single invocation names one address; the listener cannot say which declaration fired. **Suspected root cause:** the delivery's set and address are the package's own and neither crosses back (`delivery.mjs:105-208`), so **a binding's identity is its HANDLE and nothing else** — the package behaving exactly as it declares. **Proposed fix shape — none is owed**: `§4 C-3` binds one handle per declaration, so the invocation IS the attribution on every arm that can fire a module listener — a repair-fired write, `delete`, `addConstraint`, a re-arm, a reversal — and no store change, second argument or record member is needed; the request would be filed ONLY if that grain were reverted, and it is recorded so a reversal cannot rediscover it. Upstream-owned and never patched here either way (D-5, D-52).
- **THE FILING IS NOT THIS LAYER'S, AND SAYING SO IS PART OF THE ARTIFACT**: `D-306` says a handoff is *"filed in the unit's record and left upstream-owned"* and `D-307` names `H-3` as one, while **`strata/records/` is not this layer's write** (brief §3, D-3) — so §5 STATES all three with their four fields, complete enough to file without re-derivation, and filing `H-1`/`H-2` and recording `H-3` as measured away are **L0's acted items** (§7 `OWED-7`).
