## 1. What this unit is, and what it does not touch

- **THE SKELETON REGISTERS NAMES AND EXECUTES NOTHING, AND THAT IS THE UNIT'S WHOLE SUBJECT** (D-305, `modularity-research.md` A1–A3, A5): `syncModuleRouter` hands each declared capability an echoing handler and states in its own words that `entry` is never evaluated (`src/main/mcp-server.ts:317-347`); the only `CapabilityRouter` is constructed in main (`src/main/main.ts:630-631`, re-synced `:795`); four of seven `ModuleCtx` members are stubs or unwired (`src/renderer/extensions.ts:122-133,161-189`); no module can register a listener at all, because each crossing takes ONE registration at construction (`src/main/tabs-record/index.ts:1473-1503`, `src/main/view-record/index.ts:1570-1591`); `ModuleDependency.versionRange` is *"declared, no resolver this pass"* and an absent dep is a no-op (`src/shared/types.ts:213-230`); the application version is the hard-coded `'0.1.0'` literal (`src/main/mcp-server.ts:864`). So "systematize the skeleton" is **build the executor and the crossing the skeleton was shaped for** (D-305).
- **FOUR DOMAINS ARE CLOSED LITERALS WITH GATING ROWS, AND A FIFTH IS AUTHORED BY THIS DESIGN** — a module-declared id is a foundation edit until a registry exists (D-305 (i), findings 1): pane ids `DECLARED_PANE_IDS` and zone ids `DECLARED_ZONE_IDS` (`src/shared/view-shape.ts:257,273`), tool groups `ToolGroup` (`src/main/security.ts:3`) with ONE live copy of the valid set beside the union (`src/main/operator-settings/index.ts` — the pane's label table is `Record<ToolGroup, string>` since `E-1` and cannot drift), and tool names `ALL_TOOLS` (`src/main/mcp-server.ts:647-675`). **The figures are `brief.md` §2's rows and are not restated here** (D-26, D-43). §4 `C-4` is the one foundation change `D-306` (a) authorizes for those four; **the fifth — the secure overlay's placeholder ids — is ruling (b)'s, and it has no closed literal at this head** (`src/renderer/secure-panels.ts` authors `props.id` strings and no set pins one), so `S-10` AUTHORS it rather than widening it (findings 2, 5).
- **NO PRE-BUILD GRAPH HOOK EXISTS** (findings 10, A9): the bootstrap compile is one-shot and `render()` is private (`src/renderer/runtime.ts:109-121,155-173`); the only module render surface is a post-compile string transform, the `D-231` forbidden class; post-bootstrap placement routing does not work (`D-182`) while relocation does (`D-252`). §3 `S-14`/`S-15` put the ordered modification point where a compile can still see it — before `translateLegacy`, not after it (§4 `C-6`).
- **TWO THINGS THE UNIT NEEDS ARE ALREADY PROPERTIES OF THE AUTHORITY, MEASURED, AND THE DESIGN IS BUILT ON THEM RATHER THAN AROUND THEM**: the store delivers a repair's write's listeners **once per distinct handle** with the triggering address as the single argument, and it mints identities with inverses — `listen(handle, addresses)`, `unlisten(handle)`, `removeListener(handle)`, `addConstraint(pair, constraint) -> identity`, `removeConstraint(pair)` (`node_modules/provident-storeroom/index.d.ts:1213,1228,1273,1327,1329`). So one handle per module IS the batch grain (§4 `C-2`, `C-3`) and Cordis's runtime-held inverse already has a home (§5).
- **What it does NOT touch** (D-306): the secure pane's isolated graph, its `window.provident.*` handlers and its isolation contract — a module's additions land inside the overlay's placeholders and re-define nothing (`C-8`); `provident-ssr` and `provident-storeroom` (D-5), each gap a handoff request (§5); a standing `D-n`; the accepted conversion — the menus pane's and the demo contents' conversion is `U7`, the LAST sub-unit, and its own unit closes it. The four legs and the boundary instrument stay the floor (brief §6, D-301, D-302).
- **ONE CONTRACT SERVES TWO BUILDS** (D-304 (i), research B2, B3): a module declares two halves and never touches IPC, `window`, `window.provident.*` or `ipcRenderer`; the foundation's passthrough is the only way out, so the same module runs in the Electron build (two realms, main owns the store — D-63) and in the eventual browser/Node host (one realm, the store in the realm — the pending `provident-storeroom` WASM build is assumed by no step, `D-298`).

## 4. The constraints this design fixes

- **`C-1` — the passthrough is the only way out, and admission is where that is enforced.** A module's code names no `ipcRenderer`, no `webContents`, no `window`, no `window.provident.*` and no IPC channel; the foundation's ctx is its whole outside (D-304 (i), research B1). **The rule is prompt-level for a HOSTILE module** — modules are trusted-equivalent to `code` and the ctx is *"an ERGONOMICS layer, NOT a security boundary"* (`src/renderer/extensions.ts:1-10`; findings 19) — **so the gate the design can build is the one at the door it owns: `S-3`'s install-time refusal, by name**, and nothing here claims isolation it cannot build (D-44).
- **`C-2` — one batch per write per realm, and the batch carries ADDRESSES.** *"all listeners fired by a storeroom write should be sent in one block in the channel, not piecemeal"* (D-304 (ii)): the foundation's sink composes every address a write's delivery produced and flushes ONE message at that turn's end; the message is a list of addresses and **never a value, a reading or a record** (`D-92`, findings 14). Addresses are what makes batching lawful where a value would make it a second authority (D-129).
- **`C-3` — ONE HANDLE PER MODULE IS THE GRAIN OF BOTH THE BATCH AND THE INVERSE, AND A MODULE SUBSCRIBES BEFORE IT REGISTERS.** At an address a crossing already serves — `['tabs']`, the view record's roots, the secure crossing's — a module's listener is a **SUBSCRIBER** on that crossing's delivery (the fan-out `createTabsDelivery` already exposes, `src/main/tabs-record/index.ts:1505-1516`), so the crossing's ONE construction registration stays the address's only one (`D-129`, `D-93`) and the inverse is the delivery's own withdrawal; at an address the module declares for ITSELF the foundation registers **one handle per module**, `listen(handle, addresses)` — SET-ASSIGNMENT on a repeat call and never union (`index.d.ts:1194-1198`) — and `unlisten`/`removeListener` are its inverse (`:1228`, `:1327`). The store delivers **once per distinct handle** (`:1266`), so neither case can make a write deliver piecemeal.
- **`C-4` — the one-time foundation change is five registries, and the widening's price is paid in the same edit as the widening** (`D-306` (a), findings 1, 2, 16; **the fifth domain is ruling (b)'s and is AUTHORED, not widened** — §1, `S-10`): pane ids, zone ids, tool groups, tool names and the secure overlay's placeholder ids become data; the four closed literals survive ONLY as the foundation's own set, so the rows that pin them (`AL-8`) are re-grained to say *foundation*, never loosened to a lower bound (D-152's lesson); and every census the widening moves is re-read, not left behind (D-146). **No module may declare a foundation id**: the registry refuses a `source: 'module'` entry naming one. **And where a widening retires a COMPILE-TIME net — `E-1`'s `Record<ToolGroup, string>` — the step that retires it ships the runtime row that replaces it** (`S-10`).
- **`C-5` — one author per address.** The six tab declarations own `['tabs']`, the view record's three own the panes, zones and theme roots, and one construction adopts both (`src/main/main.ts:426-453`, `D-65`, `D-129`). A module's constraint or listener stands at an address IT declares — a template's own key, a module pane's own leaf — and a module that would author a foundation address is refused by name at admission (findings 18; this is the rule the corpus had not stated, and it is stated here).
- **`C-6` — the ordered graph point is ENVELOPE COMPOSITION, before `translateLegacy`.** A module contributes graph DATA — nodes whose parents it names by id — and never a post-compile string transform (the `D-231` class) and never hand-written DOM (brief §2, `docs/guides/forking.md` §3.2); the order is the resolver's activation order, so the foundation's nodes exist before any module's addition (D-304's ordering must-have, `S-15`). A throwing contribution is contained and NAMED (D-124, D-105).
- **`C-7` — the post-bootstrap phase is `applyCommand`, is unordered, and claims no placement routing** (D-182, `D-252`). Anything a module needs ORDERED must be in the composition; anything it needs after a boot is a normal command and the design says so rather than implying a lifecycle point that does not exist (findings 4, 10).
- **`C-8` — secure additions are the OVERLAY'S PLACEHOLDERS and nothing else** (`D-306` (b), `D-113`): a module fills placeholder ids authored inside the isolated graph's envelope — **adopted at that graph's OWN composition point, a second point of the same kind as `C-6`'s and never the app runtime's** (`S-21`); the graph, its `window.provident.*` handler bodies and its isolation contract stay foundation-owned, and a module adds NO crossing there. A module's content in that graph is operator-only by construction — which is the point (findings 5).
- **`C-9` — the pane predicate, and it is FIVE NOUNS**: *(declared record id, node id, head, body, geometry source)*, the body being a graph subtree the module mints (findings 15). Nothing about items, roles or menus is a member: the eighteen items are `menus-module`'s CONTENT and must never become the pane API's shape — the over-fit firewall is the substitute predicate plus this sentence (canonical D-23).
- **`C-10` — UI authority holds over modules, and it is `S-2b`'s mechanism** (brief §2, `AGENTS.md`): every module element is graph data driven through the producing graph; **a module's renderer code is reached by a NAMED ACTION registered in the foundation's own table and resolved by the foundation at dispatch** — never by a handler body carrying the module's logic and never by a fragment transform — so `dispatch`, `get_rendered_html` and `get_markdown` see everything a module draws (findings 11, B5). **Where the engine admits no such name, the indirection is the foundation's and the first-class form is `H-2`**: the delivery, the ctx and the table are `S-2b`'s, and only the binding-in-graph is upstream's.
- **`C-11` — one application-version authority.** One accessor publishes the number the build carries; the resolver judges `requires.app` against it and the MCP transport reports the same number. `src/main/mcp-server.ts:864`'s `'0.1.0'` is the SECOND spelling and retires into that accessor (findings 12, A5); a module's `requires.app` that the authority cannot satisfy is refused by name, never silently activated.
- **`C-12` — a module's declaration is checked against its registration.** What a manifest declares and what its entry registers at activation must be the same set, in both directions: an overstated declaration is refused by name at install (`S-3`) and an undeclared registration is refused by name at activation. A declaration agreeing with itself is not evidence (D-43's rule applied to a manifest).
- **`C-13` — cross-compatibility is a property of the CONTRACT, not of a host.** No Electron type, no IPC name and no `window` member appears in the module contract; the store's verbs a module is handed are the `data`-shaped five (`D-112`) reached through the foundation's one adapter, so the same module runs where the store is main-owned (today) and where it stands in the realm (the browser plan, `D-298`/`D-299`); **the WASM build is assumed by no step and no row** (D-304 (iii)).
- **`C-14` — the floor does not move.** The four legs and the boundary instrument stay the floor (brief §6, `D-301`, `D-302`); every row this unit files under `tests/e2e/` is UNMARKED and gates, and none of them is a row the machinery itself judges (D-40, D-116).

## 5. The Cordis mapping, and the two handoff requests

- **THE PREDICATE IS THE RULE AND THE NAME IS AN OPTION** (canonical D-23, research C4, findings 20): no `cordis` package exists in this tree's dependency graph (C3), so what this unit builds is the FOUR PROPERTIES, not a dependency. Each is foundation-side or a handoff, and §3 names which step carries each.
- **`C4` (i) DECLARED COEFFECTS, RE-RESOLVED ON PROVISION/UNPROVISION — FOUNDATION-SIDE** (`S-22`): a module declares the modules, addresses, pane ids, groups and placeholders it consumes; the resolver holds the classification and re-computes each module's activation when a provision moves. It needs nothing the store does not already answer: the registry is a value and the store's roots are read through the `data` adapter (`D-112`).
- **`C4` (ii) A RUNTIME-HELD INVERSE PER EFFECT — FOUNDATION-SIDE, AND THE AUTHORITY ALREADY MINTS THEM** (`S-23`): `listen` answers the handle the store watches under and `unlisten` withdraws it; `addConstraint` answers an identity and `removeConstraint(pair)` deletes it (`index.d.ts:1213,1228,1273,1329`, measured). The foundation holds one inverse per ctx registration and runs them in reverse on deactivate. **The one effect with no inverse is a COMPILED NODE** — that is `H-1`.
- **`C4` (iii) ACTIVATE/DEACTIVATE DRIVEN BY THE CLASSIFICATION — FOUNDATION-SIDE** (`S-24`), because the classification is `S-22`'s and the inverses are `S-23`'s; the sibling checkout's five-gap retrofit is priced on the graph side (`../Preempt-Providence/docs/specs/cordis-composability-scope.md:32-98`), and this unit narrows its exposure by not claiming a graph inverse it cannot hold.
- **`C4` (iv) COMPONENT-SCOPED REPLACEMENT — FOUNDATION-SIDE FOR THE COMPOSITION AND A HANDOFF FOR THE COMPILED GRAPH** (`S-25`): re-running composition for one module is lawful before a compile; replacing a compiled subtree is not (D-182), so it is `H-1`. **`H-2` IS NOT A SECOND ACCOUNT OF `S-2b`**: `S-2b` delivers the client half and holds the named-action table, and `H-2` is the gap that leaves that table reachable only through a foundation indirection instead of a first-class name in the graph (§4 `C-10`).
- **`H-1` → `provident-ssr`.** **Symptom:** after the first compile a container never re-emits its markup when a child is added, so a module cannot be activated or replaced without a fresh boot; path-compiling double-emits and a first post-bootstrap mint drops an authored bootstrap consumer. **Reproduction:** construct one `Runtime` over an envelope, `bootstrap()`, add a child to an existing authored container, re-render — the container's markup is unchanged (the class this repo recorded as `D-182`, and measured again for the move half at `D-252`). **Suspected root cause:** `render()` bootstraps once and thereafter merges per-node `prevStates`; there is no public invalidation entry keyed by node and no ancestor walk, so an added node's parent is never dirtied. **Proposed fix shape:** a public recompile/invalidate entry keyed by node id that dirties the ancestor chain to the root (or an insert/replace op whose recompile does), plus a stated sentence of what a post-bootstrap structural change re-emits. Upstream-owned, never patched here (D-5, D-52).
- **`H-2` → `provident-ssr`.** **Symptom:** behaviour on a graph node can only be a function-STRING body evaluated at translate, so a module's renderer code must be re-materialised as source text in the graph, which `C-10` forbids and which puts a module's logic where `dispatch` and a fragment read can see it as data. **Reproduction:** author a node whose `handlers[].body` is a function value — the graph admits no closure and dispatch evaluates `body` only (`src/shared/demo-envelope.ts:1-18,585`; findings 11). **Suspected root cause:** the handler contract is `{name, event, body: string}` and the dispatch path has no resolver indirection, so a host-owned function has no representation in graph data. **Proposed fix shape:** admit a `handlers[].ref` whose value is a KEY the HOST resolves at dispatch through a resolver the host supplies — exactly as it already supplies adapter and transform hooks — with an unresolved key contained per handler, so a graph authored as data can name behaviour the host owns without carrying its text. Upstream-owned (D-5, D-52).
- **THE FILING IS NOT THIS LAYER'S, AND SAYING SO IS PART OF THE ARTIFACT**: `D-306` says the handoff is *"filed in the unit's record and left upstream-owned"* and `strata/records/modularity-unit.md` already owes it, while **`strata/records/` is not this layer's write** (brief §3, D-3) — so §5 STATES both requests with their four fields, complete enough to file without re-derivation, and the filing in that record is **L0's acted item** (§7 `OWED-7`).
