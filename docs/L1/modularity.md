## 1. What this unit is, and what it does not touch

- **THE SKELETON REGISTERS NAMES AND EXECUTES NOTHING, AND THAT IS THE UNIT'S WHOLE SUBJECT** (D-305, `modularity-research.md` A1–A3, A5): `syncModuleRouter` hands each declared capability an echoing handler and states in its own words that `entry` is never evaluated (`src/main/mcp-server.ts`); the only `CapabilityRouter` is constructed in `src/main/main.ts`'s `main()` (and re-synced there); four of seven `ModuleCtx` members are stubs or unwired (`src/renderer/extensions.ts`'s `ModuleCtx`); no module can register a listener at all, because each crossing's delivery adopts ONE registration act at construction — the tab record one entry, the view record one per declared address (`src/main/tabs-record/index.ts`'s `createTabsDelivery`, `src/main/view-record/index.ts`'s `createViewDelivery`); `ModuleDependency.versionRange` is *"declared, no resolver this pass"* and an absent dep is a no-op (`src/shared/types.ts`'s `ModuleManifest` block); the application version is a hard-coded `'0.1.0'` literal beside `createServer` (`src/main/mcp-server.ts`). So "systematize the skeleton" is **build the executor and the crossing the skeleton was shaped for** (D-305).
- **FOUR DOMAINS ARE CLOSED LITERALS WITH GATING ROWS, AND A FIFTH IS AUTHORED BY THIS DESIGN** — a module-declared id is a foundation edit until a registry exists (D-305 (i), findings 1): pane ids `DECLARED_PANE_IDS` and zone ids `DECLARED_ZONE_IDS` (`src/shared/view-shape.ts`), tool groups `ToolGroup` and its valid set (`src/main/security.ts`'s `TOOL_GROUPS`/`VALID_GROUPS`) **with ONE live second copy of the valid SET — a bare set and NO label table — in `src/main/operator-settings/index.ts` (`VALID_GROUPS`, `:168`)**, and tool names `ALL_TOOLS` (`src/main/mcp-server.ts`). **THE PANE LABEL TABLE IS A DIFFERENT OBJECT IN A DIFFERENT FILE AND IS NOT THAT COPY** (`E-1`): `Record<ToolGroup, string>` is `GROUP_LABELS` at `src/renderer/secure-panels.ts:165`, `secure-panels`' table and `S-10`'s, typed by the same union — so the drift findings 1 and `D-35` name is **two copies of one SET plus one table that projects it**, and this bullet, §2's two rows and `S-10` say one thing. **The figures are `brief.md` §2's rows and are not restated here** (D-26, D-43). §4 `C-4` is the one foundation change `D-306` (a) authorizes for those four; **the fifth — the secure overlay's placeholder ids — is ruling (b)'s, and it has no closed literal at this head** (`src/renderer/secure-panels.ts` authors `props.id` strings and no set pins one), so `S-10` AUTHORS it rather than widening it (findings 2, 5).

- **WHAT THE AUTHORITY GIVES A TWO-HALF LISTENER, AND WHAT IT WITHHOLDS, MEASURED AT THE PACKAGE'S OWN BYTES — WITH REV 2'S ONE OVERSTATEMENT CORRECTED HERE** (`D-307`): a firing is **one invocation per DISTINCT HANDLE**, handed **one address** — *"the triggering ADDRESS … no other argument is declared and no return value is read"* (`src/entry/delivery.mjs:98-104,154-166,206`) — which is the WRITE's address and never the binding's (`:973-974`); and a body **cannot tell which binding matched** — *"and that is declared"* (`:137-141`, `AB-3`). **THE DELIVERED SET IS `record.pending`, AND `pending` IS SEEDED AS A CLONE OF `triggered`** (*"Push the pair into pending. Pending is seeded as a clone of triggered."*, `index.d.ts:970-974`) — **so on a write or a delete that NO REPAIR FIRES INSIDE, the delivered set DOES reach a caller**: `WriteRecord.triggered` and `DeleteRecord.triggered` (`:616-620`, `:701-705`) hand it back as `TriggerPair` `{handle, address}` (`:684-698`) — the fired handle AND the address its binding stands at. **THE DIFFERENCE BETWEEN THE TWO SETS IS A REPAIR'S MERGED FIRINGS AND NOTHING ELSE**: a repair's write's triggered listeners are merged into `pending` while `triggered` *"IS UNMOVED"* (`:980-988`; `index.mjs:743-751`; `delivery.mjs:948-988`), so on that arm the extra entries stand only in the kernel's `CommitRecord` — **AND WHICH ACTS HAND THAT RECORD TO A CALLER IS MEASURED RATHER THAN ASSUMED**: a **`delete`'s** receipt carries it at `record.commit`, and its `pending` *"IS THE SET THE DELIVERY FIRES"* (`:726-759`, the clause at `:733-735`), so **a delete's caller reads the delivered set on every arm**; a **`write`'s** does not — `WriteRecord` is `{op, watched, triggered}` and carries *"NO `attempt` and NO `pending`"* (`:616-620`, `:946-949`) — so a write's caller reads the set ONLY as `triggered`, which on a repaired write misses a repair's firings; a **registration** answers its identity and can be pre-empted by a fired throw (`:1266-1273`), and a **reversal** answers `{opId, undoneOps, restoredTo}` (`:844-847`), neither of them carrying a fired set. **SO THE SET REACHES A CALLER ON A DELETE ALWAYS AND ON A WRITE ONLY AS `triggered`, AND THE ARM `H-3` IS ABOUT IS THE WRITE'S** (§5). **AND WHERE THE SET DOES REACH, IT IS STILL NOT A PER-INVOCATION FACT**: the address carried for a handle is *"INFORMATIONAL DATA about the trigger set and NOT a per-invocation fact"* — the FIRST pair encountered, `triggered`'s order unspecified (`delivery.mjs:137-141`) — **and a fired body's throw is neither caught nor reported by the delivery loop** — *"§2.7 item 4 leaves it NOT caught, not retried and not reported"* (`src/entry/kernel-attempt.mjs:437-441`; `delivery.mjs:206`), so it crosses out of an unrelated writer's call and at a registration *"pre-empts that answer and crosses as rank 21 `ListenerBodyThrew`"* (`index.d.ts:1264-1270`); and an adopted `cfg.listeners` element carries **one address** (`:295-297`) though `listen(handle, addresses)` takes a plural set that it **set-assigns** (`:1213` with `:1194-1198`). **THE CONSEQUENCE IS A GRAIN AND NOT A HANDOFF, RE-DERIVED ON THIS BASIS**: identity must come from the **handle** — one handle per listener DECLARATION, the practice `view-record`'s `createViewDelivery` already keeps, minting one per declared address — because **(i)** the loop invokes **once per distinct handle**, so two declarations sharing one collapse to one invocation and one main half never runs; **(ii)** the invocation's one argument is the write's address and a body cannot tell which binding matched, so the HANDLE is the only attribution a firing can carry; and **(iii)** the set is unavailable to the caller on exactly the arm that matters most — a WRITE a repair fires inside — and informational where it is available (a delete's `record.commit.pending` names handles and addresses and never which invocation fired). **So the invocation IS the attribution and no fired set is relied on**, which is what keeps `H-3` withdrawn (§5). **One address per declaration is a CHOSEN narrowing of a plural verb**, its cost stated at `C-3`. Identities still mint inverses — `listen`, `unlisten`, `removeListener`, `addConstraint` → identity, `removeConstraint` (`index.d.ts:1213,1228,1273,1327,1329`) — so Cordis's runtime-held inverse has a home (§5).
- **What it does NOT touch** (D-306): the secure pane's isolated graph, its `window.provident.*` handlers and its isolation contract — a module's additions land inside the overlay's placeholders and re-define nothing (`C-8`); `provident-ssr` and `provident-storeroom` (D-5), each gap a handoff request (§5); a standing `D-n`; the accepted conversion — the menus pane's and the demo contents' conversion is `U7`, the LAST sub-unit, and its own unit closes it. - **ONE CONTRACT SERVES TWO BUILDS** (D-304 (i), research B2, B3): a module declares two halves and never touches IPC, `window`, `window.provident.*` or `ipcRenderer`; the foundation's passthrough is the only way out, so the same module runs in the Electron build (two realms, main owns the store — D-63) and in the eventual browser/Node host (one realm, the store in the realm — the pending `provident-storeroom` WASM build is assumed by no step — **`D-304` (iii), which carries that clause; `D-298`/`D-299` carry the pin's `require`/`exports` move and the `>=22.12.0` floor and name no WASM build**) —. **`D-307` DOES NOT LOOSEN THIS**: a listener's main half runs wherever the store is and its client half wherever the realm is, which is the SAME contract under one realm and under two.

## 4. The constraints this design fixes

- **`C-1` — the passthrough is the only way out, and admission is where that is enforced.** A module's code names no `ipcRenderer`, no `webContents`, no `window`, no `window.provivent.*` and no IPC channel; the foundation's ctx is its whole outside (D-304 (i), research B1). **The rule is prompt-level for a HOSTILE module** — modules are trusted-equivalent to `code` and the ctx is *"an ERGONOMICS layer, NOT a security boundary"* (`src/renderer/extensions.ts`'s header; findings 19) — **so the gate the design can build is the one at the door it owns: `S-3`'s install-time refusal, by name**, and nothing here claims isolation it cannot build (D-44). **A route that exists and is forbidden is still forbidden**: `ProvidentBridge`'s `data` member carries five store routes and the renderer reaches them as `window.provident.data.*` (`src/main/preload.ts`), so a module's realm half has a store route in reach and may not name it — the named action is its route, not the bridge.
- **`C-2` — one message per write turn per realm, AND IT CARRIES PER-LISTENER DATA — WHICH IS `D-92` READ AT ITS OWN BOUNDARY AND NOT A REPEAL OF IT** (`D-307`): *"all listeners fired by a storeroom write should be sent in one block in the channel, not piecemeal"* (D-304 (ii)). The foundation's sink flushes ONE message at the turn's end — `{turn, entries}` — where **every entry is `{turn, module, listener, outcome, data?, refusal?}` and the shape is TOTAL over FIVE arms**: `return` with `data` the main half's answer; `empty` with `data` ABSENT, for a DECLARED main half that returned nothing (`D-307`'s *"if any"*); `passthrough` with `data` the address the store handed the binding, for a listener declaring NO main half (`D-307`); `refused` with `data` ABSENT and `refusal: 'not-transport-safe'` — a function, a symbol, a host object, a cycle, a `Promise`; and **`threw` with `data` ABSENT and `refusal: 'main-half-threw'`, the arm the binding exists for**: the store catches nothing (`src/entry/kernel-attempt.mjs:437-441`), so a contained throw is the only form in which a module fault can reach its own client half without crossing out of an unrelated writer's call (D-105). **`module` IS A MEMBER BECAUSE A BATCH MAY CARRY SEVERAL MODULES' LISTENERS** (§3 `S-13`): a listener name is the module's own and is not unique across the app. **`turn` COUNTS COMMITS AND IS THE FOUNDATION'S**, not a journal ordinal: it is the flush unit — one store act including its repairs — which no store member answers to a caller who is not the writer, and the store's own `JournalOp.seq` numbers ops, not that unit (D-129's second-authority class is why the distinction is stated). **THE `D-92` DISTINCTION, STATED SO IT CANNOT BE GLOSSED**: the crossings' own push carries an ADDRESS and never a value, a reading or a record — `main()`'s `createDeliveryQueue` and its arity-0 `push()` are UNMOVED (`src/main/main.ts`; `D-92`, findings 14) — **while a module listener's `data` is the LISTENER'S OWN RETURN, produced by that module's own main half and read by nobody else**: it is not a reading of the store, it is not derived from a record, and `D-92` governs the crossings' push and not this payload (`D-307`'s own clause). **AND THE ENVELOPE ASKS THE PACKAGE FOR NO FIRED SET, WHICH IS WHY IT IS LAWFUL ON EVERY ARM**: the binding already knows which declaration fired — the handle — so **the arm where no set reaches the caller (a WRITE a repair fires inside, §1) is the arm a design resting on the set would fail, and the arm where one does (a delete's `record.commit.pending`) is no help either**, a set naming handles and addresses and never which invocation fired; **this is the whole reason the grain is per declaration.**
- **`C-3` — ONE HANDLE PER LISTENER DECLARATION IS THE GRAIN OF THE BINDING AND THE INVERSE; BOTH LISTENER PATHS OBEY THE SAME TWO-HALF RULE — THE MAIN HALF AT THE FIRING, THE CLIENT HALF AT DELIVERY** (`D-307`; re-grained from rev 1 by §1's three measured facts, and RE-DERIVED IN REV 3 because the first of rev 2's premises was overstated). **THE HANDLE IS THE CALLER'S OWN STRING AND THE STORE MINTS NOTHING** (`index.d.ts:1194-1198`'s surviving minting half, whose own words stand at **`:1196-1197`** — *"THE SURVIVING HALF IS THE MINTING HALF: the handle is the CALLER'S, so nothing mints one"*; `:1192-1193` is the sentence that clause SUPERSEDES and is cited here for nothing — read with `:1200-1211`: `listen` *"ANSWERS THE HANDLE IT WATCHES UNDER ON SUCCESS — the caller's own spelling, returned as THE IDENTITY THE STORE HOLDS FOR THAT ENTRY"*; `index.mjs:1123` → `listenOn`), **so the foundation's rule is a NAMESPACE and not a name**: `module:<module>:<listener>`, **STABLE FOR THE DECLARATION'S LIFE, INCLUDING ACROSS A WITHDRAWAL AND A RE-REGISTRATION**. **THE STABILITY IS THIS DESIGN'S CHOICE AND IS NOT PRESENTED AS A PACKAGE FACT**: rev 2 rested it on `:1219-1227`'s *"a re-`listen` at the withdrawn address answers a DIFFERENT handle"*, and that clause is **superseded by the `listen` member's own return clause in the docblock immediately above it** (`:1200-1211`, that docblock closing at `:1212`; the two are ADJACENT BLOCKS AND NOT ONE, which is the correction rev 3's wording needed), under which a re-`listen` at the withdrawn address answers **the same** handle — the design therefore picks the stable spelling, because a re-activation that re-minted would leave a second identity where `S-23` owes one inverse, and says so. **THE NAMESPACE IS DISJOINT FROM EVERY CONSTRAINED PAIR'S `id`, IN BOTH DIRECTIONS**: `register` refuses where the handle equals a carried pair's `id`, disabled pair included (`:1295-1317`, `D-98`), and `addConstraint` rejects a pair whose `id` equals a LIVE listener's handle (`:1240-1249`) — so **`register`'s replacement rule can never silently overwrite another listener's body**: *"ONE handle, ONE function — the previous entry is REPLACED and dropped without notice, AND `register` CLEARS `off`"* is `surface.md §2.4` **rule 2**, carried at `src/entry/delivery.mjs:749-757` (rev 2 cited `:1194-1198` for it, which is `listen`'s set-assignment clause and not this rule; `:1325` is `register`'s own signature) — and `C-12`'s two-directional check is made against that namespace. **At an address the module declares for ITSELF** the foundation calls `listen(handle, [address])`: `listen` takes a plural set that it SET-ASSIGNS (`:1213` with `:1194-1198`), and one address per declaration is **this design's CHOSEN narrowing** — the adopted `cfg.listeners` element's own shape corroborating it (`:295-297`) — **whose cost is stated rather than hidden: a module that wants one conceptual listener at two addresses declares two, and gets two entries.** The store then fires **once per distinct handle** with the WRITE's one address (`delivery.mjs:154-166,206`), so **the invocation IS the attribution: the binding contains the main half's throw, runs THAT listener's main half with the address as its argument, and keeps the return** — and this rests on the loop's own grain, **not** on a fired set being unreachable (§1: on a repair-less write `triggered` does reach the caller, and its address member is still not a per-invocation fact). **At an address a CROSSING already serves** a module's listener is a **SUBSCRIBER** on that crossing's delivery — at the crossing's own address (`['tabs']`, a view root) or at a leaf UNDER it, both lawful — and the fan-out is **ADDRESS-KEYED UNDER THE STORE'S OWN PREFIX RELATION**: the address the fan-out receives is the WRITE's, and a subscriber is notified when ITS declared address prefixes that one — so **a subscriber at a crossing's OWN root (`['tabs']`, or the view crossing's `['panes']`) IS notified by a write at a leaf under it, and a subscriber AT that leaf is NOT notified by a write at the root** (`delivery.mjs:132-135`'s prefix matching, the relation §6's `M-13` names and drives — **and one crossing's root with a leaf under it is the only pair that can measure it**). A subscriber adds **no registration and no inverse** (`C-5`), the crossing's registration is the ONE the construction took (`D-129`), and `C-12` counts a subscriber as DECLARED and never as registered.

## 5. The Cordis mapping, and the three handoff requests — TWO TO FILE, ONE MEASURED AWAY

- **THE PREDICATE IS THE RULE AND THE NAME IS AN OPTION** (canonical D-23, research C4, findings 20): no `cordis` package exists in this tree's dependency graph (C3), so what this unit builds is the FOUR PROPERTIES, not a dependency. Each is foundation-side or a handoff, and §3 names which step carries each.
- **`C4` (i) DECLARED COEFFECTS, RE-RESOLVED ON PROVISION/UNPROVISION — FOUNDATION-SIDE** (`S-22`): a module declares the modules, addresses, pane ids, groups and placeholders it consumes; the resolver holds the classification and re-computes each module's activation when a provision moves. It needs nothing the store does not already answer.
- **`C4` (ii) A RUNTIME-HELD INVERSE PER EFFECT — FOUNDATION-SIDE, AND THE AUTHORITY ALREADY MINTS THEM** (`S-23`): `listen` answers the handle the store watches under and `unlisten` withdraws it; `addConstraint` answers an identity and `removeConstraint(pair)` deletes it (`index.d.ts:1213,1228,1273,1329`). At `C-3`'s grain one listener is one handle, so its inverse is `unlisten`/`removeListener` and no set-assignment re-`listen` is ever owed — **a listener's two halves being ONE registration with ONE inverse** (`D-307`). **The one effect with no inverse is a COMPILED NODE** — that is `H-1`.
- **`C4` (iii) ACTIVATE/DEACTIVATE DRIVEN BY THE CLASSIFICATION — FOUNDATION-SIDE** (`S-24`), because the classification is `S-22`'s and the inverses are `S-23`'s; the sibling checkout's five-gap retrofit is priced on the graph side (`../Preempt-Providence/docs/specs/cordis-composability-scope.md:32-98`), and this unit narrows its exposure by not claiming a graph inverse it cannot hold.
- **`C4` (iv) COMPONENT-SCOPED REPLACEMENT — FOUNDATION-SIDE FOR THE COMPOSITION AND A HANDOFF FOR THE COMPILED GRAPH** (`S-25`): re-running composition for one module is lawful before a compile; replacing a compiled subtree is not (D-182), so it is `H-1`. **`H-2` IS NOT A SECOND ACCOUNT OF `S-2b`**: `S-2b` delivers the client half and holds the named-action table, and `H-2` is the gap that leaves that table reachable only through a foundation indirection instead of a first-class name in the graph (§4 `C-10`).
- **`H-1` → `provident-ssr`.** **Symptom:** after the first compile a container never re-emits its markup when a child is added, so a module cannot be activated or replaced without a fresh boot; path-compiling double-emits and a first post-bootstrap mint drops an authored bootstrap consumer. **Reproduction:** construct one `Runtime` over an envelope, `bootstrap()`, add a child to an existing authored container, re-render — the container's markup is unchanged (the class this repo recorded as `D-182`, and measured again for the move half at `D-252`). **Suspected root cause:** `render()` bootstraps once and thereafter merges per-node `prevStates`; there is no public invalidation entry keyed by node and no ancestor walk, so an added node's parent is never dirtied. **Proposed fix shape:** a public recompile/invalidate entry keyed by node id that dirties the ancestor chain to the root (or an insert/replace op whose recompile does), plus a stated sentence of what a post-bootstrap structural change re-emits. Upstream-owned, never patched here (D-5, D-52).
- **`H-2` → `provident-ssr`.** **Symptom:** behaviour on a graph node can only be a function-STRING body evaluated at translate, so a module's renderer code must be re-materialised as source text in the graph, which `C-10` forbids and which puts a module's logic where `dispatch` and a fragment read can see it as data. **Reproduction:** author a node whose `handlers[].body` is a function value — the graph admits no closure and dispatch evaluates `body` only (`src/shared/demo-envelope.ts`'s handler contract; findings 11). **Suspected root cause:** the handler contract is `{name, event, body: string}` and the dispatch path has no resolver indirection, so a host-owned function has no representation in graph data. **Proposed fix shape:** admit a `handlers[].ref` whose value is a KEY the HOST resolves at dispatch through a resolver the host supplies — exactly as it already supplies adapter and transform hooks — with an unresolved key contained per handler. Upstream-owned (D-5, D-52).
- **`H-3` → `provident-storeroom`: MEASURED, AND **NOT REQUIRED** — stated with all four of `D-5`'s fields because `D-307` expected it, and withdrawn because the measurement is what `D-307`'s *"probably"* leaves to it** — **AND ITS SYMPTOM IS NARROWED IN REV 3, BECAUSE REV 2'S UNIVERSAL WAS FALSE** (§1). **Symptom (narrow):** on **a write that a REPAIR fires inside** — the arm the package's repair-listener ruling added its merge for — *"the delivered set"* does not reach the caller: a repair's fired listeners stand in `record.pending` while the caller's `WriteRecord.triggered` *"IS UNMOVED"* (`index.d.ts:970-994`; `index.mjs:743-751`; `delivery.mjs:948-988`), `pending` stands in the kernel's `CommitRecord` and **a WRITE's receipt does not carry that record at all** — the store's write answers `{op, watched, triggered}` and carries *"NO `attempt` and NO `pending`"* (`:616-620`, `:946-949`) — while **a delete's receipt does**, carrying `pending` as *"THE SET THE DELIVERY FIRES"* (`:726-759`), **which is exactly why this symptom is the WRITE's and is never stated of a delete**; a `RollbackRecord` carries no fired set (`:844-847`), the invocation carries one address and *"no other argument is declared and no return value is read"* (`delivery.mjs:98-104`), and a body *"cannot tell which binding matched"* (`:137-141`, `AB-3`). **ON A WRITE OR DELETE THAT NO REPAIR FIRES INSIDE THIS SYMPTOM DOES NOT EXIST**: `pending` is seeded as a clone of `triggered`, so `triggered` carries every fired handle and its binding address and the caller reads them (`:616-620,701-705,684-698`). **Reproduction (unchanged, and narrow by construction):** bind ONE handle at two of a module's addresses and take a delivery a repair fires inside **a WRITE** — the caller's `triggered` does not contain the fired handle, the WRITE's receipt carries no `pending` at all, `RollbackRecord` carries no fired set, and the single invocation names one address; the listener cannot say which declaration fired. **Suspected root cause:** the delivery's set and address are the package's own and on that arm neither crosses back (`delivery.mjs:105-208`), so **a binding's identity is its HANDLE and nothing else** — the package behaving exactly as it declares. **Proposed fix shape — none is owed**: `§4 C-3` binds one handle per declaration, so the invocation IS the attribution on every arm that can fire a module listener — a repaired write, `delete`, `addConstraint`, a re-arm, a reversal — and no store change, second argument or record member is needed; the request would be filed ONLY if that grain were reverted, and it is recorded so a reversal cannot rediscover it. Upstream-owned and never patched here either way (D-5, D-52).
- **THE FILING IS NOT THIS LAYER'S, AND SAYING SO IS PART OF THE ARTIFACT**: `D-306` says a handoff is *"filed in the unit's record and left upstream-owned"* and `D-307` names `H-3` as one, while **`strata/records/` is not this layer's write** (brief §3, D-3) — so §5 STATES all three with their four fields, complete enough to file without re-derivation, and filing `H-1`/`H-2` and recording `H-3` as measured away are **L0's acted items** (§7 `OWED-7`).
