## 1. What this unit is, and what it does not touch

- The interface is **six authored pieces**: the **top-bar** (a logo/name `content` string at its left, the tabs row in the middle, the platform's own controls to the right), the **four fixed zones** (`top`, `bottom`, `left`, `right`), the **stage** between them, a **tabs row that renders the record AND switches it**, and a **menus pane** of eighteen authored items. What the tree has is **one root node carrying five cards, two terminal pages and an overlay layer** — no top-bar, no zone, no stage, and no window controls in any form (`D-176`); the zone renderer was deleted as dead surface at `D-169`.
- **THE WINDOW'S CHROME IS THE ONE PLACE UI AUTHORITY STOPS** (`D-177`): the three buttons are the PLATFORM's, in an area the page does not own — measured `visible:true`, `getTitlebarAreaRect()` `[0,0,607,36]`, the page owning the whole window (`D-179`) — so this unit authors **no window control and no dispatchable close** (`D-178` §2).
- **THE TABS ROW IS THE APP'S FIRST NON-`state-slice` WRITE** (`D-178` §1): the envelope's node list is STATIC, so one node per `['tabs'].order` entry is a MINT (`D-177`) — and **a minted row renders wherever its TARGET lives**, with `keyField` keeping its id stable across deliveries (`D-182`). **No step below relies on placement routing**: post-bootstrap routing does not work and is recorded upstream-owned (`D-182`, `D-5`/`D-52`), so the `zone` member is DECLARATIVE and every pane and row is authored where it belongs.
- **The switch act adds no crossing route.** `tabs-client.ts` is read-only by contract and the realm's own `focusActRoute` gains a DOM-originated caller — the `attach` form theme already has (`D-177`) — so `store-tabs-record` is named and NOT claimed (§2).
- **THE MENUS ARE THE HAZARD AT EIGHTEEN TIMES THE GRANULARITY** (`D-180`): an authored item is a handler body, and `provident.dispatch` reaches every one of them in the default grant (`['read','dispatch']`). So the pane renders eighteen and the ROUTE admits eleven, and the refusal is enforced in `main` — where the grant stops — and not only by an authored `disabled` (`D-181`).
- **What this unit does NOT touch**: the isolated pane graph and its capability UI (`D-113`); the drag's write set — the cards MOVE, the write set does not (`D-132`); the tab record's repairs and routes; `['zones']`'s `slot`/`distance`/`size`/`display` as geometry, which a stored figure beside authored CSS would make `D-129`'s second authority (`D-177`); `['theme']` and the overlay's four-state machine; `src/shared/{zones,layout-projection,container}.ts`; either package (D-5).
- **THE UNIT IS THREE UNITS' WORK.** `D-177` sized it *two to three* and `D-181`'s reopened zone domain takes the top of that range — **and `D-183` adds a SECOND reopened domain (the panes, one id → two) plus the window's drag region, to `U1`/`U3`, without moving the count**; §3 tags every step with the unit that closes it, and each unit is independently closable on its own rows.

## 4. The fork rulings, folded in as constraints

- **`C-1` — the controls are the platform's.** `titleBarOverlay` only: the free area is `607×36` of a `720`-wide window and the page owns the whole window (`D-179`), so the logo sits at the free area's left, the tabs row inside the same strip, the buttons to their right — **no authored node, no dispatchable close, no screenshot as proof** (`D-178` §2).
- **`C-2` — what a mint needs, and what it does not.** The declared hook (an undeclared placement mint is REFUSED), a prototype resolvable BY NAME, a mandatory `placementName`, `keyField`, the in-process minting turn and `string`-`target` resolution (`D-179`, `D-181`, `D-182`). **It does NOT need placement routing** (`D-182`).
- **`C-3` — the static node list governs what is authored and what is minted.** The eighteen items are a static enumeration and are legal as nodes; one row per tab is not, so the tabs row is minted — and `derived` cannot carry `content`, so **no label is computed in the envelope**; each is painted by a turn (`D-177`).
- **`C-4` — one authority per attribute.** The two terminal pages' `display` belongs to the STAGE paint; the witness drive is re-grained onto it and never left beside it (`D-129`, `D-126`'s `F2` lesson).
- **`C-5` — the modal's scoping survives the re-parent.** The whole layout stands INSIDE `app-surface` so it goes inert under the modal, the overlay layer stays the root's FOLLOWING sibling so the scrim still covers the viewport, and the opener stays the root's last authored control (`D-178` §3, `D-113`).
- **`C-6` — the native menu's removal is priced and paid.** `Ctrl+Q`, `Ctrl+W`, `Ctrl+R`, `Shift+Ctrl+R`, `Ctrl+Shift+I`, `Ctrl+M`, `Ctrl+0/±` and `F11` go with it; only the edit keys survive as Chromium content behaviour. **Re-binding them is a keyboard surface the app has never had and is NOT this unit's** — until it exists `Ctrl+Q` does nothing (`D-181`).
- **`C-7` — the domain widens with its price in the same edit.** Four declared zone ids, a repair writing four empty records, **~19–25 collected rows over 6–7 files re-grained** and `Z-9`'s tombstone re-opened — the figure `D-177` measured and `D-181` accepted, never discovered later.
- **`C-8` — nothing routes pixels through a member.** The `zone` member is the repair's and a future relocation's; no step reads it to place anything, and nothing reads `['zones']`'s members for geometry (`D-177`, `D-182`).
- **`C-9` — the `zone` member is OPTIONAL, and its ABSENCE means the pane lives in the STAGE** (beside `C-8`, whose discipline it inherits). `zone` names a ZONE id and the four zones are `top`/`bottom`/`left`/`right`, so **the stage is not one of them**; `pane-a` STAYS the gutter pane (`D-183`) and `D-178` puts the cards inside the stage — **so `pane-a` has no zone to name, and a REQUIRED member would force it to state one it is not in, which is a false statement in an enforced shape and `D-129`'s defect class.** `D-183` derives the only consistent shape from those three inputs and this scope ADOPTS the derivation rather than restating it as a choice: **an absent `zone` is LAWFUL and is the third placement (`D-129` bites only where a value is stated).** A `zone` that names an UNDECLARED id is a fault: refused at `paneNodeAdmits`' second seat (`ASM-14`) and named in `PANE_UNUSABLE_MESSAGE`'s register (`D-105`), never silently dropped by the read. **"The repair owns it" is read as the set the repair writes and not as a rewrite of a standing value**: the family's existing value arm refuses a value it cannot state and repairs NOTHING (`D-105`), so the creation repair's product names declared ids only and can never be the fault. **Applied per pane** the derivation reads: `pane-a` carries no `zone` (the stage) and `pane-menus` carries `top` — its default, because absence would place it in the stage and contradict `D-180`/`D-181` — which is one shape read twice and not two shapes. **`D-181`'s "absent-or-undeclared is a fault" arm is SUPERSEDED BY POINTER, not reworded (`D-46`).**
- **`C-10` — the window drags from the top-bar, its three `css` items are `S-2`'s, and none of them can be measured** (beside `C-1`, the platform's chrome, and `C-6`, the accelerators it costs). With `titleBarStyle:'hidden'` the OS title bar is gone, so **unless an authored node carries `-webkit-app-region: drag` the window cannot be moved at all** (`D-183`): the top-bar carries `drag`, the tabs row carries `no-drag` so its rows stay clickable, and **the strip the native controls own carries NOTHING — the platform handles its own region, so the third of the three items is a deliberate ABSENCE and not a declaration a later author should hunt for.** All three are `S-2`'s, as `D-178`'s CSS half. **`-webkit-app-region` is compositor behaviour, invisible to a rendered-HTML read exactly as `overflow` is**, so `D-178`'s deliberate-unverified covers it, no gating row asserts it, and the app's movability is a recorded gap rather than an implied guarantee (§6, `D-183`).

## 6. Acceptance — measurable, and what is deliberately unmeasured

## 7. The risks, and what would make a step red

- **`S-1` under-scoped**: if a string `target` also needs a node-shaped accessor for the ATTACH turn, `U2` opens with a second runtime edit and `U1`'s green means less. Red: `S-4` cannot reach the target at all.
- **`S-2`'s re-parent**: the five cards moving into the landing page changes the gutter's PIXEL geometry while every drag row stays green — **a green that means less** (`D-177`). The mitigation is that no row's write set moves (`D-132`); a red on the write set is a design fault, a red on the pixels is not.
- **`S-3`/`AL-9`**: the overlay arm is proven by contract on a probe, not on the app (`D-179`). If the built window does not show it, the fork goes back to the user (`D-178` §2) — never to authored buttons.
- **`S-4`'s `keyField`**: without it ids churn on every delivery and anything written onto a row must be rewritten per delivery (`D-182`); `AL-4` reds.
- **`S-6`'s two authors**: a stage paint left BESIDE the witness drive gives the same two pages two `display` authorities — the class `D-129` refuses — and every row stays green while the surface flickers between them.
- **`S-10`'s whitelist**: a render-side `disabled` alone hands an agent `quit`; `AL-7` reds by killing the app it is measuring, which is why that row's failure mode is stated as its own death.
- **The zone re-grain** is where a silent weakening happens: a row that stops asserting a member while its name survives is the failure `D-152` closed before; every re-grained row is re-read, not reworded.
- **`OWED-1` — SETTLED at `D-183`: `pane-a` STAYS THE GUTTER PANE AND THE FAMILY WIDENS FOR THE MENUS PANE.** *The question as it was asked of the user:* the pane family was closed to ONE id (`D-138`) whose only writer is the drag's release (`view.commitPane(DEFAULT_PANE_ID, …)`), while `D-181` gave that family a `zone` and read it as the MENUS pane's — so did the resizable pane remain the family's subject, or did the family's one id become the menus pane? **Answered: neither is displaced** — `pane-a`'s subject is UNCHANGED, so the 115-row compliance battery, `panesMustStand`, the gating `renderer-wiring` rows and the `['drag']` machinery keep their subject and need NO re-grain, which is why that arm was chosen — **and `pane-menus` is declared beside it.** The price is `S-8`'s second id (a placeholder record, an admission arm, a repair writing two ids) **plus the panes re-grain §6 names, paid in the same edit as the zone's.** `D-181`'s reading of the family as the menus pane's alone is SUPERSEDED BY POINTER (`D-46`).
