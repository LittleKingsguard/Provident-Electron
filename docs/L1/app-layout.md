## 1. What this unit is, and what it does not touch

- The interface is **six authored pieces**: the **top-bar** (a logo/name `content` string at its left, the tabs row in the middle, the platform's own controls to the right), the **four fixed zones** (`top`, `bottom`, `left`, `right`), the **stage** between them, a **tabs row that renders the record AND switches it**, and a **menus pane** of eighteen authored items. What the tree has is **one root node carrying five cards, two terminal pages and an overlay layer** — no top-bar, no zone, no stage, and no window controls in any form (`D-176`); the zone renderer was deleted as dead surface at `D-169`.
- **THE GEOMETRY IS THREE SENTENCES, AND THEY ARE THE UNIT'S SUBJECT** (`D-185`, `D-187`, `D-189`): **the four ZONES own the dimension they fix** (a height for `top`/`bottom`, a width for `left`/`right`) and the **STAGE is DERIVED** from the remainder, storing nothing and repairing nothing; **a PANE fills its zone's fixed axis, ADJUSTS the orthogonal one and SCROLLS along the axis it adjusts**; and **a pane's `width` and `height` are TWO stored members**, the zone selecting which one is painted, so the unpainted one is memory rather than a second authority. §4 states them as `C-11`…`C-13`; the handles they place are `S-2`'s and the migration they cost is §5's.
- **THE WINDOW'S CHROME IS THE ONE PLACE UI AUTHORITY STOPS** (`D-177`): the three buttons are the PLATFORM's, in an area the page does not own — measured `visible:true`, `getTitlebarAreaRect()` `[0,0,607,36]`, the page owning the whole window (`D-179`) — so this unit authors **no window control and no dispatchable close** (`D-178` §2).
- **THE TABS ROW IS THE APP'S FIRST NON-`state-slice` WRITE** (`D-178` §1): the envelope's node list is STATIC, so one node per `['tabs'].order` entry is a MINT (`D-177`) — and **a minted row renders wherever its TARGET lives**, with `keyField` keeping its id stable across deliveries (`D-182`). **No step below relies on placement routing**: post-bootstrap routing does not work and is recorded upstream-owned (`D-182`, `D-5`/`D-52`), so the `zone` member is DECLARATIVE and every pane and row is authored where it belongs.
- **The switch act adds no crossing route.** `tabs-client.ts` is read-only by contract and the realm's own `focusActRoute` gains a DOM-originated caller — the `attach` form theme already has (`D-177`) — so `store-tabs-record` is named and NOT claimed (§2).
- **THE MENUS ARE THE HAZARD AT EIGHTEEN TIMES THE GRANULARITY** (`D-180`): an authored item is a handler body, and `provident.dispatch` reaches every one of them in the default grant (`['read','dispatch']`). So the pane renders eighteen and the ROUTE admits eleven, and the refusal is enforced in `main` — where the grant stops — and not only by an authored `disabled` (`D-181`).
- **What this unit does NOT touch**: the isolated pane graph and its capability UI (`D-113`); the drag's write set — the cards MOVE, the write set does not (`D-132`); the tab record's repairs and routes; **`['zones']`'s `slot`/`distance`, which stay UNREAD as the relocate candidate's residue** — the two members that now *do* have readers, `size` and `display`, are read by the paint and never by a projection module (`D-185`, `D-169`); `['theme']` and the overlay's four-state machine; `src/shared/{zones,layout-projection,container}.ts`; either package (D-5).
- **THE UNIT IS THREE UNITS' WORK.** `D-177` sized it *two to three* and `D-181`'s reopened zone domain takes the top of that range — **`D-183` added a SECOND reopened domain plus the window's drag region, and `D-188`/`D-189` add two battery rows and a stored-member migration, none of which moves the count**; §3 tags every step with the unit that closes it, and each unit is independently closable on its own rows.

## 4. The fork rulings, folded in as constraints

- **`C-1` — the controls are the platform's.** `titleBarOverlay` only: the free area is `607×36` of a `720`-wide window and the page owns the whole window (`D-179`), so the logo sits at the free area's left, the tabs row inside the same strip, the buttons to their right — **no authored node, no dispatchable close, no screenshot as proof** (`D-178` §2).
- **`C-2` — what a mint needs, and what it does not.** The declared hook (an undeclared placement mint is REFUSED), a prototype resolvable BY NAME, a mandatory `placementName`, `keyField`, the in-process minting turn and `string`-`target` resolution (`D-179`, `D-181`, `D-182`). **It does NOT need placement routing** (`D-182`).
- **`C-3` — the static node list governs what is authored and what is minted.** The eighteen items are a static enumeration and are legal as nodes; one row per tab is not, so the tabs row is minted — and `derived` cannot carry `content`, so **no label is computed in the envelope**; each is painted by a turn (`D-177`).
- **`C-4` — one authority per attribute.** The two terminal pages' `display` belongs to the STAGE paint; the witness drive is re-grained onto it and never left beside it (`D-129`, `D-126`'s `F2` lesson).
- **`C-5` — the modal's scoping survives the re-parent.** The whole layout stands INSIDE `app-surface` so it goes inert under the modal, the overlay layer stays the root's FOLLOWING sibling so the scrim still covers the viewport, and the opener stays the root's last authored control (`D-178` §3, `D-113`).
- **`C-6` — the native menu's removal is priced and paid.** `Ctrl+Q`, `Ctrl+W`, `Ctrl+R`, `Shift+Ctrl+R`, `Ctrl+Shift+I`, `Ctrl+M`, `Ctrl+0/±` and `F11` go with it; only the edit keys survive as Chromium content behaviour. **Re-binding them is a keyboard surface the app has never had and is NOT this unit's** — until it exists `Ctrl+Q` does nothing (`D-181`).
- **`C-7` — the domain widens with its price in the same edit.** Four declared zone ids, a repair writing four empty records, **~19–25 collected rows over 6–7 files re-grained** and `Z-9`'s tombstone re-opened — the figure `D-177` measured and `D-181` accepted, never discovered later.
- **`C-8` — nothing routes pixels through a member, and the `zone` member does not state a size.** `zone` SELECTS WHICH pane member is adjustable (`C-11`) — it is never a figure and never a placement instruction; no step reads it to place anything, and `slot`/`distance` are still read by nothing (`D-177`, `D-182`, `D-185`). **The two `['zones']` members with readers are the paint's** (`size`, `display`), and their reader is a `css.style` write — not a projection.
- **`C-9` — the `zone` member is OPTIONAL, and its ABSENCE means the pane lives in the STAGE** (beside `C-8`, whose discipline it inherits). `zone` names a ZONE id and the four zones are `top`/`bottom`/`left`/`right`, so **the stage is not one of them**; `pane-a` STAYS the gutter pane (`D-183`) and `D-178` puts the cards inside the stage — **so `pane-a` has no zone to name, and a REQUIRED member would force it to state one it is not in, which is a false statement in an enforced shape and `D-129`'s defect class.** **An absent `zone` is LAWFUL and is the third placement** (`D-129` bites only where a value is stated); a `zone` naming an UNDECLARED id is a fault: refused at `paneNodeAdmits`' second seat (`ASM-14`) and named in `PANE_UNUSABLE_MESSAGE`'s register (`D-105`), never silently dropped by the read. **The derivation reads as one shape twice**: `pane-a` carries no `zone` (the stage) and `pane-menus` carries `top` — its default, because absence would place it in the stage and contradict `D-180`/`D-181`. **`D-181`'s "absent-or-undeclared is a fault" arm is SUPERSEDED BY POINTER, not reworded (`D-46`).**
- **`C-10` — the window drags from the top-bar, its three `css` items are `S-2`'s, and none of them can be measured** (beside `C-1`, the platform's chrome, and `C-6`, the accelerators it costs). With `titleBarStyle:'hidden'` the OS title bar is gone, so **unless an authored node carries `-webkit-app-region: drag` the window cannot be moved at all** (`D-183`): the top-bar carries `drag`, the tabs row carries `no-drag` so its rows stay clickable, and **the strip the native controls own carries NOTHING — the platform handles its own region, so the third of the three items is a deliberate ABSENCE.** **`-webkit-app-region` is compositor behaviour, invisible to a rendered-HTML read exactly as `overflow` is**, so no gating row asserts it and the app's movability is a recorded gap rather than an implied guarantee (§6).
- **`C-11` — ONE MEMBER PER AXIS, AND THE ZONE SELECTS WHICH ONE IS PAINTED** (`D-189`, which SUPERSEDES `D-186`'s "one `size`, two axes" by pointer). `['panes', id]` carries **`width` and `height`, BOTH STORED**, and the member's own name says its axis: **in a `top`/`bottom` zone the pane's `width` is painted and the ZONE's `size` is the height; in `left`/`right` the ZONE's `size` is the width and the pane's `height` is painted; in the stage both are the pane's.** **The non-painted member is RETAINED, NOT DEAD** — it is the memory that stops a zone change reusing one value, and it is not a second authority because at any instant exactly ONE figure is painted per axis. **`bounds` is one optional pair read against the ADJUSTABLE axis**: stored for `pane-a`, absent-and-lawful for a zone-resident pane whose clamp is the layout's, and **no repair reads `['zones']`** (`D-186`, unchanged).
- **`C-12` — A PANE FILLS, ADJUSTS AND SCROLLS; A STAGE PANE IS A SIDEBAR PANE** (`D-187`). A pane **FILLS** the axis its zone fixes, **ADJUSTS** the orthogonal one and **SCROLLS along the axis it adjusts**, because that is the only axis whose own size can be smaller than its content: `top`/`bottom` → `overflow-x`, `left`/`right` → `overflow-y`. **A ZONE WITH SEVERAL PANES SCROLLS THE ARRANGEMENT AXIS WHILE EACH PANE SCROLLS ITS CONTENT — the zone's `overflow-*` and the pane's are TWO NESTED CONTAINERS ON THE SAME AXIS**, which is how *"all scroll internally"* and this rule stop contradicting each other. **A stage pane behaves as a sidebar pane behaves** — one case fewer, and the sentence to contradict if the user wants the stage specified differently — so `pane-a` adjusts its height as it always has.
- **`C-13` — THE HANDLE SITS WHERE THE ADJUSTABLE AXIS CAN MOVE IT** (`D-189`): a **horizontally-oriented** pane — one in a `top`/`bottom` zone, whose adjustable axis is the width — carries its handle at the **LEFT EDGE**; a **vertically-oriented** one — a sidebar pane, adjusting height — at the **TOP-RIGHT**. **`pane-a` carries no `zone` (`C-9`), so `C-12` makes it sidebar-equivalent, and its handle MOVES to the top-right** — with its `axis` and cursor re-authored — and the migration bill (the demo's `[data-gutter-handle]` selector, its drive and every row whose subject is that element's position or axis) is named in §5 and paid in the same edit (`D-189`, `D-146`).
- **`D-184` IS SUPERSEDED BY POINTER AND NO CLAUSE HERE IMPLEMENTS IT** (`D-46`, `D-185`): its *"the pane record's `size` IS the top zone's height"* is REVERSED — the pane's figure never reaches a zone and the paint's subject is the ZONE. It is cited so a reader who finds only it cannot conclude the pane owns the height: **the pane owns the adjustable axis, the zone owns the fixed one, and the stage owns nothing.**
