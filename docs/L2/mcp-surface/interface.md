## 2. What the surface does with a call

- **Three steps and no more**: validate the declared argument shape, make ONE invoke over the seam, answer what the renderer answered, verbatim (D-18); a second identical call is a second invoke and never a cache hit (D-18).
- **The act itself is not here**: the renderer's `focus` route composes the record from its own committed reading and hands it to the existing `data.write` route; this surface hands the caller's two members through and transforms nothing (D-136, D-142).
- **The tier is not decided here either**: the renderer names `file`, the declared-root guard judges the request and the record's own `exactly-one-active` repair judges the value, so the tool neither names a tier nor answers for one (D-101, D-140, D-142).
- **Nothing is held between calls**: no state, no map, no registry, no minted id and no memo of the last answer (D-18).

## 3. The answer shape — the reading the route answered, member by member

`focusHandler` answers whatever the seam answered, and the seam answers the renderer's `focusActRoute`, whose declared type is `TabsClientReading & { refused?: FocusRefusal }` — FLAT, so a reading's `status` and a refusal's cannot collide on one key (`src/renderer/renderer.ts`'s `FocusActAnswer`). One object, three arms:

| Arm | Members | What each one is | Cite |
|---|---|---|---|
| **the act landed, or named no row** | `status`, `order`, `landing`, `rows`, `witness` | the CLIENT'S committed reading, copied verbatim (`src/renderer/tabs-client.ts`): `status:'committed'`, `order` the record's stored seat, `landing` the DERIVED active-tab id, `rows` one row per tab as re-read, and `witness` the client's own derivation over those rows — each terminal's `resolved` being what `Runtime.elementForNodeId` answered, `null` where the witness is false or no resolver was supplied | D-141, D-142, D-76 |
| **the act's write was refused, or the route declined to write** | the five above, plus `refused` | `refused` is the WRITER'S LEDGER, carried MEMBER FOR MEMBER (`FocusRefusal`, six): ALWAYS `{status:'refused', reason, message}` — the writer's `reason` and `message` where the store refused, or the route's own word where the route declined to write at all — plus `storeStatus`, `path` and `log` WHEREVER THE WRITER CARRIED THEM, each spread in only where answered, so no own `undefined` key is minted. The excluded members are `floor` and `through`, which ride the ledger's `cursor-unknown` arm alone, an arm this route's `write` composes on none; `log` is an enumerable array of plain records, which is exactly why a tool answer can carry it. The route's own two refusals (`malformed-arguments`, `target-absent`) carry the three always-present members and NO carried member | D-142, D-103, D-107, D-136, `ASM-10` |
| **no record stands to answer with** | the reading's OWN members, plus `refused` | carried UNCHANGED — `absent` `{status, reason}`, `unread` `{status, reason, detail}`, `refused` `{status, reason, message, address}` — with ONE object minted BESIDE it: `{status:'refused', reason: <the reading's own>, message: "the tab record answered '<status>', so this realm holds no record to compose over"}` (`unreadableOf`). **The surface re-spells and drops NONE of the reading's members**, and that sentence is the route's, not this tool's | D-127, D-142 |

- **`refused` is present on EVERY arm that refuses or declines, and ABSENT exactly where nothing was refused** (`ASM-7`) — never as `undefined`, and the docblock above `interface FocusRefusal` states the same rule in its own words.
- **The write's landed ledger is NOT the answer**: `repaired`, `cursor` and `log` are not echoed on a landed act, because echoing `data.write`'s ledger would couple an MCP answer's shape to a `data.*` write's members; the ledger rides `refused` ONLY, where it IS the judgement an agent is owed and a whole one (`ASM-10`).
- **`witness` is EVIDENCE and not the record**, and the deleted model's three members (`activeId`, `entries`, `opened`) survive in no arm (§4) (`D-142`).
- **The arms' key sets are asserted separately**, because `status` is what tells them apart and a single key-set equality over both would be satisfiable only by an answer the contract does not declare (D-142).

**The two failure classes, and the third that is neither:** (1) **the writing realm's refusals pass through as a VALUE** — `parent-absent`, `store-refused`, `declared-tier` and the store's own mapped words arrive as `refused.reason` with a sentence beside them, and this surface mints neither (D-101, D-136); (2) **the tool's own refusal is its ARGUMENTS' and the only class it mints** — a `TypeError` naming the rejected key or form, raised in `focusHandler` BEFORE any invoke, judging the argument HOLDER and never a member's value (D-141); (3) **the renderer's own statements travel as VALUES** — a reading that is not `committed` answers the third arm, and a target no row carries answers the record as read with the route's `target-absent` (D-142).

## 4. `newTab`, and a target that names no standing row

- **`newTab: true` opens one record row carrying the caller's `target` and seats it active** — one row, added once, and no standing row's bytes moved; the id is the renderer's mint (`tab-<n>`, through the existing `mintTabId`) and never the caller's target, so the tool invents no identity (D-142, D-117).
- **An act that names no row is no act**: no `target` means no write at all, and the answer is the record as read with NO `refused` member; **a `target` no standing row carries, with `newTab` not `true`, writes nothing** and answers the record as read with the route's own `target-absent` (D-18, D-142).
- **A `target` a standing row carries** seats that row and moves `order` not at all; the record's own `exactly-one-active` settles the pair (D-76, D-129, D-142).
- **`newTab` is carried uninterpreted BY THE TOOL** — no default and no `Boolean()` — while the ROUTE's own read is `newTab === true`, so only the boolean opens one; **a `target` that is not a string writes nothing and its refusal is the ROUTE'S VALUE**, `malformed-arguments`, never a throw (D-141, D-105, D-112).

## 5. The description and the schema's prose, as contract statements

- **What the words now say**: that the tool sets the ACTIVE TAB in the tab record, in the record's own terms and durably; that a repeated target activates its standing row and `newTab: true` opens one; that the answer is the record as re-read; and that the act mutates no graph node, emits no notification and renders no surface — each sentence the live description carries (D-141, D-142).
- **What no sentence says, BY SENSE**: that the tool ASKS a focus model, or names one as the target's HOLDER — the sense in which "the focus model" was the deleted mirror family's route. The sense that MAY stay is `the focus model` naming the RETAINED `src/shared/focus-model.ts`, which `D-141` leaves OPEN and which this tool consults not at all (D-141, D-142).
- **All three strings landed** — the `target` member reads "The opaque target the act seats — passed through uninterpreted. A non-string can be no tab row, so the route writes nothing and answers the refusal in `refused`." and `newTab`'s reads "Open one new tab row carrying the same target — carried uninterpreted; only the boolean true opens one, and no default is applied." — each replacing one string and moving no schema member's type, so no battery and no behaviour moved with them (D-18, D-30).
- **The surface's durability claim is the tier's, not a wish**: the act lands at `file`, the one durable tier, and the words say so because the record's own declaration is what holds it there (D-141, D-101).
- **The prose is not a battery's subject, but two things about the block ARE read**: the token scan for the three deleted names (`deletedShapeSites`) and — in `P-FT-RS-1` control (e) — the live description's own opening sentence as the scan's anchor; the schema's two `.describe()` strings sit inside that same region, which is why the writer's word moved them ahead of the scan (D-18, D-30).

## 10. The published set is the registry's composition

- **`ALL_TOOLS` stops being the whole set and becomes its FOUNDATION HALF**: the static entries stay exactly as they stand — one `ALL_TOOLS` member each, registered under their group — and the set `tools/list` answers is those entries PLUS one `module:<name>.<tool>` name per registered module tool, composed from the module registry's activations (`L1` §3 `S-5`; `src/main/mcp-server.ts`'s `ALL_TOOLS` and `allowedToolNames`). **The dynamic half's SOURCE is `module-system`'s** — `docs/L2/module-system/interface.md` §11's `activations()`, whose `tools` are already the full names — so this page composes and never re-derives (D-307).
- **The act that turns a TOOL CALL into a DELIVERY is the executor's, and this surface only publishes its verdict**: `module.install`/`module.update` hand their `source` to `install` (§2's installed-source delivery) and answer the verdicts it returns, while the set `tools/list` reads is the composition above — so no admission, no resolution and no activation is performed here (`docs/L2/module-system/interface.md` §11; `L1` §3 `S-1`…`S-5`).
- **The `module` group is the composition's group and it resolves BY PREFIX**: an exact `TOOL_GROUPS` row wins first, then any `module:<n>.<t>` name resolves to `module` (a `module:` with an empty rest is malformed and denied) — so a composed name needs no `TOOL_GROUPS` row and `ALL_TOOLS` need grow none (`src/main/security.ts`'s `groupForTool`; `L1` §1). **The group domain becoming registered DATA is `S-8`'s** and is stated there, not here.
- **The two-gate's breadth is MEASURED AND STATED PER INSTANT, because the tree's two arms are not the same predicate**: at CONSTRUCTION the `module.install`/`module.update` pair — trusted-equivalent to `code` — registers only while `module` AND `code` both stand, while `module.list` needs `module` alone AND a dynamic `module:<n>.<t>` name is admitted by its GROUP (`registeredToolNames`); at every RE-GATE each captured handle whose name begins `module.` or `module:` is toggled by the PAIR, so a `code` withdrawal also closes the census door (`regateLiveServer`); and at INVOCATION every call re-checks the pair, because a handle admitted at construction must not survive a `code` withdrawal (`invokeModuleTool`; `L1` §3 `S-5`). **A refused invocation is the protocol's error arm and not a value** — `D-105`'s value rule governs the module's ADMISSION refusals, which are `module-system`'s (§5 there).
- **And the namespace sits OUTSIDE the SDK's own naming rule, recorded rather than smoothed**: every composed `module:<n>.<t>` registration draws the SDK's `Tool name validation warning` on the `:`, a WARN and never a refusal, measured on this tree's own registration loop (`src/main/mcp-server.ts`'s dynamic-tool arm) — so a later release that made it fatal would close the namespace this design fixes, and no row of §7 asserts the absence of the warning.
- **What the transport REFUSES to publish, said so absence is a refusal and not an omission**: a module that is disabled, quarantined or not activated contributes NO name (`syncModuleRouter` registers the loaded set only); a name whose group is off is ABSENT from `tools/list` rather than present-and-refusing; and `ALL_RESOURCES` gains nothing — the composition is tools and groups and never a resource (`src/main/mcp-server.ts`'s `ALL_RESOURCES`, `brief.md` §2's three read there).

## 11. The one application-version authority

- **`serverInfo.version` reports `appVersion()`, and the `'0.1.0'` literal inside `createServer`'s `new McpServer(…)` construction retires into it**: the accessor is declared at `docs/L2/module-system/interface.md` §8, the resolver judges `requires.app` against the same answer, and this surface is its SECOND reader and never a second authority (`L1` §4 `C-11`; `src/main/mcp-server.ts`'s `createServer`).
- **The number is the BUILD's, and the drift is a row**: `I-3` holds the published number to `package.json`'s own `version` member, and it is a CONTROL because the literal and the manifest agree at this head — its bite is the day the literal stops tracking the manifest (`D-44`, `L1` §6's `M-5` drift-control rule, `D-26`).
- **What it does not do**: no tool answer gains a `version` member, no tool takes one as an argument, and no `requires.app` is judged here — the judgement is the resolver's, and this page only reports the number it judged against (`L1` §4 `C-11`).

## 12. Re-registration on activation

- **Today the live server's REGISTRATION is built ONCE**: `createServer` registers `allowedToolNames()` into it, and only a re-gate's WIDEN arm adds a name afterwards — the registry is re-read on every install (`syncModuleRouter`), the server is not — so a module installed or updated at run time is in NO live server's set, which is the reading the L1 battery records at this head (`src/main/mcp-server.ts`'s `createServer`/`regateLiveServer`, `syncModuleRouter`'s caller).
- **After `S-5` an ACTIVATION re-registers on the LIVE server**: the tool set moves, the new name answers, and the withdrawn one goes, with no rebuild and no second boot — on `stdio` (the long-lived server) and, because `http` builds a fresh server per POST from the current gate, on that transport by construction (`src/main/mcp-server.ts`'s two transport setup sites; `L1` §3 `S-5`).
- **And the mechanism is the ONE the re-gate already owns**: the captured `RegisteredTool` handles stay the single set the exclusion and the group axes toggle, so an activation ADDS and a deactivation WITHDRAWS through the same map and the three mechanisms cannot describe two different sets (`src/main/mcp-server.ts`'s `registered`; `D-123`'s one-mechanism rule read at the registry).
