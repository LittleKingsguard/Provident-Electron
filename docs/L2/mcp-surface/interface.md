## 2. What the surface does with a call

- **Three steps and no more**: validate the declared argument shape, make ONE invoke over the seam, answer what the renderer answered, verbatim (D-18); a second identical call is a second invoke and never a cache hit (D-18).
- **The act itself is not here**: the renderer's `focus` route composes the record from its own committed reading and hands it to the existing `data.write` route; this surface hands the caller's two members through and transforms nothing (D-136, D-142).
- **The tier is not decided here either**: the renderer names `file`, the declared-root guard judges the request and the record's own `exactly-one-active` repair judges the value, so the tool neither names a tier nor answers for one (D-101, D-140, D-142).
- **Nothing is held between calls**: no state, no map, no registry, no minted id and no memo of the last answer (D-18).

## 3. The answer shape — the reading the route answered, member by member

`focusHandler` answers whatever the seam answered, and the seam answers the renderer's `focusActRoute`, whose declared type is `TabsClientReading & { refused?: FocusRefusal }` — FLAT, so a reading's `status` and a refusal's cannot collide on one key (`src/renderer/renderer.ts`'s `FocusActAnswer`). One object, three arms:

| Arm | Members | What each one is | Cite |
|---|---|---|---|

| **the act's write was refused, or the route declined to write** | the five above, plus `refused` | `refused` is the WRITER'S LEDGER, carried MEMBER FOR MEMBER (`FocusRefusal`, six): ALWAYS `{status:'refused', reason, message}` — the writer's `reason` and `message` where the store refused, or the route's own word where the route declined to write at all — plus `storeStatus`, `path` and `log` WHEREVER THE WRITER CARRIED THEM, each spread in only where answered, so no own `undefined` key is minted. | **no record stands to answer with** | the reading's OWN members, plus `refused` | carried UNCHANGED — `absent` `{status, reason}`, `unread` `{status, reason, detail}`, `refused` `{status, reason, message, address}` — with ONE object minted BESIDE it: `{status:'refused', reason: <the reading's own>, message: "the tab record answered '<status>', so this realm holds no record to compose over"}` (`unreadableOf`). **The surface re-spells and drops NONE of the reading's members**, and that sentence is the route's, not this tool's | D-127, D-142 |

- **`refused` is present on EVERY arm that refuses or declines, and ABSENT exactly where nothing was refused** (`ASM-7`) — never as `undefined`, and the docblock above `interface FocusRefusal` states the same rule in its own words.
- **The write's landed ledger is NOT the answer**: `repaired`, `cursor` and `log` are not echoed on a landed act, because echoing `data.write`'s ledger would couple an MCP answer's shape to a `data.*` write's members; the ledger rides `refused` ONLY, where it IS the judgement an agent is owed and a whole one (`ASM-10`).
- **`witness` is EVIDENCE and not the record**, and the deleted model's three members (`activeId`, `entries`, `opened`) survive in no arm (§4) (`D-142`).
- **The arms' key sets are asserted separately**, because `status` is what tells them apart and a single key-set equality over both would be satisfiable only by an answer the contract does not declare (D-142).

**The two failure classes, and the third that is neither:** (1) **the writing realm's refusals pass through as a VALUE** — `parent-absent`, `store-refused`, `declared-tier` and the store's own mapped words arrive as `refused.reason` with a sentence beside them, and this surface mints neither (D-101, D-136); (2) **the tool's own refusal is its ARGUMENTS' and the only class it mints** — a `TypeError` naming the rejected key or form, raised in `focusHandler` BEFORE any invoke, judging the argument HOLDER and never a member's value (D-141); (3) **the renderer's own statements travel as VALUES** — a reading that is not `committed` answers the third arm, and a target no row carries answers the record as read with the route's `target-absent` (D-142).

## 4. `newTab`, and a target that names no standing row

- **`newTab: true` opens one record row carrying the caller's `target` and seats it active** — one row, added once, and no standing row's bytes moved; the id is the renderer's mint (`tab-<n>`, through the existing `mintTabId`) and never the caller's target, so the tool invents no identity (D-142, D-117).
- **An act that names no row is no act**: no `target` means no write at all, and the answer is the record as read with NO `refused` member; **a `target` no standing row carries, with `newTab` not `true`, writes nothing** and answers the record as read with the route's own `target-absent` (D-18, D-142).
- **A `target` a standing row carries** seats that row and moves `order` not at all; the record's own `exactly-one-active` settles the pair (D-76, D-129, D-142).
- **`newTab` is carried uninterpreted BY THE TOOL** — no default and no `Boolean()` — while the ROUTE's own read is `newTab === true`, so only the boolean opens one; **a `target` that is not a string writes nothing and its refusal is the ROUTE'S VALUE**, `malformed-arguments`, never a throw (D-141, D-105, D-112).

## 10. The published set is the registry's composition

- **`ALL_TOOLS` stops being the whole set and becomes its FOUNDATION HALF**: the static entries stay exactly as they stand — one `ALL_TOOLS` member each, registered under their group — and the set `tools/list` answers is those entries PLUS one `module:<name>.<tool>` name per registered module tool, composed from the module registry's activations (`L1` §3 `S-5`; `src/main/mcp-server.ts`'s `ALL_TOOLS` and `allowedToolNames`). **The dynamic half's SOURCE is `module-system`'s** — `docs/L2/module-system/interface.md` §11's `activations()`, whose `tools` are already the full names — so this page composes and never re-derives (D-305).
- **A COMPOSED NAME'S CALL REACHES ITS HANDLER THROUGH THE EXECUTOR'S `invoke` DOOR, AND THE NAMES AND THE HANDLERS ARE ONE EXECUTOR'S TWO ANSWERS**: a call on a `module:<n>.<t>` name is handed to `invoke(toolName, args)` — that page's §11, its fifth member — and to NO router, so the set `tools/list` publishes and the handler a call reaches are read off the same records at the same instant and cannot describe two sets. The name travels as the published `module:<name>.<tool>` (injective by that page's §1 namespace rule), `args` travels BY IDENTITY with no schema, no coercion and no wrapper beside it, and the answer is the handler's own value VERBATIM. **AND THE ARM'S OWN DECLARED SCHEMA IS WHAT DECIDES WHETHER `args` CAN TRAVEL BY IDENTITY, WHICH IS THIS REV'S ONE BEHAVIOURAL FINDING**: that arm declares `inputSchema: {}` for every composed name (`src/main/mcp-server.ts`'s dynamic-tool arm), the SDK parses each call against it and hands the handler `parseResult.data` (`mcp.js`'s `validateToolInput`), and an empty shape's parse answers `{}` — so a caller's members are STRIPPED to an empty object BEFORE `invokeModuleTool` is reached, and the arm cannot carry an argument at all as it stands. So the route's landing is the call site's substitution **and** that declaration's removal or passthrough in the SAME act, §1's `provident.focus` schema being the shape this surface already keeps for exactly that reason (a `passthrough` schema, so a bad call reaches the declared refusal instead of being stripped) — and until both move, the door's identity claim about `args` is DECLARED here and carried by no arm (`docs/L2/module-system/interface.md` §11; §12).
- **AND THE REALM HALF MINTS NO `module:<n>.<t>` TOOL NAME, which is why the route could not stay where rev 7 left it**: `src/renderer/extensions.ts`'s `CapabilityRouter` declares `registerModule`/`modules`/`listeners`/`actions`/`contributions`/`fire`/`withdraw` and no tool table at all — no `listTools`, no `invokeTool`, no `clear` — and the ctx it hands an entry is exactly the five CLIENT members, `tool` being main's alone (`docs/L2/module-system/interface.md` §3). Its `moduleHandle` mints `module:<n>#<key>`, a DECLARATION handle and a different namespace from the published `module:<n>.<t>` name, so the realm needs no tool name to do its work. So `router.listTools()` for the listing and `router.invokeTool(…)` for the call stand on no declared member at this head, and the store→router→tool chain `syncModuleRouter` closes today lands on a half that no longer holds the names: **the tool table is the executor's, and this page publishes names it is given** (D-305, §12).
