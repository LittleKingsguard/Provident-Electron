## 1. The command surface as it stands, measured at this head

`applyCommand` is the realm's one managed-channel entry: **`applyCommand(cmd: { kind: string; node?: string; [k: string]: unknown } | null | undefined): { status: string; dirtied?: string[]; minted?: string[] }`** (`src/renderer/runtime.ts`, `applyCommand`'s signature). Its resolution discipline is **three facts, and the third is the gap**:

- **A string `node` RESOLVES, and a string that does not resolve is REFUSED BEFORE THE ENGINE SEES IT**: `applyCommand`'s `node`-string guard calls `resolveTarget` and answers `{ status: 'rejected' }` for an unknown string — never a throw, because the raw string would otherwise reach `source.clone()` in the node-less clone-instance op (the adversarial `A3` fix, stated at the guard).
- **An OBJECT `node`/`source` must be a REGISTERED, undestroyed Node** — the `F5` registry gate beside that guard, whose test is `isRegisteredNode` — and a plain object masquerading as one is refused the same way, again a refusal and never a throw.
- **`target` IS NOT RESOLVED AT ALL, AND IS NOT EVEN NAMED IN THE DECLARED TYPE**: it arrives through the index signature as `unknown` and reaches `supervisor.apply` untouched, which is exactly `D-179`'s finding — **a `rows-mint`'s `target` must be a live Node OBJECT**, so the only mint that works today is one no JSON or IPC caller can send.

**AND WHAT THE ENGINE ANSWERS ONCE IT IS REACHED IS NOT THIS ARM'S** (`D-182`): an undeclared hook, an unresolvable prototype name, a missing `placementName` and a malformed `rows` each answer their own engine code — `hook-kind-mismatch`, `rows-prototype-unresolved`, `rows-placement-name-missing`, `rows-shape-invalid` — verbatim, with no throw. The distinction §2 keeps is that **`rejected` is THIS realm's word for a command it cannot resolve**, and those four are the engine's for a command it resolved and then judged.

## 2. The addition — `string`-`target` resolution, mirroring the `node` arm

**THE SIGNATURE GAINS THE MEMBER IT ALREADY ACCEPTS**, and nothing else about it: **`applyCommand(cmd: { kind: string; node?: string; target?: string; [k: string]: unknown } | null | undefined): { status: string; dirtied?: string[]; minted?: string[] }`** — `target` is declared as a `string` where it is a reference, the object form staying where it stands through the index signature because **it is the engine's** (§3).

- **THE RESOLUTION IS THE `node` ARM'S, MEMBER FOR MEMBER** (`D-179`): a string `target` resolves through the SAME resolver the `node` arm uses — `resolveTarget`, whose string path is a node id, then `css.id`, then `props.id` — and the resolved id is substituted into the payload as the live Node from `supervisor.getNode(id)` before `supervisor.apply`, which is the substitution `applyCommand` already performs for `node` when it builds its payload. **A caller therefore names the mint's target the way it already names a write's node** — one spelling for both members, and no second resolver to drift.
- **AN UNRESOLVABLE STRING IS A REFUSAL AND NOT A THROW**, and the word is the one already in the surface: **`{ status: 'rejected' }`**, answered at the `node`-string guard's own place and ahead of `supervisor.apply` — **so no new status word enters the surface, a raw string never reaches `supervisor.apply`, and the arms are one predicate read twice** (`D-179`, `D-182`).
- **A RESOLVED TARGET IS THE LIVE OBJECT THE ENGINE REQUIRES**: the mint's `target` is a Node by the time the engine sees it, which is the whole of what `D-179`/`D-182` measured — an in-process caller can pass the id its element lookup gave it instead of the element itself, and the `rows-mint`'s answer (`{status, dirtied, minted}`) is unmoved.

## 3. Containment — what this rev does not touch, stated as a list

- **NO OBJECT-`target` GATE IS ADDED** (`docs/L1/app-layout.md` §2, `D-179`): the object arm is the engine's and this rev claims nothing about it — a plain-object `target` is neither admitted nor refused HERE, and `D-179`'s requirement that a `target` be a live Node stays where it is enforced today, in the engine's own compile.
- **NO NEW `kind`, NO NEW COMMAND AND NO NEW RESOLVER** (`D-182`): the arm is the `node` arm's, applied to a second member; `resolveTarget` gains no branch, and no command's shape is judged differently.
- **NO WIRE BYTE AND NO BRIDGE** (`D-182`, and `docs/L1/app-layout.md` §2's `app-shell` row): `applyCommand` is in-process; this module owns no channel, no `ipcMain.handle` site, no preload member and no `window.provident` surface, so `app-layout`'s `endpoints` figure does not move for this step — the `7 → 8` the scope carries is `app-shell`'s ONE route and not this page's (`D-43`: a carried figure, recountable at L2).
- **THE MINTING TURN IS NOT DESIGNED HERE** (`D-177`, `D-179`): it is `src/renderer/renderer.ts`'s and `renderer-wiring`'s L2 seat's, cited and never re-derived — this page states what the RUNTIME admits, not what a caller does with it.
- **NO EXISTING ROW MOVES** (`D-179`, `D-182`): the refusals, the `rejected` word and the answers above are the head's, so a command naming neither a `target` nor an unresolvable one behaves exactly as it behaved.
