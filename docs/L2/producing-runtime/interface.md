## 1. The command surface as it stands

- **`applyCommand(cmd)` is the realm's one managed-channel entry** (`src/renderer/runtime.ts`, its own site): a `string` `node` resolves and an unresolvable string is `{status:'rejected'}` before the engine sees it; an object `node` must be a registered, undestroyed node (the `F5` gate); and a `string` `target` resolves through the SAME resolver as `node`, with an unresolvable one refused by the same word — rev 1's cell, carried (`D-179`, `D-182`).
- **The engine's four operand refusals are the engine's** (`hook-kind-mismatch`, `rows-prototype-unresolved`, `rows-placement-name-missing`, `rows-shape-invalid`), answered verbatim and never thrown; `rejected` is THIS realm's word for a command it could not resolve (`D-182`).
- **The rest of the surface is carried by the module's existing tests and is not re-derived here**: `bootstrap`, `load`, `op`, `journal`, `export`/`validate`, `dispatch`, `renderedHtml`/`markdown`/`listTargets`/`nodeState`, the id index, and the code.* methods. This page states the three cells the modularity unit adds.

## 2. The pre-build contribution point (`S-14`, `S-15`)

- **THE POINT IS THE CONSTRUCTOR, AT THE ENVELOPE COMPOSITION BEFORE `translateLegacy`** (`C-6`, `S-14`): `RuntimeOptions` gains an ordered reader — the module-system resolver's answer, each element `{parent: string; nodes: readonly Readonly<Record<string, unknown>>[]}` (`GraphContribution`, the contract's shape) — and the constructor merges each contribution's nodes into the authored template under its `parent`'s `children`, BEFORE `translateLegacy`, so a module's addition is graph DATA and never a post-compile transform or hand-written DOM (`C-6`, `D-304`).
- **THE ORDER IS THE READER'S AND THE RUNTIME SORTS NOTHING**: the foundation's own nodes exist before any module's, because the list is the resolver's total order (`S-15`, `C-11`); a module that requires another activates after it, and no caller re-sorts.
- **A THROWING CONTRIBUTION IS CONTAINED AND NAMED, AND THE BOOT NEVER TAKES THE FATAL ARM** (`S-14`, `D-124`): the runtime catches a contribution's throw, names it in the census/warnings the boot already carries, and continues — a module's fault is never the app's (D-80's fatal arm is the store's and never this). **A contribution whose parent id does not stand is the same class**, named rather than silently dropped.
- **NO NEW MCP SURFACE AND NO NEW TRANSPORT** (`D-18`): the point is in-process, read at construction; `provident.load` and the MCP routes are unmoved.

## 3. The post-bootstrap compile (`S-16`)

- **`applyCommand`'s compile HONOURS `getCompileMode()`** (`D-314`): after `supervisor.apply`, the dirty node's focused slice is compiled with `compilePath()` per member when the supervisor answers `'path'`, and `node.compile(slice, {focusNodeId})` is kept byte-for-byte when it answers `'family'`. **THE RENDER IS NOT DELEGATED TO THE SUPERVISOR'S PASS-2**: the command's synchronous answer is what `provident.op` composes its rendered read from (`C-7`).
- **`attach` needs no `registerNode` before it at `0.6.0` (register-if-new, idempotent)**, and **STILL needs a `detach` first on a freshly translated node** — that node carries its own `child` owner-token anchor and `attach` would answer `rejected single-parent` (`C-7`, `H-1`'s surviving (i)).
- **THE ROW IS `M-16`**: renders THROUGH the host path (`provident.op` → `applyCommand`) under a placement-routed bootstrap and asserts the appended child INSIDE its parent with a rendered read, five ids; the row ENTERS the mode first, because the app's authored envelope records family states (`S-16`).

## 4. The authored-envelope composition — `contribute` (`S-20`'s runtime module)

- **THE RUNTIME STORES THE AUTHORED ENVELOPE IT WAS CONSTRUCTED WITH**: the constructor keeps a clone of the COMPOSED authored document as the composition source and as the `code.*` CRUD's document. Today `this.envelope` is `null` until a `load`, so a boot-constructed runtime's `code.*` answers *"no envelope loaded"* — a measured class this rev fixes with the same field (`src/renderer/runtime.ts`'s `envelope` site, `codeGet`/`codeSet`).
- **`contribute(contributions)` MERGES A RUNTIME MODULE'S NODES INTO THAT STORED DOCUMENT AND RE-LOADS IT** (`S-20`, `C-6`): the merge is **the same routine `S-14`'s constructor runs** — `parent.children` found by the authored id, the reader's order, a throw/parentless/uncloneable contribution named and skipped — and the merged document re-loads through the construction path (`loadEnvelope`'s translate → register → render). **ONE COMPOSITION FUNCTION, TWO INSTANTS**: boot (the option, read once, before the first compile) and runtime (this member, after it). There is no second merge implementation and no second author of the template (`D-129`'s class).
- **WHY NOT THE SERIALIZER ROUTE (`exportLegacy` → merge → `loadEnvelope`)**: measured this pass at `src/shared/demo-envelope.ts` — **30 authored `handlers:`** entries — against the engine's `serializeNode`, which emits **no `handlers`** (`H-2`/`OWED-14`). That route would silently disarm the app's zone-collapse, gutter-drag, pane-move/collapse and tabs-add behaviours. **WHY NOT A RAW `LayerApplyOp`**: the engine's op needs a live `target: Node`, `decls: AnchorDecl[]` and `nodes: NodeBaseData[]` (`provident-ssr/dist/core/types.d.ts`), while a `GraphContribution` carries authored `LegacyNodeData`; building those from authored forests is a second translation, not a composition.
- **IT ANSWERS `{added, skipped, changed}`; every skip is NAMED in the runtime's warnings** — and **`changed` IS NOT `added.length > 0`**: a contributed forest carrying no authored id still reaches the document, so the flag is the MERGE's (`AN-6`'s measurement, where deriving it from ids silently dropped the forest), never a throw and never a half-attached subtree (`ASM-PR-2`'s class). A contribution naming a parent that does not stand is skipped whole.
- **THE RE-RENDER IS THE CALLER'S TO RE-DRIVE**: a re-load tears the graph down and renders the merged authored page; the delivery paints (tabs, view, shape) are the caller's turns, and `docs/L2/renderer-wiring/module-shape.md` §3 states that cost and the order it must keep.
- **THE MAP'S `endpoints` MOVES `17 → 18` FOR THE ONE NEW MEMBER** — L1's to file (`platform.md` §4, `D-14`).

## 5. What this page does not own

- **The ACTION installation is not this page's**: a module's `ctx.action(name, fn)` handlers are installed into live graph nodes by `renderer-wiring` through ONE `state-slice` with `targetProp:'handlers'` per node, the engine's declared handler target; the engine matches the handler's `name`/`event`, no source text enters graph data and no dispatch-time resolver exists (`C-10`, `D-313`). This page owns the composition and the compile; the action table is that seat's.
- **The resolver, the manifest and the contributions' production are `module-system`'s** (`docs/L2/module-system/interface.md` §7, §11): this page consumes the reader's answer and re-derives no ordering.
- **The pane declaration's grammar, and therefore `S-18`'s composed pane set, are `module-system`'s `S-17`** (`C-9`): `U2`'s declaration registry is not built, so the composed set this page would compose into does not yet exist; `renderer-wiring`'s map waits on it.
- **The rev-1 scope's rest remains the module's own**: the load/render/read surface, `dispatch`'s domain, the handler-body `apply` path and the engine-operand refusals are the module's existing rows and are not re-spelled here (`D-26`, `D-43`).

## 6. The battery and the assumptions

- **The integration rows live in `tests/integration/producing-runtime/`** (the path this page adds): `M-14`'s two arms — a contribution composed before the first compile, and a throwing contribution named while the boot continues — `M-15`'s order, and **rev 3's composition rows**: `contribute` adds a child under its parent with the authored handlers still dispatching afterwards, a parentless contribution named and skipped with the graph unchanged, and a boot-constructed `code.get('')` answering the authored document instead of *"no envelope loaded"*. **`M-16`** is the mode adoption's row in `tests/e2e/modularity/` (`S-16`); `M-18` is `renderer-wiring`'s.
- **`ASM-PR-1` — ONE composition function, called at two sanctioned instants: the constructor (via the option, once) and `contribute` (after the first compile).** Alternative rejected: `exportLegacy` → `loadEnvelope`, which drops the 30 authored handlers; and a raw `LayerApplyOp`, which needs engine-internal structures a contribution does not carry (`C-6`, `D-313`). A SECOND merge implementation remains rejected: `contribute` calls `composeContributions`.
- **`ASM-PR-2` — a throwing contribution is a named warning and the boot continues.** Alternative rejected: the fatal arm, which would make one module's fault the app's (`D-80`, `D-124`).
- **`ASM-PR-3` — the runtime stores its authored envelope, so `code.*` works before any load.** Alternative rejected: a separate `codeDocument` field, which would put two documents beside one document's edits (`D-129`).
