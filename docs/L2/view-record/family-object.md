## 0. Scope

This page fixes **the family object's I/O surface**: the one spec that goes in, the one object that comes out, the two halves' declared types, the literals the shape REFUSES, and the one row this module authors for it (`FH-1`, §5). It fixes no internals: the hunks, the bodies and the guardrails are L3's page and L4's landing (`D-3`, `D-292`). It also does not re-state what `interface.md` owns — the families, their tiers, the routes, the refusal vocabulary and the published-roots list are that page's (§1–§6), and the delivery's registration is `docs/L3/view-record/delivery.md`'s (`D-43`).

## 1. The surface, in one table

| | What crosses | Cite |
|---|---|---|
| **IN** | **ONE SPEC PER FAMILY.** `tag: 'paired' \| 'unpaired'` — the literal that NAMES the arm; `address`; `tier`, typed at this module's own tier alias (`ViewDeclaredRoot['tier']`, so a fourth word reds and no test spells the alias). **On the PAIRED arm only**: `id`, and the constraint body FACTORY `body: (getStore) => body`. | `D-292`, L1 §4 |
| **OUT** | **ONE OBJECT PER FAMILY, TWO HALVES.** `root` — a **VALUE**, `{ address, tier }`-shaped (`ViewDeclaredRoot`). `declaration(getStore)` — a **PROJECTION**, answering a `ViewConstraintDeclaration` or **`null`**. | `D-292`, L1 §4 |
| **NOT IN, NOT OUT** | No entry, no handle, no id, no listener, no store verb, no second registration route. The object DECLARES; the construction REGISTERS. | `D-292`, `D-71`, `D-219` |

- **THE ASYMMETRY BETWEEN THE TWO HALVES IS THE ORDER AND NOT A TASTE**: `viewDeclaredRoots()` takes no argument and the delivery is built **before** the store is bound (`D-219`'s holder order), while a body reads nothing at the registration instant (`D-124` iii). So **the half that needs a store is handed one and the half that does not is not** (`D-292`, L1 §4).
- **THE UNPAIRED ARM'S `declaration` IS `null` — never `undefined` and never `{}`**: `null` is a value a projection must TEST, while an absent or empty arm is one `.filter` from being dropped silently, which is the omission the unpaired arm exists to make explicit (`D-292`, `D-145`).
- **A ROOT WITH NO DECLARATION IS LAWFUL AND MUST STAY EXPRESSIBLE**: `['drag']` at `temp` is declared and unpaired by ruling, because no invariant holds a gesture transient and a repair whose subject is *"no drag has started"* would mint a placeholder for an absence that IS the product (`D-145`, `D-132`). **The guarantee runs one way**: a declaration always publishes its root; a root may publish no declaration (`D-292`, intake row 4).
- **BOTH PUBLICATIONS BECOME PROJECTIONS OF THE ONE TUPLE, so no caller changes**: `viewDeclaredRoots()` maps every spec's root and the constraint batch maps the PAIRED specs' declarations, in the tuple's order (`D-292`, `interface.md` §4). **`endpoints` moves nowhere and no address, route or tier is added** — the object declares what the crossings already declare (`D-137`, `D-145`, `D-43`).

## 2. The mechanism: a discriminated union on an explicit tag, and the arm that reds

**THE INPUT IS A DISCRIMINATED UNION ON AN EXPLICIT TAG, AND THE UNPAIRED ARM DECLARES ITS TWO PAIRED MEMBERS AS OPTIONAL `never`** — `readonly id?: never`, `readonly body?: never` (`D-292`, L1 §4). **The `?` is load-bearing**: a REQUIRED `never` member could not be satisfied by the lawful unpaired spec at all, so the optionality is what lets the arm exist (`D-292`).

- **(i) THE TAG CLOSES THE OMISSION**: a paired literal that dropped its body is missing a member its own tagged arm requires, and it is not the other arm — the other arm's tag is a different literal, so no member set of the union admits it (`D-292`, `D-72`).
- **(ii) THE `never` CLOSES THE CARRIAGE**: an unpaired spec carrying an `id` or a body is refused by **the member's type**, not by a literal's freshness, so a spec hoisted to a `const` and spread reds exactly as a fresh one — the arm excess-property checking can never reach (`D-72`, `D-292`).
- **BOTH HALVES ARE EPC-INDEPENDENT, WHICH IS THE PROPERTY THE REJECTED FORM LACKED**: an untagged `Paired | Base` union compiles a paired literal that dropped its body, because excess-property checking reads the union's WHOLE member set — so the refusal is a TAG plus a `never`, never a member's absence alone (`D-292`, `D-72`).
- **ITS ONE ESCAPE IS AN EXPLICIT `undefined`** (`id: undefined` compiles while `optional-property` exactness is off in the test project, `tsconfig.tests.json`), which is **named rather than hidden**: no projection can act on it, because `undefined` is the one value the arm's `null` discipline already separates from a declaration (`D-292`, L1 §4).
- **REJECTED FORMS, EACH WITH ITS COST**: `never` without a tag leaves the unpaired arm UNSTATED and `id` at `string | undefined` in both arms, so every projection narrows at runtime; a tag with OPTIONAL paired members classifies nothing and admits the blocker wearing a tag; the untagged union is refuted by measurement (`D-292`, L1 §4).
- **THE FIVE LITERALS THE SHAPE REFUSES AND THE TWO IT ADMITS, NAMED HERE SO A READER CAN CHECK EACH AND SO THE ROW CANNOT DROP ONE** (L1 §4). **REFUSED**, each by the arm named: a PAIRED-tagged spec carrying `address`, `tier` and `id` with **no `body`**; and a PAIRED-tagged spec with **no `id`** — both on the paired arm's own required members; an UNPAIRED-tagged spec carrying an **`id`**, and one carrying a **`body`** — each on `never` from the MEMBER's type, so a spec hoisted to a `const` and spread reds exactly as a fresh literal; and a spec at a **fourth tier word**, on the tier member (`D-292`, `D-72`). **ADMITTED**, and this is the control that the union is not merely always-red: a lawful PAIRED spec, and a lawful UNPAIRED one — a root with no pair (`D-292`, `D-145`).
- **AND ONE ARM MUST COMPILE RATHER THAN FAIL**, because it is what distinguishes this form from the `never`-only one rejected above: a **tag-narrowed read** of `spec.id` into a `string`, inside a `tag === 'paired'` branch, which the tagged union narrows and an unstated arm cannot (`D-292`, `D-72`). **THIS PAGE FIXES THE SHAPE AND THE DIRECTIVE THAT MEASURES IT IS THE UNIT ROW'S** — the five `@ts-expect-error` lines and the admitted controls are L3's `FH-3`, and an UNUSED directive is a red leg, so a shape that widened silences nothing quietly (`D-72`, `D-3`).

## 3. The exported names the unit's rows read

**NO LAYER BELOW MAY INVENT THESE, AND A ROW THAT REDS ON AN IMPORT MEASURES NOTHING** (`D-3`, `D-292` iv): the spec union `ViewFamilySpec` with its two arms `ViewPairedFamily` / `ViewUnpairedFamily`, the factory `viewFamily(spec)`, the module-scope tuple `VIEW_FAMILIES`, and the returned object `ViewFamily`. **Every name is NEW and the export is ADDITIVE**, so no counted export moves and no existing caller re-compiles differently (`D-292` iv, `D-43`).

- **THE TUPLE IS EXPORTED ON PURPOSE**: a row that measures the object's contract must read the object's own declaration set, and a module-private tuple would leave the headline claim measured by nothing — which is this unit's own root cause (`D-292`, `D-3`).
- **THE FACTORY IS DEFERRED BY CONTRACT**: `viewFamily(spec)` and `.root` produce no body; a body is built once per `declaration(getStore)` CALL and never at module scope, because a body that read or wrote at construction would be a store act before the store exists (`D-124` iii, `D-219`).

## 4. `FH-1` — what this module's row measures

**`tests/integration/store-view-record/declared-entries.test.ts`, unmarked and GATING**: authored after the rework sweep, so it carries no marker and its green is evidence (`D-40`, `D-30`). It compares **the delivery's `entries` addresses against `viewDeclaredRoots()`** — the hand-spelled listener list against the object's projection — and it reads both sides off the module's own exports (`createViewDelivery`, `viewDeclaredRoots`). **THE LISTENER SIDE CANNOT BE RE-SPELLED AT ALL** (`VIEW_DECLARED_ADDRESSES` is module-private, so that list is reachable only through the builder) **and the ROOT side is not re-spelled here**: it is `viewDeclaredRoots()`'s own literal set, read through the projection the tier guard is fed from (`D-53`, `D-101`, `D-137`).

| Arm | The assertion | Cite |
|---|---|---|
| **(a)** | **Set equality of the two address lists, BOTH directions**: no published root without an entry, and no entry at an address no root publishes — the first is `D-137`'s never-hears, the second an address the declared-tier guard is never handed and so cannot judge. **No arm of the publication is filtered**: the unpaired root is compared with the rest. | `D-137`, `D-101`, `D-145` |
| **(b)** | **`entries.length` equals `roots.length`** — MULTIPLICITY, the one relation a `Set` cannot see and the one the store does not refuse (duplicates are KEPT). | `guide §6`, `D-292` |
| **(f)** | **THE FALSIFIER, over ONE comparator that returns both verdicts** — never a set assertion in the row and a copy of it in the control: a divergent pair (an omitted entry, a spurious entry, a duplicate, and a one-segment/two-segment separator collision) must red, and the honest pair must be admitted. A re-homed row that cannot fail is a deleted row wearing a new name. | `D-3`, `D-292` |

- **THE COMPARATOR COMPARES ADDRESS TUPLES AND NEVER JOINED STRINGS** (`JSON.stringify` of the segment array per side): `['a/b']` and `['a','b']` share a `join('/')` spelling, so a joining comparator could call a spurious entry a match (`D-53`, `D-292`).
- **THE ROW'S HONEST GROUND IS NARROWER THAN "NOTHING MEASURES THIS"**: each entry is already witnessed per family by an existing count or leg, so **what is new is the SET** — the spurious direction, the duplicate at the unpaired root, and the set's closure over a family added later (`D-292`, `D-137`).

**AND WHAT `FH-1` DELIBERATELY DOES NOT MEASURE, EACH WITH THE OWNER OF THE FACT** (`D-43`):

- **NOT `declaration ↔ root`** — that is `tests/integration/central-data/declared-root.test.ts`'s, published and gating; a copy here would either red the lawful unpaired arm or duplicate a row (`D-145`, `D-132`, `D-101`). **This row may require an entry for every root and MUST NOT require a declaration for every root.**
- **NOT a count, a tier, an id or the unpaired root's literal** — the published total and the published set are that same `central-data` row's, and this row derives every figure it reads (`D-43`, `D-101`).
- **NOT the entries' ORDER**, which no consumer reads, and not the two deliveries' relative order at the boot, which is the construction's own — the order that IS load-bearing is the tab record's declaration batch, and that is `D-156`'s (`D-292`, `D-156`).
- **NOT a handle's spelling or an ordinal** — handles come from a module counter, and pinning one pins the counter (`D-71`).
- **NOT the `cfg.listeners` element SHAPE** — the package refuses a malformed or two-member element before any filesystem act, and that reading is already exercised at many call sites; a copy here would be a second measurement of an existing one (`guide §6`, `D-53`, `D-5`).
- **NOT a store, a boot, a subscription or a write** — both builders run no store verb, and the registration instants are `crossing.test.ts`'s subject (`D-219`, `D-92`).

## 5. What does not move, and what this page does not license

- **NO DELIVERY SIGNATURE MOVES**: `createViewDelivery` / `createTabsDelivery` and their signatures stand byte for byte, and so does the boot's one construction with its cast — `D-291` (iv)'s question is answered by `D-292` (iii) here and not later (`D-292`, `D-219`).
- **NO ENTRY IS MINTED OUTSIDE THE DELIVERY'S OWN CLOSURE**: the fan-out is closure-private, and deriving entries from declarations would leave the unpaired root with no listener — delivering the very defect the unit closes (`D-292`, `D-137`, intake row 3).
- **THE HAND-SPELLED LISTENER LIST STAYS HAND-SPELLED**, and the reason is the row: sourcing it from the tuple would leave `FH-1` comparing one tuple with itself, so it would measure a construction property where it exists to read an INDEPENDENT list (`D-53`, `D-137`).
- **NO SECOND REGISTRATION ROUTE AND NO SECOND MINTING AUTHORITY** — one registration per address, and it is the construction's (`D-219`, `D-129`, `D-71`; `docs/L3/view-record/delivery.md`'s `VD-1`/`VD-4`).
- **WHERE THE GUARANTEE STANDS, AND WHICH INSTRUMENT OWNS WHICH HALF — STATED HERE BECAUSE A READER WOULD OTHERWISE TAKE ONE INSTRUMENT FOR THE WHOLE**: the boot's ONE cast swallows whatever the array holds, so nothing there is a guarantee; the guarantee stands BELOW it, at each publication's DECLARED return (`readonly ViewConstraintDeclaration[]`, `readonly ViewDeclaredRoot[]`), at the answer union's CLOSED arms, and now at the spec union's two arms — which is what makes a repair answering nothing and a pair declaring no body into COMPILE ERRORS (`D-72`, `D-292`). **`npm run typecheck` owns only the narrower shape fact** that each projected half must satisfy the published type; **`FH-3` owns the MECHANISM** (which arm a spec may be); and **the DIRECTION between the two publications is `declared-root.test.ts`'s and is not this unit's to re-measure** (`D-145`, `D-43`).
- **THIS PAGE LICENSES NO HUNK**: the structure, signatures and guardrails are L3's `docs/L3/view-record/family-object.md` (`H-8`), and the row over the object itself is L3's `FH-3` (`H-9`) — the unit's red-first evidence, since `FH-1` is green on arrival by construction (`D-3`, `D-40`, `D-292`).
