## 1. The two written names, and the one that retires

- **`<userDataDir>/provident-operator-settings.json`** — the instance's file. The **directory** arrives from the module's caller and the **name** is this unit's own choice, so no other module spells it (D-13, D-19; L1 §5 ASM-6).
- **`<userDataDir>/provident-security.json`** — the retired name. It is **read at every boot until a record stands, then never again** (§3), **never written again**, and its bytes are **left standing**: this unit adds no delete, no rename and no migration of that file (D-19; L1 §5).
- This unit therefore **adds exactly one written name and retires another**, which is what stops D-13's "exactly two persisted files" being a true standing pin. The rows that read that figure divide by marks (D-31, D-30): `tests/store-persist.test.ts` and `tests/store-security.test.ts` are `scope:"file"`, `kind:"rework"` in `strata/marks.json`, so the rework **replaces each whole** and no expectation of theirs is re-pointed, while the unmarked legs that still gate are the ones this unit's L2 test writer maintains in the task that runs after the implementation (exception §2 E-5, §4 C-4) — named here as owed, not performed here (D-10, D-13, D-31).
- `<userDataDir>/provident-profile.json` is **not** this unit's and is neither read nor written here; `<userDataDir>/provident-settings.json` is a **seed** — read at most once per boot by the second import-once arm, never written and never retired, its bytes left standing (`docs/L1/settings-carrier-retirement.md` §4; §8; D-19, D-22).

## 2. What construction does, and what the boot does

| Act | What the disk shows | Cite |
|---|---|---|
| `createOperatorSettings({ userDataDir })` on a directory holding no store file | the file is **created exclusively, zero-length and empty**: a provided, absent `filePath` is created at construction, with no register key, no journal entry and no registration committed | `guide §9.1`; L1 §5 |
| the same, over an existing file that carries a record | the file is **not truncated and not reset**: the primitive is an exclusive create whose `AlreadyExists` falls through to a write-mode open that writes no byte | `guide §9.1` |
| the boot read, the import and `attach` | **no byte is written**: a read moves nothing, the absent import arm creates nothing, and the boot's flip is a gate state change with no store write | `guide §6`; L1 §5; `behaviour.md` §1 |

- **A directory or name the store cannot occupy refuses the construction and creates nothing** — no instance, no file, no directory, no byte — and every later write answers `FilePathUnreachable` (`guide §8.2`).

## 3. The retired name is read at every boot until a record stands, then never again

- The object is `<userDataDir>/provident-security.json`, the one file the replaced module wrote; the members imported are exactly its four record members, and the **six** boot arms `importOnce` declares — absent, directory/unreadable, unparsable, non-object, object, `entries` not a plain object — move as **behaviour**, not as bytes (the `importOnce` function in `src/main/operator-settings/index.ts`; D-19; L1 §5).
- **The import runs iff the instance's own file carries no record at `['operator-settings']`**, so it needs no marker, no version member and no second written name: after the first committed write the new file carries the record and the import does not run again (the construction's `RECORD_ADDRESS` read and the `importOnce` call beside it in `src/main/operator-settings/index.ts`; D-19; `guide §9.1`).
- **The absent arm writes nothing**, so a profile whose operator never writes reaches the same first-run default at every boot — exactly the landed store's behaviour (the absent arm of `importOnce` in `src/main/operator-settings/index.ts`; D-19; L1 §5).
- **The import never writes the retired name**, never renames it and never repairs it: its bytes stand as seeded, which is the row `behaviour.md` §3 states (D-19).

## 4. The row shape: the store's image and no header

- The file's content is the **store's own register image at the `file` tier**, written by the store's own writer; this module produces, parses and repairs **none** of it (`guide §9.1`: the file is the store's, not the consumer's).
- **A cleared member is stored as its absence, not as `null`**: the package's walk refuses `null` and `undefined` **anywhere** in a value — an object member whose value is `undefined` refuses the WHOLE value — so the record this module writes carries `token` only when a token stands and `maxJournalLength` only when a cap stands, and `read()` maps that absence back to the carrier's `token:null` / `undefined` (`guide §10.1`, `§10.2`; `interface.md` §2).
- **No wrapper, envelope, marker or version member** is added by this module: what `write` hands the store is the record value itself, and what `read` copies back is the record — the crossing's deep copy on both sides is the store's (`guide §10`; D-13). The third address's value is `{rows:[{name,value},…]}` (§7): that key's **own** whole record value and not a header over this record, so one key carries one record and no key carries two.
- **There is no `schemaVersion` here.** The replaced security store stamped none, and the `schemaVersion:'1'` that the second import arm validates is the **retired tier-1 carrier's** format marker: the arm requires it, then **skips** it as a row, so no record this module writes ever carries one (`src/main/operator-settings/index.ts`, the `importAppStateOnce` site; D-13, D-22).
- The format's version is the **package's** — `provident-storeroom` `^1.6.1` (the `dependencies` block of `package.json`) — and the seam's census pins the fourteen-member instance this module calls into (the seam's census in `src/main/storeroom.ts`; D-5).
- **A value is what the store admits**: a string with no lone surrogate, a finite number, a boolean, a dense array or a plain object, with `null`/`undefined` refused as a whole value, depth over `126` and more than `1,000,000` visited nodes refused, neither ceiling having a knob (`guide §10.1`, `§10.3`).

## 5. What a `file`-tier commit guarantees, and what a refusal leaves

| Guarantee | Where it comes from |
|---|---|
| a `file`-tier write either commits — the bytes then describe the state the act left — or answers `FileCommitFailed` **after** the store's own journal rollback, the previous bytes intact | `guide §9.2`, `§9.4`; L1 §3 |
| this module writes **no byte** itself: zero module-level file writes, so a torn write has no producer at this layer | D-13, D-16 |
| **no `.tmp`, no lock, no sidecar, no copy and no second name** is written at any point — the replaced module's `${path}.tmp` stage-and-rename machinery retires with it | D-16; L1 §5 |
| the store's writer **mechanism** — stage → fsync → rename, or otherwise — is **not declared by the package**, so no consumer can state that the store's own file is torn-write-free | finding **P-4**, §9; D-5 |
| a refusal leaves the record and the bytes exactly as they stood, and mints no cursor | L1 §3; `guide §9.4` |

- **The consequence, stated plainly:** the module can promise no tear at its own layer because it has no write at its own layer; the store's declared outcome is a commit or a refusal with the old bytes intact (`guide §9.4`; D-5).

## 6. The volatile pair is never persisted

- `exclusion` and the derived `tier4` are **`mem` rows at `['operator-exclusion']`** and never enter the file: a committed transition's bytes are not durable, and a fresh construction answers the safe pair (ASM-L2-2; D-17; `interface.md` §1).
- The **tier-4 boolean is never persisted** either, and `src/main/tier4-state.ts`'s holder is a projection and not a second home (L1 §3 ASM-4; `interface.md` §5).
- **The pair keeps an address of its own for a measured reason**: the instance's rows stand at **three** addresses (§7) and this pair holds the only `mem` one, because a `file`-tier write purges the versions it outranks (`file` > `mem` > `temp`) **at its own key**, so one shared address would let a settings commit reset the pair (`guide §5.1`; `interface.md` §1 `ASM-L2-1`; finding P-3).
- After a session that used both tiers, the file's bytes carry no `exclusion`, no `tier4` and no `mcp-disabled` spelling — asserted as an absence over the bytes, never as a parse of the store's image (D-13; L1 §8 **`S-4`**, whose row is the pair re-booting to its declared initial, with **`S-1`** for the boot's file state).

## 7. The key space

- **Three addresses and no fourth**: the durable record at `['operator-settings']` (`file`), the retired carrier's app-state rows at `['operator-app-state']` (`file`), the volatile pair at `['operator-exclusion']` (`mem`); this module mints no other key, reserves no namespace and interprets no segment (D-13, D-22; `interface.md` §1; the constants block of `src/main/operator-settings/index.ts`).
- **What stands at each**: `['operator-settings']` carries the record value whole — `enabled` always, `token` and `maxJournalLength` only while they stand, `entries` iff it stands; `['operator-app-state']` carries `{rows:[{name,value},…]}`, an **ordered array** and never a name→value map, written whole by `writeAppState` and re-projected by `readAppState` with **no listener**; `['operator-exclusion']` carries `{exclusion}` alone, with `tier4` derived at the read and never stored (§4, §6; the `readAppState`/`writeAppState` sites in `src/main/operator-settings/index.ts`; `interface.md` §1).
- **The third address is a sibling's declaration carried here, not this unit's invention**: the carrier's rows left `provident-settings.json` for it under D-22, so its marker, its import arm and its shape are `docs/L2/settings-carrier-retirement/` §1/§3/§4 and `docs/L1/settings-carrier-retirement.md` §3/§4; L1's exception §6 records that the crossing stands in this module's tree (`docs/L1/security-store-storeroom-exception.md` §6; D-19, D-22).
- **Three addresses and not one, because the purge is at the key**: a `file`-tier write purges the versions it outranks (`file` > `mem` > `temp`) at its own key, so a settings commit cannot reset the pair and an app-state commit cannot reset the record — the pair cannot share a durable address, and the app-state rows cannot be a member of the record's value (D-17, D-22; `guide §5.1`; `interface.md` §1 `ASM-L2-1`; finding P-3).
- A **patch names one tier**, so one call is one store write and one receipt; the surface's two channels never compose a mixed patch, and no row asserts one (`interface.md` §1 ASM-L2-5).
- `entries` is one member of the record value and not a key space of its own: an arbitrary name is a member of that map, and the store's register below `['operator-settings']` is minted by the one whole-value write (`guide §4` arm `W-4`; L1 §5). An **app-state row's name is likewise a member of a row** and never a path segment, which is why the app-state record answers at one address for any number of rows (§7's `['operator-app-state']`, above).

## 8. What this module does not touch

- **`<userDataDir>/provident-settings.json`** — `app-shell`'s tier-1 carrier, and its retirement is **executed** (D-22): the carrier's `settingsPath`, its boot read, the settings channel's guarded second read and its whole tmp+rename+fsync writer left the tree, and the name survives only as a **seed** — read at most once per boot by `operator-settings`' second import-once arm, written by none, its bytes left standing (§1; `docs/L1/settings-carrier-retirement.md` §3, §4, §6; D-19, D-22).
- **`<userDataDir>/provident-profile.json`** — `central-data`'s profile store, unmoved: this module neither reads nor writes it, and the two instances are separate on purpose (D-16; `docs/L2/central-data/persistence.md` §1).
- **`<userDataDir>/provident-security.json`** — the retired name: read at every boot until a record stands, then never again, never written again, bytes standing (§1, §3; D-19).
- **The renderer's own store** (`src/renderer/store.ts`, `store-rederive`'s) — read, written and persisted nowhere by this module (D-13).
- **No second store and no second `filePath`**: one instance per surface, constructed at most once and kept for the process's life, which is what makes the one reference of D-18 countable (`guide §3.2`; D-18).

## 9. Package findings — recorded, upstream-owned, never patched here (D-5)

| id | Symptom | Reproduction | Suspected root cause | Proposed fix shape |
|---|---|---|---|---|

| **P-5** *(new at rev 2)* | a consumer **cannot close its own refusal vocabulary and cannot open it safely either**: `StoreStatus` ends in an open `(string & {})` arm whose declaration calls the escape *"load-bearing rather than loosness"*, and the package publishes **no runtime membership predicate** — no exported list, no `knownStatus()` — so a consumer that must branch has no declared way to tell *a member the set gained* from *a store-side defect*. - **P-1's extension is this unit's measurement**, and it is the reason §3 states the import's marker as *the absence of a record* rather than as a version member: the boot-over-empty arm is undeclared, so this module never depends on it for a correctness claim — the first-run default is served for the `AddressNotFound` read arm, which is declared (`guide §4`).
