## 2. The rendered row, before and after

| Paint | `data-on` (rendered attribute) | Row text | Where it comes from |
|---|---|---|---|
| the authored envelope, before any bridge answer | `"false"` — authored in the data | the label table's entry, with no mark | `paneEnvelope()`'s toggle rows (`src/renderer/secure-panels.ts`) |
| after the first carrier answer | `"true"` iff the carrier's `enabled` names the group, else `"false"` | `☑`/`☐` + that entry, one `content` write | `syncConfig`'s `toggle:` arm |
| after a click settles | the flipped value, re-read from the carrier | the flipped mark, re-composed from the carrier | the same arm, over a `refresh()` this click caused |

- **The pane owns no state of its own:** `data-on` is written from `cfg.enabled.includes(g)` and never from the pane's prior value, so a click that the store refuses repaints the row it had (`syncConfig`'s `toggle:` arm; the `D-vi` shape in that pass's exclusion arm).
- **The authored `"false"` is the only state a *row* holds before an answer,** and it is the landed shape of the group rows — not the exclusion control's silence (that control's authored node declares no state member at all). What the **pane** holds before an answer beside it is `cfg`'s declared field default, which §4 composes into the first status line. No row of this unit asserts that pre-answer paint — P-2 and P-3 read after the first carrier answer (P-2, P-3) — **and neither does the battery**: `paneEnvelope()` is module-private and the shim's only paint follows a `refresh()`, which overwrites the authored `false` from the carrier (`interface.md` §7).
- **The sixth row is indistinguishable in kind from the five:** same `type`, same class, one generated handler name, one `[data-group]` attribute — which is what makes P-2's set comparison the whole of its drift check (P-2; L1 §5, `brief.md` §2).

## 3. What one click does, in order

1. the rendered row's `click` reaches the pane's `DomAdapter` and becomes a pane-graph dispatch — the production path, with only the event's origin synthetic (the `DomAdapter` and the supervisor's dispatch path, in `src/renderer/secure-panels.ts`; L1 §4.2).
2. the **one shared** `TOGGLE_BODY` reads the group from the node's own `data-group` and the direction from its own `data-on`, then issues **one** call: `security.set({ groups: [g] })` when off, `security.set({ disable: [g] })` when on (that body, `src/renderer/secure-panels.ts`).
3. the call crosses `IPC_SECURITY_SET` into `settingsSurface.set(patch)` (`src/main/preload.ts:108-110`; `src/main/main.ts:338`), which composes the pair patch and writes **one** `file`-tier record (`persistence.md` §1, §5; D-17).
4. that write's committed delivery re-patches the gate inside the surface's subscription, so the gate holds the new grant before the answer is minted (`src/main/settings-surface/index.ts:102-125`; D-17).
5. the DomAdapter's flush re-renders and `refresh()` re-reads the carrier, so the row and the status line paint the **carrier's** answer, not the click's intent (the supervisor's dispatch path and `refresh()`, in `src/renderer/secure-panels.ts`).
6. the gate's registered name set moved, so `tools/list` — a second, independent reading — answers the new set (`src/main/security.ts:38-42`; P-4).

- **One gesture, one write:** no second channel call, no second store verb, and no `RpcMethod` member is involved anywhere in the chain (`interface.md` §4; D-18).
- **A click with no bridge returns silently:** the body's `!s` guard is the first statement, so a plain page throws nothing and writes nothing (the one shared `TOGGLE_BODY`, `src/renderer/secure-panels.ts`; `brief.md` §2).
- **A click carries no group of its own:** `TOGGLE_BODY` takes the group off the node it runs on, so the sixth row needs no per-group body and no second handler body is added (L1 §5; `interface.md` §5).

## 4. What the status line composes

- **One `content` write into `#security-status`, one string, and one composition site:** the `security-status` arm of `syncConfig` (`src/renderer/secure-panels.ts`), whose two conditional locals are the whole of the variance. No second site composes any part of the line — `paneEnvelope()` authors the node with the placeholder content `loading…`, which is **not** a composition: the constructor renders nothing, and the boot wiring runs a `syncConfig` pass from its synchronous `refreshDebug()` beside an un-awaited `refresh()`, so the first line painted at this head is the composed one below (`src/renderer/renderer.ts`, the pane construction and its two boot calls).
- **The segments, in the order that one arm concatenates them:**
  1. `token: ` + `••••` when the carrier's `token` is **truthy**, else `token: (none)` — `null`, `''` and an absent member all compose `(none)`, and the four U+2022 BULLET characters are a **fixed literal** in that arm, never a mask sized from the token;
  2. `enabled: [` + the carrier's `enabled` list joined with `, ` + `]` — an empty list composes `enabled: []`, and this arm adds and removes no group;
  3. `journal: ≤N` when the carrier's `maxJournalLength` member is **present**, `journal: ∞` when it is **absent** — the arm tests `undefined` and not falsiness; the carrier puts that member on its answer only when the instance's record carries one, and the instance is its only author (`read()` in `src/main/settings-surface/index.ts`; `src/main/operator-settings/index.ts`), so the two forms are `≤` + a positive integer and `∞`, and neither is a pane-side default;
  4. the **exclusion segment**, composed **only when the carrier supplied `exclusion`**, in the carrier's own word: `MCP: enabled` for `'mcp-enabled'`, `MCP: disabled` for `'mcp-disabled'` — a `null`, `undefined` or absent `exclusion` composes **no segment at all** (the arm's empty string), and the arm paints no state word of its own on that absence;
  5. the **refusal segment**, composed **only when the carrier's `read` is non-null**, in the exact form `refused: tier4-closed` and **always last on the line**, whatever that object carries: the arm reads the member for **presence only** and never reads its `status` or `reason`, so the token is the whole of what the pane prints of it — no message, no address and no tier-4 value is ever on this line.
- **The separator is ` · ` — U+00B7 MIDDLE DOT between two single spaces — and it is written into the two conditional segments' own strings** (`' · MCP: …'`, `' · refused: …'`), so an absent segment takes its separator with it and no doubled, leading or trailing spacing is reachable. With an unanswered `exclusion` and a supplied `read`, the line reads `… · journal: ∞ · refused: tier4-closed`: the refusal is the line's **last** position, not a position after the exclusion word.
- **Fully composed, for one stated state — DERIVED, not measured.** The state: the carrier answers a non-empty `token`, `enabled: ['read','dispatch','data']`, no `maxJournalLength` member, `exclusion: 'mcp-disabled'`, and a non-null `read` — the pair that carrier mints together for that one state (`read()` in `src/main/settings-surface/index.ts`). The line:
  `token: •••• · enabled: [read, dispatch, data] · journal: ∞ · MCP: disabled · refused: tier4-closed`
  It is composed above by reading the arm; **this pass rendered nothing**, so it is a derivation and is not offered here as a reading.
- **One line that IS a measured reading, at the composition's other end — the pre-carrier paint.** With no carrier answer yet, `cfg` is still its declared field default (the class field declaration: `token: null`, `enabled: ['read','dispatch']`, `read: null`, no `exclusion` member), so the first composed line is `token: (none) · enabled: [read, dispatch] · journal: ∞`. Recorded verbatim at first paint by another unit's live battery (`archive/gate-corpus-2026-10-29/specs/tier4-arbitrary-storage-live-battery.md` §3 `U-1`, dated) and re-read at the node layer by that battery's fidelity anchor (`tests/tier4-arbitrary-storage.test.ts`); **this seat took neither reading, and no row of `P-1`…`P-7` reads it.** Its `enabled:` list is the **pane's own default, not a carrier's** — the one line this document quotes without naming a carrier state.
- **`data` appears in that `enabled:` composition by being in the carrier's list** — the pane composes it, it does not add it, which is why P-4 reads the line rather than the row alone (P-4; D-17).
- **The order inside the brackets is the record's own,** appended as grants arrive and never re-sorted into `VALID_GROUPS` order (`src/main/operator-settings/index.ts:176-181`); P-2 compares the composition as a **set**, so no row pins that order (P-2).

## 5. What `tools/list` gains and loses

- **Gains exactly the five `provident.data.*` names** on a grant and **loses exactly them** on a revoke, each read as a set difference against the same boot's earlier answer (P-4, P-6; D-11, D-26).
- **Absent, not present-and-refusing:** a disabled group's tools are never registered, so the roster answers their absence — the reading `central-data`'s interface states for the same group (`src/main/security.ts:86-88`; `docs/L2/central-data/interface.md` §4; D-11).
- **The rest of the list is unmoved by the gesture:** P-4 and P-6 also assert nothing was lost when granting and nothing gained when revoking, so a name moving in the other direction is a red row rather than a surprise (P-4, P-6).

## 6. What a restart paints

- **The instance owns the grant and the pane is its view** (D-17): a second boot on the **same** scratch profile, before any gesture, serves a `read()` whose `enabled` carries `data`, so the first carrier answer paints the row on and the status line names the group (P-5; `persistence.md` §3).
- **The paint is not a cache:** nothing in the renderer persists the set — the six rows are re-authored at boot and re-filled from the instance's record, so a boot with no record paints all six off and a boot with a record paints what the record carries (the constructor's one `paneEnvelope()` translation and `syncConfig`'s `refresh()` pass, in `src/renderer/secure-panels.ts`; D-19, P-5).
- **The restart is a second process on one directory:** the leg keeps boot A's profile and boots B on it, so the claim is the file's, not a warm renderer's (L1 §4.2, P-5).
- **`tools/list` at boot B carries the five names before any gesture,** which is the same fact read over the other channel (P-5; D-11).

## 7. What this document does not claim

- **No pointer-level gesture:** a body-issued `click` carries an event name and a rendered element, never a coordinate, so P-3's non-zero rendered box is a row rather than a comfort (`docs/L1/secure-panels.md` §4.2; `scripts/electron-ui.mjs:238-241`; D-30).
- **No packaged-app claim, and no claim about the pane under another display or DPI** — the leg states its own limit and this document inherits it (`docs/L1/secure-panels.md` §4.2; D-37).
- **No claim that the pane is the only control over the grant:** `security.set` is reachable by any renderer code in the operator's realm and by no MCP path; the pane's isolation is about MCP reach, not about the channel's exclusivity (`src/main/main.ts:337-338`; D-18).
- **No claim that the exclusion pair gates the sixth row's write — measurement says it does not.** Replaced, not softened: this document said a `set` while the tier is closed "answers a **refusal value** and moves no byte". **Measured at this head, with the pair at `mcp-disabled`: `read()` answers the closed token `{status:'refused', reason:'tier4-closed'}`, and `surface.set({groups:['data']})` in that same state COMMITS and rewrites the bytes** — `{"operator-settings":{"enabled":["data"]}}`, receipt `committed`. The surface declares it in its own words: `tier4-closed` is a **read outcome and never a write outcome** (`src/main/settings-surface/index.ts:28`); the token is minted only in `read()` (`:123-137`), and the module imports the tier holder's **writer** and never its reader (`:17,107,219`), so its `set` (`:139-190`) consults no tier state at all.
- **For a consumer, plainly: a closed tier stops a reader, not a writer.** A click from a closed state is a write like any other — the record moves, the receipt is `committed`, and the row repaints from the carrier's answer, so the status line can **end** `· refused: tier4-closed` — its exact form and last position are §4's — beside a row that click just changed. Nothing on this path withholds the write: the holder's one total reader has no `src/**` consumer at this head (D-22's second half parks that enforcement), so the closed pair's only effect here is the token in the read answer. **No demand against the package follows** — D-5/D-16 govern that, and this is the tree's own composition (D-16 retired `tier4-closed` as a *write* outcome; the token survives as the channel's read reading). Unasserted by `P-1`…`P-7` **and by the battery**: no row of either drives the closed pair (`interface.md` §7).
- **One stale declaration is named here rather than edited:** the comment block at `src/main/preload.ts:55-62` still says a `set` attempted while the pair is closed "answers the channel refusal `{status:'refused', reason:'tier4-closed'}` as a value" (`:60-62`) — the reading the measurement above replaces. `src/` is not this seat's write; it is routed with an owner (`interface.md` §8 `R-7`).
- **No claim about a group the pane has no row for:** under the arrangement the roster **is** the table's own key projection — there is no second list beside it — so that state is unrepresentable rather than unhandled. The declaration's exact shape is `docs/L3/secure-panels/signatures.md` §1-§2.2 and is not paraphrased here (`interface.md` §1-§2; S-1).
