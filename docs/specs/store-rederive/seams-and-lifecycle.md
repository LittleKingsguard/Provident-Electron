### 2.9 The `secure` graph — `C6` (`R2`'s no-whitelist ruling; the blocked-MCP condition)

1. **`C6`, VERBATIM.** *"secure is a separate graph, accessed by separate functions, and saves to a separate file. It cannot be accessed unless the MCP server is blocked. For all other purposes, it follows the same constraints as `file`."* `(A C6 · CONTRACT)`
2. **"SEPARATE FUNCTIONS" IS SATISFIED BY A SEPARATE SURFACE, AND *NOT* BY A `secure.` SEGMENT ON THE GENERIC SURFACE.** The `secure` graph is reached by `secureLoad`/`secureRead`/`secureWrite`/`secureListen`/`secureConstrain` and by nothing else; **the generic surface's tier domain is `{file, mem, temp}` and a `secure` tier argument is REFUSED with `reason: 'secure-refused'` (step `F-TIER`) on every generic function**; **and a `secure`-spelled SEGMENT carries no special meaning on the generic surface** — it is an ordinary segment, because `R6` superseded the segment qualifier (`docs/specs/store-rederive/store-model.md §2.1` item 2). **A design in which any generic function reaches the `secure` graph through a name, a prefix or a tier argument FAILS.** `(A C6 · A R6 · CONTRACT + NEGATIVE)`
3. **`R2` GOVERNS WHAT THE GRAPH STORES, AND IT FORBIDS EVERY WHITELIST.** *"`Secure` needs to be able to store arbitrary data, potentially at runtime. DO NOT construct an address or value whitelist."* **Therefore: the `secure` graph admits EVERY address in `docs/specs/store-rederive/store-model.md §2.3` item 1's domain (no enumerated key domain, no member census, no reserved spelling, no delete prohibition) and every value in `docs/specs/store-rederive/store-model.md §2.4` item 2's single admission set — which is a ROUND-TRIP duty (`C7`) and NOT a content restriction: it constrains no key domain and no data shape beyond what a JSON file can carry.** **`R2` REMOVED a shape; this contract constructs none.** Terms: `0` whitelists ✓. **THE PRICED ALTERNATIVE, NAMED BECAUSE `R2` IS THE MOST POINTED RULING HERE: a WIDER admission set for the `secure` graph alone.** **It is NOT taken, and the ground is `C6`'s own sentence** — *"for all other purposes, it follows the same constraints as `file`"* — **plus `C7`'s *"exactly match the data state"*: a value the JSON file cannot carry cannot be the state a `file`-peer tier is required to represent, so the refusal is a CONSEQUENCE of the file duty and not a content whitelist over tier 4.** **If the architect wants a wider `secure` set, the shape it needs is a tagged encoding for the secure file — a one-clause amendment at `docs/specs/store-rederive/store-model.md §2.4` item 2 + this item, moving `docs/specs/store-rederive/property-register.md §5.5.1`'s `P-SD-TP-4` term and no other.** `(A R2 · A C6 · A C7 · DECLARED-DEFAULT)`
4. **THE GATE — HOW THE BLOCKED-MCP CONDITION IS OBSERVED (`docs/specs/store-rederive/contract.md §0A` `DD-9`; `D10`'s residual, now closed).** The store takes a construction input **`secureAccess: () => boolean`** — **a NAMED READER, read ONCE PER CALL at that call's own turn, never captured, never cached across calls.** `true` = the MCP server is **BLOCKED** ⇒ access is granted; `false` = not blocked ⇒ **every one of the five secure functions refuses with `reason: 'secure-gated'` at step `K-GATE`, before anything else it would do.** **WHO ASKS: the store's own secure functions, at their step 1.** **WHAT AN IN-FLIGHT CALL OBSERVES: the ONE reading taken at its own turn governs the WHOLE call — a flip of the condition mid-call neither half-applies nor re-reads, so the call either completes as a whole or is refused as a whole.** **ABSENT, A THROW OR A NON-BOOLEAN ⇒ NOT BLOCKED ⇒ REFUSED (fail-closed)**, because `C6` says the graph *"cannot be accessed UNLESS"* the MCP is blocked. Terms: `5` gated functions × `2` readings = `10` drives (`docs/specs/store-rederive/census.md §4.5`). `(A C6 · T · CONTRACT + DECLARED-DEFAULT + CENSUS)`
5. **`R2` DOES NOT RE-OPEN THE MCP SURFACE.** *"A pass that reads `R2` as granting an MCP-reachable tier-4 read path has mis-read the ruling"* (`R §2.3`, the one row that would have hit). **This contract declares no MCP surface, no tool, no resource and no notification payload, and no channel that carries a `secure` value out of its realm** (`R §2.3`; `S docs/specs/mcp-endpoint.md` §6.4's manual-UI-only determination, quoted not re-derived). `(A R2 · R §2.3 · CROSS-REF + NEGATIVE)`
6. **THE `secure` GRAPH'S OWN FILE IS THE `file` TIER'S PEER: the commit duty (`docs/specs/store-rederive/write-and-read.md §2.7`), the tombstone lifecycle (`docs/specs/store-rederive/write-and-read.md §2.6` item 3) and the event surface (`docs/specs/store-rederive/seams-and-lifecycle.md §2.11`) apply inside it unchanged, and its nodes carry NO tier member** (`C11`: *"secure is determined by being in an isolated graph"*). `(A C6 · A C11 · A R12 · CONTRACT)`

### 2.10 The constraint seam — `C13` and `R4`

1. **`C13`, VERBATIM.** *"Links can contain constraint functions, which can take the current state, the prospective future state, and the changed node as parameters, perform a logical check (ex. exactly one tab node is marked `active`) and return true (state is valid) or invoke a repair function (ex. most recent active tab is marked 'active') or return false with an error message explaining the constraint violation."* **The example is an ILLUSTRATION of a MODULE's constraint — `exactly-one-active` is a module's, never a store member** (`A R1`; `docs/specs/store-rederive/contract.md` §1.1 item 3). `(A C13 · A R1 · CONTRACT)`
2. **`R4`, VERBATIM, AND THE REGISTRATION SEAM.** *"Constraints are an extensible tool - modules must be able to add additional constraints and repair functions. DO NOT add built-in constraint functions."* **The seam is `constrain(address, {constraint, repair?})`, a store-level function (`C1`), which attaches the module-supplied pair to the interface at that address: to the LINK at the address, or — at a 1-segment address — to the REGISTER ENTRY, whose `C14` words are *"It has the functionality of a link, without having a distinct parent"*.** A link or entry carries an **ORDERED LIST** of registrations **in registration order** (`C13`'s plural *"constraint functions"*). **A re-registration carrying the SAME `constraint` function identity (`===`) at the SAME address REPLACES that entry in place (idempotent wiring); otherwise it APPENDS.** **THE SEAM CARRIES NO WITHDRAWAL VERB** (`docs/specs/store-rederive/contract.md §0A` `DD-15`): a registration stands for the store instance's lifetime, and **`unconstrain`, `clearConstraints`, a constraint-kind table and a constraint id are NOT this store's surface** — `C13`/`R4` mandate ADDING, and the landed `kind · repair action · refusal reason` table family is `STALE PENDING` (`L [H]`; `R §4.4` strikes it). `(A R4 · A C13 · A C14 · DECLARED-DEFAULT + NEGATIVE)`
3. **THE EVALUATION POINT AND THE EVALUATED SET.** **Evaluation happens ONLY where a module registered a constraint** (`R §2.4`, `S-6` `ANSWERED-BY-R4`: *"evaluation happens only where a module registered one; the store contributes no evaluation point of its own"*). **DECLARED (`T`, `DECLARED-DEFAULT`): the evaluated set of a write at `W` is every registration at a PREFIX address `P` of `W` (`P ⊆ W`, including `P = W` and including `W`'s root), evaluated from the shortest prefix to `W` (register entry first, then down the walk), and within one address in registration order.** **PRICED ALTERNATIVE, NOT TAKEN: also evaluating the DESCENDANTS' constraints of a write that would discard them** — refused because (a) `R4`'s carrier is the link and the write does not visit those links, and (b) their `future` state would describe a subtree the write is discarding. **A module that must constrain an ancestor's overwrite registers at that ancestor too.** `(A R4 · A C13 · T · DECLARED-DEFAULT)`
4. **THE ARGUMENT SHAPE (`docs/specs/store-rederive/contract.md §0A` `DD-1`; `S-4`'s residual, now closed): ONE record `{address, current, future, changed}`, MINTED PER EVALUATION, carrying COPIES and never a live internal record** — because `C3` forbids providing a reference as a value and `C2`'s purpose is that writes happen only by explicit call. **`current` = the unqualified transcription (`docs/specs/store-rederive/write-and-read.md §2.8` item 3) of the addressed subtree before the write; `future` = the same transcription the write would leave; `changed` = the addressed node's own `{address, tier, literals}`.** **A constraint that mutates the record changes nothing in the store; a constraint that is handed a live node, anchor or link FAILS.** `(A C13 · A C2 · A C3 · DECLARED-DEFAULT + NEGATIVE)` **⟶ AMENDED 2026-10-08 (`R15` item 4, THE ARCHITECT; the as-filed sentence stands byte-for-byte and THIS clause is the operative form).** **ONE MUTATION NOW DOES CHANGE SOMETHING, AND IT IS THE CHANNEL `R15` CREATES: the record carries `notes: ConstraintNote[]` (`docs/specs/store-rederive/store-model.md §2.1`'s amended block), and the entries a constraint OR a repair appends to ITS OWN record's list are HARVESTED by the store after the call returns (`item 10`).** **Every OTHER mutation of the record still changes nothing in the store, and the live-record prohibition is untouched — the module never receives a node, an anchor, a link, or the write's own list.**
5. **THE THREE ARMS, EXACTLY, AND WHAT EACH DOES (`C13`'s own three):**
   - **`{ok: true}`** ⇒ the state is valid; evaluation continues with the next registration.
   - **`{ok: false, message}`** ⇒ **the write is REFUSED**; the answer is `{status:'refused', reason:'constraint-refused', step:'H-CONSTRAINT', segment:<the write's last segment or null>, message:<the MODULE's message VERBATIM>}` (step `H-CONSTRAINT`); **nothing lands.** **THE MESSAGE CHANNEL IS THE RETURNED RECORD'S `message` MEMBER** (`docs/specs/store-rederive/contract.md §0A` `DD-2`; `S-5`'s residual, now closed): **the same member carries `C17`'s store-authored sentence, so there is ONE channel with TWO authorships and no second surface.** `(A C13 · A C17 · DECLARED-DEFAULT)` **⟶ AMENDED 2026-10-08 (`R15`, THE ARCHITECT; `RCA-8(d)`: the as-filed sentence above stands byte-for-byte and THIS clause is the operative declaration): THE CHANNEL IS NOW THE MESSAGE LIST — `C13`'s message is appended VERBATIM as a `'constraint'` entry and `C17`'s sentence is the store's own entry, so it is ONE channel with THREE authorships (`docs/specs/store-rederive/contract.md §0A` `DD-21`; `item 10` below). The record's single `message` member is superseded by `messages: StoreMessage[]` (`docs/specs/store-rederive/store-model.md §2.1`'s amended block).**
   - **`{repair: true}`** ⇒ **the store invokes the registration's `repair`** with the same record; its return **REPLACES the prospective value**, is **re-admitted** (`docs/specs/store-rederive/store-model.md §2.4` item 2; a refused class ⇒ `'value-not-admitted'`), and evaluation continues with the NEXT registration. **⟶ AMENDED 2026-10-08 (`R15` item 1; the as-filed tail stands byte-for-byte and THIS clause is the operative declaration): EVALUATION DOES NOT CONTINUE FORWARD — the pass RESTARTS at the FIRST registration of the evaluated set, so every constraint is RE-EVALUATED against the repaired state (`item 8` below; `docs/specs/store-rederive/contract.md §0A` `DD-22`).** **If the registration carries no `repair`, the write is REFUSED `'constraint-failed'`** with a store-authored message naming the missing repair.
   - **A malformed answer (not one of the three arms) or a THROW from a `constraint` or a `repair`** ⇒ **the write is REFUSED `'constraint-failed'`** with a store-authored message; **the throw never propagates and nothing lands.** `(A C13 · A R4 · CONTRACT)`
6. **A REPAIR'S OUTCOME (`docs/specs/store-rederive/contract.md §0A` `DD-3`; `S-7`'s residual, now closed).** **(a) A REPAIRED WRITE IS A SUCCESSFUL WRITE: it lands, it is committed if its tier is `file` (one commit, after the repair settles — never two file writes), and `C19`'s purge runs after it.** **(b) THE REPAIRED VALUE IS NOT RE-OFFERED TO THE CONSTRAINTS ALREADY EVALUATED, and no registration is evaluated twice within one write: evaluation is ONE ORDERED PASS.** **⟶ AMENDED 2026-10-08 (`R15` items 1–2, THE ARCHITECT; `RCA-8(d)`: this sub-clause's as-filed words stand byte-for-byte and `item 9` below is the operative declaration).** **THIS SUB-CLAUSE IS SUPERSEDED: the repaired value IS re-offered — every registration, the already-satisfied included, is RE-EVALUATED in a NEW pass (`item 8`) — while NO REPAIR IS EVER RE-INVOKED: a registration's `repair` runs AT MOST ONCE per write (`item 9`).** **What survives of this sub-clause, unchanged: the repaired value REPLACES the prospective value and is re-admitted as a value (there is no second candidate and no merge).** **(c) A repair can never follow a refusal**: the three arms are exclusive and a refusal **ends the write**. **(d) The record carries `repaired: true` iff any repair was taken.** `(T · DECLARED-DEFAULT)`
7. **NO BUILT-IN CONSTRAINT, NO STORE-OWNED VOCABULARY, NO BOUND.** `R4`'s prohibition is read at its widest: **the store mints no constraint, ships no constraint, names no constraint kind, and imposes no repair-round limit** (a store-owned round limit would be a store-owned constraint policy in miniature, `R4`). **The evaluation is total because each answer is terminal** (`docs/specs/store-rederive/write-and-read.md §2.5` item 1's order), **not because a bound exists.** **⟶ AMENDED 2026-10-08 (`R15` item 2, THE ARCHITECT; `RCA-8(d)`: the as-filed sentence stands byte-for-byte and THIS clause is the operative reading).** **TWO WORDS OF IT ARE RE-GRAINED: (i) an answer is no longer TERMINAL at `{repair:true}` — that arm RESTARTS the phase (`item 8`) — and (ii) the store now carries a bound on REPETITION, and it is the ARCHITECT's, not a store-owned policy over module code: A REGISTRATION'S REPAIR RUNS AT MOST ONCE PER WRITE (`item 9`).** **THE PHASE IS STILL TOTAL AND IT NOW TERMINATES *BECAUSE OF* THAT BOUND: at most `|S|` repairs can run, so the pass count is `≤ |S| + 1` and no repair is ever re-invoked.** **`R4`'s prohibition is untouched: the store still ships no constraint, names no kind, and declares no round limit of its own.** `(A R4 · CONTRACT + NEGATIVE)`

**⟶ AMENDED 2026-10-08 (`R15`, THE ARCHITECT; `P §10`; `RCA-8(d)` ANNOTATE-BESIDE) — THE CONSTRAINT PHASE, RE-GRAINED. THE WHOLE OPERATIVE FORM OF `R15` LIVES IN ITEMS 8–11 BELOW.** **Items 1–7 above stand byte-for-byte; the three sub-clauses superseded as declarations are annotated in place (item 5's forward-continuation tail, item 5's `message`-member clause, item 6(b)'s one-ordered-pass clause, and item 7's terminality/`no bound` reading).** **The architect's own words, verbatim and unedited:** *"DD-3: Repeat constraints, don't repeat repairs. If a repair breaks a prior constraint, fail instead to prevent loops. Track with a message list that constraints and repairs write to and can be returned to verbosely document failure or change."* `(A R15 · P §10 · CONTRACT)`

8. **THE PHASE IS A PASS-SEQUENCE, AND CONSTRAINTS REPEAT (`R15` item 1).** Let `S = [r_0, …, r_{k-1}]` be the write's EVALUATED SET in `item 3`'s order (shortest prefix first, register entry before the walk, registration order within one address). **The phase runs PASSES. A pass walks `S` from `r_0`. A `{repair:true}` answer whose repair RUNS changes the state, and the phase then RESTARTS: a NEW pass BEGINNING AT `r_0`.** **Therefore every registration is re-evaluated against the repaired state — including every registration that already answered `{ok:true}` — and a repaired write IS re-checked against the whole constraint set.** **The architect's own failure arm presupposes exactly this: a repair *"breaks a prior constraint"* only if the PRIOR constraints are re-walked.** *(The as-filed `item 6(b)` reading — "no constraint is evaluated twice … one ordered pass" — is SUPERSEDED and its cell stands visible beside this clause.)* **The repaired value is re-admitted at the moment the repair returns (`item 5`; a class outside `docs/specs/store-rederive/store-model.md §2.4` item 2 ⇒ `'value-not-admitted'`, nothing landing).** **A row in which a write that took a repair leaves an earlier registration UNRE-EVALUATED FAILS.** `(A R15 · T · CONTRACT + NEGATIVE)`
9. **A REPAIR RUNS AT MOST ONCE PER WRITE — AND THAT IS THE LOOP'S BOUND (`R15` item 2).** **DECLARED (`T`, `DECLARED-DEFAULT`, `docs/specs/store-rederive/contract.md §0A` `DD-22`): the unit of "once" is THE REGISTRATION.** `r_i`'s `repair` is invoked **at most once within one write**; **no registration's repair is ever REPEATED**; across registrations a single write may therefore take up to `k = |S|` repairs, one per demanding registration. **Consequences, each a rule:**
   - **(a) A SECOND `{repair:true}` FROM A REGISTRATION WHOSE REPAIR HAS ALREADY RUN IN THIS WRITE REFUSES THE WRITE — and it does NOT run the repair again.** The token is **`'constraint-failed'` (13)**, whose as-filed third arm already reads *"`{repair:true}` with no registered `repair`"*: **the arm is RE-GRAINED by this ruling to cover "the demanded repair is not available — either unregistered, or already run in this write"**, and **it is NOT a new member** (`docs/specs/store-rederive/store-model.md §2.14` item 1's write set counts it once). **The repetition the ruling forbids thereby becomes a FAILURE.**
   - **(b) THE PHASE TERMINATES, AND THE BOUND IS THE ARCHITECT'S, NOT THE STORE'S.** At most `|S|` repairs can run, so **the pass count is `≤ k + 1 = |S| + 1`**, every pass is finite, and **no repair function is ever re-invoked**. *(This is the bound `item 7`'s re-grained reading names; `R4` is untouched — the store still ships no constraint, names no kind and declares no round limit of its own.)*
   - **(c) NO STORE-OWNED REPAIR-DEMAND POLICY EXISTS BEYOND (a).** A `{repair:true}` from a registration whose repair has **not** yet run is taken, whatever the pass — **a SECOND registration may take its own first repair while the first registration's repair stands**, and the pass then restarts again.
   - **A row in which a registration's repair runs twice in one write FAILS.** **PRICED ALTERNATIVE, NOT TAKEN: "once per write" read GLOBALLY (one repair for the whole write)** — refused because it would refuse every second registration's `{repair:true}` regardless of what it repairs, making `R4`'s module-supplied repairs unusable in a constraint set of two; the per-registration reading is the one that buys exactly the loop's bound. `(A R15 · A R4 · T · DECLARED-DEFAULT + CENSUS)`
10. **THE MESSAGE LIST — THE ONE CHANNEL, ITS ENTRY, ITS APPENDERS, ITS ORDER AND ITS RETURN (`R15` item 4; `docs/specs/store-rederive/contract.md §0A` `DD-21`).**
   - **THE MEMBER, AND WHAT IT REPLACES.** **`Refusal.message: string` is REPLACED by `Refusal.messages: StoreMessage[]`** (the fourth diagnostic member, RE-GRAINED), **and the write's `committed` record gains `messages: StoreMessage[]` as its SEVENTH payload member** (`docs/specs/store-rederive/store-model.md §2.1`'s amended block). **There is no second `message` string beside the list — one member, one channel** (`DD-2` superseded as a declaration; ONE channel, THREE authorships: a constraint, a repair, the store's own arms). **EVERY `Refusal` carries the list and `messages.length ≥ 1`; a `committed` record's list MAY be empty — EXCEPT when `repaired` is `true`, where it carries at least the store's own repair entry.** **A `committed` record with `repaired: true` and an EMPTY list FAILS.**
   - **THE ENTRY, CLOSED: `StoreMessage = { source: 'constraint' | 'repair' | 'store'; pass: number; position: number | null; step: ResolveStep; address: Address; text: string }`** — **terms `6 = 2 (the MODULE's own: `source` · `text`) + 4 (the STORE's own stamps: `pass` · `position` · `step` · `address`)` ✓**. **`source` = WHO authored it; `text` = the sentence (the MODULE's VERBATIM for `'constraint'`/`'repair'`, the store's own for `'store'`); `address` = the address it concerns (the write's address for the phase's own entries); `step` = the step id that appended it (`'H-CONSTRAINT'` for every module-authored entry).**
   - **THE TWO STAMPS, PRECISELY.** **`pass`** = the 1-based ordinal of the constraint phase's pass that appended it; **`1` for every entry appended by a call that has no constraint phase** (declared here, `T`: a `read`, `listen`, `constrain` or `load` refusal carries its one store-authored entry at `pass: 1`). **`position`** = the **0-based index of the driven registration within the write's evaluated set `S`** (`item 3`'s order), or `null` where the entry concerns no single registration. **`position` here is NOT `ConstraintRecord.position` (`docs/specs/store-rederive/store-model.md §2.1`), which indexes a registration within the addressed link's or entry's OWN list** — the two are distinct referents, and this clause is where the distinction is declared.
   - **WHO MAY APPEND — `4 = 2 + 2` DOORS, AND NOTHING ELSE.** **THE MODULE'S TWO:** **(i)** a constraint's **`{ok:false, message}` answer** — the store appends its `message` **VERBATIM** as a `'constraint'` entry (**this is `C13`'s *"return false with an error message explaining the constraint violation"*, and it is where `C13`'s message ENTERS the list**); **(ii)** **the `notes` DRAFT LIST the `ConstraintEvaluation` record is MINTED WITH (per evaluation, `DD-1`; `docs/specs/store-rederive/store-model.md §2.1`'s amended block)** — a constraint **or** a repair appends a `ConstraintNote` (`{source: 'constraint' | 'repair', text}`) to **ITS OWN record's** `notes` list, and **the store HARVESTS those drafts after that call returns, in the module's own append order, STAMPS each one (`pass`, `position`, `step`, `address`) and appends it to the write's list as a `StoreMessage`.** **THE HARVEST IS TOTAL AND IT NEVER THROWS: a draft whose `source` is not `'constraint'` or `'repair'`, or whose `text` is not a string, is DISCARDED and never minted as an entry — the module cannot forge a `'store'` entry.** **The module NEVER holds the write's own list**: handing it out would hand a module a live internal record, the very thing `DD-1` refuses. **THE STORE'S TWO:** **(iii)** **one entry for EVERY repair invocation** (`source: 'store'`, naming the repair, its `position` and its `pass`) — so **a CHANGE is documented BY CONSTRUCTION even when the module appended nothing**; **(iv)** **one entry for every refusal whose primary sentence is the store's own** — i.e. `C17`'s sentence and every other store-authored sentence (`C7`/`R8`'s save failure, the load failure, the malformed arms, the gate, the missing repair, the repeat demand of `item 9(a)`).
   - **THE ORDER IS APPEND ORDER, AND IT IS EXACTLY `(pass, position)`.** Entries stand in the order they were appended: **the module's entries during a call, then the store's own entry for that call's outcome**. **LEMMA, WHICH THE REGISTER'S ROWS DRIVE DIRECTLY: the list is ordered by `pass` ASCENDING and, WITHIN one pass, by `position` ASCENDING** — so a two-pass write's list reads *pass 1 (positions ascending), then pass 2 (positions ascending)*. **A harvested entry is never re-ordered, never dropped and never duplicated; TWO APPENDS OF THE SAME TEXT ARE TWO ENTRIES — the list is a LOG, not a set.**
   - **THE PRIMARY SENTENCE, AND HOW IT RELATES TO `C17`.** **THE REFUSAL'S PRIMARY SENTENCE IS THE LAST ENTRY'S `text`.** It is the **store's own** for **every token except 12**, whose last — and primary — entry is the **MODULE's verbatim** (`C13`); **for token 20 it is the store's own sentence naming the repair and the constraint it broke, with the broken constraint's own verbatim standing as the entry IMMEDIATELY BEFORE it** (`item 11`). **So `C17`'s *"return verbose error"* is answered by the WHOLE LIST plus its primary sentence, and `C13`'s message keeps its own authorship at its own entry.** **A refusal whose list is EMPTY, or whose last entry's `text` is empty, FAILS.**
   - **WHETHER IT IS RETURNED ON SUCCESS: YES — `R15` says *"failure OR change"*.** The `committed` record carries the list, so **a repaired write documents its own change** (`repaired: true` + the store's repair entry), and every `Refusal` carries it so **the failure is documented verbosely**. `(A R15 · A C13 · A C17 · A C2 · T · CONTRACT + DECLARED-DEFAULT)`
11. **A REPAIR THAT BREAKS A PRIOR CONSTRAINT FAILS THE WRITE (`R15` item 3) — AND WHAT THAT FAILURE CARRIES.** **If a registration answered `{ok:true}` in an EARLIER pass of the SAME write and answers `{ok:false, message}` in a LATER pass, the write FAILS. It is NOT repaired again: the loop is broken by FAILING.** **THE ANTECEDENT IS EXACTLY *previously `{ok:true}` IN THIS WRITE*:** a registration that answered `{repair:true}` and never `{ok:true}`, and then refuses, **was never satisfied** — its refusal is **`'constraint-refused'` (token 12)** with the module's message as the primary entry, **not this arm**.
   - **THE ANSWER IS A RETURNED TYPED RECORD, NEVER A THROW (`R8`/`C7`):** `{status:'refused', reason:'repair-broke-constraint', step:'H-CONSTRAINT', segment:<the write's last segment or null>, messages:<the whole list — the broken constraint's message at its own entry, then the store's own closing sentence as the last entry>}`.
   - **THE OPERATION DOES NOT LAND:** nothing is installed, **no file is written** (the `file`/`secure` commit is never attempted), **the purge does not run** and **no listener fires** (`docs/specs/store-rederive/write-and-read.md §2.5` item 1's discard rule at steps `(1)`–`(7)`; `docs/specs/store-rederive/seams-and-lifecycle.md §2.11` item 5's *"a REFUSED write fires NOTHING"*).
   - **THE TWO ARMS ARE DISTINGUISHED, AND WHY:** the loop-breaker's failure (**"the repair changed the state and a constraint that HELD no longer holds"**) is **not the same fact** as a constraint's own refusal (**"this prospective state violates me"**), and `R15`'s own purpose is that **the loop is broken by FAILING** — so the failure is named at token 20 (`docs/specs/store-rederive/store-model.md §2.14` item 5) while a first-time refusal stays token 12. **A row in which the two arms collapse into one token FAILS the ruling's documentation duty** (`item 10`'s *"verbosely document failure or change"*). `(A R15 · A R8 · A C7 · A C13 · CONTRACT + NEGATIVE)`

### 2.11 The event surface — `C22`, `C23`, `C24`

1. **`C22`, VERBATIM.** *"event listeners are used to rerun functions that collect and use stored data. (ex. the zone render process retrieves the pane information for its zone, so it can re-render on any change)"* — **an ILLUSTRATION; the zone renderer is a CONSUMER (`docs/specs/store-rederive/contract.md` §1.1 item 3).** `(A C22 · CONTRACT)`
2. **THE LISTENER SURFACE.** `listen(address, body)` registers `body` in the store's listener list in registration order and answers `{address, attached}`, where **`attached` is TRUE iff an unqualified read at that address would answer a transcription — i.e. iff the address currently resolves and is not tombstone-suppressed** (`docs/specs/store-rederive/write-and-read.md §2.8` items 2–3; `docs/specs/store-rederive/write-and-read.md §2.6` item 2). **The body is invoked with NO ARGUMENTS and collects through the store's own `read`** (`docs/specs/store-rederive/contract.md §0A` `DD-17`): **the event surface carries no payload, no cause taxonomy, no fan-out policy, no unsubscribe and no amplifier cap** — the landed eight-cause taxonomy, the `subtree` opt-in, the cap and the event count are `STALE PENDING` (`L [H]` `G-landed-code.md` §2). `(A C22 · DECLARED-DEFAULT + NEGATIVE)`
3. **`C23`, VERBATIM: *"an event listener can be unattached (waiting for an address that is currently unreachable) or attached to its target node"*.** **The two states, and nothing else: `2 = 1 (unattached) + 1 (attached)` ✓.** **The target node is the node an UNQUALIFIED read at the address would select** (`R9`; `docs/specs/store-rederive/contract.md §0A` `DD-16`) — so **the attachment is BY ADDRESS and follows the address across every re-mint (`C4`)**: **a write elsewhere in the store never detaches a listener; a re-mint of the target node does not detach it; the body, when it reruns, reads the address and therefore observes the NEW node.** `(A C23 · A R9 · A C4 · DECLARED-DEFAULT + CENSUS)`
4. **WHAT ATTACHES AN UNATTACHED LISTENER (`D12`'s residual, now closed — DECLARED).** **Attachment is re-evaluated at the END of every SUCCESSFUL write and at the END of a successful `load()`, for EVERY unattached listener:** a listener whose address now resolves becomes attached **as part of that write's landing (no explicit re-attach call exists and none is declared)**; a listener whose address has STOPPED resolving (its instance was purged, removed by a `file`-tombstone's commit, or is now tombstone-suppressed) becomes unattached. **A listener is never attached by a REFUSED write** (nothing landed). `(T · DECLARED-DEFAULT)`
5. **WHAT FIRES (`C4`/`C19`/`C22`/`R10`/`R12`), EXACTLY — the FIRE SET.** A **successful** write at address `A` fires, **once each, in registration order**, every ATTACHED listener whose address is **(i)** `A` itself, **(ii)** a strict DESCENDANT of `A` (`C19`: the subtree was overwritten) or **(iii)** a strict ANCESTOR of `A` (`C4`: the path was re-minted and its subtree now carries the new data). **Listeners on any OTHER address do not fire.** **The whole write — mint, tombstone omission, commit, removal of a committed `file` tombstone (`R12`), purge, attachment re-evaluation — is ONE firing; a write never fires a listener twice.** **A REFUSED write fires NOTHING** (`R3`/`R8`: it did not land). **THE FAN-OUT RUNS AFTER THE PURGE AND AFTER THE INSTALL**, i.e. inside step `(8)` of `docs/specs/store-rederive/write-and-read.md §2.5` item 1. `(A C19 · A C4 · A C22 · A R12 · CONTRACT + NEGATIVE)`
6. **`C24`, VERBATIM: *"On startup, event listeners are added before the store is loaded from file. This lets them trigger when the data is fully loaded."*** **THE BOOT ORDER IS THEREFORE A CONTRACT CLAUSE, NOT A WIRING ACCIDENT: the hosting component constructs the store, registers its listeners, and THEN calls `load()`; the load fires each listener whose address resolves after the load, ONCE, in registration order, AFTER the whole load has completed** — *"when the data is fully loaded"*. **A design in which the load precedes the registrations, or in which listeners fire per loaded node, FAILS** (`L [H]`: the landed order is `load → then listen`, the reverse of `C24`, and its own comment claims the opposite intent — `G-landed-code.md` §1 `C24`; `STALE PENDING`). `(A C24 · L [H] · CONTRACT + NEGATIVE)`
7. **THE BODY'S CONTRACT (`D17`'s and `D14`'s residuals, now closed — DECLARED).** **(a) A body MAY read and MAY write** through the store's own functions (`C1`); **a write issued inside a fan-out is an ORDINARY write whose own fan-out runs to completion before the body returns (depth-first), and the store imposes no depth bound, no coalescing and no deferral** (`docs/specs/store-rederive/contract.md §0A` `DD-19`). **(b) A body that THROWS is caught, does not stop the fan-out, and is reported on the write's record as one `listenerErrors` entry `{listener:<its registration index>, error:<the thrown value>}`; NO rollback follows, because the write landed before the fan-out** (`docs/specs/store-rederive/contract.md §0A` `DD-18`). **(c) A listener whose target is re-minted observes, when it reruns, the NEW node's data — read through the store's own `read` (`item 3`).** `(A C22 · A C4 · DECLARED-DEFAULT)`

### 2.12 The boot — `load()`, `C24`'s terminal, and the failed load

1. **`load(): LoadRecord` IS THE ONE FUNCTION THAT READS THE FILES.** It reads the `file` tier's file, mints the `file` instances of `docs/specs/store-rederive/write-and-read.md §2.7` item 3's condensation, **and then fires the fan-out of `docs/specs/store-rederive/seams-and-lifecycle.md §2.11` item 6** — **all inside one call, with the fan-out strictly after the whole mint, so each listener observes the fully loaded state** (`C24`). **`secureLoad()` does the same for the `secure` graph's own file, gated by `docs/specs/store-rederive/seams-and-lifecycle.md §2.9` item 4.** `(A C24 · A C6 · CONTRACT)`
2. **WHO PERFORMS IT (`docs/specs/store-rederive/contract.md §0A` `DD-8`; `S-21`'s residual, now closed — DECLARED): a store-level function called by the HOSTING COMPONENT, after the listeners are registered.** **This contract binds the ORDER and the function; the component's identity is the host wiring's, and this unit's declared wiring region is `docs/specs/store-rederive/contract.md` §1.2 item 2's boot region.** `(T · DECLARED-DEFAULT)`
3. **WHAT A LISTENER REGISTERED AFTER THE LOAD IS OWED (`docs/specs/store-rederive/contract.md §0A` `DD-8`): NOTHING — no initial call.** It is attached IMMEDIATELY if its address resolves (its `ListenerRecord.attached` is `true`, which is the caller's signal), **and it fires on the next change**. **The initial collection is the caller's own `read`, and the window between `listen` and that read is the caller's to order** (`C22`'s listener is a RE-RUN trigger, not an initial load). `(T · DECLARED-DEFAULT)`
4. **A FAILED LOAD (`D13`'s residual, now closed — DECLARED).** A missing file is **not** a failure: `{status:'loaded', present:false, roots:0}` and no listener fires (nothing resolves). **A file that is present but unreadable or unparsable answers `{status:'refused', reason:'load-failed', step:'J-LOAD', segment:null, message:<the store's own sentence>}` and the store's `file` tier enters the declared UNLOADED state, in which (i) every `file`-tier read and write refuses `'not-loaded'` at step `J-LOAD`, (ii) NO file is written — the operator's bytes are never clobbered by a save of an empty state — and (iii) no listener fires.** **A later successful `load()` leaves the state for the rest of the session.** `(T · DECLARED-DEFAULT)`
5. **NO `reset`, NO `clear`, NO `unload`, NO `hydrate` VERB IS DECLARED.** The landed `hydrate(rows)` seam — a fourth path that minted, declared, fired and never crossed or constrained (`L [H]` `G-landed-code.md` §2 item 7) — **is `STALE PENDING` and is NOT imported**: in this contract the load is the only mint-from-file path. `(A C24 · A R5 · NEGATIVE)`

### 2.13 Lifetimes — `C8`, `C9`, `R7`

1. **`C8`, VERBATIM: *"Mem is retained for the application session, but lost on app closure."*** A `mem` instance lives in the store's closure, has no persistence path, and is lost when the session ends. `(A C8 · CONTRACT)`
2. **THE SESSION BOUNDARY (`docs/specs/store-rederive/contract.md §0A` `DD-7`; `S-19`'s residual, now closed — DECLARED): the session IS the lifetime of the store INSTANCE, so an app closure AND a realm/window reload both lose `mem` and `temp`.** **The alternative — `mem` surviving a reload because the process survives — is refused: it would require a holder outside the store's closure, and `C1` makes the store's state closure-private.** `(A C8 · A C1 · T · DECLARED-DEFAULT)`
3. **`C9`, VERBATIM: *"Temp has the same behavior as mem, and is separate for policy reasons. Temp is meant to be used to contain pre-committed values for changes so that they can be tested, with easy rollback to a persistent state by retaining the state on the lower tier."*** **THE POLICY IS CARRIED EXACTLY: (a) a `temp` instance is session-scoped like `mem`; (b) a `temp` write retains the more-persistent instance at its address rather than purging it (`docs/specs/store-rederive/write-and-read.md §2.5` item 5); (c) the pre-committed value is tested through ordinary reads; (d) COMMITTING the change is an ordinary write at the more-persistent tier, which purges the `temp` instance (`docs/specs/store-rederive/write-and-read.md §2.5` item 4) — no separate commit verb exists.** `(A C9 · A C19 · CONTRACT)`
4. **`R7` — THE ROLLBACK IS AUTOMATIC AND CREATES NO VERB.** *"Automatic — dropping the temp node restores the retained lower-tier state"*; *"No new store-level verb is created: `C9`'s rollback **is** the retained lower-tier instance"* (`P §5`; `R §9` row 4). **Therefore: (i) `temp`'s rollback is a STATE CONSEQUENCE — the read's lowest-persistence selection (`R9`) answers the retained instance as soon as the `temp` instance ceases to exist; (ii) the `temp` instance is dropped by EXACTLY TWO ARMS — a later write at the same address at a tier of equal or lower persistence (`C4`'s discard-and-re-mint), and the session's end (`item 2`); (iii) NO store-level verb drops it, and NO timer, idle sweep, TTL, clock or GC hook exists** (`R1`; `NEGATIVE`). `(A R7 · A C4 · A R9 · CONTRACT + NEGATIVE)`
