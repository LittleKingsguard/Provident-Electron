### 2.5 The write — `C15`, `C18`, `C19`, `C20`, and `R6`'s parameter

1. **THE WRITE'S ORDER, WHICH IS THE WHOLE `C7`/`R3`/`R8` ROLLBACK MECHANISM (there is NO journal, NO snapshot and NO revert table in this contract):**
   `(1)` validate the address (`A-ADDRESS`) → `(2)` resolve the parent chain (`B-ROOT`…`E-CHILD`) → `(3)` check the tier argument and the monotonic invariant (`F-TIER`) → `(4)` admit the payload (`G-VALUE`) → `(5)` evaluate the constraints in order (`H-CONSTRAINT` — **⟶ AMENDED 2026-10-08, `R15`/`docs/specs/store-rederive/contract.md §0A` `DD-22`: this step is a PASS-SEQUENCE, not one pass — constraints REPEAT after a repair, a registration's repair runs at most once per write, and a repair that breaks a prior constraint FAILS the write; `docs/specs/store-rederive/seams-and-lifecycle.md §2.10` items 8–11 are its operative form, and the as-filed words here stand; the discard rule below applies to EVERY pass** `(A R15 · T · CONTRACT)`) → `(6)` mint the prospective state in memory → `(7)` if the tier is `file` (or the graph is `secure`), WRITE THE FILE (`I-SAVE`) → `(8)` on success: INSTALL the new state, run the purge (`C19`), fire the listeners (`docs/specs/store-rederive/seams-and-lifecycle.md §2.11`) → `(9)` answer the `WriteRecord`. **On any failure at steps `(1)`–`(7)` the prospective state is DISCARDED — the pre-call state and the pre-call file bytes stand byte-identical — and the answer is a `Refusal`; the purge does not run and no listener fires.** `(A C7 · A R3 · A R8 · A C19 · CONTRACT)`
2. **THE WALK'S WRITE ARMS — `C17`, `C18`, `C20`:**
   - **`C18` — A DEEPER ADDRESS THAT COULD EXIST BUT DOES NOT: the write ADDS the data, using that address as its entry.** *"If a write points to a node that could exist, but doesn't (ex. `window.tabs` exists, but link has no `landingPage` child), it adds the written data, using that address as its entry."* **The mint therefore creates whatever is missing AT THE ADDRESSED ADDRESS — the child node, and the `parent` anchor and link that reach it on the parent node.** At a 1-segment address it also creates **the register entry** (`C14`). `(A C18 · A C14 · CONTRACT)`
   - **AN ABSENT INTERMEDIATE IS REFUSED, NOT MINTED** (`docs/specs/store-rederive/contract.md §0A` `DD-11`): a failure at `i < n` answers `'unreachable'` (step `C-ANCHOR`/`D-LINK`/`E-CHILD`) and mints nothing.
   - **`C20` — A WRITE AIMED AT A LOWER TIER WHERE A MORE-PERSISTENT INSTANCE EXISTS PROCEEDS AS IF EMPTY.** *"If a write resolves to an address that already has a node, but is targeted at a lower persistence tier (ex. existing node is `file` but write is for `temp`) write proceeds as if empty."* **So the write does NOT read, inherit, merge or base itself on the more-persistent instance's data: it MINTS FRESH from its own payload, and the instances COEXIST at the address, one per tier** (`C21`'s duplicate ban forbids two at the SAME tier, never two across tiers). `(A C20 · A C21 · CONTRACT)`
   - **THE INVERSION ARM, `R9`'s invariant made a refusal:** a write whose tier **out-ranks** the parent instance's tier is refused `'persistence-inversion'` at step `F-TIER` (`docs/specs/store-rederive/store-model.md §2.2` item 3). `(A R9 · CONTRACT)`
3. **`C19` — THE OVERWRITE ARM, AND WHAT "OVERWRITES ITS DESCENDANT TREE" MEANS HERE.** *"If a write points to a node that already has data, that data and its descendant tree is overwritten."* **The overwrite is TOTAL at the addressed address AND AT ITS OWN TIER: an existing instance at `(address, tier)` is discarded and re-minted (there is no read-modify-write, no merge and no partial member update), and every node in the addressed instance's descendant tree is discarded with it.** **AND `C4` GOVERNS THE PATH: *"Nodes are not mutable - writes discard and remint new nodes"*** — so **every node on the walk from the register to the addressed address is re-minted too** (its anchors/links carry the new child), and **no node that existed before the write is mutated.** **THE OBSERVABLE OF THE RE-MINT IS THE FIRE SET** (`docs/specs/store-rederive/seams-and-lifecycle.md §2.11` item 6): a write at `A` fires the listeners at `A`, at every descendant of `A` and at every ancestor of `A` — which is exactly the path-plus-subtree re-mint, and it is the only place node identity is observable, since **no function returns a node** (`C1`/`C2`). `(A C19 · A C4 · A C1 · CONTRACT)`
4. **`C19` + `R7` — THE PURGE, AFTER A SUCCESSFUL WRITE, INCLUDING THE FILE SYNC.** *"After successfully writing data (including file sync, if writing to the file tier), any lower-persistence instances of that address are purged."* **The purge happens at step `(8)` — AFTER the commit succeeded — and its set is EXACTLY the instances at the address whose tier is STRICTLY LOWER-persistence than the written tier:** `purge(temp) = ∅` · `purge(mem) = {temp instances at the address}` · `purge(file) = {mem, temp instances at the address}` — **terms `0 + 1 + 2 = 3` ✓** (`docs/specs/store-rederive/census.md §4.5`). **A purge that removes the instance of the written tier, an instance at a HIGHER-persistence tier, or an instance at ANOTHER address FAILS.** `(A C19 · CONTRACT + CENSUS)`
5. **`R7`'s BOUND ON THAT PURGE, VERBATIM: *"Automatic — dropping the temp node restores the retained lower-tier state"*, and *"no purge may delete the retained lower copy while a `temp` instance of the address stands"* (`R §5` `R7`).** **CARRIED AS AN INVARIANT:** while an instance of an address stands at `temp`, **the instance of that address that the `temp` instance's rollback restores (the most-persistent instance at that address, `C9`'s *"retaining the state on the lower tier"*) is not removed by any PURGE.** **The `temp` instance ITSELF is not protected by this bound** — a write at `file` or `mem` at that address purges it, and that is exactly `C9`'s commit flow (`docs/specs/store-rederive/seams-and-lifecycle.md §2.13` item 3). **A row in which a purge deletes the retained copy while a `temp` instance stands FAILS.** `(A R7 · A C9 · A C19 · CONTRACT)`
6. **NO PURGE, NO EVICTION, NO CLOCK AND NO CAP EXISTS BEYOND `item 4`: the store declares no FIFO, no LRU, no per-tier root cap, no idle sweep and no severance** (`R1`'s general-purpose rule; the landed family's caps/severance/clear/sweep/export are `STALE PENDING`, `L [H]` `G-landed-code.md` §2). `(A R1 · NEGATIVE)`

THE AS-FILED WRITE ARMS IN ITEMS 1–6 ABOVE STAND BYTE-FOR-BYTE AND ARE NOT REWRITTEN; `items 2`–`3`'s add/overwrite arms are the TABLE'S `A2`/`A4` ROWS, and what the table ADDS is the PROPERTY-ADDRESS ARMS (`A5`–`A8`) and the NODE-LOCATION REFUSAL (`A3`) — the arms an addressed address that resolves to a LITERAL PROPERTY, or to something carried by an EXISTING LINK, forced and the as-filed arms never enumerated.** **THE TABLE IS TOTAL: its `4` resolution rows are `docs/specs/store-rederive/store-model.md §2.3` item 2's `M-PROP` answers (`4 = 1 + 1 + 1 + 1` ✓) and its `10` write arms partition them exactly (`3 + 2 + 2 + 3 = 10` ✓). 8. **⟶ NO PROPERTY DELETION — A `CONTRACT` CLAUSE WITH `R17`(b) AS ITS AUTHORITY — APPENDED 2026-10-08 (THE ARCHITECT).** `R17`(b) verbatim: *"No property deletion — only whole-node tombstones exist"*. **FIVE CONSEQUENCES, EACH A ROW:**
   - **(a) THERE IS NO DELETE VERB AND NO PROPERTY-LEVEL TOMBSTONE.** **A literal member can be OVERWRITTEN and never REMOVED; `docs/specs/store-rederive/write-and-read.md §2.6`'s tombstone is the ONLY deletion instrument this contract declares, and it deletes NODES (`A7`), or converts a property into a node it then deletes (`A8`) — it never subtracts a member from a node that survives.**
   - **(b) A MEMBER IS CLEARED ONLY BY OVERWRITING IT (`A4`) OR BY TOMBSTONING THE NODE THAT CARRIES IT (`A7`).** **"Clearing a literal therefore means tombstoning or overwriting the node that carries it" — the property's own parent, re-minted without it (`A1`/`A4`'s re-mint) for the overwrite arm, or the carrying node's whole subtree soft-deleted for the tombstone arm.**
   - **(c) NO `delete`-SHAPED PAYLOAD MEMBER, NO `undefined`-AS-DELETE AND NO NULL-AS-DELETE EXISTS.** **`PAR-4` already refuses `undefined` as a VALUE and never reads it as a delete; `null` is an ADMITTED literal (`docs/specs/store-rederive/store-model.md §2.4` item 2) and is DATA, not a deletion; and `docs/specs/store-rederive/store-model.md §2.1`'s `WritePayload` carries exactly `value`/`transparent` and `tombstone` — no third shape.** **A row in which a member disappears while its carrying node stands FAILS.**
   - **(d) THE AS-FILED CONTRACT NEVER HAD A PROPERTY-DELETE ARM, SO NOTHING IS SUPERSEDED BY `R17`(b) AND NO SUPERSESSION POINTER IS OWED (`docs/specs/store-rederive/contract.md §0B` item 3).** **`R17`(b) is a NEGATIVE that closes a question the as-filed text left open; its live form is this clause.**
   - **(e) `R17`(b) REMOVES *PROPERTY DELETION*, NOT THE TOMBSTONE'S REACH AT A PROPERTY ADDRESS (`A8`).** **The derivation is `P §12`'s own and is landed at item 7 `A8`, with its `C18`/`C4`/`R10`/`R11` chain printed there.** `(A R17 · A C18 · A R10 · A R11 · CONTRACT + NEGATIVE)`

### 2.6 `R10`/`R11`/`R12` — the tombstone

1. **WHAT A TOMBSTONE IS.** *"Write needs to be able to tombstone nodes … This can be used to soft-delete nodes"* (`A R10`). **A tombstone is a WRITE whose payload is `{ tombstone: true }`** (`docs/specs/store-rederive/store-model.md §2.1`'s `WritePayload`): **it mints ONE node at `(address, tier)` carrying NO literals and NO anchors — the deletion marker — and nothing else.** `(A R10 · CONTRACT)`
2. **A TOMBSTONE IS INVISIBLE TO THE READ AND NEVER RETURNED (`R11`).** *"The tombstone is invisible to the read - a `temp` tombstone hides the `mem` node *and* doesn't return on the read, because it represents deleted data."* **Consequences, each a row:**
   - **The tombstone node itself is NEVER a transcription, at any address, under any read form, qualified or unqualified.**
   - **The unqualified read at the tombstone's address answers `Refusal` with `reason: 'tombstoned'`** (step `E-CHILD`) — **the address reads as deleted, not as absent-because-never-written** (`docs/specs/store-rederive/contract.md §0A`-class declaration at `docs/specs/store-rederive/store-model.md §2.14` item 3: the two are distinguishable, and `R10`'s *"until the temp node is cleared"* requires the soft delete to be observable as such).
   - **THE READ DOES NOT PROPAGATE THROUGH IT (`R11`), IN BOTH SENSES: (i) NO FALL-BACK — the tombstone does not fall through to a lower-persistence instance of the same address; (ii) NO DESCENT — every address BELOW the tombstone is unreachable for an unqualified read, and answers `'unreachable'` at its first unreachable segment, because the walk cannot pass the tombstone.** `(A R11 · CONTRACT)`
   - **`R10`'s TIER-SCOPED READ STANDS BESIDE `R11`: a read QUALIFIED to another tier reads THAT TIER SPECIFICALLY (`R9`) and is not suppressed by a tombstone standing at a different tier.** *"…unless the read is scoped to `mem`"* — the `mem`-scoped read of `R10`'s own example reads the tombstoned `mem` node, **which is how a consumer inspects the retained state behind a soft delete.** **A read qualified to the TOMBSTONE's own tier answers the tombstone's own absence** (`'absent-address'` at the qualified read's terminal arm — the tombstone is never returned). `(A R10 · A R11 · A R9 · CONTRACT)`
3. **`R12` — THE `file` TIER'S TOMBSTONE LIFECYCLE, VERBATIM: *"Tombstone in memory → node removed on successful commit, rolled back on failure"*.** **`R10`'s own words for the same duty: *"Tombstoning at file tier omits it from the saved file, which will delete the node on commit."*** Therefore: **the tombstone node stands in memory, is OMITTED from the file's bytes, and on a SUCCESSFUL commit the node is removed from the graph as well as from the file; on a FAILED save the tombstone is rolled back and the pre-write node stands intact** (`R3`/`R8`: the operation does not land; `docs/specs/store-rederive/write-and-read.md §2.5` item 1's step-`(8)`/discard rule). **The whole tombstone — mint, omission, commit, removal — is ONE write and fires the fan-out ONCE.** `(A R12 · A R10 · A R3 · A R8 · CONTRACT)`
4. **THE TOMBSTONE AND THE MONOTONIC INVARIANT.** A tombstone node carries a tier like any node (`C11`), so **its tier is bounded by its parent's, it hides the instances BELOW it by being the same address's tombstone, and its own tier's qualified read never returns it** (`item 2`). **A tombstone at `temp` therefore hides the `mem` instance of the address and blocks unqualified reads of it and its subtree, exactly as `R10`'s example states — while a `mem`-scoped read still reads the `mem` node and the retained `file` copy stands untouched (`item 2`, `docs/specs/store-rederive/write-and-read.md §2.5` item 5).** `(A R10 · A R9 · CONTRACT)`
5. **THE TOMBSTONE AND THE `C9` FLOW — `R10`'s *"until the temp node is cleared"*.** A `temp` tombstone is a `temp` instance; it is dropped by exactly the two arms `docs/specs/store-rederive/seams-and-lifecycle.md §2.13` item 4 names (a superseding write at the address, or the session's end) — **and by nothing else, because `R7` creates no verb and this contract creates none.** `(A R7 · A R10 · CONTRACT)`

6. **⟶ THE TOMBSTONE WRITTEN WHERE A LITERAL PROPERTY STANDS — APPENDED 2026-10-08 (`P §12`'s NAMED DERIVATION, LANDED; THE ARCHITECT; `docs/specs/store-rederive/contract.md §0A` `DD-24`).** **THE CLAUSE, AND WHY IT IS NOT A QUESTION:** `P §12` names this derivation so that it is not mis-filed as one: *"`R17`(b) removes *property deletion*, not the tombstone's reach at a property address — a tombstone written where a **literal property** stands converts that property into a **node** (the tombstone mints one node at the address), which then **reads as deleted** by `R11`, while the property itself continues to exist. The successor contract's author derives this from `C18`/`R10`/`R11`/`R17`(b); it is not a new ruling."*
   - **THE ARM:** `docs/specs/store-rederive/write-and-read.md §2.5` item 7's **`A8`**, derived there with its chain printed: `C18`'s add-at-the-address ⇒ one node minted at the address; `C4`'s discard-and-re-mint ⇒ the immediate parent re-minted carrying an anchor/link at that segment **instead of the literal**; `R10` ⇒ the minted node carries no literals and no anchors; `R11` ⇒ the address **reads as deleted**.
   - **WHAT IS OBSERVABLE, EXACTLY, AND WHAT IS NOT:** the **unqualified read** at the address answers `Refusal` with `reason: 'tombstoned'` (step `E-CHILD`); **no fall-back** to a lower-persistence instance and **no descent** below it (item 2's two senses); **a qualified read of another tier** reads that tier at that address as `item 2` already states; and **the PROPERTY ITSELF CONTINUES TO EXIST** — the parent node now carries a member at that segment which names a node rather than a literal, so `M-PROP` classifies the address as a **NODE LOCATION** thereafter (`docs/specs/store-rederive/store-model.md §2.3` item 2) and **the literal is not recoverable by any arm**.

### 2.7 The `file` tier — the commit duty (`C7`, `R3`, `R8`) and the save's condensation

1. **THE TIER'S STATE IS SYNCHRONISED TO A JSON FILE, AND THE DUTY IS ABSOLUTE.** `C7`: *"file is synchronized to a JSON file. 2. **THE BOUND MUTATION SET (`R8`): *"All file-tier mutations, observed as a returned typed record"*** — **every one of these is bound, and the answer to the caller is ALWAYS a returned typed record, NEVER a throw, NEVER a swallowed status, and the operation DOES NOT LAND on failure:**
   - a **set-class write** at the `file` tier (`write(address, 'file', {value})`);
   - a **tombstone write** at the `file` tier (`write(address, 'file', {tombstone: true})`, `docs/specs/store-rederive/write-and-read.md §2.6` item 3);

   - the **boot hydration's write-back**, if the boot hydration writes anything to the `file` tier. **DECLARED (`T`): the load of `docs/specs/store-rederive/seams-and-lifecycle.md §2.12` is a READ of the file and performs NO write-back, so no record is owed by it — the duty binds MODIFICATIONS (`C7`'s *"on any modification"*), not loads.** **A design in which the load writes the file as part of an ordinary boot FAILS this item's reading and owes its own record.** Terms: `4` bound classes ✓ (`docs/specs/store-rederive/census.md §4.5`). `(A R8 · A C7 · DECLARED-DEFAULT)`

### 2.8 The read — `C21`, `C2`, and `R9`'s two forms

1. **`C21`, VERBATIM.** *"A read transcribes the tree descended from the addressed node into an object, taking the lowest-persistence version of any given node. (More than one node sharing both an address and a tier should be forbidden by store-write function logic.)"* `(A C21 · CONTRACT)`
2. **`R9` GOVERNS ASSEMBLY — THE TWO FORMS, VERBATIM:** *"If a specific tier is passed, read that tier specifically. Otherwise, read the lowest-persistence node at the targeted address and all downstream addresses when assembling."*
   - **QUALIFIED (`tier` passed): THE READ TAKES THAT TIER SPECIFICALLY, AT EVERY ADDRESS IT VISITS, WITH NO FALL-BACK.** *"an address that tier does not hold is `C17`'s verbose error, never a lower-tier answer"* (`P §6` item 1). **Therefore: (a) at the ADDRESSED address, the tier's absence is a `Refusal` with `reason: 'tier-not-held'` (step `F-TIER`); (b) at a DOWNSTREAM address, the tier's absence means the member is ABSENT from the transcription and the walk does not descend through it.** **DECLARED (`T`, `DECLARED-DEFAULT`): the qualified read applies the passed tier at every address in the tree — the alternative (*apply `R9`'s lowest-persistence rule to downstream addresses even under a passed tier*) is priced and NOT taken, because `R9`'s sentence contrasts *"that tier specifically"* against the *"otherwise"* arm, and taking the mixed form would re-open the pair the architect closed.** Reversible at this gate. `(A R9 · T · CONTRACT + DECLARED-DEFAULT)`
   - **UNQUALIFIED: THE READ TAKES THE LOWEST-PERSISTENCE INSTANCE AT THE ADDRESSED ADDRESS *AND AT EVERY DOWNSTREAM ADDRESS*.** **This is a PER-NODE rule**: a `temp` or `mem` instance of a DESCENDANT is visible to a read of its ancestor, and the walk's `E-CHILD` selection at every step takes the lowest-persistence instance standing at that step's address (`docs/specs/store-rederive/store-model.md §2.3` item 2). **This is the rule `C9`'s test-before-commit purpose needs, and `R7`'s automatic rollback falls out of it unchanged** (`P §6` item 2). `(A R9 · A C9 · CONTRACT)`

the node's own `literals` are the object's other members; **and the array rule (`docs/specs/store-rederive/contract.md §0A` `DD-13`) decides array vs object.** **⟶ AMENDED BESIDE 2026-10-08 (THE SPEC WRITER, ON THE SUPERVISOR'S REVIEW OF `docs/specs/store-rederive/contract.md §0A` `DD-13`;
