### 2.2 The four tiers, the persistence order, and the monotonic invariant

1. **FOUR TIERS — `secure`, `file`, `mem`, `temp`** (`A C5`: *"four tiers (secure, file, mem, temp)"*). Terms: `4 = 1 (secure, outside every order) + 3 (the ranked tiers: file · mem · temp)` ✓. **The generic surface's tier domain is the three ranked tokens; `secure` is not a legal argument anywhere on the generic surface** (`§2.9` item 1; `C6`'s separate-functions leg). `(A C5 · A C6 · CONTRACT + CENSUS)`
2. **THE PERSISTENCE ORDER (`R9`): `file` > `mem` > `temp`, with `secure` OUTSIDE every ordering.** Terms: `3` ranked tokens with `3` ordered pairs (`file>mem`, `file>temp`, `mem>temp`) ✓. **The order is the meaning of every "lower-persistence" and "lowest-persistence" phrase in this contract** (`C19`'s purge, `C20`'s lower-tier write, `R9`'s read): **"lower persistence" = strictly less persistent = the tier that appears to the RIGHT of the other in `file > mem > temp`.** `(A R9 · A C19 · A C20 · CONTRACT)`
3. **THE MONOTONIC INVARIANT, CARRIED AS A CLAUSE OF ITS OWN, NOT AS A PREMISE (`R9` item 3, which the architect required the successor to carry):** **A NODE MAY NOT BE MORE PERSISTENT THAN ITS PARENT.** For every parent-side anchor's link, `rank(child node's tier) ≤ rank(parent node's tier)`, where `rank(file)=3 > rank(mem)=2 > rank(temp)=1`. **A write whose tier out-ranks the parent instance's tier is REFUSED** (`'persistence-inversion'`, step `F-TIER`). **The root of a tree has no parent and the invariant is vacuously satisfied there** (`C14`). **Terms: the `9 = 3 × 3` tier pairs, of which `6` are legal and `3` are refused** (`§4.5`). `(A R9 · CONTRACT + CENSUS)`
4. **`secure` IS A SEPARATE GRAPH, SAVED TO A SEPARATE FILE, AND IT FOLLOWS THE SAME CONSTRAINTS AS `file` FOR ALL OTHER PURPOSES** (`A C6`) — so the commit duty (`C7`/`R3`/`R8`), the tombstone lifecycle (`R12`), the mint rules (`C3`/`C11`) and the event surface (`C22`–`C24`) apply inside it, with the two differences `C6` names (its own functions; its own file) plus the gate (`§2.9`). **Within the `secure` graph the tier is NOT a member of the node and NOT a parameter — `C11`'s own words: *"secure is determined by being in an isolated graph"*** (`A C11`). `(A C6 · A C11 · CONTRACT)`

### 2.3 The address space and the walk

1. **AN ADDRESS IS A NON-EMPTY SEGMENT LIST: `Address = ReadonlyArray<string>`, every segment a non-empty string.** **The store declares NO dotted-string parser and NO tier segment** (`§0A` `DD-10`, `DD-20`; `R6`; `C16`'s walk is segment-by-segment: *"Register is checked for node named 'window', node is checked for anchor at property 'tabs', associated link is checked for node named, 'landingPage'"*). **A segment is ANY non-empty string — the store declares NO segment alphabet, NO escaping and NO reserved spelling** (`R2` forbids a whitelist, and `R1` forbids a name set that serves an example; the `S-1`-row's carried half — segment domain and escaping — is thereby DISCHARGED as an empty domain restriction). `(A C16 · A R1 · A R2 · CONTRACT + DECLARED-DEFAULT)`
   - **OUTSIDE the address domain** (all refused `'malformed-address'`, step `A-ADDRESS`, `segment: null`): a non-array · an empty array · a non-string segment · an empty-string segment. **A dotted string is OUTSIDE the domain** (it is not an array) — the presentation is the caller's. Terms: `4` malformed arms (`§4.7`). `(T · CONTRACT)`
2. **THE WALK RUNS FROM THE REGISTER** (`A C16`; `A C14`: *"Register contains root nodes of trees"*). The walk's arms, in order, with their step ids and their failures:
   - **`A-ADDRESS`** — parse and validate the address (`item 1`); failure ⇒ `'malformed-address'`.
   - **`B-ROOT`** — the register's entry named `address[0]` must exist; otherwise **`'unknown-root'`** (the store declares **NO declaration input, NO reserved names and NO cold-root concept**: a root comes into being **only** by a write at a 1-segment address, `§2.5` item 3). `(A C14 · A C18 · CONTRACT + NEGATIVE)`
   - **`C-ANCHOR`** — at the current node, the **`parent`-type** anchor whose `key === address[i]` must exist (a `child`-type anchor is **NEVER** a walk step: **a row that lets the walk follow a `child`-type anchor FAILS**, `§2.3` item 4).
   - **`D-LINK`** — that anchor's link list must hold at least one link (`C12`: *"anchors are the interface between nodes and links"* — the anchor carries the links that hang children under its property).
   - **`E-CHILD`** — **among the anchor's links, the walk must select a link whose child-side node exists**; the child node is the node the prefix `address[0..i]` names.
   - **`F-TIER`** — the selection among the anchor's links is the READ's rule (`§2.8` item 2) or the WRITE's rule (`§2.5` item 4); its failure is `'tier-not-held'` (read) or the add arm (write).
   - **THE TERMINAL ARM, AND WHY THE WALK IS THE WHOLE ADDRESS RULE:** the walk consumes segment `i ≥ 2` by following `C-ANCHOR` → `D-LINK` → `E-CHILD`, so **the node named by the prefix `address[0..i]` is the child-side node reached at `i`**. With `n = address.length`: `i = n` reaches **the addressed node**. **A failure at an INTERMEDIATE segment (`i < n`) is `'unreachable'`** (`A C17`: *"If an address is unreachable (ex. no anchor at 'window.tabs'), return verbose error"*), **and NOTHING IS MINTED** (`§0A` `DD-11`: an intermediate node would carry no literals, and `C11` says *"nodes store the literals they are written with"*). Terms: `4` walk steps `+ 1` parse step `= 5` steps (`§4.3`). `(A C16 · A C17 · A C11 · CONTRACT + DECLARED-DEFAULT)`
   - **⟶ `M-PROP`, APPENDED 2026-10-08 (`R16`/`R17`, THE ARCHITECT): THE FINAL SEGMENT'S RESOLUTION STEP.** **When the walk reaches the IMMEDIATE PARENT `P` of the addressed address — `P = address[0 .. n-1]`, the node the walk reaches at `i = n − 1` (`n = 1` ⇒ `P` is the REGISTER, whose entry is `C14`'s link-without-a-parent) — the store takes ONE further decision, at step `M-PROP` (`§2.1`'s appended step id), and it is the arm-selector of `§2.5` item 7 and `§2.8` item 7: WHAT DOES THE FINAL SEGMENT NAME AT `P`?** **THE FOUR ANSWERS, AND NOTHING ELSE (`§2.1`'s `PropertyResolution`, printed there and never returned to a caller):** **(i) A NODE LOCATION** — `P`'s node carries a `parent`-type anchor at the final segment whose link holds a child-side node: *"an address that resolves to being contained in an existing link"* (`R16`(d) verbatim). **(ii) A LITERAL PROPERTY** — `P`'s node carries the final segment **in its `literals`** (`C11`), and the segment is not `_value` (`item 5`). **(`_value` standing as a literal is the FOURTH state — a TRANSPARENT NODE — and it resolves as a NODE LOCATION whose node is transparent: the node IS addressable, and only its READ is transparent, `item 5`; a TRANSPARENT NODE therefore carries exactly one literal and no anchor (`R17`(c)).)** **(iii) AN ABSENT PROPERTY** — `P` resolves and its node carries **NEITHER** a literal at that segment **NOR** a `parent` anchor at it: `C18`'s case, *"a node that could exist, but doesn't"* — and it is a **PROPERTY ADDRESS** in `R16`(d)'s sense (there is no link there to contain anything, so the segment names a property of `P`). **(iv) NO RESOLUTION** — `P` does not resolve at all (`C17`): **`R16`(a)'s own condition — *"the address's immediate parent resolves to a node"* — is FALSE**, so `R16`(a) does not apply and no arm may mint. **Terms: `4 = 1 (node location) + 1 (literal property) + 1 (absent property) + 1 (no resolution)` ✓ (`§4.2`).** **THE DISAMBIGUATION IS BY `C11`'s OWN STRUCTURE AND NOT BY A MARKER: a node's members are its `literals` and its `parent` anchors (`§2.4` item 6), so the segment is looked up in the node's literal table FIRST and then among its `parent` anchors' `key`s; `C21`'s duplicate ban is what makes this a function and not a search — the store's own write logic forbids one address-and-tier pair twice (`§2.8` item 6), so at this step exactly one of the four answers holds.** `(A R16 · A R17 · A C11 · A C16 · A C18 · T · CONTRACT + CENSUS)`
3. **THE REGISTER (`C14`) — ITS ENTRIES AND NOTHING ELSE.** *"Register contains root nodes of trees. It has the functionality of a link, without having a distinct parent."* An entry is `{ name: string, node: Node, constraints: ConstraintRegistration[] }` — **the root name as the entry's child order/key, the root node as its child, and the link-functionality's constraint list; and NO parent reference** (`C14`'s own subtraction). **The register carries no cache, no staleness flag, no reservation, no declaration input and no cap** (`R1`/`R4`; the inventory's `[H]` rows for the landed cache/reservation/two-root-caps are `STALE PENDING`, `L`; §1 item 2's `NEGATIVE`). Terms: `4` asserted parts (`§4.4`). `(A C14 · R §4.1 · CONTRACT + NEGATIVE + CENSUS)`
4. **THE NODE, THE ANCHOR AND THE LINK — THE DECLARED RECORD SHAPES, EVERY MEMBER CITING ITS `Cn`.** `C11`: *"nodes store the literals they are written with and the tier of the store they are in … Any properties that refer to other objects are replaced by `parent` anchors"*; `C12`: *"anchors are the interface between nodes and links. They contain their parent and link references, their type (parent/child) and their child order/key"*; `C13`: *"Links can contain constraint functions"*. `(A C11 · A C12 · A C13 · CONTRACT)`

```
Node   = { tier: Tier,                       // C11 — the tier of the store it is in (ABSENT in the secure graph, C11)
           literals: { [member: string]: StoreValue },   // C11 — the literals it was written with
           anchors: Anchor[] }              // C11/C12 — one parent anchor per object-valued member
Anchor = { parent: NodeRef,                 // C12 — "their parent … reference" (the link's parent-side node)
           links: Link[],                   // C12 — the interface between the node and its links
           type: 'parent' | 'child',        // C12 — "their type (parent/child)"; STORED, §0A DD-4
           key: string,                     // C12 — "child order/key" (1): the SEGMENT: the dict key
           order: number }                  // C12 — "child order/key" (2): the dense ORDINAL: the array index
Link   = { parent: AnchorRef, child: AnchorRef, constraints: ConstraintRegistration[] }  // C13
RegisterEntry = { name: string, node: NodeRef, constraints: ConstraintRegistration[] }   // C14
```

   - **THE `type` MEMBER IS STORED AND IS OBSERVABLE, AND HERE IS THE OBSERVABLE:** a `parent`-type anchor sits on the node that owns the object-valued property; a `child`-type anchor sits on the CHILD node and marks the same link's other side, carrying the SAME `key`/`order`/`parent`/`links`. **Because the two sides carry the same `key`, the walk's `C-ANCHOR` arm MUST filter on `type === 'parent'`** — otherwise a read of `address ⊕ [key]` at the child would follow the child-side anchor back onto its own node or its parent. **A row in which a `child`-type anchor is a walk step FAILS.** `(A C12 · CONTRACT + NEGATIVE)`
   - **⟶ APPENDED BESIDE 2026-10-08 (`R16`(e)/`R17`(c), THE ARCHITECT): THE NODE'S MEMBER TABLE `literals` MAY CARRY THE RESERVED KEY `_value`, AND NOTHING ELSE CHANGES IN THE SHAPE** — `C11`'s *"nodes store the literals they were written with"* is the whole carrier, so **the transparency of `item 5` needs NO new node member, NO flag, NO marker and NO second member table: a TRANSPARENT NODE is the node whose `literals` holds `_value` and NOTHING ELSE, and whose `anchors` is EMPTY** (`R17`(c) verbatim: *"Exclusive — `_value` is alone in its node"*). **Terms: `1` reserved key in the node's `literals` table; the node's member count does not move.** `(A R16 · A R17 · A C11 · CONTRACT + NEGATIVE)`

5. **⟶ THE `_value` RESERVATION AND WHERE THE RULE BITES IN THE ADDRESS GRAMMAR — APPENDED 2026-10-08 (`R16`(e) VERBATIM, `R17`(c) VERBATIM, THE ARCHITECT; `§0A` `DD-23`).** `R16`(e): *"A node should be able to be made "transparent" on read (ex. write [true, 123, "Foo"] --> link with nodes of values true, 123, "Foo"] --> read [true, 123, "Foo"]) by assigning the literal value to the `_value` property. This is otherwise a reserved keyword."* `R17`(c): *"Exclusive — `_value` is alone in its node"*. **Five clauses follow, and each is a row a TestWriter can drive:**
   - **(a) A TRANSPARENT NODE IS A NODE WHOSE `literals` HOLDS EXACTLY ONE MEMBER, `_value`, WHOSE VALUE IS A LITERAL — and no `anchors` at all.** **It IS ADDRESSABLE: the address it stands at resolves to it, `M-PROP` classifies it as a NODE LOCATION (item 2's fourth state), and a TIER-QUALIFIED read at that address still returns the node — the qualified read reports `tier` and answers the node's transcription (`{_value: <the literal>}`), because a qualified read asks WHICH INSTANCE, not WHAT IT READS AS.** **The TRANSPARENCY is a property of the UNQUALIFIED read alone (`§2.8` item 7).** `(A R16 · A R17 · CONTRACT + NEGATIVE)`
   - **(b) `_value` IS RESERVED — *"This is otherwise a reserved keyword"* — SO A CALLER'S ORDINARY PROPERTY OF THAT NAME IS NOT AVAILABLE.** **`RESERVED_VALUE_MEMBER` (`§2.1`) is NOT a member a caller writes as ordinary data: a caller who wants the transparency asks for it with the write payload's `transparent` member (`§6` `PAR-14`), and a caller who writes `{value: 'x'}` at a node location gets an ORDINARY literal member named `x`'s member key — never `_value`.** **The reservation is what keeps ONE key from carrying TWO meanings: without it, a node's `_value` literal would be at once a caller's ordinary datum and the store's own transparency marker, and no read could tell the two apart.** **The reservation is NOT an address-grammar reservation: `PAR-1` stands — any non-empty string is a legal SEGMENT, so an address MAY name a segment spelled `_value`; what is reserved is the MEMBER KEY AT A NODE, and the two are different referents.** `(A R16 · A C11 · CONTRACT + NEGATIVE)`
   - **(c) EXCLUSIVITY (`R17`(c)): `_value` IS ALONE IN ITS NODE.** **A transparent node carries EXACTLY ONE literal and NOTHING ELSE.** **A write that would place any SECOND member alongside a `_value` literal — a second literal, or a container-member (which would mint an anchor) — is REFUSED `'value-not-admitted'` (token 9, REUSED — see (e)), and a CONTAINER written to `_value` is REFUSED the same token (`§12`'s first carriage: *"a write of an object/array to `_value` is refused `'value-not-admitted'`"*).** **WHY THE EXCLUSIVITY IS NOT COSMETIC: an unqualified read of a transparent node answers the `_value` literal ALONE, so ANY second member would be RETAINED IN THE STORE WHILE BEING UNREADABLE THROUGH THE UNQUALIFIED READ — a member no read can reach is a member the contract must not permit.** `(A R17 · A R16 · CONTRACT + NEGATIVE)`
   - **(d) THE TOMBSTONE'S REACH AT A TRANSPARENT NODE.** **A tombstone written at a transparent node deletes it exactly as any other node's tombstone does** (`§12`'s second carriage; `§2.6` items 1–3 unchanged; `§2.5` item 7's tombstone arms). **The deleted transparent node is not returned by any read, its address answers `'tombstoned'` unqualified, and a qualified read of the tombstone's own tier answers the tombstone's own absence — all exactly as `§2.6` item 2 states for every node.** `(A R17 · A R10 · A R11 · CONTRACT)`
   - **(e) THE NEW TOKEN'S RELATION TO THE `_value` REFUSALS, STATED SO THE UNION IS NOT MIS-READ AS GROWING TWICE: `_value`'s TWO refusals — a container at `_value`, and a second member beside a `_value` literal — are token 9 `'value-not-admitted'`, whose class is exactly `§2.4` item 2's admission set and whose as-filed wording already covers them (`PAR-4`); the APPENDED twenty-first token `'node-location-container'` names the SEPARATE fact of `R17`(a) — a container passed to a NODE LOCATION — which is a misplacement and not an inadmissible value.** **Two facts, two tokens, ONE appended:** the union grows by one and only one member. `(A R17 · A R16 · T · CONTRACT + CENSUS)`

### 2.4 The mint — what a write STORES (`C3`, `C11`, `C18`, `C21`)

1. **`C3` — THE MINTING RULE, VERBATIM.** *"Writes mint new nodes/links/anchors to contain the primitive values contained by the received object, never providing a reference as value."* **Therefore: a write never stores a caller's object; it MINTS.** `(A C3 · CONTRACT)`
2. **THE VALUE-ADMISSION SET — `§0A` `DD-5`, ONE SET FOR EVERY TIER, PRINTED IN FULL.** A write's `payload.value` is ADMITTED iff it is one of the `6` admitted classes below; otherwise the write is REFUSED `'value-not-admitted'` (step `G-VALUE`) and **nothing is minted and no file is written**. `(T · DECLARED-DEFAULT)`
   - **ADMITTED, `6`:** a `string` · a finite `number` other than `-0` · a `boolean` · `null` · **a plain object** whose prototype is `Object.prototype` or `null`, whose every own member key is a NON-EMPTY string, and whose every own member value is admitted (a **dense data member**; an accessor is refused, `item 3`) · **an array** whose own keys are exactly the dense range `0..n-1` and whose every element is admitted.
   - **REFUSED, `16`:** `undefined` · a function · a `symbol` · a `bigint` · `NaN` · `Infinity`/`-Infinity` · `-0` · a cyclic object or array · a `Map`/`Set`/`WeakMap`/`WeakSet` · a `Date` · any object whose prototype is neither `Object.prototype` nor `null` (**class instances included**) · an array with a HOLE · an array with an own member beyond its dense indices · an own ACCESSOR property (a getter is **not invoked** — it is refused) · an own SYMBOL-keyed member · an own member key that is the EMPTY STRING.
   - **WHY THESE AND NOT OTHERS, ONE LINE EACH (the derivation, so the set is not mistaken for taste):** the `file` tier is a JSON file whose bytes must *"exactly match the data state"* (`C7`) — so a value that cannot round-trip through JSON cannot inhabit the tier as data (`NaN`/`±Infinity`/`-0`/`undefined`/functions/symbols/bigints/accessors/holes/non-plain objects: each either vanishes, changes, or cannot be represented) · a member key must be a legal address SEGMENT, because `C15` requires an address for every read and write and `C16` reaches a child by its anchor's key — an empty key would mint a node **no address can name** · `C8`/`C9`'s pre-commit flow (*write at `temp`, test, then write at `file`*) breaks if a value admitted at `temp` is refused at `file`, hence **one set**. `(A C7 · A C15 · A C16 · A C9 · DECLARED-DEFAULT)`
3. **THE MINT'S RECURSION — `C11`'s object-reference rule, whole depth.** `mint(value, tier)` produces a node and its subtree:
   - **the node** carries `tier` (`C11`; absent in the secure graph) and, per own data member of the received object **in `Object.keys` order**:
     - a **LITERAL**-classed member (string, number, boolean, `null`) ⇒ an entry of the node's `literals`, under the member's own key;
     - a **CONTAINER**-classed member (plain object or array) ⇒ **a `parent` anchor whose `key` is the member's name and whose `order` is its dense position among that node's anchors (from `0`)** — `C11`'s *"Any properties that refer to other objects are replaced by `parent` anchors"* — **plus a link and a child node minted by the SAME rule for that member's value (whole depth, recursively)**. `(A C11 · A C3 · CONTRACT)`
   - **THE DEPTH IS THE WHOLE DEPTH.** `C3` says *"the primitive values contained by the received object"* and `C11` says *"any properties that refer to other objects"* — **there is no depth bound, no level limit and no top-level-only arm**; a nested container at any depth is minted and addressable.
   - **NODES CARRY NO NAME.** `C11` enumerates a node's content as **the literals it was written with and its tier** — so **a node does NOT carry its own name, ref, flag or cache**; its name IS the `key` of the `parent` anchor that reaches it, or, at the root, the register entry's `name` (`C14`). `(A C11 · A C14 · CONTRACT + NEGATIVE)`
4. **THE `C18` EXAMPLE, IN THE ARCHITECT'S OWN TERMS, AS THE MINT'S WORKED ILLUSTRATION (an ILLUSTRATION, never a store member):** *"if it is passed data = `{active: true, contents: {...}}`, the node will contain `active: true` and a parent anchor for a link to the 'contents' object"* — the node at the address holds `literals.active = true` and one `parent` anchor `key: 'contents'`, whose link leads to the child node minted for the contents object, itself addressable as `address ⊕ ['contents']`. `(A C18 · CONTRACT)`
5. **NO VALUE IS EVER A REFERENCE, AND NO MINT IS EVER PARTIAL.** A refused write mints nothing; a minted-but-uncommitted file-tier write is discarded wholesale (`§2.7` item 2). **A row in which a returned or stored value aliases a caller's object, or a store-internal record, FAILS** (`C2`/`C3`). `(A C2 · A C3 · CONTRACT + NEGATIVE)`

6. **⟶ THE NODE'S CONTENT MODEL — THE THREE MEMBER KINDS, AND HOW EACH IS DISTINGUISHED — APPENDED 2026-10-08 (`R16`/`R17`, THE ARCHITECT; `§0A` `DD-23`).** **`C11`'s own sentence is the carrier — *"nodes store the literals they were written with … Any properties that refer to other objects are replaced by `parent` anchors"* — and the clarification forces it to be PRINTED, because `R16`(a)–(d) and `R17`(b) each turn on WHICH KIND a member is.** **A node holds EXACTLY THREE KINDS OF MEMBER, and there is no fourth:**
   - **(i) LITERAL MEMBERS** — keyed by the member name, valued by a string, a finite `number` (never `-0`), a `boolean` or `null` (`§2.1`'s `StoreValue`; the `4` literal classes of `§2.4` item 3). **Distinguished by WHERE THEY LIVE: an entry of the node's own `literals` table, with no anchor and no link.** **The distinction IS the node's two tables: `literals` versus `anchors` (`§2.3` item 4's record shape, `C11`'s two clauses) — so the store never inspects a value to classify a member, it asks WHICH TABLE the member's key stands in.** Terms: `4` literal classes ✓ (`§4.2`).
   - **(ii) ANCHOR MEMBERS** — **a `parent`-type anchor whose `key` is the member's name, whose link leads to a child node (`C11`'s object-reference rule), i.e. a member whose value is a container.** **Distinguished by: a `parent` anchor at that key, and a non-empty `links` list (`D-LINK`), and a child-side node (`E-CHILD`).** **`C18`'s worked illustration is exactly this kind: `{active: true, contents: {...}}` ⇒ `literals.active = true` + one `parent` anchor `key:'contents'` (`§2.4` item 4).** **Terms: `1` anchor member kind (the container-valued property), driven in `§2.5` item 7 and `§2.8` item 7.**

### 2.5 The write — `C15`, `C18`, `C19`, `C20`, and `R6`'s parameter

1. **THE WRITE'S ORDER, WHICH IS THE WHOLE `C7`/`R3`/`R8` ROLLBACK MECHANISM (there is NO journal, NO snapshot and NO revert table in this contract):**
   `(1)` validate the address (`A-ADDRESS`) → `(2)` resolve the parent chain (`B-ROOT`…`E-CHILD`) → `(3)` check the tier argument and the monotonic invariant (`F-TIER`) → `(4)` admit the payload (`G-VALUE`) → `(5)` evaluate the constraints in order (`H-CONSTRAINT` — **⟶ AMENDED 2026-10-08, `R15`/`§0A` `DD-22`: this step is a PASS-SEQUENCE, not one pass — constraints REPEAT after a repair, a registration's repair runs at most once per write, and a repair that breaks a prior constraint FAILS the write; `§2.10` items 8–11 are its operative form, and the as-filed words here stand; the discard rule below applies to EVERY pass** `(A R15 · T · CONTRACT)`) → `(6)` mint the prospective state in memory → `(7)` if the tier is `file` (or the graph is `secure`), WRITE THE FILE (`I-SAVE`) → `(8)` on success: INSTALL the new state, run the purge (`C19`), fire the listeners (`§2.11`) → `(9)` answer the `WriteRecord`. **On any failure at steps `(1)`–`(7)` the prospective state is DISCARDED — the pre-call state and the pre-call file bytes stand byte-identical — and the answer is a `Refusal`; the purge does not run and no listener fires.** `(A C7 · A R3 · A R8 · A C19 · CONTRACT)`
2. **THE WALK'S WRITE ARMS — `C17`, `C18`, `C20`:**

   - **`C20` — A WRITE AIMED AT A LOWER TIER WHERE A MORE-PERSISTENT INSTANCE EXISTS PROCEEDS AS IF EMPTY.** *"If a write resolves to an address that already has a node, but is targeted at a lower persistence tier (ex. existing node is `file` but write is for `temp`) write proceeds as if empty."* **So the write does NOT read, inherit, merge or base itself on the more-persistent instance's data: it MINTS FRESH from its own payload, and the instances COEXIST at the address, one per tier** (`C21`'s duplicate ban forbids two at the SAME tier, never two across tiers). `(A C20 · A C21 · CONTRACT)`

3. **`C19` — THE OVERWRITE ARM, AND WHAT "OVERWRITES ITS DESCENDANT TREE" MEANS HERE.** *"If a write points to a node that already has data, that data and its descendant tree is overwritten."* **The overwrite is TOTAL at the addressed address AND AT ITS OWN TIER: an existing instance at `(address, tier)` is discarded and re-minted (there is no read-modify-write, no merge and no partial member update), and every node in the addressed instance's descendant tree is discarded with it.** **AND `C4` GOVERNS THE PATH: *"Nodes are not mutable - writes discard and remint new nodes"*** — so **every node on the walk from the register to the addressed address is re-minted too** (its anchors/links carry the new child), and **no node that existed before the write is mutated.** **THE OBSERVABLE OF THE RE-MINT IS THE FIRE SET** (`§2.11` item 6): a write at `A` fires the listeners at `A`, at every descendant of `A` and at every ancestor of `A` — which is exactly the path-plus-subtree re-mint, and it is the only place node identity is observable, since **no function returns a node** (`C1`/`C2`). `(A C19 · A C4 · A C1 · CONTRACT)`
4. **`C19` + `R7` — THE PURGE, AFTER A SUCCESSFUL WRITE, INCLUDING THE FILE SYNC.** *"After successfully writing data (including file sync, if writing to the file tier), any lower-persistence instances of that address are purged."* **The purge happens at step `(8)` — AFTER the commit succeeded — and its set is EXACTLY the instances at the address whose tier is STRICTLY LOWER-persistence than the written tier:** `purge(temp) = ∅` · `purge(mem) = {temp instances at the address}` · `purge(file) = {mem, temp instances at the address}` — **terms `0 + 1 + 2 = 3` ✓** (`§4.5`). **A purge that removes the instance of the written tier, an instance at a HIGHER-persistence tier, or an instance at ANOTHER address FAILS.** `(A C19 · CONTRACT + CENSUS)`

### 2.6 `R10`/`R11`/`R12` — the tombstone

1. **WHAT A TOMBSTONE IS.** *"Write needs to be able to tombstone nodes … This can be used to soft-delete nodes"* (`A R10`). **A tombstone is a WRITE whose payload is `{ tombstone: true }`** (`§2.1`'s `WritePayload`): **it mints ONE node at `(address, tier)` carrying NO literals and NO anchors — the deletion marker — and nothing else.** `(A R10 · CONTRACT)`
2. **A TOMBSTONE IS INVISIBLE TO THE READ AND NEVER RETURNED (`R11`).** *"The tombstone is invisible to the read - a `temp` tombstone hides the `mem` node *and* doesn't return on the read, because it represents deleted data."* **Consequences, each a row:**
   - **The tombstone node itself is NEVER a transcription, at any address, under any read form, qualified or unqualified.**
   - **The unqualified read at the tombstone's address answers `Refusal` with `reason: 'tombstoned'`** (step `E-CHILD`) — **the address reads as deleted, not as absent-because-never-written** (`§0A`-class declaration at `§2.14` item 3: the two are distinguishable, and `R10`'s *"until the temp node is cleared"* requires the soft delete to be observable as such).

DO NOT construct an address or value whitelist."* **Therefore: the `secure` graph admits EVERY address in `§2.3` item 1's domain (no enumerated key domain, no member census, no reserved spelling, no delete prohibition) and every value in `§2.4` item 2's single admission set — which is a ROUND-TRIP duty (`C7`) and NOT a content restriction: it constrains no key domain and no data shape beyond what a JSON file can carry.** **`R2` REMOVED a shape; this contract constructs none.** Terms: `0` whitelists ✓. **THE PRICED ALTERNATIVE, NAMED BECAUSE `R2` IS THE MOST POINTED RULING HERE: a WIDER admission set for the `secure` graph alone.** **It is NOT taken, and the ground is `C6`'s own sentence** — *"for all other purposes, it follows the same constraints as `file`"* — **plus `C7`'s *"exactly match the data state"*: a value the JSON file cannot carry cannot be the state a `file`-peer tier is required to represent, so the refusal is a CONSEQUENCE of the file duty and not a content whitelist over tier 4.** **If the architect wants a wider `secure` set, the shape it needs is a tagged encoding for the secure file — a one-clause amendment at `§2.4` item 2 + this item, moving `§5.5.1`'s `P-SD-TP-4` term and no other.** `(A R2 · A C6 · A C7 · DECLARED-DEFAULT)`
4. **THE GATE — HOW THE BLOCKED-MCP CONDITION IS OBSERVED (`§0A` `DD-9`; `D10`'s residual, now closed).** The store takes a construction input **`secureAccess: () => boolean`** — **a NAMED READER, read ONCE PER CALL at that call's own turn, never captured, never cached across calls.** `true` = the MCP server is **BLOCKED** ⇒ access is granted; `false` = not blocked ⇒ **every one of the five secure functions refuses with `reason: 'secure-gated'` at step `K-GATE`, before anything else it would do.** **WHO ASKS: the store's own secure functions, at their step 1.** **WHAT AN IN-FLIGHT CALL OBSERVES: the ONE reading taken at its own turn governs the WHOLE call — a flip of the condition mid-call neither half-applies nor re-reads, so the call either completes as a whole or is refused as a whole.** **ABSENT, A THROW OR A NON-BOOLEAN ⇒ NOT BLOCKED ⇒ REFUSED (fail-closed)**, because `C6` says the graph *"cannot be accessed UNLESS"* the MCP is blocked. Terms: `5` gated functions × `2` readings = `10` drives (`§4.5`). `(A C6 · T · CONTRACT + DECLARED-DEFAULT + CENSUS)`
5. **`R2` DOES NOT RE-OPEN THE MCP SURFACE.** *"A pass that reads `R2` as granting an MCP-reachable tier-4 read path has mis-read the ruling"* (`R §2.3`, the one row that would have hit). **This contract declares no MCP surface, no tool, no resource and no notification payload, and no channel that carries a `secure` value out of its realm** (`R §2.3`; `S docs/specs/mcp-endpoint.md` §6.4's manual-UI-only determination, quoted not re-derived). `(A R2 · R §2.3 · CROSS-REF + NEGATIVE)`
6. **THE `secure` GRAPH'S OWN FILE IS THE `file` TIER'S PEER: the commit duty (`§2.7`), the tombstone lifecycle (`§2.6` item 3) and the event surface (`§2.11`) apply inside it unchanged, and its nodes carry NO tier member** (`C11`: *"secure is determined by being in an isolated graph"*). `(A C6 · A C11 · A R12 · CONTRACT)`

### 2.10 The constraint seam — `C13` and `R4`

1. **`C13`, VERBATIM.** *"Links can contain constraint functions, which can take the current state, the prospective future state, and the changed node as parameters, perform a logical check (ex. exactly one tab node is marked `active`) and return true (state is valid) or invoke a repair function (ex. most recent active tab is marked 'active') or return false with an error message explaining the constraint violation."* **The example is an ILLUSTRATION of a MODULE's constraint — `exactly-one-active` is a module's, never a store member** (`A R1`; `§1.1` item 3). `(A C13 · A R1 · CONTRACT)`
2. **`R4`, VERBATIM, AND THE REGISTRATION SEAM.** *"Constraints are an extensible tool - modules must be able to add additional constraints and repair functions. DO NOT add built-in constraint functions."* **The seam is `constrain(address, {constraint, repair?})`, a store-level function (`C1`), which attaches the module-supplied pair to the interface at that address: to the LINK at the address, or — at a 1-segment address — to the REGISTER ENTRY, whose `C14` words are *"It has the functionality of a link, without having a distinct parent"*.** A link or entry carries an **ORDERED LIST** of registrations **in registration order** (`C13`'s plural *"constraint functions"*). **A re-registration carrying the SAME `constraint` function identity (`===`) at the SAME address REPLACES that entry in place (idempotent wiring); otherwise it APPENDS.** **THE SEAM CARRIES NO WITHDRAWAL VERB** (`§0A` `DD-15`): a registration stands for the store instance's lifetime, and **`unconstrain`, `clearConstraints`, a constraint-kind table and a constraint id are NOT this store's surface** — `C13`/`R4` mandate ADDING, and the landed `kind · repair action · refusal reason` table family is `STALE PENDING` (`L [H]`; `R §4.4` strikes it). `(A R4 · A C13 · A C14 · DECLARED-DEFAULT + NEGATIVE)`
3. **THE EVALUATION POINT AND THE EVALUATED SET.** **Evaluation happens ONLY where a module registered a constraint** (`R §2.4`, `S-6` `ANSWERED-BY-R4`: *"evaluation happens only where a module registered one; the store contributes no evaluation point of its own"*). **DECLARED (`T`, `DECLARED-DEFAULT`): the evaluated set of a write at `W` is every registration at a PREFIX address `P` of `W` (`P ⊆ W`, including `P = W` and including `W`'s root), evaluated from the shortest prefix to `W` (register entry first, then down the walk), and within one address in registration order.** **PRICED ALTERNATIVE, NOT TAKEN: also evaluating the DESCENDANTS' constraints of a write that would discard them** — refused because (a) `R4`'s carrier is the link and the write does not visit those links, and (b) their `future` state would describe a subtree the write is discarding. **A module that must constrain an ancestor's overwrite registers at that ancestor too.** `(A R4 · A C13 · T · DECLARED-DEFAULT)`
4. **THE ARGUMENT SHAPE (`§0A` `DD-1`; `S-4`'s residual, now closed): ONE record `{address, current, future, changed}`, MINTED PER EVALUATION, carrying COPIES and never a live internal record** — because `C3` forbids providing a reference as a value and `C2`'s purpose is that writes happen only by explicit call. **`current` = the unqualified transcription (`§2.8` item 3) of the addressed subtree before the write; `future` = the same transcription the write would leave; `changed` = the addressed node's own `{address, tier, literals}`.** **A constraint that mutates the record changes nothing in the store; a constraint that is handed a live node, anchor or link FAILS.** `(A C13 · A C2 · A C3 · DECLARED-DEFAULT + NEGATIVE)` **⟶ AMENDED 2026-10-08 (`R15` item 4, THE ARCHITECT; the as-filed sentence stands byte-for-byte and THIS clause is the operative form).** **ONE MUTATION NOW DOES CHANGE SOMETHING, AND IT IS THE CHANNEL `R15` CREATES: the record carries `notes: ConstraintNote[]` (`§2.1`'s amended block), and the entries a constraint OR a repair appends to ITS OWN record's list are HARVESTED by the store after the call returns (`item 10`).** **Every OTHER mutation of the record still changes nothing in the store, and the live-record prohibition is untouched — the module never receives a node, an anchor, a link, or the write's own list.**
5. **THE THREE ARMS, EXACTLY, AND WHAT EACH DOES (`C13`'s own three):**
   - **`{ok: true}`** ⇒ the state is valid; evaluation continues with the next registration.
   - **`{ok: false, message}`** ⇒ **the write is REFUSED**; the answer is `{status:'refused', reason:'constraint-refused', step:'H-CONSTRAINT', segment:<the write's last segment or null>, message:<the MODULE's message VERBATIM>}` (step `H-CONSTRAINT`); **nothing lands.** **THE MESSAGE CHANNEL IS THE RETURNED RECORD'S `message` MEMBER** (`§0A` `DD-2`; `S-5`'s residual, now closed): **the same member carries `C17`'s store-authored sentence, so there is ONE channel with TWO authorships and no second surface.** `(A C13 · A C17 · DECLARED-DEFAULT)` **⟶ AMENDED 2026-10-08 (`R15`, THE ARCHITECT; `RCA-8(d)`: the as-filed sentence above stands byte-for-byte and THIS clause is the operative declaration): THE CHANNEL IS NOW THE MESSAGE LIST — `C13`'s message is appended VERBATIM as a `'constraint'` entry and `C17`'s sentence is the store's own entry, so it is ONE channel with THREE authorships (`§0A` `DD-21`; `item 10` below). The record's single `message` member is superseded by `messages: StoreMessage[]` (`§2.1`'s amended block).**
   - **`{repair: true}`** ⇒ **the store invokes the registration's `repair`** with the same record; its return **REPLACES the prospective value**, is **re-admitted** (`§2.4` item 2; a refused class ⇒ `'value-not-admitted'`), and evaluation continues with the NEXT registration. **⟶ AMENDED 2026-10-08 (`R15` item 1; the as-filed tail stands byte-for-byte and THIS clause is the operative declaration): EVALUATION DOES NOT CONTINUE FORWARD — the pass RESTARTS at the FIRST registration of the evaluated set, so every constraint is RE-EVALUATED against the repaired state (`item 8` below; `§0A` `DD-22`).** **If the registration carries no `repair`, the write is REFUSED `'constraint-failed'`** with a store-authored message naming the missing repair.
   - **A malformed answer (not one of the three arms) or a THROW from a `constraint` or a `repair`** ⇒ **the write is REFUSED `'constraint-failed'`** with a store-authored message; **the throw never propagates and nothing lands.** `(A C13 · A R4 · CONTRACT)`
6. **A REPAIR'S OUTCOME (`§0A` `DD-3`; `S-7`'s residual, now closed).** **(a) A REPAIRED WRITE IS A SUCCESSFUL WRITE: it lands, it is committed if its tier is `file` (one commit, after the repair settles — never two file writes), and `C19`'s purge runs after it.** **(b) THE REPAIRED VALUE IS NOT RE-OFFERED TO THE CONSTRAINTS ALREADY EVALUATED, and no registration is evaluated twice within one write: evaluation is ONE ORDERED PASS.** **⟶ AMENDED 2026-10-08 (`R15` items 1–2, THE ARCHITECT; `RCA-8(d)`: this sub-clause's as-filed words stand byte-for-byte and `item 9` below is the operative declaration).** **THIS SUB-CLAUSE IS SUPERSEDED: the repaired value IS re-offered — every registration, the already-satisfied included, is RE-EVALUATED in a NEW pass (`item 8`) — while NO REPAIR IS EVER RE-INVOKED: a registration's `repair` runs AT MOST ONCE per write (`item 9`).** **What survives of this sub-clause, unchanged: the repaired value REPLACES the prospective value and is re-admitted as a value (there is no second candidate and no merge).** **(c) A repair can never follow a refusal**: the three arms are exclusive and a refusal **ends the write**. **(d) The record carries `repaired: true` iff any repair was taken.** `(T · DECLARED-DEFAULT)`
7. **NO BUILT-IN CONSTRAINT, NO STORE-OWNED VOCABULARY, NO BOUND.** `R4`'s prohibition is read at its widest: **the store mints no constraint, ships no constraint, names no constraint kind, and imposes no repair-round limit** (a store-owned round limit would be a store-owned constraint policy in miniature, `R4`). **The evaluation is total because each answer is terminal** (`§2.5` item 1's order), **not because a bound exists.** **⟶ AMENDED 2026-10-08 (`R15` item 2, THE ARCHITECT; `RCA-8(d)`: the as-filed sentence stands byte-for-byte and THIS clause is the operative reading).** **TWO WORDS OF IT ARE RE-GRAINED: (i) an answer is no longer TERMINAL at `{repair:true}` — that arm RESTARTS the phase (`item 8`) — and (ii) the store now carries a bound on REPETITION, and it is the ARCHITECT's, not a store-owned policy over module code: A REGISTRATION'S REPAIR RUNS AT MOST ONCE PER WRITE (`item 9`).** **THE PHASE IS STILL TOTAL AND IT NOW TERMINATES *BECAUSE OF* THAT BOUND: at most `|S|` repairs can run, so the pass count is `≤ |S| + 1` and no repair is ever re-invoked.** **`R4`'s prohibition is untouched: the store still ships no constraint, names no kind, and declares no round limit of its own.** `(A R4 · CONTRACT + NEGATIVE)`

**⟶ AMENDED 2026-10-08 (`R15`, THE ARCHITECT; `P §10`; `RCA-8(d)` ANNOTATE-BESIDE) — THE CONSTRAINT PHASE, RE-GRAINED. THE WHOLE OPERATIVE FORM OF `R15` LIVES IN ITEMS 8–11 BELOW.** **Items 1–7 above stand byte-for-byte; the three sub-clauses superseded as declarations are annotated in place (item 5's forward-continuation tail, item 5's `message`-member clause, item 6(b)'s one-ordered-pass clause, and item 7's terminality/`no bound` reading).** **The architect's own words, verbatim and unedited:** *"DD-3: Repeat constraints, don't repeat repairs. If a repair breaks a prior constraint, fail instead to prevent loops. Track with a message list that constraints and repairs write to and can be returned to verbosely document failure or change."* `(A R15 · P §10 · CONTRACT)`

8. **THE PHASE IS A PASS-SEQUENCE, AND CONSTRAINTS REPEAT (`R15` item 1).** Let `S = [r_0, …, r_{k-1}]` be the write's EVALUATED SET in `item 3`'s order (shortest prefix first, register entry before the walk, registration order within one address). **The phase runs PASSES. A pass walks `S` from `r_0`. A `{repair:true}` answer whose repair RUNS changes the state, and the phase then RESTARTS: a NEW pass BEGINNING AT `r_0`.** **Therefore every registration is re-evaluated against the repaired state — including every registration that already answered `{ok:true}` — and a repaired write IS re-checked against the whole constraint set.** **The architect's own failure arm presupposes exactly this: a repair *"breaks a prior constraint"* only if the PRIOR constraints are re-walked.** *(The as-filed `item 6(b)` reading — "no constraint is evaluated twice … one ordered pass" — is SUPERSEDED and its cell stands visible beside this clause.)* **The repaired value is re-admitted at the moment the repair returns (`item 5`; a class outside `§2.4` item 2 ⇒ `'value-not-admitted'`, nothing landing).** **A row in which a write that took a repair leaves an earlier registration UNRE-EVALUATED FAILS.** `(A R15 · T · CONTRACT + NEGATIVE)`
9. **A REPAIR RUNS AT MOST ONCE PER WRITE — AND THAT IS THE LOOP'S BOUND (`R15` item 2).** **DECLARED (`T`, `DECLARED-DEFAULT`, `§0A` `DD-22`): the unit of "once" is THE REGISTRATION.** `r_i`'s `repair` is invoked **at most once within one write**; **no registration's repair is ever REPEATED**; across registrations a single write may therefore take up to `k = |S|` repairs, one per demanding registration. **Consequences, each a rule:**
   - **(a) A SECOND `{repair:true}` FROM A REGISTRATION WHOSE REPAIR HAS ALREADY RUN IN THIS WRITE REFUSES THE WRITE — and it does NOT run the repair again.** The token is **`'constraint-failed'` (13)**, whose as-filed third arm already reads *"`{repair:true}` with no registered `repair`"*: **the arm is RE-GRAINED by this ruling to cover "the demanded repair is not available — either unregistered, or already run in this write"**, and **it is NOT a new member** (`§2.14` item 1's write set counts it once). **The repetition the ruling forbids thereby becomes a FAILURE.**
   - **(b) THE PHASE TERMINATES, AND THE BOUND IS THE ARCHITECT'S, NOT THE STORE'S.** At most `|S|` repairs can run, so **the pass count is `≤ k + 1 = |S| + 1`**, every pass is finite, and **no repair function is ever re-invoked**. *(This is the bound `item 7`'s re-grained reading names; `R4` is untouched — the store still ships no constraint, names no kind and declares no round limit of its own.)*
   - **(c) NO STORE-OWNED REPAIR-DEMAND POLICY EXISTS BEYOND (a).** A `{repair:true}` from a registration whose repair has **not** yet run is taken, whatever the pass — **a SECOND registration may take its own first repair while the first registration's repair stands**, and the pass then restarts again.
   - **A row in which a registration's repair runs twice in one write FAILS.** **PRICED ALTERNATIVE, NOT TAKEN: "once per write" read GLOBALLY (one repair for the whole write)** — refused because it would refuse every second registration's `{repair:true}` regardless of what it repairs, making `R4`'s module-supplied repairs unusable in a constraint set of two; the per-registration reading is the one that buys exactly the loop's bound. `(A R15 · A R4 · T · DECLARED-DEFAULT + CENSUS)`
10. **THE MESSAGE LIST — THE ONE CHANNEL, ITS ENTRY, ITS APPENDERS, ITS ORDER AND ITS RETURN (`R15` item 4; `§0A` `DD-21`).**
    - **THE MEMBER, AND WHAT IT REPLACES.** **`Refusal.message: string` is REPLACED by `Refusal.messages: StoreMessage[]`** (the fourth diagnostic member, RE-GRAINED), **and the write's `committed` record gains `messages: StoreMessage[]` as its SEVENTH payload member** (`§2.1`'s amended block). **There is no second `message` string beside the list — one member, one channel** (`DD-2` superseded as a declaration; ONE channel, THREE authorships: a constraint, a repair, the store's own arms). **EVERY `Refusal` carries the list and `messages.length ≥ 1`; a `committed` record's list MAY be empty — EXCEPT when `repaired` is `true`, where it carries at least the store's own repair entry.** **A `committed` record with `repaired: true` and an EMPTY list FAILS.**
    - **THE ENTRY, CLOSED: `StoreMessage = { source: 'constraint' | 'repair' | 'store'; pass: number; position: number | null; step: ResolveStep; address: Address; text: string }`** — **terms `6 = 2 (the MODULE's own: `source` · `text`) + 4 (the STORE's own stamps: `pass` · `position` · `step` · `address`)` ✓**. **`source` = WHO authored it; `text` = the sentence (the MODULE's VERBATIM for `'constraint'`/`'repair'`, the store's own for `'store'`); `address` = the address it concerns (the write's address for the phase's own entries); `step` = the step id that appended it (`'H-CONSTRAINT'` for every module-authored entry).**
    - **THE TWO STAMPS, PRECISELY.** **`pass`** = the 1-based ordinal of the constraint phase's pass that appended it; **`1` for every entry appended by a call that has no constraint phase** (declared here, `T`: a `read`, `listen`, `constrain` or `load` refusal carries its one store-authored entry at `pass: 1`). **`position`** = the **0-based index of the driven registration within the write's evaluated set `S`** (`item 3`'s order), or `null` where the entry concerns no single registration. **`position` here is NOT `ConstraintRecord.position` (`§2.1`), which indexes a registration within the addressed link's or entry's OWN list** — the two are distinct referents, and this clause is where the distinction is declared.
    - **WHO MAY APPEND — `4 = 2 + 2` DOORS, AND NOTHING ELSE.** **THE MODULE'S TWO:** **(i)** a constraint's **`{ok:false, message}` answer** — the store appends its `message` **VERBATIM** as a `'constraint'` entry (**this is `C13`'s *"return false with an error message explaining the constraint violation"*, and it is where `C13`'s message ENTERS the list**); **(ii)** **the `notes` DRAFT LIST the `ConstraintEvaluation` record is MINTED WITH (per evaluation, `DD-1`; `§2.1`'s amended block)** — a constraint **or** a repair appends a `ConstraintNote` (`{source: 'constraint' | 'repair', text}`) to **ITS OWN record's** `notes` list, and **the store HARVESTS those drafts after that call returns, in the module's own append order, STAMPS each one (`pass`, `position`, `step`, `address`) and appends it to the write's list as a `StoreMessage`.** **THE HARVEST IS TOTAL AND IT NEVER THROWS: a draft whose `source` is not `'constraint'` or `'repair'`, or whose `text` is not a string, is DISCARDED and never minted as an entry — the module cannot forge a `'store'` entry.** **The module NEVER holds the write's own list**: handing it out would hand a module a live internal record, the very thing `DD-1` refuses. **THE STORE'S TWO:** **(iii)** **one entry for EVERY repair invocation** (`source: 'store'`, naming the repair, its `position` and its `pass`) — so **a CHANGE is documented BY CONSTRUCTION even when the module appended nothing**; **(iv)** **one entry for every refusal whose primary sentence is the store's own** — i.e. `C17`'s sentence and every other store-authored sentence (`C7`/`R8`'s save failure, the load failure, the malformed arms, the gate, the missing repair, the repeat demand of `item 9(a)`).
    - **THE ORDER IS APPEND ORDER, AND IT IS EXACTLY `(pass, position)`.** Entries stand in the order they were appended: **the module's entries during a call, then the store's own entry for that call's outcome**. **LEMMA, WHICH THE REGISTER'S ROWS DRIVE DIRECTLY: the list is ordered by `pass` ASCENDING and, WITHIN one pass, by `position` ASCENDING** — so a two-pass write's list reads *pass 1 (positions ascending), then pass 2 (positions ascending)*. **A harvested entry is never re-ordered, never dropped and never duplicated; TWO APPENDS OF THE SAME TEXT ARE TWO ENTRIES — the list is a LOG, not a set.**
    - **THE PRIMARY SENTENCE, AND HOW IT RELATES TO `C17`.** **THE REFUSAL'S PRIMARY SENTENCE IS THE LAST ENTRY'S `text`.** It is the **store's own** for **every token except 12**, whose last — and primary — entry is the **MODULE's verbatim** (`C13`); **for token 20 it is the store's own sentence naming the repair and the constraint it broke, with the broken constraint's own verbatim standing as the entry IMMEDIATELY BEFORE it** (`item 11`). **So `C17`'s *"return verbose error"* is answered by the WHOLE LIST plus its primary sentence, and `C13`'s message keeps its own authorship at its own entry.** **A refusal whose list is EMPTY, or whose last entry's `text` is empty, FAILS.**
    - **WHETHER IT IS RETURNED ON SUCCESS: YES — `R15` says *"failure OR change"*.** The `committed` record carries the list, so **a repaired write documents its own change** (`repaired: true` + the store's repair entry), and every `Refusal` carries it so **the failure is documented verbosely**. `(A R15 · A C13 · A C17 · A C2 · T · CONTRACT + DECLARED-DEFAULT)`
11. **A REPAIR THAT BREAKS A PRIOR CONSTRAINT FAILS THE WRITE (`R15` item 3) — AND WHAT THAT FAILURE CARRIES.** **If a registration answered `{ok:true}` in an EARLIER pass of the SAME write and answers `{ok:false, message}` in a LATER pass, the write FAILS. It is NOT repaired again: the loop is broken by FAILING.** **THE ANTECEDENT IS EXACTLY *previously `{ok:true}` IN THIS WRITE*:** a registration that answered `{repair:true}` and never `{ok:true}`, and then refuses, **was never satisfied** — its refusal is **`'constraint-refused'` (token 12)** with the module's message as the primary entry, **not this arm**.
   - **THE ANSWER IS A RETURNED TYPED RECORD, NEVER A THROW (`R8`/`C7`):** `{status:'refused', reason:'repair-broke-constraint', step:'H-CONSTRAINT', segment:<the write's last segment or null>, messages:<the whole list — the broken constraint's message at its own entry, then the store's own closing sentence as the last entry>}`.
   - **THE OPERATION DOES NOT LAND:** nothing is installed, **no file is written** (the `file`/`secure` commit is never attempted), **the purge does not run** and **no listener fires** (`§2.5` item 1's discard rule at steps `(1)`–`(7)`; `§2.11` item 5's *"a REFUSED write fires NOTHING"*).
   - **THE TWO ARMS ARE DISTINGUISHED, AND WHY:** the loop-breaker's failure (**"the repair changed the state and a constraint that HELD no longer holds"**) is **not the same fact** as a constraint's own refusal (**"this prospective state violates me"**), and `R15`'s own purpose is that **the loop is broken by FAILING** — so the failure is named at token 20 (`§2.14` item 5) while a first-time refusal stays token 12. **A row in which the two arms collapse into one token FAILS the ruling's documentation duty** (`item 10`'s *"verbosely document failure or change"*). `(A R15 · A R8 · A C7 · A C13 · CONTRACT + NEGATIVE)`

### 2.11 The event surface — `C22`, `C23`, `C24`

1. **`C22`, VERBATIM.** *"event listeners are used to rerun functions that collect and use stored data. (ex. the zone render process retrieves the pane information for its zone, so it can re-render on any change)"* — **an ILLUSTRATION; the zone renderer is a CONSUMER (`§1.1` item 3).** `(A C22 · CONTRACT)`
2. **THE LISTENER SURFACE.** `listen(address, body)` registers `body` in the store's listener list in registration order and answers `{address, attached}`, where **`attached` is TRUE iff an unqualified read at that address would answer a transcription — i.e. iff the address currently resolves and is not tombstone-suppressed** (`§2.8` items 2–3; `§2.6` item 2). **The body is invoked with NO ARGUMENTS and collects through the store's own `read`** (`§0A` `DD-17`): **the event surface carries no payload, no cause taxonomy, no fan-out policy, no unsubscribe and no amplifier cap** — the landed eight-cause taxonomy, the `subtree` opt-in, the cap and the event count are `STALE PENDING` (`L [H]` `G-landed-code.md` §2). `(A C22 · DECLARED-DEFAULT + NEGATIVE)`
