### 2.1 THE HERITAGE — THE IDEA ENTERED WITH A SINGLE-INSTANCE HERITAGE

**The held contract's `§0A` note 10, quoted verbatim (its bytes stand as filed; they are read here, not rewritten):**

> **Note 10 — the constraint table declares EXACTLY ONE row today, and a second owes its interaction rule.** The plan states the rule in its own words (`NW-8`(c)): **a repair that itself violates a SECOND constraint is the cascading case, which is why the table declares one constraint today and a second one owes its interaction rule before it is declared.** **RULED: `§2.10` item 9 makes that a refusal at LOAD — a declaration table carrying two distinct constraint ids where neither declares an interaction rule does not load.** **No second constraint is invented, and no interaction rule is invented for a constraint that does not exist.**

**THE SINGLE-INSTANCE HERITAGE IS THE FIRST FACT, AND IT IS WHY THE PRECONDITION WAS NEVER EXERCISED.** **The clause presumes a second row; the table declares ONE (`§0A` note 10; `§2.10` item 9); and `§3.4` `R-15` pins BOTH halves in ONE row — *"The constraint table declares EXACTLY ONE row today; its declared columns are `kind` · evaluated-on · repair action · refusal reason; its refusal reason is `null`; and a second constraint without an interaction rule does not load."*** **So the held contract printed, in a single static row, (a) the count the clause presumes is `1`, and (b) the declaration's column set — FOUR columns, NONE of them an interaction rule — beside the refusal clause that names an interaction rule as its exception.** **NO SECOND-ROW CASE EXISTED THAT COULD EVER EXERCISE THE PRECONDITION, and the exception the clause named had no member in the shape the clause constrained.**

**THE UNEXPRESSIBILITY IS THEREFORE INHERITED, NOT ACCIDENTALLY INTRODUCED** — see §2.2: the successor's own declaration shape carries no interaction-rule member either.

### 2.4 WHY EACH GATE MISSED IT

**(a) THE SPEC GATE (gate 2) APPROVED A CLAUSE WHOSE OWN EXCEPTION THE SHAPE COULD NOT EXPRESS.** **The gate's checks are about completeness — every signature, return shape, throw pattern, valid state and fail-state present and derivable (`docs/specs/store-core-graph.md` `§4.1`; `AGENTS.md` item 9/11).** **Nothing in that check set asks whether a refusal clause's PRECONDITION CAN BE FALSE FOR A DECLARED INPUT.** **THE CHECK THAT WOULD HAVE CAUGHT IT IS A PRECONDITION/EXPRESSIVENESS PAIRING CHECK, in two halves:** **(i) FOR EVERY REFUSAL CLAUSE, NAME THE MEMBER OF THE CONSTRAINED SHAPE THAT EXPRESSES ITS EXCEPTION** — here the clause's exception is *"declares an interaction rule"* and the constrained shape (`§2.7` item 1; held `§2.10` item 9) has no such member, so the pairing is EMPTY and the clause is VACUOUS-BY-CONSTRUCTION; **(ii) FOR EVERY PRECONDITION, EXHIBIT ONE DECLARED INPUT FOR WHICH IT IS FALSE** — here the two-id inputs the shape can carry are ALL covered by the precondition, so no witness exists. **A clause whose precondition is UNCONDITIONALLY TRUE for a declared input is either VACUOUS (it refuses what the contract elsewhere requires) or UNCONDITIONALLY HOSTILE (it refuses everything) — and here it was the second, because the register's own fixture is a two-id input.**

**(b) THE RED SET COULD NOT EXPOSE IT AT RED, BECAUSE EVERY CONSTRUCTION PATH FAILED ON MODULE ABSENCE FIRST.** **The two modules do not exist while the red set is the red set** (`docs/specs/store-core-graph.md` `§2.1` items 1/2; `§7` item 1, whose third clause is superseded only as to the red set's existence). **Both harnesses resolve the surface without a static import — `tests/store-core-graph.test.ts:storeModule()`/`:factoryFor()` returning a reason rather than throwing, and `tests/store-core-graph-register.ts:resolveRegisterSurface()`/`:makeStore()` returning `null` with a reason — so at red EVERY row fails with a module-absence assertion carrying its own label, and the F-19 row's two expectations (`the input does NOT load` and the register's `the fixture LOADS`) NEVER BOTH RAN against a live module.** **THE CONTRADICTION WAS STRUCTURALLY INVISIBLE AT THE RED GATE: a red set cannot falsify a clause by driving it when the module that would enforce it is absent, and it cannot falsify it by driving the fixture either, for the same reason.**

## 3. THE PROCESS LESSON, STATED AS A RULE

**R-1 — A CLAUSE CARRIED FORWARD MUST HAVE ITS INPUT SHAPE RE-CHECKED WHEN THE INSTANCE COUNT IT PRESUMES CHANGES.** **The clause was written against a ONE-ROW table (`docs/specs/store-core.md` `§0A` note 10; `§3.4` `R-15`), and it was carried into a contract whose property register declares TWO rows (`docs/specs/store-core-graph.md` `§5.5.1`'s fixture paragraph).** **The instance count changed; the clause's precondition was not re-read against the new count; and the new count is exactly what makes the precondition bite.** **An instance count is an ARGUMENT of a refusal clause, not a decoration: when it moves, the clause's subject set, its precondition and its exception are all re-derived in the same pass.**

**R-2 — A REFUSAL CLAUSE'S EXCEPTION MUST BE EXPRESSIBLE IN THE DECLARATION SHAPE IT CONSTRAINS.** **Where a clause reads *"an input carrying X where Y"*, the shape that carries X MUST BE ABLE TO CARRY Y.** **Absent that pairing the clause is VACUOUS (it refuses what the contract elsewhere requires — here, the register's own fixture) or UNCONDITIONALLY HOSTILE (it refuses every input of the class it names) — and either way it is a FINDING at the gate that approves it, not at the pass that drives it.**

**WHERE THE CHECK BELONGS IN THE GATE CHAIN, NAMED RATHER THAN LEFT TO HABIT:**

| What | Where | Who | The artifact |
| --- | --- | --- | --- |
| the PAIRING CHECK (R-2) over every refusal clause of a carried/filed contract | **the SPEC GATE (gate 2)**, before the contract is approved and before any red set is authored | the spec writer's own derivation (`role_spec_writer`) as the author, and the spec gate's reviewer as the checker — the same split the contract's own `§4.1`/`§4.5` already use for derivation vs. authoring | **a REFUSAL-CLAUSE TABLE in the contract itself: one row per refusal clause, naming (a) its declaration class, (b) its exception, (c) THE SHAPE MEMBER THAT EXPRESSES THE EXCEPTION, and (d) ONE WITNESS — a declared input for which the precondition is FALSE.** **An EMPTY (c) or a missing (d) is a finding; the table is checkable by reading, which is what a `[T]` gate can honestly do** |
| the INSTANCE-COUNT RE-CHECK (R-1) whenever a carried clause's presumed count moves | the same gate, and again at any pass that changes the count | the pass that moves the count, in the same pass | a dated reading of the clause BESIDE the moved count — the repo's own `RCA-8(d)` annotate-beside form, which this amendment has used at every site it touched |

**DOES THE REPO ALREADY HAVE A RULE WHOSE REMIT COVERS THIS?** **PARTLY, AND THE GAP IS NAMED:**
- **COVERED, for CONTROLS and DRIVES:** *"a positive control that cannot express its failing case is VACUOUS and is itself a finding"* — `docs/specs/store-core-graph.md` `§2.3` item 4 · `§3.2` F-23 · `§3.4` `R-2`. **Its remit is the CONTROL, not the clause.**
- **NOT COVERED, and therefore OWED:** **a rule that a REFUSAL CLAUSE'S PRECONDITION IS CHECKED FOR SATISFIABILITY against the shape it constrains.** **The nearest neighbours are the adoption gates' parameter-semantics rule (`docs/specs/store-core.md`'s adoption dossier discipline; this repo's gate-2 parameter-semantics rule) — which covers EXTERNALLY-SOURCED identifiers, not internally carried clauses — and the register/total disciplines (`REGISTER-ATTEMPT-TOTALS-PRINT-THEIR-TERMS`), which cover arithmetic, not expressiveness.** **So the answer is: THE PAIRING CHECK IS OWED, named with an owner and a revisit condition at §5 item 4 below — never a bare `OWED`.**
